# 地物時空変遷編纂機 - 開発ガイド

## 重要な注意事項

> **フェーズ注記**: 以下の注意事項は主に保守・不具合修正フェーズを想定した制約である。初期実装フェーズでは「変更箇所を最小限にとどめる」「既存コメントの温存」等の制約は必要に応じて緩和される。ただし「根本原因の修正」「省略の禁止」「教訓の記録」は全フェーズで有効。

- 余計な変更は行わないこと。
- 指示されていない変更をしないこと。
- 変更箇所を最小限にとどめること。
- 既存のコメントは温存すること。
- コメントを記載するときは、本質的に必要な内容を書くこと。一時的な情報を含めないこと（「// 修正 :～」「//ここを修正」「//--修正ここから--」などの書き方をしないこと）。
- 論ずるときは、根拠となるソースコードを直接引用すること。
- コードの修正時は、「～も同様に～」といった省略は一切禁止。
- 不具合修正時は、必ず根本原因を修正すること。場当たり的な対応をしないこと。
- まずは原因の解析に注力すること。
- 実装上の失敗は開発ガイドに保存していくこと。
- 実装のやり残しは現状.mdに追記していくこと。
- **文書の役割分担**:
  - `現状.md` = 未解決課題・既知不具合・残作業・テスト総数。完了した課題は原則として即時削除すること。
  - `実装済み.md` = 実装履歴・フェーズ進捗・完了した機能の記録。
  - 例外として、同一課題を複数回の作業で分担し、削除すると進行文脈が失われる場合にのみ現状.mdに一時的に残してよい。行頭に[完了]とつけ、残作業完了時に課題全体を削除する。
  - 必要な履歴や再発防止策は本ガイドの「開発上の注意点とよくある落とし穴」に移すこと。
- 現状.mdから記載を削除する場合、それがリストの最後でない限り欠番として残すこと。
- 要件定義書は、仕様本文（完全日本語）と内部実装補遺を分離して記述すること。
  - 仕様本文では英語識別子・内部キー名・クラス名・コード値を直接記載しないこと。
  - 実装詳細は内部実装補遺に集約すること。

## 1. アーキテクチャ概要

本アプリケーションはドメイン駆動設計（DDD）の原則に基づいて構築される。

### 1.1 技術スタック

| レイヤー                   | 技術                         |
| -------------------------- | ---------------------------- |
| デスクトップフレームワーク | Electron                     |
| 言語                       | TypeScript (strict mode)     |
| UIフレームワーク           | Svelte 5 (Runes API)         |
| 状態機械                   | XState v5                    |
| レンダリング               | SVG                          |
| データ形式                 | JSON（ローカルファイル保存） |
| ビルド                     | Vite (electron-vite)         |
| テスト                     | Vitest + Playwright          |
| 幾何学計算                 | polygon-clipping             |

### 1.2 ドメイン層

アプリケーションの中核となるビジネスロジック。

- エンティティ: Vertex, Feature, Point, Line, Polygon
- 値オブジェクト: Coordinate, TimePoint, FeatureAnchor, PropertyProjection, Ring
- ドメインサービス: GeometryService, TimeService, HierarchyService
- 集約ルート: World

### 1.3 アプリケーション層

ユーザー操作をドメインロジックに変換し、結果を表示層に返す。

- ユースケース: EditFeatureUseCase (facade), AddFeatureUseCase, UpdateFeatureAnchorUseCase, DeleteFeatureUseCase, VertexEditUseCase, NavigateTimeUseCase, ReassignFeatureParentUseCase, SaveLoadUseCase
- PolygonEditService: ポリゴンのリング構造編集
- PrepareFeatureAnchorEditUseCase, ResolveFeatureAnchorConflictsUseCase, CommitFeatureAnchorEditUseCase
- CQRSの原則: コマンド/クエリ/イベントの分離

### 1.4 インフラストラクチャ層

外部リソースへのアクセスやフレームワーク統合。

- JSONWorldRepository, FileSystem, JSONSerializer
- SVGRenderer (split into ViewportManager, FeatureRenderer, StyleResolver, LabelRenderer)
- Logger, ConfigManager

### 1.5 プレゼンテーション層

ユーザーインターフェースとユーザーとの対話。Svelteコンポーネントを使用。

- コンポーネント: MapCanvas, TimelinePanel, Toolbar, Sidebar, ConflictResolutionDialog
- 状態管理: XState v5 ステートマシン (toolMachine, conflictResolutionMachine, timelineMachine)
- XState v5 は `createActor` ベースで手動統合する（`@xstate/svelte` はSvelte 5未対応のため不採用）。ユーザー操作はイベントとしてマシンに送信する

## 2. 実装ガイドライン

### 2.1 一般的なコーディング規約

- TypeScript strict mode を有効にし、any を禁止
- インデントは2スペース
- セミコロン使用
- 命名規則:
  - クラス名: PascalCase
  - 変数/関数: camelCase
  - 定数: UPPER_SNAKE_CASE
  - プライベートメンバー: TypeScriptのprivate修飾子を使用（アンダースコア接頭辞ではなく）
- 関数は1つのことだけを行い、30行以下に抑える
- ネストを3レベル以下に抑える
- コメントは日本語で記述
- 1ファイルあたり300行を目安に分割（Svelteコンポーネントは200行以下、2.5節参照）

### 2.2 ドメイン層の実装ガイドライン

- 不変性: エンティティと値オブジェクトはreadonlyプロパティで設計。状態変更は新インスタンスを返す。
- 値オブジェクトの等価性: equals()メソッドによる属性値比較。
- ドメインサービスはステートレス。
- ドメインロジックは他の層に漏れ出さない。
- 集約ルートの整合性を保つ。集約間参照はIDで。

### 2.3 アプリケーション層の実装ガイドライン

- CQRS原則に従い、コマンドとクエリを分離。
- ユースケースは特定のタスクに集中。
- トランザクション管理（操作の原子性保証）。
- イベント駆動で状態変更を通知。

### 2.4 インフラストラクチャ層の実装ガイドライン

- 外部依存性はこの層に閉じ込める。
- アダプタパターンで抽象化。
- リポジトリは永続化詳細を隠蔽。
- 低レベル例外はアプリケーション固有の例外に変換。

### 2.5 プレゼンテーション層の実装ガイドライン

- Svelteコンポーネントは表示とイベント受付に専念。
- ビジネスロジックはコンポーネントに書かない。ユースケースに委譲。
- XState v5の状態機械でツール状態を管理。状態遷移を宣言的に定義し、不正な遷移を起こしにくくする。
- コンポーネントは200行以下を目安に分割。

### 2.6 テスト戦略

- ドメイン層: jsdom不要の純粋な単体テスト（Vitest）。GeometryServiceはカバレッジ100%目標。
- アプリケーション層: DIで依存を差し替えてテスト。
- UI: Playwright（E2E）で主要シナリオのみ。
- テストは tests/ 配下に、ソースと同じディレクトリ構造で配置（例: `tests/domain/entities/Feature.test.ts`）。
- **テストは実装と同時に書く。** 実装後にテストを後回しにしない。
- 現状.md / 実装済み.md の総数・E2E ファイル別テーブルは pre-commit hook（[`scripts/sync-test-counts.sh`](scripts/sync-test-counts.sh)）が自動更新する。それ以外の箇所（サブフェーズ narrative の `+N件`・累積差分・per-module 件数表など）に件数を手書きしない。質的記述（追加したテスト群の名称・カバレッジ対象）で表現する。詳細は `memory/feedback_no_test_count_in_narrative.md`。

### 2.7 ビルド・テスト環境の注意点

- `vitest.config.ts` にパスエイリアス（`@domain`, `@application` 等）を定義する必要がある。`electron.vite.config.ts` のエイリアスと二重管理になるため、片方を変更したらもう片方も追従すること。

## 5. 開発フロー

### 5.1 開発プロセス

要件分析→設計→実装（TDD）→テスト→デプロイ→ドキュメント改善

**開発フローに改善が見つかったら、即座にこのセクションに還元すること。** ワークフローの知見はコードと同じく資産であり、会話の中に埋もれさせない。

#### 5.1.1 1機能の作業フロー

1. 実装する機能を宣言し、要件定義書の該当セクションを引用する。
2. 本ガイド 5.1.2 の「AI作業開始ゲート」に従い、関連教訓を引用・適用宣言する。
3. 実装する。
4. テストを書き、全パスを確認する。
5. `npm run build` でビルドが通ることを確認する。
6. 現状.md を更新する（実装ステータス）。テスト件数は pre-commit フックが自動更新するため手動更新不要。サブフェーズ narrative や追補エントリにも件数（`+N件` / `1XXX → 1XXX`）を書かない（質的記述に置き換える。`memory/feedback_no_test_count_in_narrative.md` 参照）。
7. コミットする。

#### 5.1.2 AI作業開始ゲート

このリポジトリで作業するAIは、実装・修正・リファクタリング・設計提案に入る前に、必ず以下を行う。

1. `開発ガイド.md` §6 から今回の作業に関連する教訓を最低1件引用する。
2. 引用は節番号・見出し・教訓本文を含める。要約だけで済ませない。
3. 引用直後に、その教訓を今回どの判断に使うかを「適用:」として1文以上で明示する。
4. `実装済み.md` の近い履歴に原因が記録されているのに §6 に対応する教訓がない場合は、作業前または作業と同時に §6 へ教訓化する。
5. 完了報告では、実装済み.mdへの履歴追記だけでなく、§6へ新規教訓を追加すべき根本原因があったかを明示する。

推奨フォーマット:

```text
今回参照する教訓:
- 開発ガイド§6.x.y「見出し」: 「教訓: ...」
適用: 今回は ... なので、... を確認してから変更する。
```

## 6. 開発上の注意点とよくある落とし穴

ここからが最も重要なセクション。過去の開発で得られた教訓を記録。

### 6.0 教訓の使い方と更新ルール

- 教訓は「読んだ」だけでは作業開始条件を満たさない。作業前の応答で、関連する節番号・見出し・教訓本文を直接引用し、今回の実装判断へどう適用するかを明示する。
- `実装済み.md` は履歴であり、再発防止策の置き場ではない。不具合の根本原因・見落としやすい判断基準・回帰テスト観点は、本節へ移す。
- 既存教訓で説明できる不具合なら、完了報告で参照した教訓を明示する。既存教訓で説明できない不具合なら、新しい教訓を追加してから完了扱いにする。
- 教訓は具体的な禁止・確認観点として書く。「注意する」「気をつける」だけで終わらせず、どの状態・層・テストで検出するかまで記録する。
- 一時的な実装状況や進捗はここに書かない。進行中の課題は `現状.md`、完了履歴は `実装済み.md`、再発防止の恒久知識は本節に置く。

#### 6.0.1 仕様文書での用語撤廃・追加宣言時の同一文書同期

- 教訓: 仕様文書の特定章で「この用語は使わない」「この用語に置き換える」と用語注記を追加した場合、同一文書内の全用例 + 関連する用語表 + 対応する設計サマリ (`現状.md` §6 / 開発ガイド §6 / `実装済み.md`) を**同じ変更単位で同期する**。「この章だけ修正、他は次回」と先送りすると同一文書内に self-contradiction が残り、Phase 完了として扱えなくなる。
- 検出観点1 (語彙の grep + 修正した表現の他箇所同期): 用語注記を追加したコミットでは、撤廃語をリポジトリ全文 grep し、同期対象のヒット箇所を全部直すか、明示的に「対象外 (理由つき)」と現状.md に記録する。レビュー時もこの観点で grep 検証する。同一文書内 self-contradiction は「Phase 完了前」のレビューで検出できる粒度の問題なので、本人レビュー時に必ず grep で確認する。**同じ説明表現を別箇所で再利用している場合（用語集、マニュアル備考、他章のサマリ等）も grep で検出して同期する**。本文を修正したら同じ表現の他出現を必ず grep し、同期しないと「本文と要約で表現が食い違う」 self-contradiction が残る。**関数シグネチャ撤去・引数撤去では tests/ にも grep を広げる**: `npm run check` (svelte-check) は `tsconfig.web.json` で `include: ["src/renderer/**/*"]` のみのため tests/ は型チェック対象外。vitest は実行時に型を見ない。`addPoint(coord, layerId, time)` のような旧シグネチャ呼び出しが tests/ に残ると、新シグネチャでは `currentTime = 'l1' (string)` となり `anchor.timeRange.start` に string が入る壊れた Feature を生成するが、テストアサーションが timeRange を参照しないと沈黙して通過する。引数撤去コミットでは `grep "<関数名>\(.*['\"]l\d['\"]"` 等で tests/ を全文検索し、漏れの 0 件を確認する。
- 検出観点2 (対概念の同期): ある概念に仕様判断を加えたら、その**対概念**にも同じ判断を反映する。「混在結合 ↔ 既存への子追加」「リーフ ↔ コンテナ」「同一性継続 ↔ 同一性終了」「下位領域獲得 ↔ 下位領域提供」のように、ある概念を変えたら対概念の説明文も同期する。仕様判断（例: 「結合は終了+新規生成で統一」）の影響範囲は、該当概念だけでなく対概念にも及ぶため、grep だけでなく「対概念の説明文がこの判断と整合するか」を能動的に確認する。
- 検出観点3 (実装状況主張の事実確認 + 同じ表内の同類対象一括確認): ドキュメント内で「既存の」「継承」「実装済み」「現行」「採用済み」など、実装状況や既存性を主張する記述を書くときは、書く前に必ずその対象識別子を src/ で grep して実在を確認する。ファイル名・関数名・型名・定数名など具体的な識別子を主張する記述は、語彙ではなく対象自体を grep する。Phase 未着手の機能の識別子を「既存」と書いてしまう事例を防ぐ。書いた後のレビューでも「既存」「継承」キーワードで検索し、各記述の対象が実在するかを確認する。**ある表内の1行を修正したら、同じ表内の同類対象も一括確認する**。同じ表内の同類エントリ（例: §6.12 の内部実装識別子列の他行）にも同じ問題が含まれている可能性が高いため、表全体の identifier を src/ で grep してまとめて修正する。
- レビュー指摘の即時反映ルール: レビューで「次回検討」と書きたくなる再発防止観点があれば、それは本節の趣旨（同じ変更単位で同期）に反する。判明した観点は同一作業内で本節へ追記し、先送りしない。
- 関連する経過:
    - 2026-04-28 §2.1 改訂第1回で「祖先・子孫・系譜」を撤廃した際、§2.1 内「直轄化」説明文と現状.md §6.5/§6.7/§6.8/§6.9/§6.12 の用語表に取りこぼしが発生し、外部レビューで指摘された。検出観点1 (grep) で防げた事例。
    - 2026-04-28 §2.1 改訂第2回で混在結合の同一性を「既存への子追加」から「終了+新規生成」へ統一した際、対概念である「下位領域獲得経路」の説明が前回追補時に「混在結合または所属変更」と書かれたまま残り、結合機能本体と矛盾していた。検出観点1 (grep) では発見できず、検出観点2 (対概念の同期) が必要だった事例。

### 6.1 状態管理と更新ロジック

#### 6.1.1 状態間の依存関係の更新漏れ

- 教訓: ある状態が変化したら、それに依存する他の状態も検証・更新する。例えば「時間が変わったら、選択中の地物がその時間に存在するか検証し、存在しなければ選択解除」。暗黙的ルールはコードで明示的にチェックする。

#### 6.1.2 非表示要素の選択・操作の混入

- 教訓: ユーザー操作の対象は「現在UI上に表示されている要素」に限定する。データソース全体を直接検索せず、Svelteのリアクティブ状態（`$derived`等）が管理する表示状態を基準にする。

#### 6.1.3 Undo/Redoスタック操作の副作用

- 教訓: pushUndoがclearRedoStackを呼ぶような副作用を持つメソッドは、全呼び出しコンテキストで副作用が適切か慎重に検討する。Redo操作からのpushUndoではRedoスタックをクリアしてはならない。

#### 6.1.4 コンポーネント間での状態同期漏れ

- 教訓: 共有リソースを更新したら、依存する全コンポーネントに変更を通知する。イベントバスで汎用的な状態変更イベントを発行し、各コンポーネントがリフレッシュするパターンが有効。リアクティブ状態やXStateコンテキストは内部データが常に最新とは限らない前提で設計する。

#### 6.1.5 プロジェクト設定とアプリ設定の責務混在

- 教訓: プロジェクト固有設定とアプリ全体設定の境界を先に定義し、保存先と反映先を一貫させる。

#### 6.1.6 UI文脈を既定値で上書きする追加・編集処理

- 教訓: 追加・編集・複製・結合の対象は、現在のUI文脈（フォーカス中レイヤー、選択中地物、現在時刻、表示中wrapなど）を第一候補にする。コレクションの先頭要素や固定デフォルトを使うのは、UI文脈が存在しない場合だけに限定する。特にレイヤーフォーカス中の追加処理では、追加先レイヤーの解決をUI状態からテストし、先頭レイヤーへ落ちる回帰を防ぐ。

#### 6.1.7 時間操作の粒度と速度の二重適用

- 教訓: 時間軸UIでは、年・月・日を分解した一部の値だけを下位層へ渡さず、`TimePoint` のような完全な時間値を受け渡す。再生処理では、タイマー間隔と1tickあたりの進行量のどちらが速度を表すのかを一箇所に決め、両方へ倍率を掛けない。月日ステップ、再生速度、プロジェクト設定の時刻範囲は同じヘルパーで検証し、10x再生などの回帰テストを置く。

#### 6.1.8 状態遷移の検出は入力経路でゲートせず結果状態で判定する

- 教訓: 「ある状態変化が起きたら追加処理（派生物の生成・剪定・再計算）を走らせる」検出は、**特定の入力経路（呼び出しフラグ・引数の有無）でゲートせず、変異後の結果状態で判定する**。同じ状態変化を**複数の経路**が引き起こす場合、特定経路に絞ったゲートは新経路・別経路で必ず漏れる（§6.0.1 検出観点2 のコード経路版: 仕様文書で「対概念ペア」に当たるものが、実装では「同じ結果状態に至る対経路ペア」になる。文書は対概念の説明文を同期し、コードは対経路の網羅を確認する、という対応関係）。
- 具体例（Phase 4-4b-1 のレビュー指摘）: 末端地物が下位領域を獲得して集約地物へ遷移したら直轄領を生成する処理を、`params.createNewParent === undefined && 新親が末端` という**入力経路ゲート**で起動した。だが「既存末端が子を獲得する」状態変化は (1) 既存末端を新親に指定（征服）だけでなく (2) 新規上位領域作成サブフローの**所属先 Q が既存末端**（自治化）でも起きる。後者はゲートで除外され、Q が「shape あり + childIds 非空」の移行期間ノードのまま残り、要件定義書 §2.1「形状属性は破棄」「親領域は下位領域の和に厳密一致」に違反した（保存後 `validateParentChildUnion` が拒否し得る壊れた状態）。修正は「変異前に末端だった全 changedFeatureId のうち、変異後に移行期間ノード錨を持つもの」を結果状態で走査する形へ置換。
- 検出観点: 起動条件に「この経路でだけ起きる」という前提を書いたら、**同じ結果状態を生む他の経路を列挙**して網羅を確認する。理想は経路非依存の「結果状態スキャン」。変異前状態を併用するゲート（例: 「変異前は末端だった」）は、ロード済みデータの既存状態（移行期間ノード等）を誤って巻き込まないために有効だが、それ自体を入力フラグで絞らない。回帰テストは**経路ごと**（征服・自治化・追加ツール親指定 等）に1本ずつ置く。
- 実装パターン（`ReassignFeatureParentUseCase.resolveLeafToContainerTransition` で確立）: (1) 変異前の features マップを保持、(2) 変異前状態の判定クロージャ（`wasLeafAtEffectiveTime`）を変異前マップから作る、(3) 変異後に `changedFeatureIds` の**スナップショット**（反復中の追記と分離するため `[...set]` で固定）を走査し、「変異前に末端 ∧ 変異後に移行期間ノード錨」を結果状態で検出する。類似ケース（`MergeService` 結合後の遷移検出 / `updateParentChildIdsFromTime` の錨分割連鎖）にもこのパターンを適用する。
- 関連: §6.0.1 検出観点2（対概念の同期）/ §6.6.8（in-memory コンテナ構築の不変条件は全経路で保証）。

### 6.2 UIインタラクションとユーザー操作フロー

#### 6.2.1 操作フローの完了トリガー欠落

- 教訓: UIインタラクションのフロー（開始・途中操作・完了/キャンセル）では、必ず「完了」のトリガーを定義・実装する。ユースケースにメソッドがあってもUIからの呼び出しがなければ機能しない。

#### 6.2.2 排他的イベント処理による意図しない動作

- 教訓: 排他的な条件分岐が他の重要な処理をスキップさせていないか確認する。頂点クリック時にその地物の選択も行うべきか等、選択優先順位と同時/排他選択を明確に定義する。

#### 6.2.3 オーバーレイ上のモーダルUIでのイベント競合

- 教訓: 地図の上にモーダルを表示する場合、イベント発生源を検証し、モーダル内のイベントが地図操作をトリガーしないようにする。stopPropagationだけでは不十分な場合があり、リスナー内でevent.targetを判定する。

#### 6.2.4 選択ハイライトで穴が塗り潰される

- 教訓: 穴や飛び地を持つポリゴンの塗りでは、領土リングと穴リングを同じpathのサブパスとして定義し、fill-rule="evenodd"を適用する。本体描画とオーバーレイ描画でリング階層の解釈を共有する。

#### 6.2.5 選択状態の分類漏れ

- 教訓: 複数の選択状態（単一・複数・不明・空）を扱うUIでは、派生済みのヘルパー結果だけでなく、生のIDセットを全て評価して分岐を網羅する。仕様のメッセージとViewの条件分岐を一対一で対応付ける。

#### 6.2.6 設定フォームのスクロール領域不足

- 教訓: フォームの操作ボタンが下部に配置されるUIでは、親の高さとoverflowを明確にし、min-height: 0とoverflow-y: autoを設定する。最小ウィンドウサイズでボタンが見切れていないか確認する。

#### 6.2.7 マウスイベントシーケンスの状態管理不備

- 教訓: mousedown→mousemove→mouseupのシーケンスで、全てのパス（クリック、ドラッグ）で状態が正しく開始・更新・終了されることを保証する。mousedownで設定した状態はmouseupで必ず解除する。mousemoveが発生しなかった場合（クリック）の考慮漏れに注意。

#### 6.2.8 一時的なインタラクション状態と描画の連携不備

- 教訓: 複数ステップのUIインタラクションでは、一時的な状態をXStateマシンのコンテキストで一元管理し、プレビュー描画はそのコンテキストから状態を取得して反映する。
- 教訓: XState外に補助的な一時状態を置く場合は、描画座標と同じ開始・確定・キャンセル・ツール切替・モード切替の全経路で明示的に破棄する。HUDの選択値やドラフト設定が残ると、次回の操作へ暗黙に引き継がれ、ユーザーが意図しない親指定や設定で確定できてしまう。E2Eでは「選択→キャンセル→再作成」と「選択→確定→再作成」の連続操作を確認する。
- 教訓: Svelteの`<select>`はoption DOMの再利用で現在値が残ることがある。補助状態を減らす場合でも、描画セッション単位のkey化と`{#each ... (id)}`でoptionを安定識別し、E2Eで「propは既定値に戻ったがselectの表示だけ残る」ケースを確認する。

#### 6.2.9 条件付き描画内の未定義参照による更新停止

- 教訓: 選択時やモード切替時にだけ描画されるUI分岐では、渡すprop名とローカル変数名の不一致が `ReferenceError` を起こし、無関係なリアクティブ更新停止に見えることがある。条件付きで出現するツールバーやオーバーレイは、表示契機を含むE2Eで実際に描画させ、ブラウザ実行時エラーも検出する。
- 診断ポイント: 「値は変わっているのに DOM が反映されない」症状が出たら、まずブラウザコンソールの `ReferenceError`/`TypeError` を確認する。`$.set()` やストアの値が更新されていても、フラッシュ中の未捕捉エラーで後続の `$effect` や DOM 更新が全停止する。`console.log` では値が読めるため「リアクティビティ故障」と誤診しやすい。E2Eでは `page.on('pageerror')` を設定してフラッシュ中のエラーを捕捉する。

#### 6.2.10 横方向無限スクロールでオーバーレイだけが追随しない

- 教訓: 横方向無限スクロールでは、ベース地図や地物本体だけでなく、頂点ハンドル・描画プレビュー・測量線のようなSVGオーバーレイも同じ `wrapOffset` 描画文脈に置く。地図本体とオーバーレイでラップ位置が分離すると、複製地図上に操作対象が出ず、パン後に「表示されない」「ずれて見える」不具合になる。

#### 6.2.11 東西端またぎの描画と無限スクロール本体は別々に担保する

- 教訓: 頂点や測量点の保存座標は `-180〜180` に正規化してよいが、`LineString` / `Polygon` / 大円パスの描画・ヒットテストでは、点列を前後関係からアンラップして `179° → -179°` を短い経路として扱う。同時に `wrapOffset` は `-360 / 0 / +360` の固定列挙ではなく、現在の `viewBox` と交差する全タイルを動的に生成する。保存用正規化座標をそのままパス化したり、隣1枚だけを描画すると、東西端またぎが世界横断線になり、1周以上のパンで空白が出る。

#### 6.2.12 巻き戻し前提のプレビューで正規化・クランプをしない

- 教訓: ドラッグ中プレビューのように「中間状態を一時適用し、確定前に逆変換で巻き戻す」処理は、可逆でなければならない。`normalize()` や緯度クランプをプレビュー段階へ入れると、東西端またぎで頂点ごとに別周回へ飛んで描画経路が壊れたり、`y > 90` のような一時値が失われて逆移動で元に戻らなくなる。正規化・クランプ・保存形式への整形は、コミット処理や永続化直前の責務として分離する。

#### 6.2.13 非正規化プレビュー座標は描画時だけ主表示帯へ戻す

- 教訓: 6.2.12 の都合でプレビュー中の経度が `±180` を超えること自体は許容されるが、そのまま `geoToSvgX()` へ流すと、図形やハンドルが別タイルの overflow に依存して表示され、`wrapOffsets` の境界でジャンプする。`LineString` / `Polygon` はアンラップ後の経度列全体を、`Point` やハンドルは単点経度を、SVG化直前に主表示帯（`-180〜180`）へ寄せてから描画する。プレビュー状態の保存値を変更してはいけない。

#### 6.2.14 タイル単位クリップは局所座標化なしで導入しない

- 教訓: `wrapOffset` ごとの `<g transform="translate(..., 0)">` の内側に `overflow="hidden"` なネスト SVG を入れるだけでは、地物がまだワールド全体の SVG 座標で描かれている限り、180°子午線またぎの面や線をタイル境界で切断してしまう。タイル単位クリップを使うなら、そのレイヤー全体を各タイルの局所座標系へ射影してから描画すること。そこまで行わない場合は、背景・ベースマップ・地物・グリッド・各種オーバーレイを「レイヤー単位で全タイル分まとめて描く」順序に再構成し、隣接タイルの背景やグリッドが、はみ出して描かれる地物を後から上書きしないようにする。

#### 6.2.15 頂点ドラッグ開始座標に保存経度をそのまま使わない

- 教訓: 180°超の経度幅を持つ面や共有頂点では、保存中の頂点経度と、ユーザーが実際に掴んだハンドルの表示経度が別周回になることがある。頂点ドラッグ開始座標やエッジ中点は、`VertexHandles` が描画に使ったアンラップ済み経度をそのままコールバックへ渡し、ドラッグ中もその周回に追従して更新すること。頂点移動・共有頂点移動で経度を `normalize()` すると、この周回情報が失われて接続方向が反転しやすい。経度正規化は、地物全体の平行移動や永続化直前など、周回情報を保持しなくてよい責務に限定する。

#### 6.2.16 経度は生値で保存し、描画時にunwrapしない（経度生値設計）

- 教訓: 経度は数直線として扱い、円環性は表示層だけが知る。
    - **保存**: 頂点の経度は生値のまま保存する。`190°` は「180°から東に10°」を意味する。`normalize()` は保存・移動・描画の経路で呼ばない。
    - **描画**: `buildRingPath` / `buildPolygonPath` / `buildLinePoints` で `unwrapLongitudeSequence` を使わない。頂点の生値座標に同一のタイルオフセットを加算して `geoToSvgX()` するだけにする。頂点間の相対位置が方向情報を自然に持つため、短い弧の仮定が不要になる。
    - **ラベル重心**: `labelRendererUtils` でも `unwrapLongitudeSequence` を外し、生値座標の算術平均を取る。結果を表示帯へ折り返す。
    - **頂点追加・クリック**: SVG→geo変換で既存リングの座標系と整合する経度を返す。`wrapOffset` 付きタイル上のクリックはそのタイル基準の生値になる。
    - **正規化の使用箇所**: ステータスバーの座標表示、手入力値の変換など、ユーザー向け表示に限定する。
    - **2周超・排他判定**: 720°超の地物や描画中プレビューは、固定枚数のwrap描画ではなく、地物の生値経度範囲と現在viewBoxに基づいて必要なタイルを動的算出する。排他判定・差分適用も `-180〜180` 前提に戻さず、360°シフトを含めた候補範囲で評価する。
    - 参照: `../time-map-app-2` は同じ設計で動作しており、星をぐるぐる回るポリゴンの作成・編集が正常に機能する。

#### 6.2.17 表示専用モードに編集操作を残さない

- 教訓: 表示モードでは、編集HUD・頂点ハンドル・コンテキストメニューの編集項目・ショートカット（例: Ctrl+Aの頂点選択）を同じ権限判定で無効化する。UI部品ごとに個別判定を書くと、見た目だけ非表示でショートカットや右クリック操作が残る。モード境界は共通ヘルパーまたは状態機械で表現し、表示モードのE2Eでは「編集用DOMがない」「編集ショートカットが効かない」「選択表示は残る」を同時に確認する。

#### 6.2.18 スクリーン固定UIを世界座標サイズで描かない

- 教訓: 頂点ハンドル、エッジハンドル、スナップマーカー、測量マーカーのような操作UIは画面ピクセル基準で大きさを決める。SVGの度単位やワールド座標半径をそのまま使うと、ウィンドウ幅・ズーム・viewBoxの変化で巨大化または極小化する。描画直前に現在のviewBoxと画面サイズからピクセル→SVG単位へ変換し、ズーム/リサイズの回帰テストを置く。

#### 6.2.19 変換後の選択状態を一律クリアしない

- 教訓: 結合・分割・移動・削除のように対象IDや形状が変わる操作では、完了後の選択状態を固定の `clearSelection()` で決めない。コマンド結果が「残る地物ID」「新規地物ID」「削除されたID」を返し、UIはその結果から選択を再解決する。成功後もユーザーが次に調整すべき対象が残る操作では、選択維持を回帰テストに含める。

#### 6.2.20 外部SVGの座標系を固定スケール前提で読まない

- 教訓: ベースマップやユーザー指定SVGは、特定ファイルの座標スケールに依存せず `viewBox` / `width` / `height` から正規化する。固定の出界図スケールや暗黙サイズに合わせて読み込むと、別SVGへの差し替え時に地図位置・操作座標・ラップ描画がずれる。不適合SVGのフォールバックと、正規化後の 360x180 表示をテストする。

#### 6.2.21 拒否理由・警告メッセージの寿命を無関係操作で消さない

- 教訓: 検証拒否や保存失敗など、ユーザーが次の判断に使うメッセージは、発生元と関係のないクリックやマウス操作で即時消去しない。メッセージを消す契機は「同種操作の再試行」「明示的な閉じる」「成功した置換操作」のように意味を持つイベントへ限定する。特に地図クリックの共通ハンドラで一律に通知状態を初期化しない。

#### 6.2.22 視覚レイヤーと入力レイヤーの重なりを同時に設計する

- 教訓: 測量マーカー、頂点ハンドル、メニューのバックドロップ、モーダルのような重なり合うUIは、描画順だけでなく入力を受ける層も同時に決める。透明バックドロップや測量オーバーレイが編集ハンドルを覆うと、見た目は正しくても操作が奪われる。E2Eでは表示確認に加えて、重なった状態で背面/前面の期待操作が通ることを確認する。

#### 6.2.23 SVG上の巨大表示を実マーカーだけと決めつけない

- 教訓: SVG上で大きな丸・枠・ハイライトが見える場合、アプリが描いた `circle` / `rect` / `path` のサイズだけでなく、ブラウザ既定のフォーカスアウトライン、選択ハイライト、CSS疑似状態、ドラッグ中クラスを最初に切り分ける。ズームしても画面上の大きさが変わらない視覚物は、SVGの世界座標サイズではなくCSS/UA由来の可能性が高い。広範囲のマーカーサイズ変更に入る前に、スクリーンショット、DOMの `boundingBox`、`getComputedStyle()`、該当状態のE2Eで「実要素の半径」と「周辺ハイライト」のどちらが巨大なのかを固定する。

#### 6.2.24 Svelte 5 ルーン値の参照と関数呼び出しを混同しない

- 教訓: `$derived(expr)` と `$derived.by(callback)` はどちらも値を返すルーンであり、結果は値として参照する。`$derived(() => fn)` のように右辺が関数式であれば結果は「関数」であり呼び出し側で `fn()` と書くが、`$derived.by(() => value)` の結果は callback の評価結果（値そのもの）であり `value()` のように呼び出してはいけない。同じ画面でも普段通る経路では問題が出ず、ある条件分岐（例: `placement.childIds.length > 0` のときだけ走る派生形状計算）に入ったときだけ `TypeError: $.get(...) is not a function` を投げ、§6.2.9 の通りフラッシュ中の未捕捉エラーで以降の DOM 反映が停止する。
- 検出観点: 条件付き描画やサイドパスを含むコンポーネントでは、その条件を実際に通す E2E を用意し、`page.on('pageerror')` でランタイムエラーを必ず捕捉する。`afterEach` で `pageErrors` が空であることを断言するパターンを使う。型チェックは通ってしまうため、テスト側で押さえる必要がある。

#### 6.2.25 クリック経路の最終決定は一元化する

- 教訓: クリック処理で DOM の `data-feature-id` から得る ID と `hitTest` の双方が候補になりうる場合、最終決定をどちらか一方に集約する。DOM 由来 ID を即採用すると、render order によっては親集約地物のパスが子末端の上に描画されたとき子をクリック選択できなくなる。逆に hitTest を即採用すると、点情報がポリゴン上にあるケースなど、同一 depth の重なりで実クリック要素と異なる地物が選ばれることがある。
- 採用ポリシー: hitTest を最終決定として優先し、`preferredFeatureId` に DOM target を渡して tie-break キーとする。ソートの優先順位は (1) depth 降順（深い子側を優先）、(2) DOM target 一致。hitTest が 1 件もヒットしない場合のみ DOM target にフォールバックする（点/線で閾値由来の取りこぼし対策）。フォールバック判断は呼び出し側（`App.svelte`）の責務とし、hitTest 自体は sceneEntries に含まれない地物を返してはならない（§6.1.2 非表示要素の選択禁止）。
- データ側に寄せる: tie-break で使う `depth` は `MapSceneEntry.depth` フィールドに集約し、`HierarchyService.deriveDepth` を経路ごとに呼び直さない（§6.6.9 適用パターン: 判定をデータ側に寄せる）。これにより描画順ソート（ASC）と hitTest tie-break（DESC）が同じ派生値を共有し、対概念矛盾を構造的に排除する。
- 検出観点: 「親子コンテナで子の方が深いとき子が選択できるか」「点/線をポリゴン上に置いて preferredFeatureId 指定で点/線が選択できるか」「preferredFeatureId が指定されても depth DESC が優先されること」をユニットテストで固定する。`hitTest` の戻り値ロジックを変えるたびに depth tie-break と DOM tie-break の順序を確認する。
- 背景: 旧版（〜Phase 2-D-6）では「(1) layerOrder 降順、(2) depth 降順、(3) DOM target 一致」の 3 キーだったが、Phase 2-D で `Layer` 概念を撤去したため第1キーが消滅し、現在は depth + DOM target の 2 キーで運用する。

### 6.3 データ整合性と型

#### 6.3.1 ドメインオブジェクトの代わりにリテラルオブジェクトを使用

- 教訓: DDDでは、エンティティや値オブジェクトは定義されたクラスのインスタンスとして扱う。プレーンオブジェクトを渡さない。TypeScriptの型システムでこれを強制する。

#### 6.3.2 コンポーネント間のデータ構造不一致

- 教訓: コンポーネント間でデータを渡す際、プロパティ名・型・構造が受け取り側の期待と一致しているか確認する。TypeScriptのインターフェースで契約を明示する。

#### 6.3.3 コンテキスト上の時刻とシステム時刻の混同

- 教訓: 時間軸を持つアプリでは、データのタイムスタンプは必ずコンテキスト上の時刻（タイムラインの現在時刻）を参照する。時刻源を一元管理するサービスから取得する。

#### 6.3.4 継承関係におけるメソッドオーバーライド漏れ

- 教訓: クラス継承でサブクラスが追加状態を持つ場合、基底クラスのwithXxx系メソッドはサブクラスでオーバーライドが必要か慎重に検討する。

#### 6.3.5 Undo/Redoのデータ復元

- 教訓:
  - 「操作を元に戻す」に必要な情報を正確に特定し、依存データも含めて過不足なく保存する。
  - 履歴にはプレーンオブジェクトを保存し、復元時は必ず新しいドメインインスタンスを生成する。
  - デシリアライズは再帰的に行い、ネストされた値オブジェクトも正しく変換する。
  - 履歴データのフォーマットは一貫させる。

#### 6.3.6 データ構造と描画ロジックの不整合

- 教訓: データ構造の全有効状態組み合わせを、描画・シリアライズ・操作の全箇所で網羅する。条件分岐は排他的ではなく組み合わせで考える。仕様から削除した属性はUI→状態管理層→永続化→レンダリングの順に全て除去する。

#### 6.3.7 JavaScriptのTruthiness/Falsinessの罠

- 教訓: 空配列[]や空オブジェクト{}はtruthyである。||での短絡評価に頼らず、型や状態を明示的に判定する。TypeScriptの型システムを活用すればこの問題の大部分は防げる。

#### 6.3.8 イミュータブルエンティティのAPI不備

- 教訓: withXxx系メソッドを導入する際、全属性について必要なメソッドが網羅されているか洗い出す。呼び出し側と提供側の変更が揃っているかテストで検証する。

#### 6.3.9 イミュータブルオブジェクトと可変データの混在

- 教訓: 世界データの復元では、後続処理が期待するデータ形式（イミュータブル vs 可変）を把握し、適切な形で返す。Object.freeze済みのエンティティを共有キャッシュに直接入れて後続が書き込もうとすると例外になる。

#### 6.3.10 初期データのエンティティ化漏れ

- 教訓: ドメインエンティティ化したデータ構造に依存するユースケースを導入したら、初期データ・テストデータ・スタブも全て同じエンティティ型にする。デフォルト生成コードは見落としやすい。

#### 6.3.11 preload/main/renderer のAPI契約不一致

- 教訓: renderer から呼ぶ `window.api`、preload が公開する関数名、main のIPCチャンネル名は、文字列の偶然一致に任せない。共有型・型付きラッパー・preload/main の単体テストで契約を固定する。API名変更時は renderer / preload / main / テストを同じ変更単位で更新し、旧名（例: `window.fileAPI`）が残っていないか検索する。

#### 6.3.12 列挙値・識別子の表記ゆれ

- 教訓: 地物種別、リング種別、モード名、設定キーのような分岐識別子は、表示文字列や思い込みで判定せず、型定義・定数・ファクトリを経由する。`Line` と `line` のような大小文字差でもUIバッジ、描画確定可否、保存形式が分岐する。新しい識別子を追加・改名したら、作成、表示、編集、保存、検索の全経路で同じ値を使うテストを置く。

#### 6.3.13 optional フィールド導入は全層を1サブフェーズに詰めない

- 教訓: ドメイン値オブジェクトの required フィールドを optional に変えるとき、影響は (1) 型定義、(2) consumer narrow、(3) JSON 永続化（型・serialize・deserialize・migration）、(4) validation、(5) 描画、(6) ヒットテスト、(7) PropertyPanel/Label/関連ダイアログの UI、(8) 派生サービス（cycle guard / multi-polygon 保持）に波及する。これら全部を1サブフェーズに詰めるとレビュー往復が10回を超え、対概念の同期漏れも増える。1サブフェーズあたりの差分は ~15 ファイル / ~300 行を上限に分割する。
- 推奨分割（型 optional 化の場合）:
    1. 型 + 永続化（型・serialize・deserialize・migration の判定）
    2. consumer narrow をドメイン+アプリ層
    3. consumer narrow をインフラ+プレゼン層
    4. shape 保持規則 validation（独自規則のみ。子参照健全性・親子整合は別フェーズ）
    5. UI/描画/ヒットテストは別の「UI 基盤」フェーズに切る
- 検出観点: 着手前に「触る経路」を最大2層で宣言する。宣言外の経路に修正が及びそうになったら別タスクへ切り出す。レビューで「対概念」と感じた修正は、そのレビューでは直さず別サブフェーズへ切る。

### 6.4 共有データと永続化

#### 6.4.1 検証前の共有キャッシュ破壊

- 教訓: 結果が確定するまで共有キャッシュの世界データを破壊的に更新しない。検証用の仮データを作り、成功が確認できた段階でのみ反映する。永続化が失敗してもキャッシュが汚染されないようにする。

#### 6.4.2 頂点差し替え時のロールバック漏れ

- 教訓: 頂点IDを差し替える処理では、検証前にworld.featuresを書き換えない。失敗時は追加した頂点と地物の両方をロールバックする。

#### 6.4.3 共有頂点化の保持頂点選択

- 教訓: 共有頂点化で残す頂点をIDの古さだけで決めず、操作コンテキスト（ドラッグ対象かどうか）に基づいて決定する。

#### 6.4.4 リング階層の削除ルール

- 教訓: リング階層削除ではリング種別ごとの許容親を尊重する。親領土リング削除時は直下の穴をカスケード削除し、領土リングのみを親の親へ付け替える。

#### 6.4.5 ID生成の衝突

- 教訓: ミリ秒精度のタイムスタンプだけに依存したID生成は同一ミリ秒内で衝突する。ID生成サービスを経由し、既存データとの重複検査を行う。

#### 6.4.6 共有頂点化の参加制限単位

- 教訓: 共有頂点化の禁止条件を「地物単位」に広げない。要件がリング/線形単位で定義されている場合、ドメイン判定・UI候補探索・回帰テストのすべてを同じ粒度で揃える。同一地物でも別リングなら許可し、同一リング/同一線形だけを拒否する。

#### 6.4.7 新規プロジェクト時の保存コンテキスト引き継ぎ

- 教訓: 新規プロジェクト開始時は、表示中データだけでなく保存ユースケースが保持するファイルパス・メタデータ・バックアップ対象も同時に初期化する。UI state だけを空にすると、次回 `保存` が旧ファイルを上書きしたり、旧プロジェクト設定を持ち越す。

#### 6.4.8 自動バックアップ仕様の層間不一致

- 教訓: 自動バックアップの仕様が「保存場所・世代管理・命名規則」を含む場合、renderer のユーティリティだけで完結させず、preload/main のファイルI/O契約と一緒に更新する。固定連番ローテーションをローカル実装すると、`/savebackup/` 配下の実ファイル一覧と乖離しやすい。バックアップ作成時は、実ディレクトリ上のタイムスタンプ付きファイル一覧を基準に保持上限を判定する。

#### 6.4.9 共有頂点付き移動のトランザクション境界

- 教訓: 地物移動・複数頂点移動・共有頂点ドラッグでは、頂点座標だけでなく共有頂点グループの `vertexIds` と `representativeCoordinate` も同じトランザクションで更新する。Undo/Redoコマンドは変更前後の共有グループ状態を保存し、存在しない対象へのno-op実行で共有グループを消さない。プレビュー中は開始時スナップショットから復元し、クランプや制約処理を通っても元座標へ戻れることをテストする。

#### 6.4.10 未保存変更とファイル文脈をUI stateだけで管理しない

- 教訓: 保存済みパス、プロジェクトメタデータ、バックアップ対象、dirty state、close guard は同じ保存文脈として扱う。画面上のWorldだけを初期化・更新しても、保存ユースケースやmain側の終了確認が古い状態を持っていれば旧ファイル上書きや未保存警告漏れが起きる。新規作成、開く、保存、閉じるの各経路で renderer と main/preload の状態同期を確認する。

#### 6.4.11 頂点削除時の共有グループ整理

- 教訓: 頂点削除では形状からIDを外すだけでなく、削除後にどの地物からも参照されなくなった頂点を `vertices` から削除し、`SharedVertexGroup.vertexIds` からも同じトランザクションで除去する。グループが1頂点以下になった場合は共有関係として残さない。Undo/Redoコマンドは削除前の地物・頂点・共有グループ状態を一括で保存し、共有頂点を含む頂点削除の回帰テストを置く。

#### 6.4.12 Redoで生成IDを採番し直さない

- 教訓: Undo/Redo対象コマンドが頂点ID・リングID・地物IDなどを生成する場合、redoでUseCaseを再実行して新IDを採番し直してはいけない。初回executeで生成されたIDと変更後スナップショットを保持し、redoでは同じIDを復元する。後続コマンドがそのIDをparamsに保持する操作列（挿入→削除→Undo×N→Redo×N）を回帰テストに含める。

#### 6.4.13 共有辺を切る分割の隣接地物更新

- 教訓: ナイフ分割などで共有辺の途中に新しい切断点が生じる場合、分割対象地物だけに頂点を作って共有グループを更新しても不十分である。共有先地物の該当辺にも同座標の頂点を挿入し、その頂点を分割対象側の新頂点と同じ `SharedVertexGroup` に入れる。ただし、共有先へ挿入する座標は分割結果に含まれる全境界座標ではなく、分割片A/Bの両方に現れる切断境界座標へ絞る。共有先地物だけが共有端点間に中間頂点を持つ場合も、共有端点同士を直接セグメント判定するのではなく、共有端点間の直線チェーン上の各セグメントを探索する。既存頂点が切断点そのものにある場合は、新規頂点を作らずその既存頂点を共有グループへ入れる。その既存頂点が別グループに所属済みなら、1頂点1グループ制約を壊さないよう新規グループではなく既存グループへ分割側頂点を統合する。Undo/Redoでは、分割対象・新地物・共有先地物・追加頂点・共有グループを同じスナップショットとして復元する。回帰テストでは、共有辺の端点ではなく辺途中の切断点に共有先頂点が追加されること、同じ共有辺に複数の切断点がある場合に辺上の順序で挿入されること、共有辺上の既存中間頂点が非切断時に共有先へ挿入されないこと、共有先側だけに中間頂点がある場合も切断点が挿入されること、切断点と同座標の既存共有先頂点が再利用されること、既存共有先頂点の所属グループへ分割側頂点が統合されることを確認する。

#### 6.4.14 親子グラフを辿る再帰サービスは visited セットで cycle guard を入れる

- 教訓: `getAncestors` / `getDescendants` / `deriveParentShape` のような親子関係を辿る再帰サービスは、壊れたデータ（循環親子参照、parentId と childIds の不一致）でも無限ループしないように、visited セットで再入を遮断する。`validateJsonWorld` 側で循環を検出するが、シリアライズ層を通らない経路（テスト・直接構築・手作りフィクスチャ）でも runtime 安全性を保つため二重防御する。
- 適用パターン: 再帰関数のラッパーを `func(...args)` として、内部実装 `funcInternal(...args, visited: ReadonlySet<string>)` を持ち、再帰時に visited を伝播する。既訪問 ID を辿ろうとしたら早期 return（空結果やループ break）。
- 検出観点: 循環親子参照のテストケースを各サービスに置く（A→B→A など）。タイムアウトや `RangeError: Maximum call stack` ではなく有限結果を返すことを確認する。

#### 6.4.15 永続化 shim は read / write / validate / round-trip test を同じ変更単位で同期する

- 教訓: 保存形式の移行中に一時 shim を入れる場合、`serialize` / `deserialize` / validation / migration / round-trip test を同じ変更単位で揃える。旧フィールドを読み捨てるなら、再保存したファイルを即座に再読み込みできることを必ずテストする。互換破棄方針でも「保存できるが次に開けない」状態は許容しない。シリアライズ・デシリアライズ・validation のいずれか片側だけを変えると、ユーザーの目から見ると「保存は成功した、でも次に開けない」という壊れたファイル経路ができる。これは型チェックでも runtime テストでも検出されず、ユーザーのデータを失うリスクがある。
- 検出観点: 永続化フィールドを optional 化・撤去・固定値出力する変更では、`deserialize(serialize(deserialize(input)))` 相当の再保存 round-trip を必ず追加し、validation が同じファイルを拒否しないことを確認する。validation 側に「変更したフィールドを参照する経路」が残っていないか grep で確認する（例: `placement.layerId` を撤去するなら `validateLayerReferences` や `world.layers` 参照経路も同時に整合させる）。
- 関連する経過:
    - 2026-05-19 Phase 2-D-6-3b で `serializeAnchorPlacement` が `pl.layerId ?? 'default'` を固定値出力する shim を入れた一方、`deserializeAnchorPlacement` は `json.layerId` を読み捨て、`validateLayerReferences` は `anchor.placement.layerId` が `world.layers` に存在することを引き続き要求していた。結果として旧 .gimoza（layers: [l1, l2]、anchor.placement.layerId: 'l1'）を読込→再保存すると anchor 側だけ `'default'` に置き換わり、`world.layers` には `'default'` がない状態で次回ロード時に `non-existent layer "default"` で拒否される経路ができた。レビュー指摘で発覚し、`validateLayerReferences` を本サブフェーズで前倒し撤去 + round-trip test を追加して再発防止。元の D-6-3c スコープから前倒しした分は実装済み.md に明示。

#### 6.4.16 undo/redo の Map 直接復元でもイベント通知を対称に発火する

- 教訓: コマンドの undo / redo が features Map を直接復元（`set` / `delete`）する経路でも、初回 execute と同じイベント規約（**存在・更新 = `feature:added` / 削除 = `feature:removed`**）で **touch した全地物** へ通知する。UI（Svelte リアクティブ状態）は undo / redo 直後の明示 `refreshFeatureData()` で追従するため、emit 漏れは画面に一切現れず、eventBus を購読する派生 consumer だけが静かに stale 化する。「動いて見える」ため通常の動作確認では検出できない失敗モード。
- 具体例（B29, 2026-06-10 修正）: `AddFeatureCommand.undo()` は追加地物と直轄領（`createdFeaturesDuringAssign`）を features Map から delete するのに `feature:removed` を発火せず、redo 側（`restoreAddedFeature`）も addedFeature のみ emit して直轄領・変更済み親が無通知だった。同型の漏れが `MergeFeatureCommand`（undo の emit ゼロ + execute / redo のセカンダリ削除無通知）、`SplitFeatureCommand`（undo の emit ゼロ + 分割元・共有エッジ先の変更無通知）、`CommitFeatureAnchorEditUseCase.applyAnchors`（錨更新経路のみ無通知）、`App.svelte` の `onConfirmRing`（リング追加確定の Map 直接 set + 手動 refresh 補償）にもあった。
- 基準実装: `ReassignFeatureParentCommand.restoreState` — changedFeatureIds を走査し、復元後に存在すれば `feature:added`、消えていれば `feature:removed` を emit する。
- 重複 emit の禁止: **同一の状態変化を二重に通知しない**。委譲先 UseCase（`addPolygonFromShape` 等）が生成時に emit する場合、コマンド側で同じ生成通知を重ねない（2026-06-10 `SplitFeatureCommand` 初回 execute の新地物二重 emit を解消。redo は 1 回で execute と多重度が非対称だった。push 型 consumer は「単一のアンドゥ単位」の操作を二度処理し得る）。生成後の placement 変更など**別個の状態変化**への連続 emit は重複に当たらない。
- 検出観点: **コマンド・UseCase・UI（`App.svelte` 等のイベントハンドラ）を問わず**、features Map を直接 `set` / `delete` する行を追加・変更したら、execute / undo / redo の全経路（UseCase / UI は当該経路）で「touch した全 featureId へのイベント」が対称かを確認する。直後に手動 `refreshFeatureData()` を書きたくなったら emit 漏れのサイン。イベント発火の回帰テスト（`feature:added` / `feature:removed` 両リスナーで収集 + execute / undo / redo の各経路で期待イベント集合を**厳密一致**検証 — 包含判定 `toContain` は漏れしか検出できず重複・過剰 emit を素通しする）を置く。
- 関連: §6.1.4（共有リソース更新の通知）/ §6.3.5（Undo/Redo のデータ復元）/ §6.1.3（Undo/Redo スタック操作の副作用）。

#### 6.4.17 地物削除は「全時間軸からの消滅」として参照を掃除する

- 教訓: 地物を features Map から削除する操作は、削除対象自身を消すだけでは完了しない。残存する全地物の**全錨**（特定時刻の有効錨に限定しない）から、削除対象への参照（`placement.parentId` / `placement.childIds`）を同じ操作内で掃除する。参照掃除の結果「shape なし・childIds 空」となったコンテナ錨は剪定し、全錨が消えた集約地物は連鎖的に消滅させる（要件定義書 §2.1「面情報の削除は、全時刻を通じて…参照を持つ他の地物が存在しないか、削除に伴う再編が許容される場合にのみ可能」「集約地物が下位領域を全て失った場合は自動的に消滅する」。shape を持つ移行期間ノードは最後の子を失っても末端地物へ戻るだけで消滅しない）。片方向（子の parentId だけ）や単一時刻（currentTime の有効錨だけ）の掃除は dangling 参照を残し、ロード時検証（参照先の存在 / 親子相互整合）が拒否する「保存できるが開けないファイル」（§6.4.15 が禁じる状態）を作る。
- 実装: `HierarchyService.planFeatureRemoval`（純粋な掃除計画の算出）+ `applyFeatureRemoval`（Map 反映 + §6.4.16 のイベント対称発火）を全削除経路（`DeleteFeatureUseCase` / `VertexEditUseCase` の退化形状削除 / `UpdateFeatureAnchorUseCase.deleteAnchor` / `MergeFeatureCommand` のセカンダリ削除 = `DeleteFeatureUseCase` 経由）で共有する。新しい削除経路を追加するときも素朴な `features.delete()` を書かず本経路を通す（§6.1.8: 同じ結果状態を生む全経路の網羅）。
- 具体例（B31/B32, 2026-06-10 修正）: `DeleteFeatureUseCase` が「子の parentId クリア」だけを currentTime の有効錨に対して行い、親の childIds から削除 ID を除去していなかった（B31）。さらに `DeleteFeatureCommand.undo()` のスナップショットが削除地物のみで、参照掃除で**変更**された地物の before 状態を含まず、undo 後に親子相互整合が壊れた（B32。修正は before/after 全マップスナップショット undo = `ReassignFeatureParentCommand` と同型への移行）。`MergeFeatureCommand` のセカンダリ削除にも同根の dangling が残存していた（B33。2026-06-10 に `DeleteFeatureUseCase` 共有経路 + 全マップスナップショット undo へ統一して解消）。
- 検出観点: `features.delete(` を追加・変更したら、(1) 削除対象への参照が全地物・全錨から消えるか、(2) 削除後の状態の保存→再ロード round-trip をロード時検証が拒否しないか、(3) undo で「削除された地物」と「参照掃除で変更された地物」の両方が復元されるか、を確認する。
- 関連: §6.4.11（頂点削除時の共有グループ整理 — 頂点版の同型教訓）/ §6.3.5 / §6.4.15 / §6.4.16 / §6.1.8。

#### 6.4.18 値未変更でも発火する確定ハンドラをコマンド化するときは no-op guard を入れる

- 教訓: `onblur` / `Enter` のように「値が変わっていなくても発火する」確定ハンドラを `UndoRedoManager.execute` 経由のコマンドへ載せると、フォーカスして離脱しただけ（実質 no-op）でもスナップショットコマンドが undo スタックへ積まれる。見た目に変化しない「幽霊 undo エントリ」となり、直前の実操作を取り消すのに Ctrl+Z を 2 回押す必要が出る後退になる。コマンド化の前は単なる重複 set / spurious dirty で済んでいたものが、コマンド化で undo スタック汚染という新しい後退に化ける点に注意する。確定ハンドラをコマンド化するときは、確定値が現在状態（フォーム同期時の baseline）と一致するなら execute を呼ばない no-op guard を必ず入れる。
- baseline の導出はフォーム同期と同一ソースを共有する（§6.6.9）: フォーム初期化（`$effect` での anchor → 編集 state 同期）と guard の baseline 算出が別々に既定値（未設定 style の既定色・既定パレット等）を持つと、未設定フィールドで baseline ↔ form がずれて guard が空振りする。両者が同じ既定値処理（例: `buildAnchorFormValues`）を呼ぶように抽出する。
- 具体例（B36 修正のレビュー指摘, 2026-06-12）: プロパティ編集確定（`PropertyPanel.applyChanges`）を `SnapshotFeatureEditCommand` 経由へ載せた際、`applyChanges` が値未変更の blur でも `onPropertyChange` を呼んでいたため幽霊 undo が新規に入った。`buildAnchorFormValues` を form 同期 `$effect` と guard で共有し、フォーム値が baseline と全フィールド一致なら確定をスキップして解消（spurious dirty も同時に消滅）。検証を通った実変更のみを確定する経路（`onConfirmRing` のリング追加）は対象外。
- 検出観点: 確定ハンドラ（blur / Enter / change）をコマンド化する変更では、「値を変えずにフォーカス→離脱」操作で undo スタックが増えないことを確認する。guard の baseline がフォーム同期と同じ既定値処理を共有しているか（別実装の既定値が無いか）を grep で確認する。
- 関連: §6.4.16（Map 直接変異の確定経路を undo 履歴に乗せる — 本教訓の前提となる変更クラス）/ §6.6.9（同じ判定は同じ実装を共有）。

### 6.5 テスト環境の落とし穴

#### 6.5.1 Playwright × Electron 41 の直接起動不能

- 教訓: Playwright 1.58 の `_electron.launch()` は Electron 41 (Chromium 136+) で動作しない。根本原因は二つあり、(1) Chromium 136 以降は `--remote-debugging-port=0` を CLI 引数として拒否するため Playwright が追加する引数で即終了する、(2) `-r loader.js` プリロードの `require('electron')` が Electron ビルトインではなく npm パッケージ側の CLI ラッパー（パス文字列を返す）に解決され `app` が undefined になる。`node_modules/electron/` の存在自体が原因で、Electron ダウングレードやローダー差し替えでは回避できない。
- 回避策: dev サーバー経由のブラウザ E2E を採用する。`playwright.config.ts` で `reuseExistingServer: true` を設定し、ユーザーが VSCode ターミナルから `npm run dev` を起動した状態で `npm run test:e2e` を実行する（Git Bash から `npm run dev` を起動すると同じ `require('electron')` 問題で失敗するため、dev サーバー起動元は PowerShell/cmd に固定する）。
- 失うテスト範囲: Electron IPC（保存/読み込みダイアログ）、ネイティブメニュー（Menu API）、マルチウィンドウ、`app.getPath()` 等の Electron 固有 API。
- 復帰条件: Playwright PR #39012（`fix(electron): pass port via switches not args`）がリリースされ、かつ `require('electron')` 解決問題も解消されたバージョンが出たら `_electron.launch()` に戻す。それまで `scripts/patch-playwright-electron.js` は参考用に保持する。

#### 6.5.2 設定ファイルのモジュール形式を実行環境と揃える

- 教訓: Vite/Svelte/Playwright などの設定ファイルは、拡張子と `package.json` のモジュール種別を実行環境に合わせる。ESMとして読まれる設定を `.js` のまま置くと、ローカル環境やNodeバージョン差で `npm run check` が落ちる。設定ファイルのリネームや形式変更は、`npm run check` と関連ツールの起動確認まで同じ変更単位に含める。

#### 6.5.3 ツールが直接使う依存は transitive dependency に頼らない

- 教訓: テスト・型チェック・ビルド・スクリプトが直接 import / execute するパッケージは、別パッケージ経由の推移依存に頼らず `package.json` へ直接依存として宣言する。ツールチェーン更新時に推移依存の解決が変わると、コード変更と無関係に `npm run check` やテストが失敗する。

#### 6.5.4 E2Eで失った範囲は単体テストで補う

- 教訓: Electron直接起動E2Eを一時的に使えない間も、IPC、preload、ファイルI/O、close guard、未処理Promise rejectionのようなElectron固有経路を未検証にしない。main/preloadの純粋関数化・アダプタ分離・モックIPCでVitest対象にし、E2Eで見られない保存/読込失敗や終了確認を単体テストで固定する。

#### 6.5.5 テスト fixture は実体クラスのインスタンスで構築する

- 教訓: 実体クラス（`Ring` のような値オブジェクト、ドメインエンティティ）を要求する型へ fixture を渡すとき、ヘルパーで返すリテラル `{ ... }` が実体の必須プロパティを欠いていても、テスト経路で参照されない限り silent pass する。後で別の経路（派生サービス・新しいバリデーション）が同じ fixture を別プロパティ経由で参照し始めると、リテラル fixture では `undefined` が返り silent fail する。TypeScript の構造的型付けは欠落プロパティを検出しないか、`as` キャスト経由で抑制されることがあるため、コンパイラに頼らずヘルパーは必ず実体クラスを `new` する。
- 例: `polygonShape` ヘルパーが `{ type: 'territory', vertexIds }` リテラルを返していた。`Ring` クラスは `{ id, vertexIds, ringType, parentId }` であり `ringType` プロパティが必要。リーフ単独描画 `resolveAnchorPolygonRings`（当時の描画側ローカル実装。後の B30 解消で `resolvePolygonAnchorPolygons` へ統一され撤去済み）は `vertexIds` のみ参照するため silent pass し、派生形状ルート `resolvePolygonAnchorPolygons` は `ring.ringType === 'territory'` で除外され silent fail していた。Phase 2.5-B でコンテナの派生形状ルートが本格運用される際にテストで顕在化し、リテラルを `new Ring(id, vertexIds, 'territory', null)` に修正して解消した。
- 検出観点: テストヘルパーで複合構造（リング・錨・地物・座標など）を構築するときは、`new ClassName(...)` で実体化する。`{ ... }` リテラルでドメイン型を満たそうとせず、ヘルパー定義のシグネチャ自体を実体クラスに揃える。新しい派生サービスが既存 fixture に対して silent fail していないかは「未参照プロパティが新たな経路で必要になったとき」に発覚するため、新規派生サービスを書くサブフェーズでは fixture ヘルパーも同時に見直す。

### 6.6 幾何制約・リング構造・編集コマンド

#### 6.6.1 検証をUIだけ・ドメインだけに偏らせない

- 教訓: 自己交差、末端地物の地図全体重複、リング階層破綻、共有頂点禁止条件のような編集制約は、UIの候補表示だけでなくコマンド・ユースケースの確定前にも同じサービスで検証する。UIが候補を隠しても、ショートカット、コンテキストメニュー、Undo/Redo、テスト用直接呼び出しで不正状態が入る。拒否理由はユーザー通知とテスト可能な戻り値の両方で扱う。

#### 6.6.2 穴・飛び地・複数領土リングを平坦化しない

- 教訓: ポリゴンのリング構造では、`territory` と `hole` の親子関係を常に保つ。領土リングが複数ある地物を再マージ・再分割するとき、2つ目以降を機械的にhole扱いしない。穴内の島はhole配下の `territory` として再構築し、占有面の判定では「領土リング + 直下の穴リング」を単位にする。描画、ヒットテスト、競合検出、結合、分割コマンド、ナイフ確定可否UI、保存のすべてで同じリング階層を使う。複数territoryの開線バリデーションでは交差回数を合算せず、少なくとも1つのterritory外周が2回以上交差することを条件にする。開線が横断していないterritoryは、延長半平面で分断せず、形状を丸ごと維持したまま所属先だけを判定する。

#### 6.6.3 結合対象の事前条件を明示する

- 教訓: 結合（合体）と所属変更（割譲・連邦化・帰属・直轄化等）は別概念であり、事前条件も分けて検証する（要件定義書 §2.1 は両者を別の機能として定義する）。共通の事前条件として、対象が同一地物ではないこと・面地物であること・時間上有効であることを、操作開始前と確定前の両方で検証する。加えて操作種別ごとに固有の条件を検証する:
    - **結合（合体）固有**: 選択集合内の地物が互いに上位・下位関係にないこと（集約地物とその下位領域を同時に結合対象にできない。要件定義書 §2.1 合体・結合機能の「制約」）。
    - **所属変更固有**: 新しい上位領域（親候補）が、対象地物自身およびその下位領域すべてに含まれないこと（循環参照防止。新しい上位領域を自身の下位領域に設定するとツリーに循環が生じる。要件定義書 §2.1 所属変更フローの「親候補の制約」）。対象地物の上位領域（より上位の既存領域）は循環を生まないため親候補に含めてよい（直轄化がこれに該当）。実装上の循環検出は、新親の上位領域連鎖（`getAncestors(newParentId)`）に移動対象が含まれないことで判定する（`MergeService.validateTransfer`）。
- 不正対象をモーダルやサービスへ流してから失敗させると、選択解除や部分更新の副作用が残りやすい。結合後は残る地物ID・追加リング・削除対象を結果として返し、UI選択とUndo情報をそこから再構築する。
- 補足（新階層モデルへの移行）: 旧「同一レイヤーに属すること」という結合事前条件は撤廃した。グローバルなレイヤー序列概念は廃止されており（現状.md §6）、結合対象は異なる上位領域に属していてもよい（異なる上位領域に属する場合は結合後の上位領域を決定するダイアログを表示する。要件定義書 §2.1）。

#### 6.6.4 EdgeSlideは終点だけでなく移動線分全体を判定する

- 教訓: エッジ滑りや頂点ドラッグの制約では、移動先点が合法かだけでなく、開始点から移動先までの線分が障害物や境界を横切るかを判定する。障害物を横切る移動は通過させず、内部へ入る移動は最初に交差した境界を衝突応答の基準にする。境界上の始点から内部へ向かう移動を反対側エッジへ飛ばさず、移動先が境界上の合法接触であるケースは許可する。

#### 6.6.5 ブーリアン演算結果の複数片を落とさない

- 教訓: `polygon-clipping` などのブーリアン演算は、単一ポリゴンではなく複数ポリゴン・複数リングを返す前提で扱う。差分・結合・競合解決では、返却された全ての片を頂点・リング・親子関係へ変換し、Commit側で作成頂点とリングをまとめて反映する。Resolve側で共有キャッシュを直接書き換えず、`createdVertices` などの結果データとして返す。

#### 6.6.6 隣接・自動配色はレイヤーと表示経度の文脈を揃える

- 教訓: 隣接辺ベースの自動配色や境界共有判定は、全地物を一括で見ず、同一レイヤー・現在の表示経度文脈・生値経度設計に揃えて評価する。保存済み色と自動解決色の優先順位を明示し、180°子午線またぎの共有辺も同じ正規化/生値方針で比較する。

#### 6.6.7 衝突検出と滑り応答を分ける

- 教訓: EdgeSlideのようなドラッグ制約では、Time of Impactで最初の接触点を求める処理と、接触後の残り移動を処理する衝突応答を分ける。接触点で毎回止めると、辺上や頂点近傍で固着しやすい。頂点-辺は接触辺の接線へ、移動辺-障害物点は固定点-障害物点の接触線へ残り移動を射影し、その結果を再度制約判定する。`t=0` の既存接触は新規衝突として止め直さず、法線方向の食い込みだけを捨てて接線方向の移動を許可する単体テストを置く。ただし、辺-点滑りの候補線分が障害物面の内部を通る場合は、外周線上の点衝突として採用しない。障害物は外周線だけでなく面として再評価し、単に直前座標へ戻すのではなく、ドラッグ線分に近く、かつ移動辺が面内部を通らない境界候補へ退避させる。高速ドラッグでは目的地に近い候補を優先すると奥の角へ飛ぶか固着しやすいため、ドラッグ線分からの距離と進行方向で候補を選ぶテストを置く。

#### 6.6.8 排他検証は仕様の対象範囲を実装で広げない

- 教訓: ドメインの基本ルール（排他性・整合性・階層）が仕様で明示的に対象を限定しているとき、実装で「対称性確保」「自然な拡張」を理由に対象範囲を広げない。要件定義書 §2.1 line 145-153 は「**末端地物の排他性は地図全体に適用する**」「**排他検証は末端地物同士のみ**。集約地物には直接の排他制約を課さない」「**集約地物ペアに対して直接の非重複検証を実装してはいけない**」と明記しており、`ConflictDetectionService` を集約地物・移行期間ノード（shape あり + childIds 非空）に拡張するのは禁止。集約地物同士の重なりは、子の末端地物が末端地物排他を満たしていれば派生的に保証される。
- 検出観点: ドメイン基本ルールに触れる変更前に、要件定義書 §2.1 / §2.2 の該当節を引用する（開発ガイド §5.1.2 の AI 作業開始ゲート）。「描画/ヒットテストとの対称性」「直感的な拡張」と感じた変更ほど、仕様で例外規定されている可能性を疑う。
- リーフ判定の運用: shape を保持し `childIds.length === 0` であることを必要十分条件とする（要件定義書 §2.1 / 現状.md §6.4）。`isLeafPolygonAnchor` のような共通ヘルパーで判定をひとつに集約し、検証経路間でのドリフトを防ぐ。
- childIds のみでリーフ判定する経路の不変条件依存: `parentTransferDialogUtils.isLeafFromTime` のように shape を見ず `childIds.length === 0` だけでリーフを絞る経路は、`isLeafPolygonAnchor`（shape チェック込み）から意図的に分岐しており、「shape なし ⟹ childIds 非空」という不変条件に暗黙依存する（この前提下でのみ shape 込みの判定と論理的に等価）。この不変条件はロード時の `validateShapePresence`（`jsonSerializerValidation`）でのみ保証され、有効な世界では「shape なし・childIds 空」の Polygon は存在し得ない（ロード拒否 + 実行時は剪定で自動消滅）。**in-memory でコンテナ（shape なし Polygon）を構築・変異させる経路を新設するときは、同等の不変条件を生成・変異の各ステップで保証するか、当該リーフ判定経路に防御的な shape 存在確認を入れる**。さもないと不正な「shape なし・childIds 空」Polygon が childIds-only 経路でリーフ誤判定される（クラッシュはしないが分類が狂う。`collectFeatureVertexIds` は `if (!anchor.shape) continue;` で skip するためデータ破損は起きない）。

#### 6.6.9 描画・ヒットテスト・派生サービスは同じ shape 解決経路を共有する

- 教訓: 集約地物（shape を持たない Polygon）の形状を「子の和として導出する」とき、描画 (`FeatureRenderer.getPolygonPath`)・ヒットテスト (`hitTestUtils`)・派生サービス (`HierarchyService.deriveParentShape`) の3経路は同じ判定で動かす。判定条件のドリフト（一方が `childIds.length > 0` で derive、別の一方が `shape !== undefined` を即リーフ扱い、など）があると、画面では描画されているのに選択できない、ラベル位置が描画と異なる、移行期間ノードの祖先派生が落ちる、といった対概念矛盾が次々と出る。**MapCanvas の選択コンテキストアンカー取得（`selectionAnchor` derive）も同じ shape 解決経路を共有する 4 経路目**（Phase 2-D-7e で `features.find().getActiveAnchor()` 直接走査から sceneEntries 経由へ移行済み）。
- 適用パターン: `featureType === 'Polygon'` && `childIds.length > 0` の場合は派生形状を優先し、derive 結果が空のときのみ自身の shape を fallback として使う。この判定を `resolveFeaturePolygonsAt` のような共通関数へ集約し、3経路すべてからこの関数を呼ぶ。`LabelRenderer` のラベル位置・面積判定も `containerPolygons` 引数で同じ派生形状を受け取り、描画と一致させる。選択コンテキストアンカーは sceneEntries を直接 `find` するだけで shape 解決済みのアンカーが得られる（sceneEntries 構築時点で派生形状が解決できないコンテナは除外されているため、選択側で別フィルタを書かなくて済む）。
- 適用パターン（判定をデータ側に寄せる）: 経路ごとに「polygon-like か」をハードコード（`feature.featureType === 'Polygon'` / `anchor.shape?.type === 'Polygon' || (!anchor.shape && polygonRings)` など）で書くと、規約変更（例: sceneEntries の除外条件変更）時に経路ごとに追従漏れが発生する。共通中間表現（`MapSceneEntry.polygonRings`）に規約を寄せ、「`polygonRings !== null` ⇔ Polygon-like」を MapSceneEntry の不変条件として宣言し、3 経路すべて `entry.polygonRings !== null` で振り分ける。規約自体を unit テスト（`Polygon entry は必ず non-null` / `Point/LineString entry は必ず null`）で固定する。新規経路（PropertyPanel のコンテナ表示 等）が増えても同じ判定基準を共有できる。
- 派生サービスの実装規則:
    - 子地物が集約地物（`shape === undefined`）であれば孫の和を再帰呼び出しで取り込む（多段階層）
    - `polygonUnion + polygons[0]` のような片落としを避け、`polygonUnionAll` を使って多 polygon を保持する（§6.6.5 の応用）
    - cycle guard を入れる（§6.4.14）
    - 再帰時は polygon 構造（`RingCoords[][]`）を保持し、トップレベルの公開 API でのみ territory/hole の順でフラット化する。再帰中に flat 化すると、孫の MultiPolygon が親 polygon の hole として誤解釈される（polygon-clipping は受け取った rings 配列の 2 番目以降を hole 扱いするため、孫の 2 個目以降の territory が hole に化けて片落としが発生する）
- 検出観点: 「描画される領域 = 選択できる領域 = ラベル位置の基準形状」を回帰テストで固定する。多段階層・離れた孫リーフ・shape あり + childIds 非空 の各ケースで、3経路の結果が一致することを確認する。

#### 6.6.10 同じピッカー UI を別操作へ流用するとき候補一覧を共有しない

- 教訓: 「親候補を選ぶ」「移動先を選ぶ」のように **見た目が同じピッカー UI** を複数の操作で使うとき、候補の **除外規則は操作種別ごとに固有** なので、派生した候補一覧（`$derived`）を安易に共有しない。§6.6.9 が「同じ判定を共有すべき経路を別実装にしてドリフトさせるな（過少共有）」を戒めるのに対し、本教訓はその **対概念**「制約が異なる操作で候補一覧を共有して片方に誤った除外を適用するな（過剰共有）」を戒める。
- 具体例（Phase 4-3 自治化）: 所属変更ダイアログの「既存への再割当」候補は `scope='children'` のとき現在の親を除外する（子を現在の親へ再割当するのは no-op）。同じ候補一覧を「新規中間コンテナの所属先（自治化）」へ流用すると、自治化の主目的である「既存子と既存親の間への挿入」（現在の親 = 所属先）が候補から消え、機能が UI から到達不能になる。除外規則が異なるため別の `$derived`（`parentCandidates` と `newParentParentCandidates`）として導出し、UI の select・退避ロジック・確定前検証（`resolveParentTransferTarget`）をそれぞれ正しい候補一覧へ接続する。
- 検出観点: 候補一覧を流用する前に「2 つの操作の除外規則は本当に同一か」を、操作種別ごとに列挙して確認する。`npm run check` / 型は同じ `ParentCandidateItem[]` のため通ってしまうので検出できない。**「候補一覧 A に無いが候補一覧 B にはある対象を、操作 B が受理する」回帰テスト** を置いて、共有に戻す回帰を弾く（例: `parentCandidates` 空でも `newParentParentCandidates` にある所属先を `resolveParentTransferTarget` が解決する）。ユニットだけでなく「機能が UI から到達できること」をユースケース層の正常系テストでも固定する。
