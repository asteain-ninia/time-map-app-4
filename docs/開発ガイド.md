# 開発ガイド

本書は time-map-app-4 の開発作法をまとめた恒久文書である。技術非依存の開発規律・文書の役割分担規約・ドメインとアルゴリズムに関する教訓を収録する。具体的な技術スタック・フレームワーク・ライブラリの選定および言語固有の規約は本書では扱わず、技術方針.md で定める。

本書の各教訓は「何に注意するか」ではなく「どの状態・層・テストで検出するか」を記述する。作業に着手する前に、関連する節を直接引用し、今回の実装判断へどう適用するかを宣言してから着手すること（後述の「AI 作業開始ゲート」）。

---

## 1. 開発規律（workingRules）

### 1.1 根本原因の修正

不具合修正時は必ず根本原因を修正し、場当たり的・対症療法的な対応をしない。まず原因解析に注力する。この規律は初期実装・保守・不具合修正のすべてのフェーズで有効である。

### 1.2 省略の禁止

コードの修正時に「～も同様に～」といった省略は一切しない。影響箇所はすべて明示的に修正する。同種の箇所が複数あるなら、その全件を列挙して直す。

### 1.3 保守時の最小変更

保守・不具合修正フェーズでは、指示されていない変更・余計な変更を行わず、変更箇所を最小限にとどめる。初期実装フェーズでは、土台を整える目的に限り必要に応じて緩和される。

### 1.4 論拠の引用義務

何かを論ずるときは、根拠となるソースコード（または仕様の該当節・行番号）を直接引用する。要約だけで済ませない。レビュー・設計判断・不具合報告のいずれでも、引用なしの主張は根拠不十分とみなす。

### 1.5 失敗の教訓化（全フェーズで有効）

実装上の失敗・不具合の根本原因は恒久知識として本書（§5 教訓集）に保存する。既存の教訓で説明できない不具合は、新しい教訓を追加してから完了扱いにする。完了報告では、新規に教訓化すべき根本原因があったかを必ず明示する。

### 1.6 教訓は読むだけでなく適用宣言する（AI 作業開始ゲート）

作業開始前に、関連する教訓を節番号・見出し・本文ごと直接引用し、今回の実装判断へどう適用するかを「適用:」として 1 文以上で明示してから着手する。引用と適用宣言を省略して着手してはならない。

### 1.7 教訓は具体的な禁止・確認観点として書く

「注意する」「気をつける」で終わらせない。どの状態・どの層・どのテストで検出するかまで記録する。再現条件と検出手段が書かれていない教訓は不完全である。

### 1.8 やり残しの記録

実装のやり残しは、未解決課題文書（現状.md）に追記する。口頭・記憶・コミットメッセージだけに残してはならない。

### 1.9 テストは実装と同時に書く

実装後にテストを後回しにしない。1 機能のフローは次の順序で進める。

1. 機能宣言 + 仕様引用
2. 関連教訓の引用・適用宣言
3. 実装
4. テスト全パス
5. ビルド確認
6. 状態文書更新
7. コミット

### 1.10 ワークフロー知見の即時還元

開発フローに改善が見つかったら、即座にプロセス文書へ還元する。レビューで「次回検討」と書きたくなる再発防止観点は、先送りせず同一作業内で教訓集へ追記する。

### 1.11 コミットメッセージ規律

コミットメッセージは全文をその言語（本文は日本語）で記述し、type のみ慣例に従う（Conventional Commits）。状態文書のみの更新コミットは、メッセージを定型に統一する。

## 2. 文書の役割分担規約（docConventions）

### 2.1 文書の役割を厳守する

文書は次の 5 つで完結する。どれに書くべきか迷ったら、この表の役割で決める。

| 文書 | 役割 | 書かないもの |
| --- | --- | --- |
| **要件定義書.md** | 何を満たすべきか（技術非依存の仕様本文） | 実装方法・進捗・識別子（§2.5） |
| **技術方針.md** | どう実現するか（技術選定と、実装で確定した設計判断） | 未解決課題・作業履歴 |
| **開発ガイド.md**（本書） | 開発作法・文書規約・再発防止の恒久知識（§5 教訓集） | 一時的な実装状況・進捗 |
| **現状.md** | 未解決課題・既知の不具合・残作業 | 完了した課題（即時削除し実装済み.md へ）・機械算出値（§2.6） |
| **実装済み.md** | いつ何を実装したかの履歴 | 再発防止策（§2.4）・未解決事項 |

補助資料として、`specs/` にユニット単位の着手指示書、`reference/` に前世代（v3）の参照素材を置く。
どちらも**凍結した過去の資料**であり、新規の追記はしない（`specs/README.md` / `reference/README.md`）。
`.autopilot/` も 2026-08-11 に凍結した過去の作業ログである（`.autopilot/README.md`）。
現在の状態を判断する根拠は `docs/` とソースコードのみとする。凍結資料と `docs/` が食い違ったら `docs/` が正。

### 2.2 完了課題を残す例外

完了した課題は原則として即時削除するが、同一課題を複数回の作業で分担し、削除すると進行文脈が失われる場合に限り、未解決課題文書に一時的に残してよい。その場合は行頭に `[完了]` を付け、残作業完了時に課題全体を削除する。

### 2.3 課題番号は欠番として残す

未解決課題文書からリスト項目を削除するときは、それがリストの最後でない限り欠番として残す（番号を詰めない）。番号を詰めると過去の参照が壊れる。

### 2.4 再発防止知識は履歴文書に書かない

再発防止の恒久知識・見落としやすい判断基準・回帰テスト観点は、履歴文書ではなく教訓集（本書 §5）へ移す。履歴文書はあくまで「何をいつ実装したか」の記録に限定する。

### 2.5 要件定義書は仕様本文と内部実装補遺を分離する

要件定義書は仕様本文と内部実装補遺を分離する。仕様本文（完全自然言語）には、識別子・内部キー名・クラス名・コード値を直接記載せず、実装詳細は内部実装補遺へ集約する。

### 2.6 機械算出値は手書きしない

テスト件数のように機械的に算出できる数値は自動更新（コミット前フック等）に任せ、ナラティブや追補エントリへ件数を手書きしない。件数差分ではなく、追加したテスト群の名称・カバレッジ対象といった質的記述で表現する。

### 2.7 コメント規律

コメントは本質的に必要な内容のみを書き、一時的な情報を含めない。「修正:～」「ここを修正」「--修正ここから--」のような書き方をしない。既存のコメントは温存する。

### 2.8 用語撤廃・置換は同一変更単位で同期する

仕様文書で用語を撤廃・置換すると宣言したら、同一文書内の全用例・関連する用語表・対応する設計サマリを同じ変更単位で同期する。「この章だけ修正、他は次回」と先送りすると、同一文書内に自己矛盾が残る。

### 2.9 用語注記を追加したら全文検索で同期する

用語注記を追加したら、撤廃語をリポジトリ全文検索し、ヒット箇所を全部直すか「対象外（理由つき）」と未解決課題文書に記録する。同じ説明表現を別箇所で再利用している場合（用語集・備考・他章サマリ）も検索して同期する。

### 2.10 対概念へ判断を反映する

ある概念に仕様判断を加えたら、その対概念にも同じ判断を反映する（混在結合↔既存への子追加、リーフ↔コンテナ、同一性継続↔同一性終了 等）。検索だけでなく、対概念の説明文がその判断と整合するかを能動的に確認する。

### 2.11 既存性の主張は実在確認してから書く

ドキュメントで「既存の」「継承」「実装済み」「現行」等、実装状況や既存性を主張する識別子を書くときは、書く前にその識別子をソースで検索して実在を確認する。表内の 1 行を修正したら、同じ表内の同類対象も一括確認する。

## 3. 本プロダクトの前提（v4 の文書方針）

### 3.1 クリーンルーム原則

本プロダクトの文書は、外部の既存実装・他プロダクト・過去の作業文脈に依存しない自己完結した記述とする。必要な制約は本プロダクト自身の要件・方針として直接記述し、「以前のやり方」「従来」といった外部参照に頼らない。

### 3.2 技術と作法の分離

本書は技術非依存の作法のみを扱う。採用技術・実行環境・ライブラリ・言語固有規約は技術方針.md に集約する。本書に技術スタック名が混入したら、それは記述場所の誤りである。

## 4. ドメイン・アルゴリズム共通の設計指針

以下は §5 の個別教訓の背景にある、横断的な設計指針である。

- **単一の真実源**: 同じ判定・同じ基準値（baseline）・同じ既定値処理は、同じ実装を共有する。判定ロジックの分散はドリフトを生む。
- **対概念の整合**: 一方の概念に判断を入れたら、必ず対をなす概念（追加↔削除、開始↔終了、リーフ↔コンテナ）に同じ判断を反映する。
- **UI 文脈の優先**: 操作対象は「いま UI 上に表示・選択されている要素」を第一候補にし、コレクションの先頭やデータソース全体を既定で使わない。
- **結果状態での判定**: 「ある状態変化が起きたら追加処理を走らせる」検出は、特定の呼び出し経路ではなく、変異後の結果状態で判定する。
- **層をまたぐ契約の固定**: 呼び出し側・公開側・受信側で共有する名前・型・構造は、偶然の一致に頼らず型や両側テストで固定する。

## 5. 技術非依存の教訓集（techAgnosticLessons）

各教訓は「再発防止の恒久知識」である。新たな不具合の根本原因が既存教訓で説明できないときは、本節へ追記してから完了扱いにする。

### 5.1 集合演算は複数片を返す前提で扱う

ブーリアン（集合）演算は単一ポリゴンではなく、複数ポリゴン・複数リングを返す前提で扱う。差分・結合・競合解決では返却されたすべての片を変換し、片落とし（配列の先頭だけ採用）を避ける。

- 検出: 差分・結合の結果が 2 片以上になる入力で、全片が出力に現れることをテストする。

### 5.2 一時的 UI 状態は全経路で破棄する

一時的 UI 状態（描画プレビュー・選択中の値・ドラフト設定）は、開始・確定・キャンセル・ツール切替・モード切替のすべての経路で明示的に破棄する。残ると次回操作へ暗黙に引き継がれ、意図しない値で確定できてしまう。

- 検出: 「選択 → キャンセル → 再作成」と「選択 → 確定 → 再作成」の連続操作を E2E で確認する。

### 5.3 操作対象は表示状態に限定する

ユーザー操作の対象は「現在 UI 上に表示されている要素」に限定する。データソース全体を直接検索せず、表示状態（リアクティブ派生状態）を基準にする。

### 5.4 追加・編集・複製・結合は現在の UI 文脈を第一候補にする

追加・編集・複製・結合の対象は、現在の UI 文脈（フォーカス中対象・選択中対象・現在時刻・表示中要素）を第一候補にする。コレクションの先頭要素や固定デフォルトを使うのは、UI 文脈が存在しない場合だけに限定する。

- 検出: 先頭要素へ落ちる回帰をテストで防ぐ。

### 5.5 依存する状態は変化時に再検証する

ある状態が変化したら、それに依存する他の状態も検証・更新する。例: 時間が変わったら、選択中要素がその時間に存在するか検証し、なければ選択を解除する。暗黙的ルールはコードで明示的にチェックする。

### 5.6 状態変化の検出は結果状態で判定する

「ある状態変化が起きたら追加処理を走らせる」検出は、特定の入力経路（呼び出しフラグ・引数の有無）でゲートせず、変異後の結果状態で判定する。同じ状態変化を複数経路が引き起こす場合、特定経路に絞ったゲートは別経路で必ず漏れる。

- 検出: 起動条件に「この経路でだけ起きる」と書いたら、同じ結果状態を生む他経路を列挙して網羅を確認し、回帰テストを経路ごとに置く。

### 5.7 完了トリガーを必ず実装する

UI インタラクションのフロー（開始・途中操作・完了/キャンセル）では、必ず「完了」のトリガーを定義・実装する。ロジック側にメソッドがあっても、UI からの呼び出しがなければ機能しない。

### 5.8 押下→移動→解放シーケンスを全パスで保証する

押下 → 移動 → 解放のシーケンスは、全パス（クリック・ドラッグ）で状態が正しく開始・更新・終了することを保証する。押下で設定した状態は解放で必ず解除し、移動が発生しなかった場合（クリック）の考慮漏れに注意する。

### 5.9 排他分岐が重要処理をスキップしていないか確認する

排他的な条件分岐が、他の重要な処理をスキップさせていないか確認する。選択優先順位と、同時選択/排他選択を明確に定義する。

### 5.10 選択状態は生の集合まで評価して網羅する

複数の選択状態（単一・複数・不明・空）を扱う UI では、派生済みヘルパー結果だけでなく、生の ID セットをすべて評価して分岐を網羅する。仕様メッセージと表示条件を一対一で対応付ける。

### 5.11 構造変更操作後の選択は結果から再解決する

結合・分割・移動・削除のように対象 ID や形状が変わる操作では、完了後の選択状態を固定の全クリアで決めない。コマンド結果が「残る要素 ID」「新規要素 ID」「削除された ID」を返し、UI はその結果から選択を再解決する。

- 検出: 次に調整すべき対象が残る操作では、選択維持を回帰テストに含める。

### 5.12 判断用メッセージを無関係な操作で消さない

検証拒否・保存失敗など、ユーザーが次の判断に使うメッセージは、発生元と無関係なクリックやマウス操作で即時消去しない。消す契機は「同種操作の再試行」「明示的な閉じる」「成功した置換操作」など、意味を持つイベントへ限定する。

### 5.13 表示専用モードでは編集経路を一括無効化する

表示専用モードでは、編集 UI・編集メニュー項目・編集ショートカットを同じ権限判定で一括無効化する。部品ごとに個別判定を書くと、見た目だけ非表示でショートカットや右クリック操作が残る。モード境界は共通ヘルパーまたは状態機械で表現する。

### 5.14 重なる UI は入力を受ける層も同時に設計する

重なり合う UI（オーバーレイ・バックドロップ・ハンドル・モーダル）は、描画順だけでなく入力を受ける層も同時に設計する。透明な背景層が操作ハンドルを覆うと、見た目は正しくても操作が奪われる。

- 検出: 重なった状態で、背面/前面の期待操作が通ることをテストする。

### 5.15 タイムスタンプはコンテキスト上の時刻を参照する

時間軸を持つデータのタイムスタンプは、必ずコンテキスト上の時刻（現在時刻）を参照し、システム時刻と混同しない。時刻源は一元管理するサービスから取得する。

### 5.16 時間値は完全値で受け渡し、倍率の二重適用を防ぐ

時間軸 UI では、年・月・日を分解した一部の値だけを下位層へ渡さず、完全な時間値を受け渡す。再生処理では、速度を表すのが「間隔」か「1 tick あたりの進行量」かを一箇所に決め、両方へ倍率を掛けない（二重適用防止）。

### 5.17 イミュータブルなエンティティ/値オブジェクトの設計

イミュータブルなエンティティ/値オブジェクトを設計するとき、状態変更は新インスタンスを返し、等価性は属性値比較で定義する。変更系メソッド（withXxx 等）を導入する際は、全属性について必要なメソッドが網羅されているか洗い出し、サブクラスが追加状態を持つ場合は基底メソッドのオーバーライド要否を検討する。

### 5.18 空配列・空オブジェクトは真値である

空配列・空オブジェクトは真値である。論理和による短絡評価のデフォルト補完に頼らず、型や状態を明示的に判定する。

### 5.19 分岐識別子は型定義・定数・ファクトリを経由する

種別・モード名・設定キーのような分岐識別子は、表示文字列や思い込みで判定せず、型定義・定数・ファクトリを経由する。大文字小文字差でも分岐が変わる。

- 検出: 新識別子を追加・改名したら、作成・表示・編集・保存・検索の全経路で同じ値を使うテストを置く。

### 5.20 元に戻す情報は依存データも含めて過不足なく保存する

操作（undo を含む）を元に戻すのに必要な情報は、依存データも含めて過不足なく特定・保存する。履歴にはプレーン形式で保存し、復元時は新インスタンスを生成、ネストした値も再帰的に変換、フォーマットを一貫させる。ID 等を生成するコマンドは、redo で採番し直さず初回生成 ID を復元する。

### 5.21 削除は参照掃除と連鎖剪定まで行う

削除操作は、対象自身を消すだけでは完了しない。残存する全要素の全（時間軸）状態から、削除対象への参照を同じ操作内で掃除し、参照が消えて空になった派生要素は剪定・連鎖消滅させる。片方向・単一時点だけの掃除は dangling 参照を残す。

### 5.22 確定まで共有データを破壊的に更新しない

結果が確定するまで、共有キャッシュ/共有データを破壊的に更新しない。検証用の仮データで成功を確認してから反映し、失敗時は追加した要素をすべてロールバックする。永続化が失敗してもキャッシュが汚染されないようにする。

### 5.23 コマンドの execute/undo/redo は対称に通知する

状態変更を伴うコマンドの execute / undo / redo は、同じイベント規約で、touch した全要素へ対称に通知する。直後に手動リフレッシュを書きたくなったら、通知漏れのサインである。同一の状態変化を二重通知しない。

- 検出: イベント発火の回帰テストは、期待イベント集合を厳密一致で検証する（包含判定は重複・過剰を見逃す）。

### 5.24 確定ハンドラには no-op ガードを入れる

値が変わっていなくても発火する確定ハンドラ（blur/Enter 等）を undo 履歴付きコマンドへ載せるときは、確定値が現在状態（baseline）と一致するなら実行しない no-op ガードを入れる。さもないと「幽霊 undo エントリ」が積まれる。ガードの baseline は、フォーム同期と同一ソースから導出する。

### 5.25 仕様が限定した対象範囲を実装で広げない

ドメインの基本ルール（排他性・整合性・階層）が仕様で対象を明示的に限定しているとき、実装で「対称性確保」「自然な拡張」を理由に対象範囲を広げない。直感的拡張と感じた変更ほど、仕様で例外規定されている可能性を疑い、変更前に仕様の該当節を引用する。

### 5.26 編集制約はコマンド確定前にも同じサービスで検証する

編集制約（自己交差・全体重複・階層破綻・禁止条件）は、UI の候補表示だけでなく、コマンド/ユースケースの確定前にも同じサービスで検証する。UI が候補を隠しても、ショートカット・メニュー・undo/redo・直接呼び出しで不正状態が入る。拒否理由は、ユーザー通知とテスト可能な戻り値の両方で扱う。

### 5.27 結合と所属変更は事前条件を分けて検証する

結合（合体）と所属変更（割譲・帰属等）は別概念であり、事前条件を分けて検証する。共通条件（同一対象でない・有効である等）に加え、操作種別固有の条件を検証する。所属変更では循環参照防止（新親が対象自身とその下位すべてに含まれない）を確認する。

### 5.28 階層を辿る再帰サービスは循環で無限ループしない

階層（親子）グラフを辿る再帰サービスは、壊れたデータ（循環参照・親子不整合）でも無限ループしないよう、visited セットで再入を遮断する。シリアライズ層の検証とは別に、直接構築・テスト経路でも runtime 安全性を二重防御する。

- 検出: 循環参照のテストケースを置き、有限結果を返すことを確認する。

### 5.29 派生形状は単一の解決判定で全経路を動かす

形状を「子の和として導出する」派生形状では、描画・ヒットテスト・派生サービス・選択など複数経路を、同じ形状解決判定で動かす。判定条件のドリフトは「描画されているのに選択できない」「ラベル位置が描画と違う」等の対概念矛盾を生む。判定を共通関数/共通中間表現へ集約し、規約自体を単体テストで固定する。

### 5.30 過少共有と過剰共有の両方を戒める

同じ判定・同じ baseline・同じ既定値処理は、同じ実装を共有する（過少共有の戒め）。一方で、見た目が同じピッカー UI でも除外規則が操作種別ごとに異なるなら、派生候補一覧を安易に共有しない（過剰共有の戒め）。共有前に「2 操作の制約は本当に同一か」を列挙して確認し、回帰テストで弾く。

### 5.31 永続化の読み書き・検証・移行・往復テストを同期する

永続化の読み（deserialize）・書き（serialize）・検証（validation）・移行（migration）・往復テストは、同じ変更単位で同期する。片側だけ変えると「保存はできるが次に開けない」壊れたファイル経路ができ、型チェックでも実行時テストでも検出されず、データ損失リスクになる。

- 検出: フィールドを optional 化・撤去・固定値化する変更では、再保存往復テストを必ず追加する。

### 5.32 多層に波及する変更は最大 2 層に分割する

一度に多層へ波及する変更（required→optional 化など、型・永続化・consumer・検証・描画・ヒットテスト・UI・派生サービスに及ぶもの）は、1 単位に詰めず、影響経路を最大 2 層で宣言して分割する。宣言外の経路に及びそうなら別タスクへ切り出し、レビューで「対概念」と感じた修正は別単位へ切る。

### 5.33 層をまたぐ API 契約は両側テストで固定する

層をまたぐ API 契約（呼び出し側・公開側・受信側のチャネル名/関数名）は、文字列の偶然一致に任せず、共有型・型付きラッパー・両側の単体テストで固定する。API 名変更時は、全層とテストを同じ変更単位で更新し、旧名が残っていないか検索する。

### 5.34 コンポーネント間データ受け渡しは契約を型で明示する

コンポーネント/モジュール間でデータを渡すとき、プロパティ名・型・構造が受け取り側の期待と一致するか、型定義（インターフェース）で契約を明示する。データ構造の全有効状態の組み合わせを、描画・シリアライズ・操作の全箇所で網羅し、条件分岐は排他ではなく組み合わせで考える。仕様から削除した属性は、UI → 状態管理 → 永続化 → 描画の順にすべて除去する。

### 5.35 共有リソース更新は全依存先へ通知する

共有リソースを更新したら、依存する全コンポーネントに変更を通知する（イベントバス等）。リアクティブ状態やコンテキストは、内部データが常に最新とは限らない前提で設計する。

### 5.36 プロジェクト設定とアプリ全体設定の境界を先に定義する

プロジェクト固有設定とアプリ全体設定の境界を先に定義し、保存先と反映先を一貫させる。新規プロジェクト開始時は、表示中データだけでなく、保存先パス・メタデータ・バックアップ対象・dirty 状態・終了確認ガードも、同じ保存文脈として同時に初期化する。

**区分は 2 つでは足りないことがある。第 3 の「セッション限りの見え方」を用意する**（2026-09-04 に実際に必要になった）。グリッドの表示 ON/OFF は「いま見えているものを変えるだけ」なのに、保存される既定値がプロジェクト設定にあったため、**押すだけで未保存の印が立った**。表示専用モード（読むだけ）の関門を「保存ファイルに書くかどうか」で引いたところ、**起動直後は常に読むだけなので、開いて眺めるだけの人が一度もグリッドを消せない**という別の不具合が生まれた。

- 症状の形: 「保存したい既定値」と「いまだけ変えたい見え方」が**同じ 1 つの鍵**に同居していると、権限の関門を掛けた瞬間に後者まで巻き添えになる。
- 直し方は関門をゆるめることではなく、**置き場を分けること**。セッション用の上書き（`null` = 上書きなし）を別に持ち、読むのは「上書きがあればそれ、無ければ設定」。上書きを書く経路は保存もせず dirty にもしないので、権限の関門を掛ける必要がない。
- 検出: 設定の鍵を 1 つずつ「**これを変えたら保存ファイルが変わるべきか**」「**読むだけの人が変えたいか**」の 2 問で分類する。両方 yes なら鍵を 2 つに割る。「見え方かどうか」だけで分類すると必ず取り違える。

### 5.37 ID 生成はタイムスタンプ単独に依存しない

ID 生成はミリ秒精度タイムスタンプだけに依存すると、同一ミリ秒内で衝突する。ID 生成サービスを経由し、既存データとの重複検査を行う。

### 5.38 移動制約は線分交差で判定し、衝突検出と応答を分ける

ドラッグ等の移動制約では、移動先点が合法かだけでなく、開始点から移動先までの線分が障害物や境界を横切るかを判定する。最初の接触点を求める処理（衝突検出）と、接触後の残り移動を扱う処理（衝突応答）を分ける。既存接触（t=0）は新規衝突として止め直さず、食い込み成分だけ捨てて接線方向移動を許可する。

### 5.39 テスト fixture は実体クラスをインスタンス化する

テスト fixture で複合的なドメイン構造を構築するときは、実体クラスをインスタンス化する。リテラルオブジェクトで型を満たそうとすると、未参照プロパティの欠落が現状のテスト経路では沈黙通過し、後で別経路が参照したとき沈黙して失敗する。構造的型付けやキャストは欠落を検出しないことがあるため、コンパイラに頼らず、ヘルパーは実体を生成する。

### 5.40 直接利用する依存は直接依存として宣言する

テスト/型チェック/ビルド/スクリプトが直接 import・実行する依存は、推移依存に頼らず直接依存として宣言する。設定ファイルのモジュール形式（拡張子とモジュール種別）は実行環境に揃え、形式変更は型チェック・起動確認まで同じ変更単位に含める。

### 5.41 検証不能になった範囲は別手段で補う

E2E 等で一時的に検証できなくなった範囲（外部統合・ファイル I/O・終了確認等）は、未検証のまま放置しない。純粋関数化・アダプタ分離・モックで単体テスト対象にして補う。

### 5.42 点の密度と、点をまとめる許容値は必ず一組で決める

形を点列へ落とす処理（曲線の分割・間引き）と、近い点を同じ点とみなす処理（吸着・スナップ・量子化）は、片方だけ変えてはならない。点を細かく置くほど隣の点どうしが吸着許容値の内側に入り、**小さい形が丸ごと潰れて消える**。逆に許容値だけ上げると、離れているべき点まで併合される。精細にしたいときは、間引き間隔と吸着許容値を一緒に下げる。

- 「隙間が閉じない」類の不具合を、吸着許容値を上げて解決しない。吸着は全点に一律に効くため、狙った隙間以外も巻き込む。閉じたい対象（行き止まりの端点など）だけを狙う処理を別に足す。
- 検出: 密度または許容値を変える変更では、**変更の前後で形の個数**（面・リング・独立した島の数）を数えて比較する。総面積は変わらないまま個数だけ減る形で現れるので、面積の一致を根拠にしてはいけない。

### 5.43 粗い点列化を入れる前に、粗さに関係なく成り立たせるべき不変条件を洗い出す

点列を粗くする改善（サンプリングの間引き、直線の端点だけを使う等）は、それ自体は正しくても、**密なサンプリングが偶然満たしていた不変条件を破る**。密だった頃は「長い辺が自然に細かく刻まれていた」ために表面化しなかった前提が、粗くした瞬間に破れる。

- 実例: 保存形式は 1 辺で経度 180 度以上を渡る形を表現できない（技術方針 §6.8）。等長サンプリングは南緯 90 度を横断する辺を自動的に何千点にも刻んでいたため成立していた。直線の端点をそのまま使う方式にした途端、その辺が 2 点 1 本になり読み直しで形が壊れた。
- 手順: 粗くする変更では、まず「隣接する 2 点のあいだに暗黙に期待されている上限」（距離・角度・経度差）を列挙し、粗くした後もその上限を保つ処理を同じ変更単位に入れる。
- 検出: 保存・読込の往復テストと整合性チェックを、**粗い点列を生む実データ**に対して掛ける。合成した小さな入力では、そもそも長い辺が生まれず素通りする。

### 5.44 共通ロジックを差し替えたら、呼び出し側に残る写しを全部検索して潰す

共通化した処理を新実装へ差し替えたら、同じ処理の**写し（ローカルに再定義された同名・同目的の関数）**が呼び出し側に残っていないかを全文検索する。写しが残ると、経路によって新旧の実装が混在し、改善の効果が一部の経路にしか出ない。§5.33 は名前の変更時の検索を求めるが、本項は**名前が変わらないまま中身だけ差し替えた場合**を対象とする（検索対象が「旧名」ではなく「同名の別定義」なので、名前で追うと見つからない）。

- 「重複定義がある」と既知の問題として記録してあっても、差し替えのときに突き合わせなければ意味がない。既知の重複は、差し替え作業の**着手時チェックリスト**として読む。
- 検出: 差し替えの前後で、**経路ごとに**所要時間または結果を計測して比較する。全体の合計値だけを見ると、片方の経路が旧実装のままでも「速くなった」ように読める。

### 5.45 厳密比較で書かれた幾何述語に、新しい種類の点を流さない

「外積がちょうど 0 なら境界上」のように**厳密比較**で書かれた幾何述語は、入力が同一の格子・同一の頂点列から来ることを前提にしている。この厳密さは多くの場合、意図的な設計である（同じ頂点を共有する 2 面の共有辺は本当に外積 0 になる）。

そこへ前提の外の点——辺の中点、補間で作った点、別経路で丸められた座標——を流すと、丸め誤差で判定が揺れ、境界上の点が在／不在をでたらめに返す。同じ関数だから同じように使える、は成り立たない。

- 対応の形: 述語に許容値を引数として足し、**前提外の点を問い合わせるときだけ**正の値を渡す。許容値は量子化の粒度より 1 桁小さい値を目安にする。既定を緩める形にしてはいけない（前提を満たす呼び出し側の厳密さまで失われる）。
- 検出: 述語の呼び出し元を列挙し、渡している点が「データに実在する頂点」か「計算で作った点」かを分類する。後者があれば、その経路の判定結果を実データで突き合わせる。

### 5.46 「A が効いていない」の原因は A の実装とは限らない

ある機能が効いていないという報告を受けたとき、その機能の実装を読み始める前に、**結果を実際に決めている経路**を確かめる。同じ仕様を 2 系統が二重に実装していると、見た目を決めているのは報告された側ではないことがある。手前の経路が入力そのものを取り除いていれば、後段の判定は正しく書かれていても一度も呼ばれない。

- 実例: 「島が国の領内に別地物として残る国と残らない国がある」という報告で、実際に効いていたのは領有判定ではなく、その手前で特定の国の海岸線を丸ごと捨てる処理だった。捨てられた国では島の面がそもそも生成されず、「領有できている」ように見えていただけだった。
- 手順: 症状が出る入力と出ない入力を 1 つずつ取り、**結果に至る経路を上流から順に**、どこで両者が分岐するかを実測する。仕様の該当節から実装を辿る向き（上から下）ではなく、結果から遡る向きで見る。
- 検出: 同じ仕様が複数箇所に実装されていないかを先に検索する。二重実装が見つかったら、どちらが結果を決めているかを実データで確認してから直す（§4 単一の真実源も参照）。

### 5.47 原因不明のまま回避策へ逃がしてよいが、逃げた先を「解決済み」と記録しない

不安定な判定・再現しない不具合に対し、**原因を特定できないまま「その判定に依存しない設計」へ逃がす判断は正しい**。原因究明で手が止まるより、動くものを届けるほうが価値がある。

してはならないのは、**逃げた先を「解決済み」として記録する**ことである。「〜が不安定だったので、依存しない方式に切り替えた」とだけ書いて閉じると、後から誰も真因を探さなくなり、同じ原因が別の場所で再発しても結び付けられない。

- 書き方: 「**真因は未特定**。回避策として〜へ切り替えた」と、逃げたこと自体を明示して残す。分かっている症状・再現条件・調べて外れた仮説も併記する。
- 実例: 「点線の判定が不安定なので、結合ロジックは点線判定に依存しない方針に切り替えた」と記録してあったおかげで、後日その「不安定」の正体（正規表現の 1 文字の誤りで、判定が一度も成立していなかった）に辿り着けた。逃げたことを書き残していなければ、探す手掛かりが残らなかった。
- 検出: 完了報告で「〜に依存しない設計にした」と書いたら、その理由が「そのほうが良い設計だから」なのか「原因が分からなかったから」なのかを自問する。後者なら未解決課題文書へ残す（§1.8）。

### 5.48 実データの正準ファイルをアプリで直接開かない — 検証は一時コピーで行う

アプリは「開いたファイル」をそのまま保存先に昇格する（読み込みが確定した時点で保存先が移る）。したがって調査や検証のつもりで実データの正準ファイル（`derle-import/*.gimoza`）をアプリで開くと、その後の保存・自動保存・修復の適用が**正準ファイルを上書きする**。2026-09-03 の調査中に実際に起き、正準ファイルが書き換わって隣に自動バックアップ（`*.gimoza.bak.*`）が残った。

- 手順: 実データを載せる検証（E2E・手動・調査スクリプトを問わず）は、必ず一時ディレクトリへコピーしてから開く。E2E は `launchAppWithProject` にコピーのパスを渡す（`e2e/real-data.spec.ts` の形）。
- 検出: 検証の前後で正準ファイルのサイズと更新時刻を比べる（同 spec が最後に確かめている）。正準ファイルの隣に `*.gimoza.bak.*` が新しく出来ていたら、誰かが直接開いた印。

### 5.49 レイアウトを持たないテスト環境で寸法を測ると、その検査は永久に緑になる

jsdom は**レイアウトを計算しない**。`getBoundingClientRect()` は常に全部 0 を返し、`offsetWidth` も 0 である。したがって「地物を選ぶ前後で地図セルの矩形が一致する」のような**寸法の不変条件を jsdom の単体テストで書くと、中身が何であっても一致して必ず通る**。検査したつもりで何も守っていない状態が、赤くならないまま残り続ける。

同じ罠は「必ず一致する対象を測ってしまう」形でも起きる。全幅 × 固定高の帯どうしの矩形を比べても、中身に関わらず一致する。

- 守り方は二段にする。**①寸法ロジックの単一真実源である CSS の宣言そのものを読む契約テスト**（`src/ui/shell/shell-layout.test.ts` / `src/ui/add/add-input-layout.test.tsx` の形。`height: 40px` / `flex: 0 0 240px` / `flex-wrap: nowrap` / `overflow: hidden` を直接読む）と、**②実際にレイアウトする環境（E2E）での実寸比較**。
- **測る対象は「守りたいものが動かないこと」で選ぶ。** 「帯が動かない」ではなく「**帯の中身が変わっても地図セルが動かない**」を測る。前者は自明に成り立つ。
- 検出: 寸法の assertion を書いたら、**わざと壊してテストが赤くなるか**を確かめる。赤くならなければ、それはレイアウトの無い環境で測っているか、必ず一致する対象を測っている。

### 5.50 CSS グリッドの `1fr` は「その行のいちばん長い中身」で広がる — 窓幅に収めたい列は `minmax(0, 1fr)` にする

`grid-template-columns: 1fr` の自動最小サイズは `auto`（＝その列に置かれたアイテムの min-content）である。したがって**折り返さない長い文字を持つ行が 1 本あるだけで、列そのものが窓幅を超えて広がる**。列を共有している他の行（このアプリでは地図セル）も一緒に広がり、地図の幅と上端の位置が動く。実測では、**オプションバーの「次の一手」**（`1fr` の区画）に長い拒否理由を入れただけで地図セルが 940px → 2,254px に広がり、上端 y も 121 → 72 へ動いた（初版は出どころを「状態行」と書いていたが、実際に測ったのはオプションバーである）。

- 直し方: 窓幅に収めたい列は **`minmax(0, 1fr)`**（トラックの最小を 0 にする）。あわせて、その列に置く grid item 側にも `min-width: 0` を付ける（grid item の既定の `min-width: auto` が同じ経路で効く）。行の中に `overflow: hidden` を書いても**それだけでは足りない**——中身の min-content は依然として外へ効く。
- 同じ話が flex にもある。`min-width: 0` を付けない flex item は、中身の min-content より小さくならない。
- 検出: **中身がいちばん長くなる状態を作って外側の矩形を測る**（空のときだけ測っても捕まらない）。E2E で長い文字を差し込んでから、動いてほしくない要素の矩形を比べる。

### 5.51 「人が読める名前」と称するフィールドが、実際には内部識別子と混ざっていることがある

型定義のコメントが「Human-meaningful label for menus/history UI」と書いてあっても、**全部の呼び出し元がそのつもりで埋めているとは限らない**。このリポジトリの `Command.label` は、ドメイン側の 4 か所が日本語（「所属変更」「地物の削除」「自動配色」「結合」）を入れているのに、UI 側の 5 か所は内部の英語（`edit` / `delete` / `interval` / `palette` / `unshare`）を入れていた。状態行に「元に戻せます: ◯◯」として出したところ、実機に「元に戻せます: edit」と表示された（U-1「内部の英語値を画面に出さない」違反）。

なお **最初に数えたときは日本語を 3 か所と書いていた**（`結合` を数え落としていた）。「混在している」という結論は変わらないが、**「全呼び出し元を列挙した」と書くなら本当に全件でなければならない**。列挙は検索結果をそのまま貼るのではなく、定数経由で埋めている箇所（`MERGE_COMMAND_LABEL` のような）も追う。

- 手順: **画面に出す前に、そのフィールドを埋めている全呼び出し元の実値を列挙する**（型ではなく値を見る）。コメントの宣言は根拠にならない。
- 混在していたら、出さない（可否だけ出す等）か、語彙を揃える作業を別に立てる。**混ざったまま出すと、たまたま日本語の経路だけ試して「大丈夫」と判断してしまう。**
- **出口 1 か所で写像する**のが有効な手である（2026-09-04 に採った形）。呼び出し元を全部書き換えるのは全コミット経路に触る作業になるので、画面へ出す直前に「実際に入っている値 → 日本語」の表を 1 か所だけ置き、**表に無い値は粗い日本語へ落とす**（`src/ui/shell/command-result.ts`）。こうすると、後から増えた呼び出し元が内部の値を入れても、画面には内部の値が出ない。
- **写像表を守るテストは「手書きの一覧」にしない。** 初版は表に載せた値を配列で直書きしていたが、それでは**新しい経路が増えて表から漏れた**ことを検出できない（一覧のほうを直し忘れるだけで緑のまま）。守り方は 2 つ組で書く。
    1. **ソースの定数を走査する**。値の定義箇所（このリポジトリでは UI 側の `UI_COMMAND_LABEL` と、ドメイン側の各コマンド module の定数）から**値の集合をそのまま流し込み**、全件が日本語へ写ること・既定へ落ちる漏れが無いことを見る。定数が増えれば検査も自動で広がる。
    2. **直書きが復活していないことをソース走査で見る**。定数を作っても、次に書く人が文字列を直書きすれば表から漏れる。実装ファイルを走査して「内部の識別子の形をした文字列リテラル」が代入されていないことを固定する。
- **「値がどこで最終的に決まるか」を取り違えない。** 上の直書き検査を最初は `label:` という**属性の代入だけ**で書いたが、実際に画面へ出ていた値は `createCompositeCommand('edit', […])` の**第 1 引数**だった（経路ごとに label を分けたのに、包み直す側が古い値を直書きしていたので実機の表示は 1 文字も変わらなかった）。**同じ意味の値が「属性」と「引数」の両方の形で書かれうる**ことを疑い、両方を走査する。
- **経路ごとに分けたなら「違う値になる」ことも見る。** 6 つの確定経路が共通の生成関数を通っていて、全部が同じ label を入れていた。写像表の検査は全件が日本語になることしか見ていなかったので、**全部が同じ日本語**でも緑だった。「経路の数だけ違う表示になる」を 1 本足す。
- 検出: 実データ・実アプリでその表示を **複数種類の操作** について目で見る。1 種類だけ試すと、その経路がたまたま日本語だったときに通り抜ける。

### 5.52 作業ディレクトリのドライブ文字の大小で、テストの実行環境（jsdom / node）が静かに外れる

Windows で `vitest` の `environmentMatchGlobs`（このリポジトリでは `src/**/*.test.tsx` → jsdom）は、
**テストファイルの絶対パスを設定のルートからの相対に直してからグロブに当てる**。ルートは
`process.cwd()` から決まるので、**cwd のドライブ文字が小文字（`e:\...`）だと相対化に失敗し、
グロブが 1 つも一致しない**。すると `.test.tsx` が全部 **node 環境**で走り、DOM を触るテストが
`document is not defined` で落ちる。**設定ファイルは正しいのに、走らせ方だけで結果が変わる。**

2026-09-04 に実測した（同じコマンド・同じリポジトリ・同じシェル。違うのは cwd の表記だけ）:

| cwd | 結果 |
| --- | --- |
| `e:\WORKSPACE\time-map-app-4` | `Test Files 1 failed` / `environment 0ms` |
| `E:\WORKSPACE\time-map-app-4` | `Test Files 1 passed` / `environment 409ms` |

全件でも同じで、小文字の cwd では `.test.tsx` 76 本のうち **62 本が失敗**した（残り 13 本は
そもそも DOM を触らないので通っただけ）。**シェルの種類（Git Bash / PowerShell）は関係ない。**
Git Bash でも `cd "E:/..."` と打ち直せば通る（どんな形でも明示的に `cd` すればドライブ文字は
大文字へ正規化される）。小文字になるのは、**起動した側が小文字で cwd を渡したときだけ**である
（このリポジトリでは、サブエージェントのシェルが `e:\...` で始まる）。

- **検出**: vitest の締めくくりの行にある **`environment` の時間**を見る。jsdom が効いていれば
  数百 ms、効いていなければ **`environment 0ms`** になる。「`document is not defined` が
  たくさん出た」ときは、まず実装ではなくここを見る。
- **回避**: 走らせる前に `node -e "console.log(process.cwd())"` で cwd を確かめ、小文字なら
  `cd "E:/WORKSPACE/time-map-app-4"` してから走らせる。1 本だけ試すなら
  `--environment jsdom` を明示してもよい（ただしこれは症状を隠すだけで、全件ゲートには効かない）。
- **同じ型の罠**: 「設定は正しいのに、呼び出し側の環境の些細な違いでテストの**環境割り当て**が
  外れる」ものは、赤くはなるが**原因が実装に見える**ので時間を溶かす。環境割り当てを持つ設定
  （`environmentMatchGlobs`・`poolMatchGlobs`・`include`）は、**効いていることを示す観測値**
  （上の `environment` の時間）を先に押さえてから中身を疑う。

### 5.53 「下書きが汚れている」は、種との差だけでは判定できない

入力中の内容を捨てる前に確認を出す仕組みを作るとき、「汚れている」を
**「下書きが、種にした姿と違う」だけで判定すると、保存の直後に確認が出る**。

保存が成功すると確定済みの姿が下書きの内容へ追いつくので、普通は問題にならない。
しかし **保存が「編集対象の同一性」を変える場合**（このリポジトリでは保存で錨が
1 本増え、編集対象が「地物×錨×年」なので錨が変わる）、同じ描画で
「対象が変わった」かつ「下書きが種と違う」が同時に成立し、**自分で保存した直後に
「入力中の内容が失われます」と聞かれる**。

- 直し方: 汚れを **「種にした姿とも、いまの確定済みの姿とも違う」** で定義する。
  どちらかと一致していれば失われるものは何も無い。
- 同じ型の罠: 取り消し（ドメインが巻き戻る）でも同じ式が成立しうるが、こちらは
  **黙って追従するのが正しい**（ドメインの巻き戻しのほうが下書きより強い）。
  「対象が変わった」と「中身だけが変わった」を別の枝に分け、前者だけ確認を出す。
- 検出: **「入力 → 保存 → 別の年へ移る」を E2E で 1 本通す**。単体テストでは
  「保存で錨が増える」を偽物が再現しないので、編集対象の同一性が動かず通り抜ける。
- **例外の相手は「値」ではなく「出来事」で決める**（2026-09-04 追記）。上の直し方を
  「種とも、いまの確定済みの姿とも違う」という **値の比較** で書くと、逆向きの穴が開く:
  0 年で `A → B` と打ち、移動先の確定値が **たまたま** `B` だったとき、確認なしで
  「0 年に B を保存する」という意図だけが消える。値が偶然一致することは珍しくない
  （同じ名前へ戻す・既定値へ戻す・隣が同じ名前）。**例外にしてよいのは「自分がいま保存した」
  という出来事ちょうど 1 つ**なので、保存に成功した値を覚えておき、それと一致するときだけ
  黙って追従する。**「汚れているか」は種との差で判定したままでよい。**

### 5.54 E2E で入力欄のフォーカスを外すために、選択を変える場所を押さない

大域のショートカット（Ctrl+Z / Ctrl+K 等）は、テキスト入力欄にフォーカスが
あるとそちらに食われる。だから E2E では「どこかを押してフォーカスを外す」手が要るが、
**地図を押すのはだめである**——地図クリックはその場所の地物を **選び直す**。

2026-09-04 の探索で実際に踏んだ: 子を選んでから地図の左上を押して Ctrl+K を送ったところ、
選択が別の地物（その座標にあったまとめ役）へ移っており、**錨が意図した地物とは別の
地物に作られていた**。画面の表示もその地物のものになるので、**テストは緑のまま
別のことを検査していた**（差分の文に親の名前が出ていたので気づけた）。

- 代わりに押す場所: 状態行の表示やパネルの見出しのような、**押しても何も起きない場所**。
- 検出: ショートカットを送る spec では、送る直前と直後に **選択中の地物 id（`app-active-feature`）
  を読んで同じであることを確かめる**。選択が動く手を挑んでしまっても、この 1 行があればその場で赤くなる。

### 5.55 「その時点の全体の写し」を並べる形では、過去を直しても未来の写しが古いまま残る

履歴を「ある時刻の全体のスナップショット」の列で持つと、**時刻 T のスナップショットを直しても、
T より後ろのスナップショットは直す前の値の写しをそのまま持ち続ける**。利用者から見ると
「1000 年で名前を直したのに、2000 年へ進むと元の名前に戻る」になる。

**これは「保存が効いていない」不具合ではない。** T の保存は正しく効いており、後ろのスナップショットも
それぞれ正しく「その時刻に記録された姿」を保持している。食い違うのは、**利用者が「1000 年に改名した」
という 1 つの出来事を入力したつもりなのに、データの側には「1000 年の姿」しか記録されない**からである。

この形は普段は目立たない。スナップショットが 1 本しか無ければ後ろが存在しないからで、**後ろの
スナップショットが増える契機が別にあるとき**（このリポジトリでは、まとめ役の下の兄弟を直すと
親の系列に錨が立つ）に初めて表に出る。**「同じ地物を続けて直したときは起きず、他人を直してから
自分を直すと起きる」**ので、素朴な手順の検査を素通りする。

- **直し方 A（データの形を変える）**: スナップショットを差分にする／変わっていない部分を共有する。
  根治するがコストが大きい。
- **直し方 B（書き込み側で補う）**: 保存した属性を「**次にその属性が本当に変わるスナップショット**」
  まで前へ引き継ぐ。止まる位置は属性ごとに独立に決める。記録された変更は 1 つも壊れない。
  書き換えた枚数が何枚でも **1 回の操作＝1 つの取り消し単位**にする。**引き継ぐ範囲は操作の前に
  文字で見せる**（黙って後ろを書き換えるのは、黙って上書きするのと同じくらい怖い）。
- 検出: **「別の対象を後の時刻で直してから、当の対象を前の時刻で直す」** を 1 本通す。同じ対象を
  時刻の昇順に直すだけの検査では絶対に出ない。実装は 2026-09-04 の
  `src/domain/editing/carry-forward.ts`（規則）と `apply-proposal.test.ts` の
  「兄弟を 2000 年で直したあと 1000 年で改名すると…」（検出）。

### 5.56 `hidden` 属性は、クラスで `display` を書いた瞬間に効かなくなる

ブラウザの既定は `[hidden] { display: none }` だが、これは**属性セレクタ 1 個ぶんの
優先度**しか持たない。同じ要素にクラスで `display: flex` などを書くと**クラスのほうが勝ち**、
`hidden` を付けたのに要素は表示され続ける。しかも `position: fixed` を併用していると、
座標が決まる前は **画面の左上（0,0）に居座る**ので、見た目には気づきにくいまま
**その下にある本来のボタンのクリックを奪う**。

2026-09-04 の増分 3 で実際に踏んだ。オプションバーの「吸着 ▾」ポップオーバーが閉じている
はずなのに、E2E が「一覧タブが押せない（`snap-options__row` がポインタを横取りしている）」
で落ちた。原因は `.snap-options__panel { display: flex }` が `[hidden]` に勝っていたこと。

- 直し方: **同じファイルに `[hidden]` の打ち消しを併記する**（`.foo[hidden] { display: none }`）。
  あるいは要素そのものを条件付きで描かない（`{open && <div…>}`）。前者は開閉のたびに
  DOM を作り直さないので、位置の計算（`getBoundingClientRect`）を保ちたいときに向く。
- 同じ型の罠: `visibility` / `opacity` で隠したつもりの層も、`pointer-events` を切らない限り
  入力を奪う（§5.14 の別の顔）。
- 検出: **閉じている状態で、その下にあるものが押せることを E2E で確かめる**。単体テストは
  レイアウトを持たないので「重なって押せない」を再現できない（§5.49）。K-2 の格子走査
  （地図セルを 5×5 で走って入力層が返るか）を、一時部品の**閉じている状態**にも掛ける。

### 5.57 ファイルを書き換える道具の既定の改行で、生テキストを読む契約テストが落ちる

この作業ツリーは **LF と CRLF が混ざっている**。`core.autocrlf=true` なのでチェックアウトした
ファイルは CRLF、編集ツールが新しく書いたファイルは LF になる（git は保存時に LF へ正規化
するので、**差分にも履歴にも現れない**）。

ここで Python の `open(path, 'w')` のようにプラットフォーム既定の改行で書き戻すと、
LF だったファイルが黙って CRLF になる。ほとんどのテストは何も言わないが、
**CSS やソースを生テキストとして読み、改行をまたぐ正規表現で照合する契約テスト**
（`src/ui/shell/shell-layout.test.ts` の `ruleBody`、`property-layout.test.ts`、
直書き走査のテスト）は、パターンの中の改行 1 文字がファイル側で 2 文字になった瞬間に
「規則が見つからない」で落ちる。**落ち方が「実装を壊した」ように見える**ので時間を溶かす。

- 手順: 書き戻す前に **元のファイルの改行を読み取り、同じもので書く**。バイナリで読み書き
  するのがいちばん確実である（読むときに CR+LF が含まれるかを見て、書くときに同じ形へ戻す）。
- 検出: 「CSS の規則が見つからない」「直書き走査が急に 0 件になる」で落ちたら、
  **実装ではなく改行を先に疑う**。CR が含まれるかを shell の `grep` で確かめるのは
  当てにならない（引用の解釈が shell ごとに違う）。バイト列を直接数える。

### 5.58 「同じものが既に載っていればその場で差し替える」分岐は、後片付けが先に走るので通らない

一時的な登録（画面の差し込み・購読・リスナー・ハンドラ表）を持つ器で、「同じ鍵が既に載って
いれば**その場所で**差し替え、無ければ末尾へ足す」と書くと、**その場で差し替える枝は実際には
一度も通らない**ことがある。**再登録の直前に、古い登録の後片付けが走る枠**では、登録し直す
瞬間には**古い後片付けが既に登録を外し終えている**からである。結果、中身を更新するたびに
部品が末尾へ回り、画面上で左右に飛ぶ。

- **そういう枠の例**: React の effect（「古い後片付け → 新しい実行」の順で走る）。ほかにも、
  購読を張り直すときに必ず先に解除する API、設定を再読込するときに旧設定を落としてから
  読む枠が同じ形になる。**「後片付けと再登録のどちらが先か」を枠ごとに確かめる**のが要点で、
  後片付けが先なら「その場で差し替え」は死んだ分岐である。
- 直し方: **並び順の鍵を器が持つ**。鍵が初めて来たときに順序番号を配り、取り外しでは番号を
  捨てず、公開するときに必ずその順で並べる。器を畳むとき（道具を降りるなど）に番号も捨てる。
- **検出: 検査を「後片付けを挟んだ順序」で書く。** 「同じ鍵で登録し直す」だけの検査は、
  実装を壊しても緑のままである（実物と呼び出し順が違うため）。外す → 入れ直す、を明示的に
  書いた検査だけがこの欠陥を捕まえる。

### 5.59 一覧を仮想スクロールにすると、「行の DOM 数」を数えていた検査が静かに嘘になる

仮想スクロールは **画面に入るぶんだけ DOM を作る** 仕組みなので、入れた瞬間から
**「行の DOM 数」と「一覧に載っている件数」は別物**になる。ところが件数を数える検査は
`page.locator('[data-testid^="feature-list-item-"]').count()` のように **DOM を数えて**
書かれていることが多い。これは仮想化のあとも**例外を投げずに小さい数を返す**ので、
「地物が 3 つあるはず」の検査が「窓に 3 行入っていた」だけで緑になる。**壊れたことに
気づけない。**

2026-09-05 の増分 4 で実際に踏んだ。件数を数えるヘルパが 17 本の spec に写しで置かれて
いて、そのすべてが行の DOM を数えていた（`e2e/__bughunt__/explore*.spec.ts` ほか）。

- **直し方**: **件数の真実源を画面の 1 か所に決める**（このリポジトリでは一覧の件数表示
  `unified-list-count`）。数える口を共通ヘルパ 1 本へ寄せ、そこだけがその表示を読む。
  写しが 17 本あるなら 17 本とも寄せる（教訓 5.44 と同じ「同名の写し」の話）。
- **同じ型の罠**: 「描かれている図形の数」を DOM で数える検査も、canvas 化した瞬間に
  同じ壊れ方をする。**「画面に出ている数」と「データの数」が一致しなくなる変更**は
  すべてこの型である。
- **検出**: 仮想化を入れたら、**わざと件数を 1 件だけ増やす／減らす**変更を入れて、
  件数の検査が赤くなるかを確かめる。赤くならなければ、それは DOM を数えている。

### 5.60 大規模データの検査を「1 つのスナップショットに全部詰める」形で作ると、fixture の作り方を測ってしまう

「5,000 件で固まらないこと」のような規模の検査を作るとき、**その場で合成データを組む**のは
正しい（5,000 件入りの保存ファイルを置くと重い）。しかし **組み方が実データの形から外れると、
測っているのはアプリではなく fixture の形になる。**

2026-09-05 に実際に踏んだ。5,000 件を **1 本の錨（＝1 つのスナップショット）** に詰めて
5,000 本の履歴から同じ錨を指したところ、時刻断面の解決（`featuresAt`）が
**履歴数 × スナップショット内の地物数 ＝ 2,500 万回**の走査になり、E2E が 10 分でも
終わらなかった。実データは **1 履歴 ＝ 自分と自分の頂点だけのスナップショット**なので、
本物では起きない形である。

- **手順**: 合成データは **実データの構造を数えてから**作る。件数だけ真似ても、
  「1 件あたり何を持っているか」を外すと計算量の桁が変わる。
- **検出**: 合成データを載せる操作そのものに時間の上限を置く（載せるのに 30 秒かかるなら、
  そのあとの測定は何を測っても意味がない）。**「検査が終わらない」を「アプリが遅い」と
  読み違えない** ―― まず fixture の形を疑う。

### 5.61 下端に固定した部品は、器が低いと上の中身を覆う（`position: sticky` の裏面）

保存ボタンのような「いつも見えていてほしい部品」を `position: sticky; bottom: 0` で
下端に固定するのは正しい。ただし **その器の高さが部品の高さに近づくと、固定された部品が
中身のほとんどを覆う**。スクロールして目的の見出しを画面へ入れても、入った先が
固定部品の下なので**押せない**。見た目には「そこに在る」のに反応しない。

2026-09-05 の増分 4 で実際に踏んだ。右パネルを上下 2 区画にしたとき、下段（素性欄）が
実測 159px になり、下端に固定した保存列（＋その上の予告・断りの行）が約 90px を占めて、
節の見出しがその下に隠れた。E2E が「スタイルの節が押せない（`property-save-bar` が
ポインタを横取りしている）」で捕まえた。

- **直し方**: **器の側に下限の高さを持たせる**（`min-height`）。固定部品の高さ＋最低限の
  中身が同時に見える値にする。仕切りで手動で縮められる場合は、**その下限も同じ値**にする
  （片方だけ動かすと、引き切ったときに外側へスクロール条が出る）。
- **同じ型の罠**: `position: sticky; top: 0` の見出しも、器が低いと下の中身を覆う。
  上下に固定を置いたら、**両方の高さの合計 + 1 行**が器の下限である。
- **検出**: **器をいちばん低くした状態で、いちばん下の部品を押す** E2E を書く。
  jsdom はレイアウトを持たないので再現できない（教訓 5.49）。

### 5.62 `toBeVisible()` は、先祖のスクロール範囲の外にある要素も「見えている」と判定する

Playwright の `toBeVisible()` が見るのは「表示ボックスがあり、`visibility: hidden` でなく、
面積が 0 でない」ことだけである。**スクロールする器の外へはみ出した要素も真になる**
（器をスクロールすれば見えるから、というのが判定の理屈）。だから「一覧の行が画面に
出ている」を `toBeVisible()` で固定すると、**行が器の下 23px から始まっていて 1 行も
読めない**状態でも緑のまま通る。

2026-09-05 の増分 4 でこれを踏んだ。右パネルの上段が 108px しか取れないのに一覧の中身は
207px あり、既定の窓（1280×800）でも最小の窓（800×600）でも **行が 1 行も区画の中に
入っていなかった**。E2E も単体テストも全部緑で、実データの探索で初めて見つかった。

- **禁止**: 「画面に出ている」「読める」「押せる」を `toBeVisible()` だけで固定しない。
- **直し方**: **矩形の交差で見る**。`getBoundingClientRect()` を要素と器の両方から取り、
  `min(bottom) - max(top) > 0` を数える。件数を数えるなら「器と交差している行の数」を
  返す小さな関数を spec に 1 つ置き、全部そこを通す。
- **同じ型の罠**: `toBeInViewport()` は窓との交差しか見ないので、**器の中で隠れている**
  場合には効かない（窓の中に居るが器の外、という状態を通す）。
- **検出**: 「1 行も見えない」をわざと作って（区画の下限を元に戻して）赤くなることを
  確かめる。窓の大きさを 2 つ以上（既定・最小）で回す。

### 5.63 同じコミットで撮った基準画像が、そのコミットの最終コードで撮られているとは限らない

視覚回帰の基準画像は「撮った時点のコード」を写す。ところが 1 つのコミットの中で
「画像を撮る → さらに直す」と進めると、**基準画像だけが 1 世代古いまま**コミットに入る。
画像は差分に載っているので撮り直した事実は残り、レビューでも見落とされる。

2026-09-05 の増分 4 で 3 枚がこれになった。「◀ 前へ（まとまりなし）」の行が写った画像が、
その行を出さないようにしたあとのコミットに入っていた ―― 基準画像が **現物と違う姿を
「正しい姿」として固定していた**。

- **禁止**: 直しの途中で基準画像を撮らない。
- **直し方**: **その変更単位の最後**に、全件ゲート（build → typecheck → lint → test → e2e）
  を通したコードで撮り直す。撮り直したら、進捗報告の「何が写っているか」も実物に合わせる。
- **検出**: 画像を含むコミットでは、画像の撮影時刻と最後のソース変更の時刻を比べる。
  撮影が先なら撮り直す。

## 6. 教訓追加の手順

1. 不具合の根本原因を特定する（§1.1）。
2. 既存教訓（§5）で説明できるか確認する。説明できるなら、その節を引用して適用宣言する（§1.6）。
3. 説明できないなら、本書 §5 に新しい教訓を追加する。見出しは禁止・確認観点として書き、「検出:」にどの状態・層・テストで捕まえるかを記す（§1.7）。
4. 回帰テストを同一作業内で追加する（§1.9）。
5. 完了報告に「新規教訓化した根本原因」を明示する（§1.5）。
