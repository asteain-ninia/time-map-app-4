# 開発ガイド

本書は time-map-app-4 の開発作法をまとめた恒久文書である。開発規律と文書の役割分担を定める。技術の選定は技術方針.md で定める。教訓は `.claude/rules/` に置く（§5）。

---

## 1. 開発規律（workingRules）

### 1.1 根本原因の修正

不具合修正時は必ず根本原因を修正し、場当たり的・対症療法的な対応をしない。まず原因解析に注力する。この規律は初期実装・保守・不具合修正のすべてのフェーズで有効である。

### 1.2 省略の禁止

コードの修正時に「～も同様に～」といった省略は一切しない。影響箇所はすべて明示的に修正する。同種の箇所が複数あるなら、その全件を列挙して直す。

### 1.3 保守時の最小変更

保守・不具合修正フェーズでは、指示されていない変更・余計な変更を行わず、変更箇所を最小限にとどめる。初期実装フェーズでは、土台を整える目的に限り必要に応じて緩和される。

### 1.4 論拠の引用義務

何かを論ずるときは、根拠となるソースコード（または仕様の該当節・行番号）を直接引用する。要約だけで済ませない。レビュー・設計判断・不具合報告のいずれでも、引用なしの主張は根拠不十分とみなす。

### 1.5 失敗の教訓化（全フェーズで有効）

実装上の失敗・不具合の根本原因は `.claude/rules/` の教訓に残す（§6）。既存の教訓で説明できない不具合は、新しい教訓を追加してから完了扱いにする。完了報告では、新規に教訓化すべき根本原因があったかを必ず明示する。

### 1.6 教訓の再発は検査で止める

教訓の引用と適用宣言は求めない。再発は lint とテストで止める。検査にできない教訓は、関係するファイルを扱うときに `.claude/rules/` から読み込まれる。同じ失敗を繰り返したら、その教訓を検査へ格上げする。

### 1.7 教訓は正しい道・誤った道の兆候・確かめ方で書く

「注意する」「気をつける」で終わらせない。作業中に気づける具体的な兆候と、確かめる手段を書く。日付や再現の物語は書かない。ただし、試して戻した直し方や別の壊れ方をした直し方は、誤った道の兆候として残す。正しさの根拠は、所有者の裁定か、繰り返し確かめられる検査に置く。

### 1.8 やり残しの記録

実装のやり残しは、未解決課題文書（現状.md）に追記する。口頭・記憶・コミットメッセージだけに残してはならない。

### 1.9 テストは実装と同時に書く

実装後にテストを後回しにしない。1 機能のフローは次の順序で進める。

1. 機能宣言 + 仕様引用
2. 実装
3. テスト全パス
4. ビルド確認
5. 状態文書更新
6. コミット

### 1.10 ワークフロー知見の即時還元

開発フローに改善が見つかったら、即座にプロセス文書へ還元する。レビューで「次回検討」と書きたくなる再発防止観点は、先送りせず同一作業内で教訓集へ追記する。

### 1.11 コミットメッセージ規律

コミットメッセージは全文をその言語（本文は日本語）で記述し、type のみ慣例に従う（Conventional Commits）。状態文書のみの更新コミットは、メッセージを定型に統一する。

---

### 1.12 テストの速さ（普段の短い確認と、受け入れの全件）

**普段は `npm run check`、受け入れでは全件。** 全件は `npm run typecheck`・`npm run lint`・`npm run test`・`npm run build && npm run e2e`・`npm run e2e:explore`。

`npm run check`（`scripts/check.mjs`）が順に走らせるもの:

1. 型検査の増分（キャッシュは `node_modules/.cache/tsc`）
2. lint の増分（`npm run lint:cached`。キャッシュは `node_modules/.cache/eslint`）
3. 変更が import で届く単体（`vitest --changed`）
4. ソースや CSS を文字として読む単体（`scripts/check.mjs` の `TEXT_READING_TESTS`。3 では拾えない）
5. `src` か `e2e` が変わっていれば、build して `e2e/launch.spec.ts` と変えた spec

既定は手元の未コミットの変更を見る。コミット済みの範囲は `npm run check -- --base=HEAD~3`。

**短い確認が見逃す範囲:**

- E2E は変えた spec と起動の確認だけ。アプリ本体を変えても、そこを通る他の spec は走らない。`e2e/helpers.ts` など共通部品を変えたときは `npm run e2e` を流す（画面に注意を出す）。
- 探索（`e2e:explore`）は変えた spec しか走らない（§5.88）。
- lint のキャッシュは、そのファイルの中身と設定だけで判定する。別のファイルの変更で赤に変わる場合（import の解決先の消失など）、触っていないファイルでは検査し直さない。全件の `npm run lint` はキャッシュを使わない。
- `vitest --changed` は静的な import をたどる。文字として読むテストは 4 で別に走らせるが、一覧へ足し忘れると走らない。実データを開くテストは入れていない。

**単体の速さで守っていること:**

- **1 ファイルの上限の目安は 40 秒。** vitest はファイル単位でしか並列に分配しないので、長い 1 本が全件の待ち時間になる。性質テストを足して超えたら describe の単位で割り、生成器と補助は `*.arbitraries.ts` へ出す。割ったら前後で「結果＋題名」の一覧を比べる。
- **回数の多い性質テストは `src/test-support/fast-expect` の `expect` を使う。** vitest の `expect()` は呼ぶたびに内部状態を作り直すので、不変条件を何十万回も確かめる検査では CPU の 75% がここになる。通るときだけ本物を飛ばし、失敗の判定と文面は本物のままにしてある（`fast-expect.test.ts` が突き合わせる）。`expect.assertions()` を使う検査には使わない。
- **隔離（`isolate: true`）は外さない。** 外すと速いが、モジュールの状態が漏れて `src/domain` だけで 7〜9 件が赤になり、件数も回ごとに変わる。
- **並列の上限は 8 本**（`vitest.config.ts`）。同じ PC で所有者の作業が動いているので、既定の 23 本まで広げない。

**E2E が縮まらない理由:** 6 ワーカーへの分配はほぼ均等で（テスト時間の合計 ÷ 6 ≒ 実時間）、固定の待ち（`waitForTimeout`）は合計の 2% に満たない。合計の 4 割弱は 1 テストごとの Electron の起動と終了で、ここを縮めるには起動の共有が要るが、前のテストの状態が漏れないことの保証が先に要る。

## 2. 文書の役割分担規約（docConventions）

### 2.1 文書の役割を厳守する

恒久の文書は次の 5 つと教訓である。どれに書くべきか迷ったら、この表の役割で決める。

| 文書 | 役割 | 書かないもの |
| --- | --- | --- |
| **要件定義書.md** | 何を満たすべきか（技術非依存の仕様本文） | 実装方法・進捗・識別子（§2.5） |
| **技術方針.md** | どう実現するか（技術選定と、実装で確定した設計判断） | 未解決課題・作業履歴 |
| **開発ガイド.md**（本書） | 開発作法・文書規約 | 一時的な実装状況・進捗 |
| **`.claude/rules/lessons-*.md`** | 再発防止の教訓（§5） | 日付・再現の物語 |
| **現状.md** | 未解決課題・既知の不具合・残作業 | 完了した課題（即時削除し実装済み.md へ）・機械算出値（§2.6） |
| **実装済み.md** | いつ何を実装したかの履歴 | 再発防止策（§2.4）・未解決事項 |

進行中の作業の設計・進捗・審査は `docs/ui-redesign/` に置く。所有者の裁定は同じ場所の README が正本である。

補助資料として、`specs/` にユニット単位の着手指示書、`reference/` に前世代（v3）の参照素材を置く。
どちらも**凍結した過去の資料**であり、新規の追記はしない（`specs/README.md` / `reference/README.md`）。
`.autopilot/` も 2026-08-11 に凍結した過去の作業ログである（`.autopilot/README.md`）。
現在の状態を判断する根拠は `docs/` とソースコードのみとする。凍結資料と `docs/` が食い違ったら `docs/` が正。

### 2.2 完了課題を残す例外

完了した課題は原則として即時削除するが、同一課題を複数回の作業で分担し、削除すると進行文脈が失われる場合に限り、未解決課題文書に一時的に残してよい。その場合は行頭に `[完了]` を付け、残作業完了時に課題全体を削除する。

### 2.3 課題番号は欠番として残す

未解決課題文書からリスト項目を削除するときは、それがリストの最後でない限り欠番として残す（番号を詰めない）。番号を詰めると過去の参照が壊れる。

### 2.4 再発防止知識は履歴文書に書かない

再発防止の恒久知識・見落としやすい判断基準・回帰テスト観点は、履歴文書ではなく教訓（`.claude/rules/`）へ移す。履歴文書はあくまで「何をいつ実装したか」の記録に限定する。

### 2.5 要件定義書は仕様本文と内部実装補遺を分離する

要件定義書は仕様本文と内部実装補遺を分離する。仕様本文（完全自然言語）には、識別子・内部キー名・クラス名・コード値を直接記載せず、実装詳細は内部実装補遺へ集約する。

### 2.6 機械算出値は手書きしない

テスト件数のように機械的に算出できる数値は自動更新（コミット前フック等）に任せ、ナラティブや追補エントリへ件数を手書きしない。件数差分ではなく、追加したテスト群の名称・カバレッジ対象といった質的記述で表現する。

### 2.7 コメント規律

コメントは本質的に必要な内容のみを書き、一時的な情報を含めない。「修正:～」「ここを修正」「--修正ここから--」のような書き方をしない。既存のコメントは温存する。

### 2.8 用語撤廃・置換は同一変更単位で同期する

仕様文書で用語を撤廃・置換すると宣言したら、同一文書内の全用例・関連する用語表・対応する設計サマリを同じ変更単位で同期する。「この章だけ修正、他は次回」と先送りすると、同一文書内に自己矛盾が残る。

### 2.9 用語注記を追加したら全文検索で同期する

用語注記を追加したら、撤廃語をリポジトリ全文検索し、ヒット箇所を全部直すか「対象外（理由つき）」と未解決課題文書に記録する。同じ説明表現を別箇所で再利用している場合（用語集・備考・他章サマリ）も検索して同期する。

### 2.10 対概念へ判断を反映する

ある概念に仕様判断を加えたら、その対概念にも同じ判断を反映する（混在結合↔既存への子追加、リーフ↔コンテナ、同一性継続↔同一性終了 等）。検索だけでなく、対概念の説明文がその判断と整合するかを能動的に確認する。

### 2.11 既存性の主張は実在確認してから書く

ドキュメントで「既存の」「継承」「実装済み」「現行」等、実装状況や既存性を主張する識別子を書くときは、書く前にその識別子をソースで検索して実在を確認する。表内の 1 行を修正したら、同じ表内の同類対象も一括確認する。

## 3. 本プロダクトの前提（v4 の文書方針）

### 3.1 クリーンルーム原則

本プロダクトの文書は、外部の既存実装・他プロダクト・過去の作業文脈に依存しない自己完結した記述とする。必要な制約は本プロダクト自身の要件・方針として直接記述し、「以前のやり方」「従来」といった外部参照に頼らない。

### 3.2 技術の選定と教訓の分離

採用技術・実行環境・ライブラリの選定は技術方針.md に集約する。特定の技術で踏んだ失敗は、教訓に具体的な技術名のまま書く。

## 4. ドメイン・アルゴリズム共通の設計指針

以下は §5 の個別教訓の背景にある、横断的な設計指針である。

- **単一の真実源**: 同じ判定・同じ基準値（baseline）・同じ既定値処理は、同じ実装を共有する。判定ロジックの分散はドリフトを生む。
- **対概念の整合**: 一方の概念に判断を入れたら、必ず対をなす概念（追加↔削除、開始↔終了、リーフ↔コンテナ）に同じ判断を反映する。
- **UI 文脈の優先**: 操作対象は「いま UI 上に表示・選択されている要素」を第一候補にし、コレクションの先頭やデータソース全体を既定で使わない。
- **結果状態での判定**: 「ある状態変化が起きたら追加処理を走らせる」検出は、特定の呼び出し経路ではなく、変異後の結果状態で判定する。
- **層をまたぐ契約の固定**: 呼び出し側・公開側・受信側で共有する名前・型・構造は、偶然の一致に頼らず型や両側テストで固定する。

## 5. 教訓

教訓は `.claude/rules/` に分野別で置く。番号は変えないので、コードや文書の「開発ガイド §5.N」は `### 5.N` を検索して引く。

| ファイル | 分野 | 読み込まれるとき |
| --- | --- | --- |
| `lessons-ui.md` | 画面と入力 | `src/ui/` を扱うとき |
| `lessons-domain.md` | 中核の処理 | `src/domain/` を扱うとき |
| `lessons-persistence.md` | 保存・読み込み・本体プロセス | `src/domain/persistence/`、`src/shell/`、`src/domain/geo/`、`src/ui/` の状態・設定・ファイル操作を扱うとき |
| `lessons-render.md` | 描画 | `src/render/`、`src/domain/display/`、`src/ui/map/` を扱うとき |
| `lessons-test.md` | テストの書き方 | `e2e/`、テスト、テストの設定、E2E 用の観測の部品を扱うとき |
| `lessons-process.md` | 進め方 | 常に |

---

## 6. 教訓追加の手順

1. 不具合の根本原因を特定する（§1.1）。
2. 既存の教訓で説明できるか確認する。説明できるなら、なぜ検査で止まらなかったかを調べる（§1.6）。
3. 説明できないなら、`.claude/rules/` の該当する分野へ、次の番号で教訓を追加する（§1.7 の形式）。
4. 回帰テストを同一作業内で追加する（§1.9）。
5. 完了報告に「新規教訓化した根本原因」を明示する（§1.5）。
