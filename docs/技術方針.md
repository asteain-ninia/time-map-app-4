# time-map-app-4 技術方針

本書は time-map-app-4 の技術スタックとアーキテクチャ方針を定める。要件定義書（FR-01〜FR-118、NFR 5.1〜5.8）を唯一の根拠とし、以下の三つを設計の最優先軸に据える。

- **保守性**: 本要件は 100 を超える機能要件と、ジオメトリ・時間・階層という三つの本質的に難しいドメインを抱える。本質的複雑性が高い以上、勝敗は「偶発的複雑性をどれだけ足さないか」で決まる。
- **AI 自走開発容易性（agent-legibility）**: 単一言語による文脈統一・「魔法」の少ない明示的ライブラリ・層境界のファイル可視化・機械検証可能な不変条件（NFR 5.8）への純粋関数での直結を、開発速度と安全性の前提条件とする。
- **テスト容易性（NFR 5.8）**: ドメインの不変条件を機械的に検証でき、複合操作を「入力状態 → 期待状態」で再現でき、時間計算を副作用なく境界網羅できること。

性能（NFR 5.1 の 60FPS・100ms、NFR 5.2 の 5,000 オブジェクト・2GB）はこれらと同格の絶対防衛線として扱うが、要件のデータ規模は描画層を適切に設計すれば到達可能と見積もり、まず可読性と保守性の高い構成を選び、性能未達が計測で判明した場合にのみ描画層を局所的に強化する段階戦略を採る（後述 4. リスクと緩和策）。

## 2. 各レイヤの選定理由

### 2.1 言語: TypeScript（strict 全有効）

全層（ドメインコア・状態・描画・UI・Electron メイン／preload）を単一言語で記述できるため、層をまたいでも型定義を共有でき、文脈切替コストが発生しない。これは AI 自走開発の最大の前提条件である。`noUncheckedIndexedAccess` は頂点配列アクセス（FR-30 系の共有頂点・リング操作）の境界外参照をコンパイル時に排除し、`exactOptionalPropertyTypes` は任意属性の取り違えを防ぐ。strict 群は NFR 5.8 のテスト容易性とドメイン不変条件の型表現を直接支える。

ドメインの判別共用体（点／線／末端／集約、領土リング／穴リング）により、「集約地物は形状を持たない」「リング階層は領土 → 穴交互」「最上位フラグと親なしの同値」（FR-24 / FR-35 / FR-39）などの不変条件を **型で表現し、不正状態を表現不能** にする。これは長期保守でのリグレッションを最も効果的に抑える。

### 2.2 デスクトップシェル: Electron

FR-02（通信不要・オフライン完結のスタンドアロンデスクトップ）と FR-103 / FR-108（ローカルファイル保存・自動バックアップ世代管理）が必須要件であり、Electron はランタイムを同梱し外部接続なしで単一インストーラとして配布できる。プリセット出界図・ベースマップ画像・暦データもアプリ内に同梱できる（FR-03）。Node.js の `fs` へ直接アクセスでき、一時ファイル → fsync → アトミックリネームによる原子的置換（NFR 5.3）はブラウザサンドボックスでは実現できない安全性を与える。レンダラは `sandbox: true` でネットワークを遮断し、ファイルアクセスを preload 経由の型付き IPC に限定する。

Rust ベースのシェル（Tauri 等）も候補だが、言語を二つ（Rust ＋ TS）に分けると層境界が言語境界と化し、AI エージェントの文脈が分断され自走開発容易性が損なわれる。本方針は単一言語統一を優先して Electron を選定する。

### 2.3 UI フレームワーク: React 18（UI シェルに限定）

FR-111 の業務 UI（左ツールバー／中央マップ／右サイドバー／下部タイムライン）、多数のモーダル（FR-62 競合解決／FR-93 分割継承／FR-109 設定）、プロパティパネル（FR-83〜FR-102）は宣言的で状態駆動な UI が多い。React の関数コンポーネントはこれらを見通しよく低工数で構築でき、AI の学習データが厚く定型コード生成の速度・正確性が高い。

ただし **高頻度更新の地図描画は React の再レンダリングサイクルから完全に切り離し、Canvas 側で直接管理する**。描画状態を React state に持たせると再レンダリングで 60FPS（NFR 5.1）が破綻するため、地図描画状態は Zustand と命令的 Canvas 側に置き、React は周辺 UI のみを管理する規律を設計初期から徹底する。

### 2.4 地図描画: Canvas 2D（差し替え可能インタフェース）

FR-05（正距円筒図法）／FR-07（無限横スクロール）／FR-08（世界〜都市内の連続ズーム）／FR-17（ズーム非依存の画面上一定サイズの点・線・ラベル）／FR-21（穴の透過・飛び地の独立描画）／FR-28（エッジ滑りハイライト）は、いずれも「ワールド座標 → スクリーン座標」変換を完全に自前制御する必要がある。地理特化のタイル地図ライブラリ（Leaflet / MapLibre 等）は、正距円筒の架空地図・無限横ループ・カスタム面階層描画にはむしろ制約と「魔法」になり、要件由来の独自データモデル（FR-26〜FR-33 の末端排他・共有頂点・リング階層）にも乗らない。したがってどの選択肢でも自前描画は不可避である。

命令的な Canvas 2D 描画は、描画ロジックがコードとして一読で追える明快さを持ち、AI エージェントの読解・修正・検証が容易で、保守性レンズでも有利である。NFR 5.1 が明示する最適化方針（空間インデックス・視野外クリッピング・LOD・描画バッチ・イベントスロットリング）を組み込めば、NFR 5.2 の 5,000 オブジェクト規模で 60FPS は到達可能と見積もる。

性能リスクへの備えとして、描画層は **`MapRenderer` インタフェース**（カメラ変換・地物バッチ・ヒットテストの契約）として抽象化する。これにより既定の Canvas 2D 実装で性能未達が計測で判明した場合、ドメイン・UI・状態を変更せず WebGL 実装（PixiJS 等）へ局所的に差し替えられる退避路を確保する。

### 2.5 状態管理: Zustand ＋ 純粋ドメインコア

状態を二層化する。ドメインの真実（地物・錨・ツリー・頂点・フラグ）は、React にも Electron にも依存しない純粋関数 ＋ イミュータブル更新の独立コアに置く。UI / セッション状態（選択・モード・ズーム・現在時刻）のみ Zustand で薄く扱い、React 外のドメインストアを Zustand の `subscribe` でブリッジする。Zustand は単一の真実源として機能し、Canvas 側は購読のみで React の描画経路に乗らない。

この分離により、アンドゥ／リドゥ（FR-73 / FR-74）は「過去のイミュータブル状態への差し替え」として自明に実装でき、複合操作（分割・結合・競合解決）を単一アンドゥ単位として原子的に扱う要件（FR-94）を構造的に保証する。Redux のボイラープレートや signals 系の暗黙再計算より、Zustand は魔法が少なく層境界が明快で、AI が同期バグを起こしにくい。

### 2.6 ドメイン更新／履歴: 純粋コマンド ＋ Immer ＋ 二重スタック

ドメイン状態は Immer で不変更新し、各ユーザーアクションを「コマンド → 新状態」の純粋関数として記録する。構造共有により、5,000 オブジェクト規模でもアンドゥスタック（FR-74、上限 100）をメモリ効率よく（NFR 5.2 ≤ 2GB）保持する。コマンド適用結果を二重スタックに積む純粋実装は、前後状態をテストで直接比較でき、NFR 5.8 の「複合操作を入力 → 期待状態で再現」に直結する。

> ドラッグ中の連続更新など、毎フレーム不変コピーを取ると 100ms 応答（NFR 5.1）を脅かすホットパスは、Immer のトランジェント（`produce` のドラフト保持）またはミュータブルな一時バッファで処理し、操作確定時にのみ正式なイミュータブルコマンドを発行する（4. リスクと緩和策で詳述）。

### 2.7 空間インデックス: RBush

NFR 5.1（100ms 応答／60FPS）・NFR 5.2（5,000 オブジェクト）・FR-26 / FR-27 / FR-28（末端地物同士のペア排他検証・エッジ滑り）・FR-89（リアルタイム衝突判定）に対応する。末端地物のみを R-tree に載せ近傍候補を絞ることで、全ペア検証 O(n²) を回避する。視野外クリッピング（描画対象の絞り込み）と共有頂点の近接スナップ候補探索（FR-30〜FR-33、FR-110 のスナップ距離既定 50px）にも同一インデックスを再利用でき、最適化手段が一つの明快な部品に集約される。

### 2.8 幾何ブーリアン演算: polygon-clipping

FR-20（穴・飛び地・ネスト）／FR-37（差分から直轄領生成）／FR-45（穴あけ新地物）／FR-50・FR-51（結合の論理和）／FR-63（競合解決の差分調整）／FR-35（集約地物＝下位領域の和）の中核を担う。面のブーリアン演算は自己交差・数値誤差で破綻しやすく自前実装のリスクが高いため、多重リング・穴を正しく扱える成熟ライブラリへ確実に委譲する。これは「枯れた技術を使い、数値的に最も危険な難所だけ実績ライブラリに任せる」というリスク最適配分である。

**float union と共有頂点 ID 同一性（FR-30 系）の整合**: polygon-clipping は浮動小数座標で動作し union 後に頂点を再生成するため、量子化（R2）で入力座標を整数格子へ揃えても、結果リングの頂点が入力頂点の ID 同一性（FR-30〜FR-33 の共有頂点：同一座標を厳密共有）を保つ保証はない。したがって union/差分の結果には**頂点再マッピング規則**を必須化する。すなわち (1) 演算前に入力頂点を量子化格子へスナップし、格子座標 → 頂点 ID の対応表を保持、(2) 演算後の結果頂点を同じ格子へ量子化し、格子座標が既存頂点 ID と一致するものは ID を継承、一致しないもの（交点等で新生した頂点）のみ新規 ID を採番、(3) 共有継続が必要な辺（FR-95 の結合後共有）は対応表経由で同一 ID へ再結線する。この再マッピングは R6（共有頂点とイミュータブルモデルの両立）と統合して扱う。整数座標で堅牢性の高い Clipper2 を退ける以上、float union がもたらすこの ID 同一性破壊は polygon-clipping 採用の代償として明示的に設計対応すべき事項である（候補比較・R2 / R6 参照）。

### 2.9 測地計算: 自前純粋関数モジュール

FR-05 は正距円筒図法を前提とし、ユーザーが赤道長（km）を入力する。さらに FR-109 はプロジェクト設定として赤道長と並んで**扁平率（flattening）**を明示列挙する。距離・面積・大円距離（FR-14 / FR-19 / FR-20）は、この前提に閉じた小さな純粋関数で実装する。汎用測地ライブラリは用途に対して重く、依存表面積・破壊的変更追従・ロックインを増やすため採用しない。自前モジュールは小規模かつ副作用がないため、紀元前・世界端ラップなどの境界ケースを fast-check と Vitest で網羅検証でき（NFR 5.8）、追従コストもない。将来の独自歴（FR-7.1）に向けた暦設定の引数化もここで吸収する。

**赤道長・扁平率の引数化（FR-109）**: 測地モジュールの全公開関数は、赤道長（km）と扁平率を**明示引数**として受け取る（暦設定と同様に外部から注入し、モジュール内に隠れた定数を持たない）。シグネチャは概念的に `distance(a, b, { equatorLengthKm, flattening })` / `area(ring, { equatorLengthKm, flattening })` の形を取り、プロジェクト設定（FR-109）の値がそのまま流れ込む。

扁平率の正距円筒前提下での反映方針を次のとおり定義する。正距円筒図法はワールド座標（経度・緯度を等間隔に展開した平面）を採るため、扁平率は**緯度方向の地表スケール（メートル毎度）を経度方向と非対称にする係数**として距離・面積計算に取り込む。具体的には、赤道長から導く経度方向スケールに対し、扁平率 f に基づく緯度方向の子午線弧長補正係数を緯度の関数として乗じ、距離は経度成分・緯度成分を分離してから合成、面積はリング積分時に緯度依存スケールを反映する。これにより扁平率は**測地計算（FR-14 / FR-19 / FR-20）に正面から作用する設計パラメータ**として扱われ、描画アスペクト比のみの飾りには落とさない。扁平率 = 0（真球相当）を既定・退化ケースとして fast-check の境界ジェネレータに含め、f を変えた際の距離・面積の単調性を不変条件として検証する。

### 2.10 スキーマ検証: Zod

FR-104（バージョン検証）／FR-106（読込時の整合性チェックと自動修復）／FR-116（入力検証・サニタイズ）／NFR 5.5 に対応する。スキーマを単一の宣言として書き、そこから TS 型を導出できるため、「検証ロジックと型が二重定義される」偶発的複雑性を排除する。保存形式のバージョン分岐は discriminated union で明示し、互換マイグレーションはスコープ外（FR-7.3 で将来実装）のためバージョン不一致は警告／拒否のみとしてコアを単純に保つ。IPC・ファイル読込・外部地図入力の境界では必ず Zod を通す運用を lint ルールで強制する。

### 2.11 Markdown: markdown-it ＋ DOMPurify

FR-98 の詳細文書（画像埋込・リンク・書式）を markdown-it でレンダリングし、DOMPurify で XSS 無害化する（FR-116 / NFR 5.5）。画像はプロジェクト ZIP 内アセットとして相対参照し、オフラインで完結する。

### 2.12 永続化: `.gimoza` ZIP コンテナ ＋ アトミック保存

FR-103 が「全頂点・錨・親子関係・フラグ・設定・ベースマップ画像」を保存内容と定めるため、バイナリ画像と JSON を 1 ファイルに同梱できる ZIP コンテナ（`.gimoza`）を採用し論理的完全性を確保する。マニフェスト先頭にバージョン文字列を保持し（FR-104）、読込時整合性チェックは Zod スキーマ検証で実装する（FR-106）。書き込みは一時ファイル → fsync → アトミックリネームでデータ破損を防止し、5 分間隔の自動保存と最大 10 世代のタイムスタンプ付きバックアップ（NFR 5.3）を Node `fs` のファイル単位コピーで単純に実装する。ZIP 入出力は軽量な fflate を用いる。

### 2.13 ビルド: Vite ＋ electron-vite（単一パッケージ・ディレクトリ層分離）

electron-vite はメイン／preload／レンダラの 3 ターゲットを小さく明示的な構成で扱え、設定ファイルを一読で理解できる。層分離は pnpm/npm のワークスペース（モノレポ）ではなく、**単一パッケージ内のディレクトリ構造 ＋ 依存方向の lint 強制** で実現する。これにより、ワークスペース間の参照解決・tsconfig 共有・ビルド順序という偶発的複雑性を避けつつ、`domain`（フレームワーク非依存・純粋）／`render`（描画層）／`ui`（React）／`shell`（Electron）の境界をファイル構造として可視化し、依存方向を `domain` へ内向きに固定する。`domain` は Electron／React／Canvas 抜きで Vitest 実行できる。

### 2.14 テスト: Vitest ＋ fast-check ＋ Playwright ＋ 自作計測ハーネス

NFR 5.8 が要求する三本柱に対応する。

- **不変条件の機械的検証**: fast-check のプロパティテストで「任意の編集後も末端地物は重ならない」（FR-26）「リング階層は領土 → 穴交互」（FR-24）「集約地物＝下位領域の和」（FR-35）「最上位フラグと親なしの同値」（FR-39）「錨列は常に昇順・非重複」（FR-56）「時間正規化の境界（紀元前・錨境界・非存在期間）」（FR-72）を生成入力で網羅する。
- **複合操作の再現**: Vitest で「入力状態 → コマンド → 期待状態」を単体テストし、分割・結合・所属変更・競合解決・アンドゥ／リドゥを原子単位で検証する。
- **性能指標の計測**: 60FPS／100ms／2GB／5,000 オブジェクト × 平均 10 錨を計測可能な指標として扱うため、FPS・応答時間・メモリを記録する自作ハーネスを整備し、Playwright for Electron の E2E と組み合わせて回帰計測する。

### 2.15 自動配色: ドメイン純粋関数（隣接判定 ＋ 四色彩色）

FR-100 / FR-101（自動配色：四色定理ベース・同一階層（同じ階層深度・親子文脈で隣接を定義する範囲）内の共有境界を持つ面が同色にならない割当・不足時の基準色からの決定的派生色生成）は could だが算法的に非自明（平面グラフ彩色 ＋ 隣接判定）であり、スタック表の空白は論拠の弱さとして残るため最低限の方針を定める。

- **隣接判定（共有境界検出）**: 隣接 = 同一階層（同じ階層深度・親子文脈で隣接を定義する範囲）内で共有境界（共有辺・共有頂点）を持つこと。共有頂点システム（FR-30〜FR-33）の頂点 ID 共有を一次情報として用い、候補絞り込みには既存の RBush（2.7）を再利用してバウンディングボックスが交差する面ペアのみを共有境界判定に回す（全ペア O(n²) を回避）。これにより新規の空間構造を増やさず最適化部品を一点に集約する。
- **彩色の純粋関数化**: 隣接グラフからの彩色割当を `domain` の純粋関数（隣接グラフ → 色割当）として実装する。四色での貪欲彩色を基本とし、4 色で割り当て不能な縮退ケースでは基準色（パレットテーマ：FR-100 の使用パレット）から**決定的**に派生色を生成する（同一入力 → 同一出力。乱数や時刻に依存しない）。決定的派生色は NFR 5.8 のテスト容易性（出力が再現可能で入力 → 期待状態テストに乗る）へ直結させる。
- **再配色トリガの限定**: 再配色は FR-101 が定める条件（共有境界の成立／解消・面の分割・面の結合）のときのみ起動し、時間移動・単純な頂点移動では起動しない。隣接関係が変化する操作のコマンド適用後にのみ隣接グラフを差分更新して彩色を再評価する。許可解除時は色を維持し手動編集を解放する（FR-100）。選択表示色は通常色から決定的に明度・彩度を上げて導出し、飛び地は同一面として同色、穴は透過扱いとする（FR-101）。

## 5. 本構成が要件をどう満たすか

### 5.1 保守性

本要件の本質的複雑性（ジオメトリ・時間・階層）は避けられないが、本構成は偶発的複雑性を徹底排除する。単一言語（TypeScript）で全層を統一し、`domain` / `render` / `ui` / `shell` の境界をファイル構造として可視化、依存方向を `domain` へ内向きに固定する。これにより UI・描画・シェルの技術が変わってもコア資産が温存され、長期ロックインが小さい。外部依存は最小化（測地計算を内製、描画はブラウザネイティブの Canvas 2D、ビルドは electron-vite の薄い構成）し、数値的に最も危険なブーリアン演算だけを成熟ライブラリへ委譲する「リスク最適配分」を採る。判別共用体による不正状態の排除（FR-24 / FR-35 / FR-39）は、リグレッションを型レベルで抑える。

### 5.2 性能

NFR 5.1 が明示する最適化方針（空間インデックス・視野外クリッピング・LOD・描画バッチ・イベントスロットリング・重い計算の分離）を構成部品に直結させる。RBush で末端地物ペア排他（FR-26〜28）と視野クリッピングの候補絞りを行い O(n²) を回避。FR-17 / FR-86 のズーム非依存一定サイズ表示はワールド → スクリーン変換で制御。ドラッグ中の軽量判定と確定時フル整合性の二段戦略、ホットパスのトランジェント処理で 100ms 応答を防衛。Immer 構造共有でアンドゥスタックのメモリを抑え 2GB 以内を狙う。Canvas 2D で未達の場合は `MapRenderer` 経由で WebGL に局所差し替えできるため、性能上限に天井を作らない。

### 5.3 AI 自走開発容易性（agent-legibility）

単一言語による文脈統一・魔法の少ない明示的ライブラリ（Zustand・markdown-it・自前測地）・層境界のファイル可視化・純粋関数ドメインコアという四つが、AI が層をまたいでも一読で追える明快さを与える。Zod 単一宣言で検証と型の二重定義を排除し、不整合の余地を消す。命令的 Canvas 2D は GPU シーングラフ抽象より読解・修正・検証が容易。fast-check ＋ Vitest がドメインコードを即座に反証でき、自走ループが安全に回る。WebGL/Worker といった偶発的複雑性を既定構成から排除し、必要になった時点で純粋関数の移設・差し替えとして局所導入する段階戦略が、自走時の手戻りを最小化する。

### 5.4 テスト容易性（NFR 5.8）

ドメインを Electron／React／Canvas から完全分離した純粋関数として `domain` に閉じ込めることで、不変条件のプロパティテスト（FR-24 / 26 / 35 / 39 / 56 / 72）、複合操作の入力 → 期待状態テスト（FR-94）、時間計算の境界網羅（紀元前・錨境界・非存在期間）を副作用なく実施できる。性能指標（60FPS／100ms／2GB／5,000 オブジェクト × 平均 10 錨）は自作計測ハーネス ＋ Playwright で計測可能な形に落とし込む。

## 6. 実装で確定した設計判断（参照用）

実装の過程で確定し、以後の変更で崩してはならない設計判断を記録する。
再発防止の一般則は開発ガイド §5 教訓集にあり、ここには本プロダクト固有の構造的判断だけを置く。

### 6.1 経度±180度の継ぎ目は「連続座標へ展開してから」比較する

幾何述語（内外判定・線分交差）は連続した座標系で動作する契約であり、継ぎ目をまたぐ展開は呼び出し側の責務とする。
展開処理はリング単位で自身の先頭頂点を基準にするため、継ぎ目をまたぐ親子・兄弟・飛び地では
両者の基準が反対側になり約360度ずれる。そのため比較の直前に一方を他方の周回へ整列させる。
ブーリアン演算を呼ぶドメイン経路（表示・穴あけ・集約の和・排他検証・結合・階層検証・昇格・競合解決の差分）は
すべてこの整列ヘルパを単一の真実源として経由する。独自の折り返しは実装しない。

### 6.2 穴を削除したとき、穴の中の飛び地は吸収して消す

穴を削除すると穴の空白が親領土の実体に吸収されるため、穴の中にあった飛び地（領土）は
親領土に内包され、独立した外周にはできない。飛び地を最上位へ繰り上げる実装は
自身の幾何検証が「飛び地の重なり」と判定する欠陥だった。現在は飛び地を吸収して削除し、
その子（穴）を穴の親領土へ繰り上げる（領土削除の鏡像）。

### 6.3 選択状況の判定・表示解決は単一の純粋判定に集約する

プロパティパネルの表示分岐（アクティブ地物／頂点選択の所有者／複数所有者／所有者不明／空選択）は
生の ID 集合まで評価する1つの純粋判定に集約する。
頂点から所有地物を引く対応表は、クリック判定と描画が使うものと同一の表示解決結果から取る。
「画面でクリックできるもの」と「パネルが解決できるもの」が原理的にずれない構造を保つ。

### 6.4 錨の選択から現在時刻への同期は既存の単一経路を通す

錨を選ぶと現在時刻がその開始時刻へ動くが、この書き換えは時刻変更の共通経路を必ず経由し、
専用の時刻書き換え経路を作らない。保存時の編集時刻は、選択中の錨の開始時刻を使う。

### 6.5 表示制御は「表示状態の単一算出」を全消費者が共有する

表示・非表示・不透明度・強調・現在時刻での存在は1つの解決判定で算出し、
検索の母集合も描画もクリック判定もその結果を真とする。
表示制御の軸（種別・階層深度・個別地物）は定数で固定し、文字列リテラルで分岐しない。

### 6.6 外部から入る値は Zod の単一宣言から型を導出する

保存データ・設定・外部入力の検証は Zod のスキーマを単一の宣言とし、型はそこから導出する。
書き込み側の検証は読み込み側と対称にする（読めないファイルを書かない）。
Markdown は「解析 → 画像参照の解決 → 無害化」の単一経路のみで挿入する。
