## 指摘

### 1. 未保存の確認で「保存」を選ぶと、選んだ世代そのものが消える（重症度 3）

- **場所**: `src/ui/file-ops/file-commands.ts:255-262`（一覧 → 選ぶ → 未保存の確認 → `openBackup` の順）、`src/shell/io/backup.ts:253-281`（保存のたびに古い世代を間引く）、`src/shell/main/ipc-handlers.ts:398`（保存の世代数）。
- **再現**（探針 `main.probe.test.ts` の P1。主プロセスの本物のハンドラと `openBackupCommand` をつないだ）:
  1. 世代が上限まで溜まっている（世代数 3 で 3 回保存。既定の 10 でも、10 回保存したあとはいつもこの状態。自動保存が 5 分ごとに世代を足すので、普通に作業していればすぐ上限に着く）。
  2. 編集して未保存の状態で、ファイル →「以前の保存から開く」→ **いちばん古い行**を押す。
  3. 未保存の確認で「保存」を選ぶ。
  4. → その保存が新しい世代を 1 つ作り、**いちばん古い世代（いま選んだもの）を間引いて消す**。続く `openBackup` はファイルが無いので失敗し、
     `{"ok":false,"reason":"read-failed","message":"ファイルの読み込みに失敗しました。"}`。選んだ世代は二度と戻らない。
  - 出力（run1.log）: 選んだのは `/d/w.gimoza.bak.0001700000060000-0000`、終わったあとのディスクにはそれより新しい 3 つしか無い。
- **内容**: 利用者が「この時点へ戻したい」と選んだまさにその世代を、アプリ自身の保存が戻す直前に消している。所有者の原則「削除以外でデータが勝手に消えるのは良くない」に当たる。
  id は表に載っているので `UNKNOWN_BACKUP_MSG` には落ちず、`readAndParse` の汎用の失敗文（`ipc-handlers.ts:453`）になる（指摘 11）。
  間引かれるのは確認の保存 1 回ぶん（上限にいれば 1 個＝いちばん古いもの）だが、指摘 2 で世代数を下げた直後ならもっと多い。
  戻したい時点が古いほど（壊れたのに長く気づかなかったほど）いちばん古い行を選びやすいので、起きやすい場面と重い場面が重なる。
- **直し方の案**（どれにするかは司令塔・所有者の判断。順序を変える案は設計書 §J.4 の #9 と V14 手順 (a) の順序に触る）:
  - (a) 選ばれた世代を、そのコマンドが終わるまで間引きの対象から外す（例: 主プロセスが `openBackup` までの間「直前の一覧に載っている世代」を `runBackup` の削除候補から除く）。
  - (b) 確認の保存が走ったら一覧を取り直し、選んだ世代が消えていたら「保存したので、その世代は古い順に整理されて無くなりました」とはっきり言って止める（消えること自体は防げない）。
  - (c) 未保存の確認を一覧より前に出す（設計書の順序を変える。所有者の裁定が要る）。
  - どれでも、この経路を固定する検査（上限にいる・いちばん古い行・確認で保存）を足す。

### 2. 世代数を下げると、次の保存で古い世代がまとめて黙って消える（重症度 2）

- **場所**: `src/ui/settings/SettingsDialog.tsx` の `BackupTab`、`src/shell/main/ipc-handlers.ts` の `handleWriteAppPrefs`（書いたその場で `maxGenerations` を変える）、`src/shell/io/backup.ts:84-98`。
- **再現**（P2）: 世代が 10 個ある状態で世代数を 2 にして［適用］→ 次の保存 1 回で 9 個消え、2 個だけ残る。
  利用者が保存しなくても、**次の自動保存**（変更があれば最長 5 分後）が同じことをする。打ち間違い（「10」のつもりで「1」で［適用］／［保存］）でも同じ。
- **内容**: 設定の画面は「いま N 個あります」とは出すが、「次の保存で古い N−k 個が消えます」とは言わない。消えるのは設定の結果ではあるが、利用者が「消す」と言った操作ではない。
- **直し方の案**: いまの数より小さい値で［適用］／［保存］したときに「次の保存で古い世代が N 個消えます」と確かめる。または、下げたときは既存の世代をすぐには間引かない（新しく作るたびに 1 個ずつ減らす）。

### 3. 世代数の下限 1 では戻せない（重症度 2）

- **場所**: `src/shell/ipc/contract.ts:338`（`BACKUP_GENERATIONS_RANGE = { min: 1, max: 100 }`）、`src/shell/io/backup.ts:243-247, 273`（世代は「書き終えた正規のファイル」を **保存のあとで** 写す）。
- **根拠**（P7）: 世代数 1 で 2 回保存すると、残る世代は 1 個で、その中身はいまのファイルと 1 バイトも違わない（`disk.get(世代) === disk.get(元のファイル)` が真）。
  つまり、いちばん新しい世代はいつも「いまのファイルの写し」で、**本当に前の状態は世代数−1 個しか無い**。1 にすると、アプリの保存で壊れたときに戻す先が無い。
- **内容**: 「残す世代の数」を 1 にした人は 1 つ前に戻れると思うはずだが、戻れない。一覧の先頭の行がいまのファイルと同じであることも画面に出ていない。
- **直し方の案**: 下限を 2 にする／文言を「いまのファイルを含めて N 個」にする／一覧の先頭の行に「いまのファイルと同じ」と添える、のどれか。

### 4. 主プロセスが「新規」を知らないことによる取り違え（重症度 2）

- **場所**: `src/ui/file-ops/file-commands.ts:272-278`（新規は主プロセスへ何も知らせない）、`src/shell/main/ipc-handlers.ts:361`（`askSaveTarget` は `restoredSource` があれば既定にする）、`:490`（一覧の対象は `currentPath ?? restoredSource`）。
- **再現**（P3）:
  - 世代から戻す → ファイル →「新規」→ Ctrl+S（新規なので名前を付けて保存）→ 主プロセスは `showSaveDialog('/d/w.gimoza')` を呼ぶ。**新しい空のプロジェクトの保存の既定の名前が、前に戻した元のファイル**になる。そのまま Enter を押すと元のファイルの上に書く。
    Windows の保存ダイアログが既存ファイルに上書きの確認を出すかは **未確認**（出るなら一段の歯止めがある。出なければ重症度 3 寄り）。E2E は `E2E_SAVE_AS_PATH` でネイティブのダイアログを飛ばすので、どちらでも E2E では捕まらない。
  - 普通のファイル → 新規 → 「以前の保存から開く」／設定の「いまの世代」: 新規なのに前のファイルの世代を返す（P3b: 1 件、`w.gimoza`）。一覧の上に元の名前は出るので、取り違えて開く危険は小さいが、設定の「w.gimoza の世代はいま N 個」は新規の画面の上では事実と食い違う。
- **内容**: 実装係の申告どおり、主プロセスの覚え書き（`currentPath`・`restoredSource`）は新規で消えない。8D はその上に「戻したあとの既定の名前」を足したので、新規のあとにも元のファイルが既定として残る。
- **直し方の案**: 新規のときに主プロセスへ「保存先と覚え書きを捨てる」口を 1 本通す（`commitLoadedPath` と同じ形で、確定の点だけで呼ぶ）。最低でも、新規の確定で `restoredSource` を消す。

### 5. 世代のファイルを直接開くと、世代が保存先になり上書きされる（重症度 2・前からある経路）

- **場所**: `src/shell/main/ipc-handlers.ts:432`（`handleLoadDropped` は名前を見ずに読む）、`:564`（確定で `currentPath` を読んだパスにする）。
- **再現**（P4）: `w.gimoza.bak.0001700000060000-0000` を D&D → 確定 → 保存 → **世代そのもの**に書かれ、さらにその隣へ `…-0000.bak.0001700000180000-0000` という入れ子の世代ができる。
- **内容**: 前からある経路だが、設計書 §E.1 の V14（02-設計書.md:1238）がまさに「普通に load すると `.bak…` が保存先に昇格し、次の Ctrl+S でバックアップ自身を上書きする」と名指しした危険で、8D はメニューの入口だけを閉じた。
  エクスプローラで `.bak` を見つけて窓へ落とすのは、メニューを知らない人がいちばん自然にやる戻し方である。初回の上書き確認は出るが、そこに出るのは世代の長い名前で、それが世代だと気づける作りではない。
  入れ子の名前は、元のファイルの間引き（`selectBackupsToDelete`）では世代として数えられるのに、一覧（`listBackupGenerations` は数字だけの鍵）には出ない、という食い違いも生む。
- **直し方の案**: 確定の点（`handleCommitLoadedPath`）で、読んだファイル名が `<名前>.bak.<数字>-<数字>` の形なら `openBackup` と同じ扱い（保存先は未確定、元の名前を覚える）にする。主プロセスの側に 1 か所足せば D&D・開くの両方に効く。

### 6. 一覧を作るたびに全部の世代を読む（重症度 2）

- **場所**: `src/shell/io/backup.ts:185-215`（世代ごとに読んで地物数を数える）、`src/ui/file-ops/file-commands.ts:255`（一覧が返るまで板を出さない）、`src/ui/settings/useBackupSettings.ts:124`（設定を開くたびに同じ口で数える）。
- **根拠**（P6。実データ 775 地物・2.0 MB を並べ、ディスクの読み込みを除いた計算だけ）: **10 世代で約 0.6 秒、100 世代（設定の上限）で約 6.3 秒**。1 世代ぶん（約 60 ms）ずつは主プロセスで同期に走る（`unzipSync` と `JSON.parse`）。実際にはこれにディスクの読み込みが足される。
- **内容**: メニューを押してから一覧の板が出るまで、画面には何も出ない（ラッチは握ったまま）。設定の「保存とバックアップ」は**数を出すだけ**なのに同じだけ読む（設定を開くたびに）。設計書 V12 手順 (b) の例の 20 世代でも 1 秒超。
- **直し方の案**: 数えるだけの呼び出しは名前の一覧だけで済ませる（地物数を読まない別の口か引数）。一覧の地物数は板を出してから後で埋める、または前回数えた結果を世代の名前と大きさで覚えておく。

### 7. 修復ダイアログの既定が「捨てる」になる行がある（重症度 2・取り込みで解消する見込み）

- **場所**: `src/ui/file-ops/repair-flow.ts:152`（`defaultRepairChoices` は各行の先頭を選ぶ）、この worktree の `src/domain/persistence/repair.ts:189-202`（孤立した歴史の先頭は `DropOrphanHistory`）。
- **再現**（R1）: 孤立した歴史を 1 件含む報告で、既定は `drop-orphan-history`（選択肢は `[drop-orphan-history, materialize-orphan-history]`）。読んで［修復して読み込む］を押すだけで、その歴史の中に残っていた地物の記録が捨てられる。8D 以前は初期値が空で、利用者がどちらかを選ばないと押せなかった。
- **内容**: 本体（`ui-redesign-2026-09`）の `repair.ts` はすでに `MaterializeOrphanHistory` を先頭にしている（所有者の裁定 2026-09-07）ので、取り込めばこの行の既定は捨てない方法になる。8D の検査に孤立した歴史の既定を `drop` で固定しているものは無い（`RepairDialog.test.tsx` に該当なし。確認済み）。ただし本体の新しい方法の文が「どの方法の文にも英字が混ざらない」検査（`RepairDialog.test.tsx:212`）を通るかは **未確認**（実装係の申し送りと同じ点）。
  ただし「先頭＝既定」にしたことで、**今後だれかが選択肢の並びを変えると既定が黙って変わる**のに、「方法が 2 つ以上ある行では、先頭が地物を捨てない方法である」ことを固定する検査が無い。
- **直し方の案**: 取り込み後に、方法が 2 つ以上ある種類（孤立した歴史・階層の食い違い・末端なのに下位を持つ）について「既定は除外しない方法」を固定する検査を足す。取り込みの前にこの worktree 単体で使うことは無いように。

### 8. 名前のある地物を「名前のない地物」と書く（重症度 2）

- **場所**: `src/ui/file-ops/repair-flow.ts:77-92`（`targetNamesOf`）、ドメインの `consistency.ts:468, 495, 529`（時間の矛盾・孤立した歴史・重複した歴史は名前の欄に ID を入れてくる）。

### 9. 一覧の id の表は、別のファイルを開いても消えない（重症度 1）

- **場所**: `src/shell/main/ipc-handlers.ts:560-575`（確定で表を空にしていない）。
- **根拠**（P5b）: 一覧を作ったあと保存先が別のファイルに移っても、前の一覧の id で `openBackup` すると開ける。画面の流れ（一覧 → 選ぶ → 確認 → 開く）の外からは届かず、届いても選んだ世代を開くだけなので害は小さい。
  そのほかの入力（前の一覧の id・世代のパス・`__proto__`・`constructor`・空文字・`toString` で id を返す物・配列・`String` の包み・null・数）は**すべて断られた**（P5）。照合のすり抜けは見つからなかった。
- **直し方の案**: 普通の読み込みの確定と新規で表を空にする（指摘 4 の口と一緒に）。

## 見て、問題が無かったもの

- `openBackup` は文字列以外を読まずに断り、表は `Map` なのでプロトタイプの鍵も通らない。パスは描画プロセスへ渡っていない。
- 世代から開いて確定すると、主プロセスは保存先を未確定へ戻し、描画プロセスも `savePath` を持たない（両側）。直後の Ctrl+S は名前を付けて保存へ落ちる。修復で中止すれば保存先も印も前のまま。保存中に確定が来ても、保存の完了が保存先を巻き戻さない（既存の世代番号の仕組みが効いている）。
- 自動保存のティックは、一覧から開くまでのラッチの間は走らない（`opInFlightRef`）ので、一覧を出している間に自動保存が世代を間引くことは無い（指摘 1 は確認の「保存」だけが起こす）。
- 一覧の板は Esc・［やめる］・閉じるボタンで null を返し、鍵盤の持ち主を名乗る。行の二度押しは、待っている約束（Promise）が 1 回しか解決しないので 2 回開くことにはならない（コードを読んだだけ。画面では見ていない）。
- 設定の「保存とバックアップ」: 範囲外は既定へ倒す（読み）／今の値のまま（併合）。［保存］で打ちかけを書くときも範囲外ならそのタブに留まる。

## 確かめていないもの

- E2E（`inc8d-recovery.spec.ts`）は走らせていない。
- Windows の保存ダイアログの上書き確認の有無（指摘 4）。
- 修復でまだ解消しなかったときのダイアログの出し直しで、選択の初期値が新しい報告に合わせて作り直されるか（板が作り直されるはずだが、画面では見ていない）。
- 読むだけの鍵で「以前の保存から開く」を使ったときのふるまい。

## 総合判定

**revise**。指摘 1（選んだ世代を確認の保存が消す）を直し、その経路を固定する検査を足すこと。重症度 2 のうち 2・3・4・5 は同じ「世代が黙って消える／取り違える」系統なので、まとめて扱うのがよい。6 は世代数の上限 100 を入れたこの増分で目立つようになった重さの問題。7 は取り込みで解消する見込みだが、検査の固定は要る。
