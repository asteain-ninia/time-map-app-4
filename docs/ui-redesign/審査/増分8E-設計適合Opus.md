### S2-1 頂点の削除を新しい関門が断ると、何も言わずに何も起きない

- 重症度: **2**（取り込みの前に直してほしい）
- 場所: `src/ui/vertex-delete.ts:279`（`if (result.status !== PROCESS_STATUS.Committed) return; // Rejected: keep selection.`）、`src/ui/App.tsx:1757-1798`（`runDeleteFunnel` の口に断りを知らせる口が無い）。対して編集ドラッグの経路は `src/ui/map/mount/hit-test.ts:417-422` で理由を出す
- 根拠: 関門は編集の束ね（`createLiveEditBinding`）の `checkConstraints` に入ったので（`consistency-binding.ts:841-842`）、頂点の削除（`vertexDeleteBinding` も `createLiveEditBinding`）にも掛かる。凹んだ穴の頂点を 1 つ消すと、つなぎ直した辺が隣の穴を横切る形になりうる。外周の頂点を消して外周の辺が穴を横切る形も同じ。そのとき関門が断るが、削除の経路は断られた結果を黙って捨てるので、**Delete を押しても何も起きず、状態行にも何も出ない**。
  この経路の黙り方はもとからあった（時刻の検査で断られても同じく黙る）が、増分 8E 以前は制約の断りがこの経路で起きなかった（`checkConstraints` が空を返していた）。**増分 8E の関門で、黙る場面が実際に起きるようになった** のである。進捗 §1 の §5.26 の行（「拒否理由は、ユーザー通知とテスト可能な戻り値の両方で扱う」）と、README B-3 の「頂点の削除…の確定前に U07 へ掛ける」に反する。実機では確かめていない（コードを読んでの判断。未確認）
- 直し方の案: `EditDeletePorts` に省略できる `onRejected(result)` を足し、`runDeleteFunnel` で `announceEditRejectionRef.current` へつなぐ。`e2e/inc8e-ring-gate.spec.ts` に「凹んだ穴の頂点を消すと隣の穴を横切る形では、消えずに理由が出る」を 1 本足す

### S2-3 年を動かして無くなった地物の詳細パネルを「隠す」判断は覆し、閉じることを勧める（残すなら文書の誤りを直す）

- 重症度: **2**
- 場所: `src/ui/property/DetailPanels.tsx:94-96`（その年に居ない地物は `return null` で描かない）、`src/ui/shell/useDrag.ts:42-43`（ドラッグで動かした位置は部品の中の `useRef` にしか無い）、`src/ui/property/detail-panels.ts:47`（新しく開くパネルのずらし幅を、隠れているものも含めた枚数で決める）。文書は `docs/ui-redesign/README.md:155`、進捗 §4 の 8 と §5
- 根拠:
  1. **「在る年へ戻れば同じ位置にまた見える」は事実と違う。** 隠れている間は部品ごと外れるので、ドラッグで動かした位置は失われ、戻ると **開いたときの位置** に出る。利用者がパネルを脇へ寄せて作業していた場合、戻ったときに地図の真ん中へ出てくる。
  2. 隠れているパネルも枚数に数えるので、次に開いたパネルが理由の分からない位置まで右下へずれる（重症度 1 相当）。
  3. **所有者の前例がある。** README の裁定一覧 A（2026-09-07）で、同じ種類の「一時的なしるし」である一覧のチェックについて「**その年に居ない州のチェックは外し、戻しても付け直さない**」と決まっている。詳細パネルも保存しない一時状態で、同じ扱いにそろえるのが自然。設計書 §J.4 #12 の言葉も「パネルが **消える**」。
  4. 隠すことで守っているものは小さい（パネルは読むだけで、閉じても地物を選び直せばまた開ける）。一方、利用者から見えないパネルが状態に残り続けるのは、§5.2「一時状態は全経路で破棄する」の考え方とも合わない
- 直し方の案: README B-3 の「戻し方」の欄にある形（年が変わったときも、その年に居ない地物のパネルを `setDetailPanels` から外す）をそのまま採る。`liveStore` の購読は、1 つ遅れを直すために残してよい。
  **所有者が「隠す」を選ぶなら**、少なくとも README と進捗の「同じ位置にまた見える」を「開いたときの位置にまた出る」へ直し、所有者への問い（進捗 §5）に 9/7 の裁定を前例として添える

### S2-4 色見本で 2 件を見分けられる、という根拠は言い過ぎで、検査もそこを見ていない

- 重症度: **2**
- 場所: `docs/ui-redesign/README.md:148`（「地図の塗りの色なら、重なる 2 面は隣どうしなので自動配色で必ず違う色になる」）、`src/ui/conflict/participant-color.ts`（試しの状態の色を読む）、`src/ui/add/AddPropertyForm.tsx:42-45`（新しく足す面の色は、確定して自動配色が走るまで既定の `#90caf9`）、`e2e/inc8e-conflict.spec.ts:152-159`（題は「色見本で見分ける」だが、2 つの色が **違う** ことは確かめていない）
- 根拠:
  - 自動配色（四色）が保証するのは「**配色したときに隣だった** 面どうしは違う色」だけである。離れていて同じ色だった 2 面を、頂点のドラッグで重ねれば、2 つの色見本は同じ色になる（コードを読んでの判断。未確認）。名前も空なら、行もラジオも見分けがつかない。これは決めごと 1 が守りたかった場面そのもの。
  - 追加の道具で重なったときは、新しい面の色見本は確定前の既定色（`#90caf9`）で、**地図に塗られる色ではない**（確定すると自動配色で別の色になる）。「地図で塗られている色」という説明とずれる
- 直し方の案: E2E に「2 つの色見本の色が違う」を足す。違わないときのために、色見本の横に ①② のような番号札を付け、ミニマップの下見にも同じ番号を出す（8B の「番号札＋面積＋方角」と同じ考え方）。README の根拠の文は「たいていは違う色になる。同じときは番号で見分ける」へ直す
