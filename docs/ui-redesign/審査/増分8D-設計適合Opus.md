#### 2-1 世代から戻したあとに「新規」にすると、名前を付けて保存の既定が元のファイルのまま残る（主プロセスが「新規」を知らない）

- **場所**: `src/shell/main/ipc-handlers.ts:361`（`askSaveTarget`）、`:490-491`（`handleListBackups` の対象 `currentPath ?? restoredSource`）、`src/ui/file-ops/file-commands.ts:272-278`（`newProjectCommand` は主プロセスへ何も伝えない）
- **根拠（コードから。実機での再現はしていない＝未確認）**:
  1. `A.gimoza` の世代を開く → 主プロセスは `currentPath = undefined`・`restoredSource = A`
  2. ファイル →「新規作成」（描画プロセスだけで初期化。主プロセスの `restoredSource` は消えない）
  3. 新規のプロジェクトで Ctrl+S → `needsSaveAs` → `handleSaveAs` → `askSaveTarget` が **`A.gimoza` を既定の名前にして**ダイアログを出す。Enter を押し、OS の「置き換えますか」で［はい］を選ぶと、元のファイルが新規の中身で上書きされる
  4. 同じ状態で「以前の保存から開く」や設定の「保存とバックアップ」を開くと、新規なのに「A.gimoza を保存したときの世代です」「A.gimoza の世代はいま N 個」と出る
- **重さ**: 上書きの直前に OS の確認があり、元のファイルの直前の中身は最新の世代に残る（世代は保存のたびに「書いた後の本体」を写したもの）ので、**データは戻せる**。ただし設計書 V14 の規則 ②「既定のファイル名は元の名前」は **世代から開いたプロジェクトについての規則**で、新規のプロジェクトへ漏れているのは設計の意図から外れる。手順 4 の一覧の対象も、設計書の「いまの保存先」と食い違う（ふつうに A を開いてから「新規」にした場合も、主プロセスの `currentPath` が A のままなので同じ表示になる）。
- **申告**: 進捗文書・README の B-3 に書かれていない（役割表には「主プロセスが『新規』を知らない」という申告があったとあるが、文書の中には見当たらない）。
- **直し方の案**: (a) 「既定の名前を付けるか」を主プロセスの覚え書きで決めず、**描画プロセスの保存文脈（`restoredFrom` の有無）から `SaveRequest` に 1 つ印を載せて**渡す（両側の規則が同じ真実を見る）。または (b) 「新規」の確定時に主プロセスへ保存先と `restoredSource` を捨てる口を 1 本通す（`listBackups` の対象のずれも同時に直る）。どちらでも「世代を開く → 新規 → 保存のダイアログに既定の名前が無い」と「新規のあとの一覧は空」を単体で固定する。

#### 2-2 未保存の確認で「保存」を選ぶと、選んだ世代がその保存の剪定で消えることがある

- **場所**: `src/ui/file-ops/file-commands.ts:249-265`（一覧 → 選ぶ → 確認 → 開く）、`src/shell/io/backup.ts:268`（保存のたびに古い世代を上限まで剪定）
- **根拠（コードから。未確認）**: 世代が上限（既定 10）まで溜まった保存ファイルで、未保存の変更があるまま「以前の保存から開く」→ **いちばん古い行**を押す → 未保存の確認で「保存」→ 本体を保存すると `runBackup` が新しい世代を 1 つ作り、いちばん古い世代を消す → 続く `openBackup(id)` は消えたパスを読みに行き、「ファイルの読み込みに失敗しました。」で終わる。**利用者が戻そうとした世代そのものが、同じ操作の中で消える。**
- **重さ**: 上限まで溜まった状態はふつうに起きる（保存のたびに 1 つ増える）。古い時点へ戻りたい場面ほど古い行を選ぶ。所有者の原則「削除以外でデータが勝手に消えるのは良くない」に当たる。手順の順序自体は設計書（V14 (a) と §J.4 #9）どおりで、**順序から自然に生じる穴を設計も見落としている**。
- **直し方の案**: いちばん軽いのは、主プロセスが **いま発行中の一覧に載っている世代を剪定の対象から外す**（`issuedBackups` のパスを `selectBackupsToDelete` の除外に渡す。次の一覧で表が差し替わればふつうの剪定に戻る）。別案は、確認で「保存」を選んだ場合に保存のあとで一覧を出し直す。どちらでも「上限まで溜まった状態で最古の行 → 保存して続行 → その世代が開ける」を単体で固定する。設計書 §J.4 #9 にもこの注意を 1 行足す。

#### 2-3 この worktree だけで見ると、「持ち主の居ない歴史」の行は「捨てる」が 1 押しの既定になる

- **場所**: `src/ui/file-ops/RepairDialog.tsx:85`（`defaultRepairChoices(rows)`）、`src/ui/file-ops/repair-flow.ts:152`。分岐元の `src/domain/persistence/repair.ts:199-202` は `OrphanHistory` の先頭が `DropOrphanHistory`
