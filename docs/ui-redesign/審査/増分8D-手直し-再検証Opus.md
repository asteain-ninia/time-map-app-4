## (2)(3) 新しい指摘

### 2-1［重症度 2］設定の書き込みが途中で失敗すると、設定ファイルが壊れ、次の起動で世代数が既定の 10 に戻り、次の保存で古い世代がまとめて黙って消える（「値は変えていません」も事実に反する）

- 場所: `src/shell/io/app-prefs.ts:42`（`nodeAppPrefsFs.writeFile` が `fs.writeFile` そのまま）、`:160-175`（`writeAppPrefs`）、`:143-149`（`readAppPrefs` は壊れていれば既定）
- 根拠（探針 R7）: 世代数 50 を書いたあと、別の項目（間隔）を書く途中で `ENOSPC` が起きる形を再現した。Node の `fs.writeFile` はファイルを開いた時点で中身を空にするので、途中で失敗すると先頭の数バイトだけが残る。結果:
  - 戻り値は `{"ok":false, "prefs":{…"backupGenerations":50}, "message":"設定をファイルに書き込めませんでした（ENOSPC…）。値は変えていません。"}`
  - ディスクの中身は `"{\n  \"sh"`。読み直すと **backupGenerations = 10**（既定）。
  - その起動の間は主プロセスの世代数は 50 のまま（書けなかった値は効かせない）。**次に起動すると 10** になり、50 世代あるファイルを次に保存（自動保存でも）した時点で 41 個が確認なしに消える。
  - さらに、次に何かを書けた時点（初回ガイドの「今後表示しない」など）で既定の 10 が併合されて書き込まれ、10 が固定される。
- 電源断・アプリの強制終了が書き込みの途中に来た場合も同じ（空のファイルが残る）。起きる頻度は低いが、手直しの 11 番（書き込み失敗の扱い）の範囲そのもので、結果が「世代がまとめて黙って消える」なので重症度 2 とした。実機で ENOSPC を起こしてはいない（Node の `writeFile` の性質からの再現。**実機は未確認**）。
- 直し方の案: プロジェクトの保存と同じく、一時ファイルへ書いて fsync してから名前を替える（`atomicFs` の形）。あわせて、ファイルが **在るのに読めない** ときは世代数を既定へ倒さず「間引かない（上限なし扱い）」にして画面で知らせる、のも候補（既定へ倒すと、利用者が既定より多くしていた分が消える）。

### 2-2［重症度 2］E2E「V12 の④」は保存の待ち方の競合で、再試行なしでは毎回落ちる（全件ゲートでは再試行 1 回が隠している）

### 2-3［重症度 2・司令塔／所有者の判断］開いているファイルが無いときに世代数を下げると、確認が出ないまま、あとでファイルを保存した時点で古い世代がまとめて消える

- 場所: `src/ui/settings/useBackupSettings.ts:225-233`（`shrinkFor` は世代の数が分からないと `null` を返し、確認を挟まない）、`src/ui/settings/SettingsDialog.tsx:747-751`・`:822-825`（注意文だけ）。E2E 自身も `e2e/inc8d-recovery.spec.ts:247` で「ファイルを開く前なので…確認も出ない」と書いている。

- 直し方の案: 下げたときは **いつも** 確認を挟む（数が分かれば数、分からなければ「次にそれぞれのファイルを保存したときに、超える分の古い世代が消えます」）。E2E の `applyBackupSettings`（`:119-120`）はすでに「確認が見えたら押す」形なので、既存の E2E は崩れない。下げても既存の世代はすぐには間引かない案（記録 11.4 の 2 つ目）に替えるなら、この指摘ごと消える。

## 見て問題が無かったもの（短く）

- **手直しで足した口**: `CountBackupFeatures` は直前の一覧の id しか受けず、表に無い id は null。`CountBackups` はファイルを開かない。`EndBackupChoice`・`ForgetSaveTarget` は信用しない送り手からは何もしない。preload は `pickSource` の真偽だけを組み立て直して渡す。
- **1 回の終わりの出口**: `openBackupCommand` は `try … finally` で、一覧の取得失敗・やめる・未保存の確認でやめる・保存失敗・開く失敗・修復でやめる、のどれでも `endBackupChoice` を呼ぶ。主プロセスも `handleOpenBackup` の `finally`・読み込みの確定・新規で表を空にする。保存は守りの集合を書き込みの前に取るので、書き込みの途中で合図が来ても影響しない。自動保存も同じ `runSave` を通るので守られる。
- **新規**: `ForgetSaveTarget` は保存先・戻した元のファイル・基準の候補・一覧・確定待ちを捨て、確定の世代番号も進める（書き込み中の保存が保存先を戻さない）。描画プロセスは同じ同期処理の中で送るので、次の保存より先に届く。
- **修復したら未保存で始める**: `reflectLoadedProject` の `notOnDisk` は clean の基準点を作らない。基準点を作り直すのは `markProjectSaved`（保存の成功）と `resetToDomain` だけで、`hydrateSettings` には本番の呼び出し元が無い（Grep で確かめた）。読み込みの流れのあとで黙って clean に戻る経路は無い。普通のファイルを開いて修復した場合は従来どおり clean（元のファイルはディスクに残るので、閉じても失うのは修復だけ。依頼書の決定の範囲どおり）。
- **設定の［適用］と［保存］**: 書き込み中は欄とボタンを止め、二重の［適用］は落とし、待っている間に打った値を応答で上書きしない（下書きの版）。［保存］は書けるまで待ち、確認待ち・失敗なら閉じない。確認で「やめる」と世代数は保存してある値へ戻る。消える数の式 `count + 1 − next` は `selectBackupsToDelete` の動きと合っている（R2 の 6 → 3 のとおり）。
- **下限 2**: 契約の範囲定数から主プロセスの読み込み・画面の検証・欄の `min` が引いている。古い設定の 1 は 2 として読む。

## 総合判定

**revise**

重症度 3 だった 2 件（戻そうとした世代が確認の保存で消える／壊れた元のファイルから世代へ辿れない）は、主プロセスの単体・実アプリ・実データのどれで当て直しても塞がっていた。手直しで足した口と「一覧に出した世代を守る」形にも、世代が永久に溜まる・守られずに消える漏れは見つからなかった。

ただ、手直しの項目そのものに 2 つの穴が残っている。

- 2-1: 設定の書き込み失敗の扱い（手直しの 11 番）が、途中で失敗したときにファイルを壊し、次の起動で世代がまとめて黙って消える経路を残している（所有者の原則に当たる）。
- 2-2: 保存の待ち方（手直しの 14 番）が新しい競合を作り、V12 の④ が再試行なしでは毎回落ちる。

この 2 件を直せば accept でよい。2-3・2-4 は確認の範囲と入口の置き方の判断なので、司令塔か所有者の裁定に回す。
