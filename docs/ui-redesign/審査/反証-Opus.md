## 1. 重大度 4 — 設計を成立させない

### B-1. 錨を増やす設計と、保存形式の「錨 1 本＝スナップショット全体の複製」が正面から衝突する（severity 4）

**何を確かめたか。** `src/domain/persistence/schema.ts:337-343` の `anchorSnapshotSchema` は

```ts
export const anchorSnapshotSchema = z.object({
  features: z.array(featureSchema),
  vertices: z.array(vertexSchema),
}).strict()
```

で、**錨 1 本ごとに、その履歴が持つ地物の配列と頂点の配列を丸ごと**持つ。`serialize.ts:265-269` も `vertices: serializeVertexStore(snapshot.vertices)` とそのまま書き出す。`applyPastEdit` が新しい錨を作るときは `resolveAt` の実効スナップショットを土台に `anchorFor(shared.features, shared.vertices, ...)` を作る（`apply-proposal.ts:1516-1545`）ので、**新しい錨 1 本＝その履歴のジオメトリの完全な複製**になる。

**実データで測った（正準ファイルのコピーを zip として読んだだけ）。**

| 実測 | 値 |
| --- | ---: |
| `manifest.json`（非圧縮） | **5,384,927 バイト** |
| 履歴（＝錨列） | 689 本。**全部が錨 1 本ずつ** |
| 錨 1 本あたりの平均 | **8,604 バイト** |
| 最大の錨 1 本 = `agg-02` **デーレ共和国**（61 地物・3,067 頂点を 1 つのスナップショットに持つ） | **306,229 バイト** |
| 同 `agg-03` 正統ノル王国（15 地物・1,082 頂点） | 101,721 バイト |
| 同 `agg-01` ラヴィエンド・ウィル同君王国（13 地物・847 頂点） | 81,839 バイト |

**掛け合わせると何が起きるか。**

- 設計書 §D.3 の中核は「保存はすべて現在時刻に効き、その年に錨が無ければ**自動で新しい錨が生まれる**」である。
- 裁定 2(b) は「**選択中の 1 地物だけでも印が極めて多い**前提で設計せよ」と言い、設計書 §F.2 はそれを「**1 地物あたり 5 万錨**」と読んで受け入れ条件にしている。
- **デーレ共和国の子 60 件のどれか 1 件の名前・種別・親・色を、新しい年で 1 回直すたびに、manifest が 306 KB 増える。** V6（南ケナ州を 1200 年に独立させる）はまさにこれで、1 回で 306 KB。設計書 §K の増分 2 の探索的バグ狩りは「10 地物 × 5 年で錨を作る」と書いているが、対象が集約の子なら 1 回で +15 MB になる。
- 要件の想定規模（5,000 地物 × 平均 10 錨、`要件定義書.md:425`）をそのまま当てると manifest はおよそ **54 MB**（現状 5.4 MB の 10 倍）。読み込みは現状 5.4 MB で 1.8〜2.2 秒（現状分析 §7.1）なので、**20 秒級**になる。
- §F.2 が受け入れ条件にした「1 地物 5 万錨」を平均値で見ると **430 MB**、デーレ共和国で見ると **15 GB** の manifest になる。

**設計書のどこが抜けているか。**

- §F.2 は 5 万錨を **描画の 16ms** としてのみ扱い、規則 1〜7 のどれも保存量・読み込み時間・メモリに触れていない。§L.1 の不確かさ 1 も「密度集計を実測していない」だけで、同じ問題を見ていない。
- §J.1 は K-9 を「**適合**。本設計が保存する新しい概念は 0 個」としている。**概念を足していないのは事実だが、K-9 は「保存形式を凍結する」制約でもある**（`docs/現状.md` B3: スキーマ版が完全一致しないファイルは拒否）。したがって「**いまの形式が、この設計が作る量の錨を収容できるか**」という問いに答えないと K-9 適合の主張は成立しない。**この設計は、いまの形式が持てない量の錨を作ることを目的にしている。**
- 増分 2 の受け入れ条件（`03-実装計画.md` §2）は「錨が 1 本 → 2 本になる」「0 年へ戻すと元の名前が出る」までで、**サイズも読み込み時間も測らない。**

**直し方（3 つセットで）**

1. **増分 2 の受け入れ条件に量を入れる**: 「デーレ共和国の子 10 件に 5 つの年で錨を作ったあと、manifest の増分と保存・読み込みの秒数を記録する」。増分 2 は変更量が小さいので、**ここが最も安く事実を掴める場所**である。
2. **§N に裁定項目を 1 つ足す**: 「歴史を刻むほど保存ファイルが膨らむ。錨を『前の錨からの差分』で持つ／頂点ストアを錨をまたいで共有する、といった保存形式の作り替え（＝スキーマ版を上げ、既存 `.gimoza` の変換が要る）を認めるか」。**K-9 は「勝手に足すな」であって「絶対に変えるな」ではないが、これは所有者の裁定なしには動かせない。** 認めないなら、裁定 2(b) の「5 万錨」を現実的な上限（例: 1 地物 200 錨）に引き直してもらう必要がある。
3. **集約の子を直すと親の錨が丸ごと複製されることを §A.3・§D.3 に明記する。** 「まとめ役の地物の下にあるものを直すと、そのまとめ役が持っている 60 件ぶんの形が、その年の記録として丸ごともう 1 部作られます」という日常語の説明を、§N-2 の裁定文にも入れる。所有者は「どの年に何を記録するか」を選ぶとき、この費用を知っている必要がある。

### B-2. 集約の子 86 件について、錨レーンの仕様が無い。V6 の合格条件③が満たせない（severity 3）

**事実。** 実データを数え直した: **地物 775 / 履歴 689 / 自分の履歴を持たない地物 86**（＝ 3 つの集約の子ちょうど全部）。`SidebarContent.tsx:86-91` の `anchorSeriesOf` は

```ts
const history = getRoot().histories.find((h) => h.featureId === featureId);
return history?.series ?? null;
```

なので、**86 件は必ず `null`**。設計書 §F.1 の C2(b) はこれを「錨の欄が消える」問題として正しく捉えている。

**しかしレーン側が抜けている。** §C.7 は「**描くのは選択中の 1 地物だけ**」、§F.2 の規則 1 も「選択中の 1 地物の錨だけ」としか書いていない。**集約の子を選んだときにレーンが空になるのか、親の系列（60 人ぶんの変更が混ざったもの）を出すのかが、どこにも書かれていない。** どちらも問題がある。

- 空にする → **V6 の合格条件③「独立した当人の画面にその事実が現れる」が満たせない。** §E.1 の V6 は「確定後、時刻レールの錨レーンに 1200 年の印が増える」「**当人の画面に事実が現れる**（合格条件③）」と明記しているが、南ケナ州はデーレ共和国の子なので、その錨は**親の系列**に立つ（設計書自身が同じ V6 の中で「変更は親のデーレ共和国の錨として記録される」と書いている）。**同じ段落の中で自己矛盾している。**
- 親の系列をそのまま出す → 裁定 2(a)「印を出すのは**選択中の地物だけ**」に反する（60 件ぶんの他人の変化が混ざる）。

**あわせて §F.2 規則 3 も成り立たない。** 「`DomainProject.histories` は平坦な配列なので、選択中の 1 地物の系列を引くのは 1 回の検索で済む」と書いてあるが、86 件については `findHistoryContaining`（時刻ごとにスナップショットの中身を見る封じ込め検索）が要る。

**直し方**: §C.7 に 1 行足す。「まとめ役の下にある地物を選んだときは、**親の系列のうち、その地物に関わる錨だけ**をレーンに出す（どの錨がその地物に関わるかは、前後の錨のスナップショットを比べれば分かる。§C.6 の錨表で同じ計算を既にやると書いてある）」。親の系列をそのまま出す案を採るなら、裁定 2(a) の例外として §N に出して裁定を仰ぐ。

### B-3. K-6 の守り方が §D.1 の導出式と矛盾している。裁定 1 が「必ず書け」と言った、まさにその点（severity 3）

**§D.1 の導出式**（設計書 1,010 行目付近）:

```
mode = （面／線／点 の道具を持っている）? 'add' : 'edit'   ← FR-75 の排他はここで保たれる
```

**この式には `view` が出てこない。** ところが `EDIT_MODE` は `{ View: 'view', Add: 'add', Edit: 'edit' }`（`src/ui/state/session.ts:18-24`）で、`canEdit(mode)` は `mode !== EDIT_MODE.View` の 1 行（`permissions.ts`）。つまり **§D.1 のとおりに実装すると `canEdit` は常に true になり、K-6（読み取り専用での一括無効化）が丸ごと消える。**

§A.1 は別の場所で「鍵＝`EDIT_MODE.View` と読み替えるだけ」と書いているが、**2 つの記述が別の節にあり、1 本の式になっていない。** 実装者がどちらを写しても動く形になっていないので、これは文言の問題ではなく状態機械の欠陥である。裁定 1 が「K-6 をどう守るかは設計書に必ず書け」と指定した唯一の点でここが割れているのは重い。

**直し方**: §D.1 の式を 1 本にする。

```
mode = 鍵が閉じている        ? 'view'
     : （面／線／点の道具）  ? 'add'
     :                        'edit'
```

そして「鍵 → mode → `canEdit` の順で流れる。鍵は mode の値を決める唯一の入力であり、`canEdit` の実装には触らない」と書く。あわせて §D.2 の遷移表の「鍵を開ける／閉める」行に「mode が view ⇄ add/edit に変わる」を明記する。

### B-4. 増分 2 を増分 6 より先に出すと、時刻の粒度の汚れが「データ」に固着する（severity 3）

**現状**（現状分析 C8-3）: 時間帯のスライダー・再生・範囲外クランプはすべて**年月日**を返し、1 回触るだけで現在時刻が「5080年12月31日」になる。実データの錨は全 689 本が年だけ。

**設計の順序**: 増分 2 で「保存は必ず現在時刻に効く」を入れる。**年への量子化（レール由来の時刻を年に丸める）は増分 6 の中身 4**。増分 5 → 6 は増分 2 の 3 つ後。

**したがって増分 2〜5 の間、うっかりスライダーに触れた状態での保存が「5080年12月31日」に開始時刻を持つ錨を作り、それが `.gimoza` に入る。** これは U-14（月日を勝手に補わない）に反するデータで、しかも設計が「保存のたびに錨が生まれる」形に変えた直後なので、**現状より確実に増える**。後から年へ直す導線は `changeStart` だけで、その UI（§C.7 の右クリック「この錨の開始年を変える」）も増分 6 以降にしかない。

設計書 §D.3 の「危険と、その打ち消し方」は「行き先を先に見せる」だけで、**行き先の年そのものが汚れている場合**を見ていない（バッジには「5080年12月31日 ｜ 錨を新しく作ります」と正直に出るが、それは危険の表示であって防止ではない）。

**直し方（どちらか）**

- (a) **年への量子化を増分 2 に前倒しする。** レール（現行の時間帯）から来る時刻を年に丸めるのは小さな変更で、増分 6 のレール作り直しとは独立に入れられる。設計書 §C8 の (3) が「粒度が汚れない」を増分 6 に置いているのは、レールの作り直しと束ねたからで、必然ではない。
- (b) 増分 2 の保存ボタンを「現在時刻が年ちょうどでないときは押せない（脇に理由と［年に丸める］ボタン）」にする。§H.5 の「無言の失敗を次の一手ボタンにする」の作法にそのまま乗る。

### B-5. V6・V7 の「素性欄の親欄で所属を変えて保存する」経路の契約が未定義（severity 3）

**事実。** 親の変更は `propertyEditDispatch`（`App.tsx:3039-3080`）を通らない。この関数が扱うのは `createBasicAttributes(name, startYear, endYear)` と `createColorInfo(...)` だけで、**親（`parentId`）も種別ラベルも触らない。** 所属変更は `applyAffiliationProposal`（`apply-proposal.ts:1414`）という別の経路で、確定に 2.8 秒かかり、直轄領の生成を伴い、**古い親と新しい親の両方の系列に錨を立てる。**

**設計書は §C.6 で親欄に所属変更の 3 択を置き、§E.1 の V6 で次のように数えている。**

> 素性欄の親欄の［最上位へ］(2.65)｜**［1200年に錨を作って保存］**(1.30)｜M(1.35) ＝ 13.18

ここで書かれていないことが 3 つある。

1. **［最上位へ］を押した時点で所属変更が確定するのか、保存まで保留されるのか。** §D.3 と N-46 は「押さないと保存されない側に揃える」としているが、所属変更は自前の確定手順（§C.2-22 の作業ダイアログ、G-4 の直轄領の名前入力、進行中の表示）を持つ操作である。
2. **保存ボタンの文言「1200年に錨を作って保存」が、実際には 2 つの系列に錨を立てる操作をどう表すのか。** 文言は 1 地物 1 錨を約束しているが、実体は違う。
3. **V7 が計上している「確定 2.8 秒・進行中の表示」と「直轄領の名前を上書きできる欄つきの予告」が、V6 では丸ごと落ちている。** 同じ操作なのに 2 つのシナリオで手順が違う。

さらに `03-実装計画.md` の増分 4 中身 8 は「親欄に所属変更の 3 択（**G-3 の入口だけ。実体は増分 7**）」としているので、増分 4 の完了時点で V6 のこの手順が通るのかどうかも読めない。**V6 は本設計の主戦場と宣言されているシナリオなので、ここが未定義なのは重い。**

**直し方**: 素性欄の「保存」の対象を **名前・種別ラベル・見た目・詳細文書**に限ると宣言し、**親欄の 3 つの操作は押した瞬間に所属変更の確認へ入る**（＝ §C.4 の所属の道具と同じ手順・同じ確認・同じ進行表示に合流する）と §C.6 と §D.3 に書く。そのうえで V6 の手順と秒数を引き直す（確認 1 手と 2.8 秒が乗る）。

**直し方**: §C.2 の 26 番に規則を足す。「入力が数字だけなら年として扱い、年へ飛ぶ候補だけを出す。文字を含むなら地物名の**前方一致 → 部分一致**の順に並べ、同名があれば〈親名〉を添える（台帳と同じ規則）。コマンドは `>` を頭に付けたときだけ。」

## 6. まとめ

**verdict = revise。** severity 4 が 1 件、3 が 4 件。

- **B-5（3）** 素性欄の親欄で所属を変えて保存する経路の契約が未定義（V6・V7 の主手順）。
