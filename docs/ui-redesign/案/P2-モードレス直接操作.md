# P2 モードレス＋直接操作＋段階的開示（Figma／Illustrator 流）
執筆: Opus

この文書は gimoza の UI を白紙から設計し直した案の 1 つである。レンズは「**モードを無くし、直接操作と段階的開示で組む**」。5 名の設計者が独立に書いた案のうちの 1 本であり、他案は読んでいない。

根拠はすべて `docs/ui-redesign/01-現状分析.md`（以下「現状分析」）の節番号、`docs/ui-redesign/調査/` の各報告、`ファイル:行`、評価シナリオ番号で示す。内部の造語は日常語に言い直す。

## A. 設計思想と、3 つの論点への立場

### A.0 一段落の設計思想

**この案は「道具を持ち替えても、選んでいるものを失わない」ことを設計の中心に置く。** 現状の gimoza は、モード 3 個 × ツール 11 個の二段構造の上に立っており、そのどちらを触っても選択が消える（`store.ts:1399-1401`／`store.ts:1405-1414`）。その結果、**「探す → 選ぶ → 直す」という人間が自然に踏む順序が、必ず一度失敗する**（現状分析 §2 の C5、報告 C §1-2）。この案は、モードという上の段を取り払ってツールを 1 段にし、ツールを持ち替えても・読むだけの鍵を外しても・時間を動かしても、選択と視点は保たれるようにする。そのうえで、画面を「左＝道具（常に同じ場所・同じ大きさ）／中央＝地図（最大化）／右上＝索引（階層ツリー）／右下＝素性（選択に追従するインスペクタ）／上＝いま持っている道具の設定 1 行／下＝時間」に固定し、**どの部品も「いま選んでいるもの」に追従して中身だけが差し替わる（器の寸法は動かない）**。使わない機能は畳んでおき、必要になった文脈でだけ開く（段階的開示）。全機能への到達は、常設の部品 ＋ 右クリック ＋ コマンドパレット（Ctrl+K）の 3 経路で保証する。**合格条件は「機能があるか」ではなく「画面のどのボタンから何クリックで届くか」**（現状分析 §2.0）なので、この案は §E で評価シナリオ 15 件すべての手順と操作数を書く。

### A.1 論点 1 — 追加／編集モードの排他（FR-75, must）を残すか

**この案の立場: モードの段は画面から消す。ただし FR-75 の条文は破らずに済む道がある。**

FR-75（`docs/要件定義書.md`、現状分析 §4.1）は「追加モードと編集モードは排他。ツールバーのトグルで切替。各モードで関連ツール群が出る」と定める **must** 要件である。一方、比較調査（報告 F 定石 1）は「同種の道具（Inkscape / Illustrator / Figma）はモードという上位の段を持たず、ツール 1 段で、切り替えても選択を失わない」とし、15 個の定石のうち**唯一 must 要件と正面衝突するもの**として挙げている（現状分析 §5.4、§9.2）。

この案の提案は次の 3 段構えである。

| 案 | 中身 | FR-75 との関係 | この案の評価 |
| --- | --- | --- | --- |
| **甲（推奨）** | **モードをツール選択から導出する。** 画面にはモードの段が無く、ツールが 1 段だけ並ぶ。ストア内部の `mode` は「面／線／点を描くツールを持っている間は `add`、それ以外は `edit`」と**ツールから機械的に導かれる**。したがって `add` と `edit` が同時に立つことは構造上あり得ず、切替はツールボタン（＝ツールバーのトグル）で起きる | **条文どおりに読める。** 「排他」は保たれ、「ツールバーのトグルで切替」も保たれ、「各モードで関連ツール群が出る」だけが「全ツールが常に出る」に変わる。**ここだけが裁定を要する差分** | **主案。** 実質モードレスでありながら、`aria-pressed` を使う E2E 39 ファイル（T-4）とストアの契約を大きく壊さずに済む |
| 乙 | モードを完全に廃止し、`mode` という状態自体を消す | 条文に正面から違反。D56（要件も誤りうる／黙って直さずユーザーへ）に従い裁定必須 | 甲との差は内部だけで、利用者から見た画面は同一。**甲で得られるものが乙でも同じなら、要件を壊さない甲を採る** |
| 丙 | 現状維持（モード 3 ボタンを残す） | 適合 | **採らない。** 報告 C の実測で、モード切替は 1 タスクあたり 2.65 秒の固定費であり、かつ「探してから編集モードへ」という直感的順序が必ず 1 回失敗する（現状分析 C5、報告 C §1-2）。この 2 つは丙のままでは消えない |

**「表示専用」だけは残す。** ただし意味を変える。現状の「表示専用モード」は 3 状態の 1 つで、押すと編集モードに着地するという否定形のボタンだった（現状分析 §1.5）。この案では**モードではなく「読むだけの鍵」という 1 個のトグル**にし、次の性質を持たせる。

- 鍵が掛かっている間は、**編集経路を 1 つの関門で一括無効化する**（K-6 の実装原則をそのまま踏襲。現状 N-03 で「地物を削除」だけがこの関門を通っていないので、そこも同じ関門に入れる）。
- **鍵が掛かっていても、地図クリックで地物を選び、インスペクタで素性を読み、一覧を辿り、時間を動かせる。**（§7.4-4 の非目標を覆す。現状分析 §5.1 が「最有力候補」と評価している項目）
- **鍵の開け閉めで選択は消えない。** 現状の `setMode` が選択を全消しする契約（`store.ts:1399-1401`）を、ここで変える。
- 鍵が掛かった状態で編集ツールを押したときの扱いは**裁定候補**（§L-3）。この案の既定は「押した操作を編集開始の意思表示とみなして鍵を外し、アプリバーの鍵表示を目立つ色に変えて、ステータスバーに『編集できる状態にしました』を**消えない形で**残す」。より安全側の代替は「鍵は手でしか外せない。ツールを押したら『鍵が掛かっています』とオプションバーに出す」。

FR-75 の裁定を仰ぐときの文面案は §L-1 にまとめた。

### A.2 論点 2 — 時間軸に既存の錨の印を描くか

**この案の立場: 描く。ただし「しおり」とは別物であることを設計で担保し、裁定を仰ぐ。**

現状分析 §5.2 のとおり、非目標 §7.4-1（D32、ユーザー本人が 2026-06-21 に撤去を決めた）が禁じたのは「**利用者が自由に置くしおり**」であり、この案が描くのは「**すでにデータの中にある錨（地物の歴史の節目の記録）を、軸の上に映すこと**」である。両者の違いを設計側で担保する:

- **保存形式に何も足さない**（K-9 適合）。描く材料は既存の錨列だけで、印の位置・色・表示/非表示のどれも `.gimoza` に書き込まない。
- **利用者は印を置けない・消せない・名前を付けられない。** 印は錨の写しなので、錨が増えれば増え、消えれば消える。「印を置く」操作を画面に一切作らない。
- **飛べるが、栞ではない。** 印をクリックするとその年へ移動するが、これは「一覧の行をクリックすると視点が合う」（U-4）と同じ「データの居場所へ行く」操作である。

**規模への備え（想定 5,000 地物 × 平均 10 錨 ＝ 5 万錨、現状分析 §7.1）。** 全部を点で描くと破綻するので、帯を 3 層に分ける。

| 層 | 何を描くか | 5 万錨での重さ |
| --- | --- | --- |
| 下層 | **年ごとの錨の密度**（淡いグレーの濃淡）。軸 1px ≒ 8 年なので、1px に何本の錨が集まるかを濃さで出す | 年単位のヒストグラム（範囲 0〜10000 なら要素 10,000 の配列）を 1 本だけ持ち、編集で差分更新する。5 万錨でも走査は 1 回 |
| 中層 | **選択中の地物の親・子の錨**（中間の濃さの短い縦線） | 実データの階層は 1 段（集約 3 件・子 86 件）なので最大 87 本 |
| 上層 | **選択中の地物自身の錨**（濃い縦線＋ホバーで年と内容） | 目標規模でも 1 地物あたり 10 本前後 |

**E2E との衝突**: `ux-cluster.spec.ts:216-219` が「栞 UI が存在しないこと」を固定している（現状分析 §5.1）。この案の印は栞 UI ではないが、**セレクタが `[class*=marker]` 等の広いパターンなら落ちる**。裁定が下りたら、このテストを「利用者が栞を追加する操作部品が存在しないこと」に書き換える（§K の増分 6）。

### A.3 論点 3 — 削除の方針（現状分析 §6.3）

**この案の立場: 現在の「参照を掃除してから消す」方式を正本として維持し、`judgeDeletion` は「拒否」ではなく「消す前に何が起きるかを見せる」用途に結線する。**

現状分析 §6.3 は、`judgeDeletion`（`deletion/eligibility.ts`、G-16）が「参照があれば拒否する」という**現在の実装とは別方針**の実装であり、FR-41 の条文は両方の読み方を許すので裁定が要る、としている。

この案が「拒否」を採らない理由:

1. **架空世界の編纂では、参照があるものを消したい場面のほうが多い。** 「1500 年に滅んだ国を、そもそも無かったことにする」は正当な作業であり、参照を理由に断られると回避手段が無い（親の錨を先に全部直す、という到底やれない手順になる）。
2. **現在の実装は既に安全側で動いている**（`App.tsx:2150-2151` のコメントが「全時刻を掃いて参照を掃除してから消す」と明言）。方針を変えると、既に正しく動いているものを壊す。
3. **本当の問題は「消える前に何が消えるか分からない」ことのほうである。** 現状は錨の削除・リングの削除・頂点の削除に確認が無い（N-05）。

したがってこの案は、削除を **「影響プレビュー付きの 1 段確認」** に統一する。

```
┌ 削除の確認 ───────────────────────────┐
│ 「アアウェン州」を削除します。                        │
│                                                       │
│ 一緒に消えるもの                                      │
│   ・この地物の歴史の記録（錨）2 件（0年 / 1200年）    │
│   ・頂点 412 個                                       │
│ 他から参照されているところ                            │
│   ・デーレ共和国 の 2 つの記録から、子として外れます  │
│     （0年・1200年）                                   │
│                                                       │
│ ［削除する］  ［やめる］     ※ Ctrl+Z で戻せます      │
└───────────────────────────────────┘
```

この「一緒に消えるもの／他から参照されているところ」は `judgeDeletion` / `hasReferencesInAnchor`（G-16）の戻り値をそのまま文章にしたものである。**同じ器を、錨の削除・リングの削除・複数頂点の削除にも使う**（N-05 の 3 件がまとめて片付く）。取り返しのつかない操作の確認は 1 種類だけにする。

## B. 画面構成

### B.0 設計の骨格

**現状の大枠（左＝道具、中央＝地図、右＝情報、下＝時間）は良い設計として引き継ぐ**（現状分析 §9.3 末尾「作り直しても骨格は変えなくてよい」）。変えるのは中身と寸法である。

寸法の決め方は 3 つの原則に従う。

1. **縦のクロームを削って地図を稼ぐ。** 現状は 1280×800 で縦のクロームが 310.4px（38.8%）あり、地図が窓の 45.0% しかない（現状分析 §1.2）。この案は縦クロームを **216px 固定**に落とす。
2. **窓幅が変わっても行の高さが変わらない。** 現状は上部バーが `flex-wrap` で折り返すため、窓を横に伸ばしただけで地図の上端が最大 95px 動く（§1.3）。この案は上部の 2 行をどちらも**固定高**にし、あふれる部品は折り返さずに固定幅の「≫」ボタンへ畳む。
3. **選択状態で寸法が変わらない**（K-3）。中身が変わる枠は、すべて**固定幅の器に入れて中身だけ差し替える**（現状分析 §5.3 の E-3 が勧める方法。今の「押せないボタンを 400px ぶん常設する」方式をやめる）。

### B.3 800×600（FR-114, could）

```
縦: 32 + 40 + 384 + 120 + 24 = 600
横: 88 + 432 + 280 = 800
地図 432 × 384 = 165,888 / 480,000 = 34.6%（現状 22.2%）
```

- **横にあふれない。** シェルの最小内容幅は「道具 88 ＋ 地図の最小 240 ＋ 右パネル 280 ＝ 608px」で、800px を下回る。現状の「右端 20.6px が永久に到達不能」（§1.2）は構造的に起きない。理由は、アプリバーの部品を `flex-shrink:0` の固定幅ブロックにせず、**優先度の低いものから「≫」に畳む**からである（畳んだ後の最小幅は 320px）。
- **道具レールは 384px に収まる。** ボタン 80×32 が 10 個、隙間 3px、群の隙間 8px（4 群 → 3 箇所）、上下余白 4px ＝ 320 + 27 + 12 + 8 = **367px** < 384px。現状の「8 個中 5 個が窓の外」（§1.5）は起きない。
- FR-114 は could なので必達ではないが、**この案では追加コストなしで満たせる**。

### B.4 窓幅で折り返さないことと、上部の帯が伸縮しないこと（K-3）の担保

| 帯 | 高さ | 中身が変わっても高さが動かない仕組み |
| --- | ---: | --- |
| **① アプリバー** | 32px 固定 | 子要素はすべて `height:24px` の 1 行ブロック。`flex-wrap: nowrap`。世界名／ファイル名は `flex:1 1 auto; min-width:0; overflow:hidden; text-overflow:ellipsis` で**省略記号にする**（折り返さない）。経度ジョグは **176px 固定枠**（U-25 の「現在値を数値で常に表示・直接入力できる」を、幅を動かさずに満たす。§J で詳述）。鍵は **96px 固定枠**で、掛かっている／外れているの 2 状態とも同じ幅の文字（「読むだけ」「編集できる」＝ともに 5 文字ぶんの枠）を使う |
| **② オプションバー** | 40px 固定 | 4 つの固定幅ブロックに分ける。**道具名 112px（固定）／対象の表示 240px（固定）／道具ごとの設定（可変・あふれたら「≫」に畳む）／確定ボタン 176px（固定）**。**対象が 0 件でも 240px の枠は残り、「選んでいません」と薄く出る。** これが K-3 の要点で、現状が「押せないボタンを 400px ぶん常設する」ことで守っていた不変条件（`GlobalDepthControl.tsx:77-88`）を、**枠を残して中身だけ差し替える**方式に置き換える（§5.3 の E-3 が勧める方法）。確定ボタンの枠も、確定が要らない道具のときは空の 176px として残る |
| **⑥ 時間軸** | 120px 固定 | 現状は入力エラーが 1 行出ると 200 → 220px に伸びる（§1.3、報告 06 §6.11）。この案では**エラーは軸の中に行を足さず、ステータスバーに出す**（後述 §C.7）。「単位: 年」の文字（U-27、消してはいけない）は操作行の粒度セレクタのラベルとして残す（「年 ▾」）ので、右端の目盛りと重ならない |
| **⑦ ステータスバー** | 24px 固定 | 3 区画（左＝座標／中央＝選択／右＝保存）とも固定幅。文字は省略記号 |

**「≫」に畳む順序**（優先度の低いものから）: グリッド → 階層深度 → 表示制御 → 個別フォーカス（深掘り）→ 吸着。畳まれた項目は「≫」を押すとポップオーバーで出る。**畳む判定は窓幅だけで決まり、選択状態には一切依存しない**（K-3）。

現状分析 K-2 は「地図に重なる部品はクリックを奪わない」を、3 回の実害を根拠に不変条件としている。この案は地図の中に 2 つだけ部品を置く。

| ズームと全体表示 | 右下から 16px 内側 | 3 ボタン縦積み 40×40、計 40×128 | 層は `none`、**ボタンだけ `auto`** |
| 縮尺バー | 左下から 16px 内側 | 160×20 | **`none`**（表示のみ・押せない） |

**行の高さ 26px 固定・折り返し無し**（省略記号）。現状は 31.6 / 49.2 / 51.6px の 3 種類で、113 行（14.6%）が 2 行になっていた（現状分析 §0 の #1）。**26px 固定にすると 1600×1000 の一覧 352px に 12 行、1280×800 の 260px に 9 行が入る。** 現状（9〜14 行）と同程度だが、1 行が運ぶ情報が「名前 1 個」から「色・名前・種別・親（必要時）・表示・ロック・対象」の 7 個に増える。

**仮想スクロール**（見えている行だけ描く）にする。5,000 件でも DOM に載るのは 15 行前後。現状は 775 行を全部 DOM に置いてスクロール全長 29,086px になっている。

**表示制御パネルはここから追い出す。** 現状は可変長の一覧の後ろに固定パネルを置いたせいで `offsetTop` 28,546px（63 画面ぶん下）になっていた（`SidebarContent.tsx:190`、C7）。この案では表示制御はオプションバーの「表示 ▾」ポップオーバーに移す。**データが増えても設定が遠ざからない。**

## D. 状態機械

### D.1 状態の全体像

```
                 ┌─────────────────────────────┐
  読むだけの鍵    │ locked（既定） ⇄ unlocked                   │  ← 1 本のトグル。K-6 の関門
                 └─────────────────────────────┘
                            │ 選択は保持される（現状は全消し）
                            ▼
                 ┌─────────────────────────────┐
  道具（1 段）    │ 選択 / 頂点 / 面 / 線 / 点 / リング / ナイフ /  │
                 │ 穴あけ / 所属 / ものさし  （常に 1 つ、既定＝選択）│
                 └─────────────────────────────┘
                            │ 選択は保持される（現状は全消し）
                            ▼
                 ┌─────────────────────────────┐
  道具の手順      │ idle → armed（対象を掴んだ）→ working（描いている）│
                 │      → pending（確定待ち）→ idle                │
                 └─────────────────────────────┘
                            │ 手順の途中の状態だけは全経路で捨てる（K-5）
                            ▼

  選択（ドメイン）│ activeFeature: 0 or 1（FR-79 must）             │
                 │ selectedVertices: Set                           │
                 │ markedFeatures: Set（結合・連邦化の「対象」。別概念）│
                 └─────────────────────────────┘

  内部で導出されるもの（画面には出ない）:
    mode = （面/線/点を持っている）? 'add' : 'edit'     ← FR-75 の排他はここで保たれる
```

### D.2 何が保たれ、何が捨てられるか

| 遷移 | 保たれるもの | 捨てられるもの | 現状との差 |
| --- | --- | --- | --- |
| **鍵を開ける／閉める** | 選択（地物・頂点）、カメラ、時刻、絞り込み | 手順の途中の状態（描きかけ・対象マーク・プレビュー） | **変更**。現状は `setMode` が選択を全消し（`store.ts:1399-1401`）。これが「探してから編集モードへ」を必ず失敗させていた（報告 C §1-2） |
| **道具を持ち替える** | 選択（地物）、カメラ、時刻、絞り込み、結合の対象マーク | 手順の途中の状態、**頂点の選択**（頂点ツール以外へ移るとき） | **変更**。現状は `setActiveTool` が選択を全消し（`store.ts:1405-1414`）。第 2 引数「選択を持ち越す」は既に存在するので、**全経路をこの引数付きに揃えるだけ**（結合点 #6） |
| **右クリックから道具を起動** | 選択と、**右クリックした地物を対象として引き継ぐ** | 手順の途中の状態 | **変更**。現状は右クリックから起動しても対象が引き継がれない（C9） |
| **時刻を動かす** | 選択、カメラ、道具、絞り込み | **手順の途中の状態は捨てない**（描いている最中に年を動かしても描きかけは残る。ただし「記録する年」の表示が変わる） | 現状も概ね同じ。ただしオプションバーの「記録する年」が変わることを見せる |
| **地物を選び替える** | 道具、カメラ、時刻 | 頂点の選択、インスペクタの畳み状態はそのまま（スクロール位置は先頭に戻す） | **変更**。現状はプロパティ欄のスクロール位置が残って名前欄が画面外になる（C5-4、報告 C §1-5） |
| **手順を確定する／取り消す** | 選択（**確定した地物を選択したまま残す**）、道具 | 手順の途中の状態すべて | **変更**。現状は確定後の振る舞いが揃っておらず、分割だけ道具が外れ、他 3 つは次の対象待ちで居座る（C9） |
| **Esc を押す** | §D.3 の階段に従う | 同上 | **変更**。現状は道具中に Escape が止まる（`App.tsx:2780-2791`） |
| **プロジェクトを開き直す** | 何も | すべて | 現状どおり |

**K-5（一時的な UI 状態は全経路で捨てる）との整合**。K-5 が捨てろと言っているのは「開始・確定・キャンセル・ツール切替・モード切替で、**一時的な UI 状態**を残さないこと」（開発ガイド §5.2）である。この案が保つ「選択」は一時的な UI 状態ではなく**ドメインの選択状態**であり、`activeFeature` は FR-79 が定義するアプリの正式な状態である。**捨てるべきもの（描きかけの頂点列・対象マーク・プレビュー・確定待ちの案）は、この案でも全経路で捨てる。** 実装上は「一時状態を持つのは道具のコントローラだけ、選択はストア」と層を分けることで、K-5 を機械的に守れる形にする。

### D.3 Esc の階段（1 つのキーが常に「1 段戻る」）

```
描きかけの頂点がある      → 最後の頂点を 1 つ取り消す（何も無くなるまで）
  ↓ 無ければ
手順の対象を掴んでいる    → 対象を離す（道具は持ったまま）
  ↓ 無ければ
確認ダイアログ／作業画面が開いている → 閉じる
  ↓ 無ければ
頂点を選んでいる          → 頂点の選択を解除
  ↓ 無ければ
地物を選んでいる          → 選択を解除（U-5）
  ↓ 無ければ
道具が「選択」以外         → 「選択」道具に戻る
```

U-5（Escape で選択解除。描きかけ・モーダルがあるときはそちらのキャンセルが優先）を、階段として一般化したもの。**「Esc を連打すれば必ず素の状態に戻れる」**という一貫した安心を作る。

### D.4 道具中でも取り消し・削除・右クリックを止めない

現状の最大の落とし穴の 1 つは、5 つの道具が「アイドルでない」間ずっと Ctrl+Z・Delete・Escape・右クリックを止めること（`shortcutsSuspended` は 11 項目の手書き OR、`App.tsx:2780-2792`）。実測では**所属変更を確定して 775→776 件になった直後の Ctrl+Z が無反応**で、「間違えた直後のいちばん押したい瞬間だけ取り消しが効かない」状態だった（報告 04 §3.5）。

この案では、キーボードの占有を**「誰が握っているか」を表す 1 つの値（focusOwner）**に統合する（結合点 #5 の改修）。

| focusOwner | Ctrl+Z / Ctrl+Y | Delete | Esc | 右クリック | 単一キー（V/A/F…） |
| --- | :-: | :-: | :-: | :-: | :-: |
| `map`（既定） | ○ | ○ | ○ | ○ | ○ |
| `tool-drawing`（描いている最中） | **○**（描いた頂点を 1 つ戻す） | ○（選んだ頂点を消す） | ○（階段） | ○ | **×**（誤爆を防ぐ） |
| `text`（文字入力欄） | ○（欄の中） | ×（欄の中） | ○（欄から抜ける） | ○（欄の標準） | × |
| `modal`（確認・作業画面） | × | × | ○（閉じる） | × | × |

**「確定した直後」は `map` に戻っている**ので、Ctrl+Z は必ず効く。現状の「道具を降りてからでないと取り消せない」は消える。

### D.5 選択が地図に必ず見えること（C10 の回避策の逆転）

現状は、階層深度フィルタで描画対象外になっている地物を一覧から選ぶと、**カメラは飛ぶのに地図には何も描かれない**（報告 11 §4）。回避策は「階層深度を +1 する」だが、実行すると今度は選択の強調が消え、州 1 件を見るのに 8 手かかった（報告 E §2.1）。

この案の規則: **選択中の地物（とその親までの道筋）は、表示フィルタ・階層深度・個別非表示のいずれに関わらず必ず描く。** 隠れているものを選んだときは、オプションバーの「表示 ▾」に「この地物は表示条件から外れています（一時的に表示中）」を出し、押せば条件そのものを緩められる。**「選んだのに見えない」は起きない。**

## H. 用語と文言の方針

### H.1 基本の考え方

現状の言葉の問題は 3 つある（現状分析 N-29・N-30・N-31）。

1. **同じものに 2 つの名前**（親領域／上位領域、継承先／引き継ぐプロパティ、グリッドスナップ／グリッドにスナップ、一覧・通史／錨一覧）
2. **内部語がそのまま画面に出る**（末端地物・集約地物・リング・領土リング・減衰（淡く）表示・縦方向領域・`f-5-4`・`childIds`/`parentId`）
3. **難しい語と、意図を表す語が逆になっている**——用語集が定義する 7 つの操作名（割譲・帰属・連邦化・独立・直轄化・自治化・解体）が画面に 1 つも出ないのに、上部バーには最も難しい語（階層深度・個別フォーカス・フォーカス深度・縦方向領域を強調・深掘り対象なし）が最も使わない機能として常時並ぶ

この案の方針: **①「同じものは 1 つの名前」に統一する ②内部語は画面から追い出す ③難しい語は使ってもよいが、必ず「その場で意味が分かる形」で出す。**

### H.2 初見の人に「錨」「直轄領」「深掘り」がどう見えるか

| 内部の語 | 画面での見え方 | 根拠と理由 |
| --- | --- | --- |

## I. キーボードと右クリックの体系

### I.1 設計の前提

- **Electron 標準メニューは復活させない**（K-1）。Ctrl+R（リロード＝編集中データ喪失）とページズーム（座標破壊）を含むため 2026-07-25 に完全撤去されている。**自前のメニューバーとこのキー表が唯一の標準操作導線。**
- **単一キーのスコープは「地図に入力の権利があるとき」に限る**（Inkscape 方式。現状分析 §9.2 の回避策）。文字入力欄・確認の器・道具の描画中は単一キーが降りる（§D.4 の focusOwner）。
- **`focus-guard.ts` が range を守っていない**ため、現状はスライダーにフォーカスが残った状態の Ctrl+Z がドメインの取り消しを走らせる（実測で追加した地物が消えた。C8）。**range・checkbox・radio も守る対象に加える。**
- **`Ctrl+0` は使えない**（Electron の既定が奪う経緯が `menu.ts:123-131` に残る）ので全体表示は `Ctrl+Home` のまま（K-1）。

### I.3 右クリックの体系

**原則: 右クリックは「いま指しているものに対して、いまできることを全部出す」。押せない項目は出さない（灰色で並べない）。**

現状の欠陥（C9、報告 F 定石 9）: 空白部は 1 項目だけ／「結合」が構造上つねに無効で押せる状況が存在しない／道具を持っている間は右クリックが止まる／右クリックから道具を起動しても対象が引き継がれない。**「常に無効な項目が出ている」「道具中は開けない」は他のツールに例が無い。**

| 右クリックした場所 | 出る項目 |
| --- | --- |
| **地図の地物の上** | 素性を見る（インスペクタへフォーカス）／名前を変える（F2）／**この年に記録を作る**／所属を変える ▸（既存の親から選ぶ／新しい上位領域を作る／最上位へ）／分割する／穴をあける／穴・飛び地を足す ▸／この地物の中を見る（深掘り）／薄くする／隠す／ロック／**対象にする**／削除 |
| **地図の頂点の上** | 頂点を消す／ここに頂点を足す（**現状は辺の中点がクリックでは無反応でドラッグ必須＝ N-06**）／この頂点を共有している地物を選ぶ |
| **地図の辺の上** | **ここに頂点を足す**（N-06 の解）／この辺で分割する |
| **地図の空白** | 全体表示／ここを中心にする／グリッド／表示 ▸／選択を解除 |
| **一覧の行** | 地図で見る（視点を合わせる）／名前を変える／種別を付ける ▸／所属を変える ▸／対象にする／隠す／ロック／削除 |
| **一覧で対象が 2 件以上あるとき** | **結合する**／**新しい上位領域にまとめる（連邦化）**／まとめて薄くする／まとめて隠す |
| **一覧の種別チップ** | この種別だけ表示／この種別を薄くする／この種別を強調（G-22） |
| **時間軸の錨の印** | この年へ移動／この記録を見る（インスペクタへ）／この記録を削除（影響プレビュー付き） |
| **時間軸の空白** | この年へ移動／範囲を変える／粒度 ▸ |

**道具を持っている間も右クリックは開く**（§D.4）。ただし手順の途中では「この手順を取り消す」「対象を選び直す」が先頭に出る。

判定は **適合** ／ **要改修**（この案の実装で手を入れる必要があるが、制約そのものは守る）／ **衝突**（制約と正面からぶつかるので裁定が要る）の 3 段階。

### L.3 確かめられなかったこと（次工程・実装への申し送り）

1. **「UI が使いづらい」の具体的な中身を、所有者から聞いていない。** 18 本の報告すべてが同じ限界を挙げており、この案も同じ限界の上に立っている（現状分析 §11-1）。とくに「装飾の話なのか導線の話なのか」（HB3-27 との関係）は、**この案を着手する前に確認する価値が高い**。この案は**導線の話として書いている**ので、もし所有者の不満が主に見た目（配色・余白・書体）なら、増分 8 を先頭に持ってくるべきである。
2. **集約の子（州）に「その子自身の錨」として画面を出せるか**（§E.6 の (b)）。報告 E §2.9 は「子の頂点を動かすと、錨は**親に**付く」と実証した。この案は「内部の置き場所と画面の見え方を切り離す」と書いたが、**ドメイン側に「子の錨として読み出す」導出が必要かどうかはコードで確かめていない**。増分 5 の最初に確かめること。
3. **`AddToolController` に 2 つのポートを渡したあと、`resolveSnap` が期待どおり動くか**（C1 の注記、報告 F §6-5）。渡すだけで直るのか、`resolveSnap` 側にも手が要るのかは未検証。**増分 1 の最初に確かめること。**
4. **描画エンジンが窓に対して縦横どちらを基準にフィットさせるか。** 1600×1000 で「ベースマップが縦 465px 程度＝セル高さの約 65%」という観察（§1.2）と、N-49（リサイズで視点が追従しない疑い、要実機確認）は、どちらもこの案の面積計算に影響する。**実機で確かめること。**
5. **穴・飛び地の頂点編集が本当に不正な形を通すか**（G-14）。確定前ゲートを迂回しているのは事実だが、解放時の整合性検査が同じ違反を捕まえる可能性がある。**実機で「穴の頂点を親領土の外へ引きずり出す」のが最短の確認**（現状分析 §11-5）。
6. **ナイフの n 分割は「穴なし・単一リングの単純な面」に限られる**（`split-geometry.ts:886`）。実データの国は穴（内陸国）や飛び地を持つので、HB3-5 の「余計な分断」が再現しうる。**この案は V10 でこれを解決していない**（文言の分離＝ N-08 と、継承先の呼び方＝ N-09 しか直していない）。何件で起きるかも数えられていない（現状分析 §11-14）。
7. **1 辺で経度 180 度以上を渡る形を描けてしまい、塗りが内外反転する**（N-51）。これは保存形式の恒久的な表現限界で、直せるのは「書く側で長い辺に中間点を打つ」ことと「UI で検知して止める」ことだけ。**実データの残作業「東西の地図端で分断された大陸をアプリ内で合体する」は、まさにこの地雷を踏む位置にある。** この案は**吸着の配線（増分 1）で長い辺を作りにくくすることしかしておらず、検知は入れていない**。増分 1 か 7 に「1 辺の経度差が 180 度を超えたら断って理由を出す」を足すべき。
8. **錨が 10 個に育ったときの一覧・時間軸・表示解決の挙動は未測定**（現状分析 §11-7）。この案の時間軸（増分 6）と錨の一覧（増分 5）は、実データで錨が増えてから初めて本当の負荷がかかる。
9. **実機（GPU あり）での見え方は未検証。** 全報告がヘッドレスのオフスクリーン描画で、ホバー・フォーカスリング・日本語のフォント解決・読み上げは未確認（現状分析 §11-3）。**この案は「ホバーで最寄りの頂点を大きく描く」（§E.9）という、ホバーに依存する仕組みを 1 つ入れている**ので、実機での確認が要る。
10. **KLM の秒数は絶対値としては当てにならない**（報告 C §3.1）。§E の数値は**現状との比**として読むこと。とくに「M（心の準備）」の置き方は、新しい画面では現状と同じ規則で置けるとは限らない（慣れるまでは M が増え、慣れると減る）。
11. **この案は他の 4 案を読んでいない。** レンズが「モードレス」に固定されているので、**モードを残したほうが良い理由がある場合、この案はそれを見落としている可能性がある**。とくに「モードがあるおかげで誤操作が防がれている」という側面は、この案では鍵 1 本に集約しており、それで十分かは実運用で確かめるしかない。
12. **調査中に実データの正準ファイルがアプリ自身によって 1 回上書きされている**（現状分析 §11-13）。**この案の増分 2 で「開いているファイル名の常時表示」と「上書き保存の前に対象ファイルを示す」がセットで入る**ので、そこまでは調査用の起動で正準ファイルを直接開かず、コピーを開く運用を続けること。
