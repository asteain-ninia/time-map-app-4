## 0. 最初に押さえておくこと（3 点）

1. **所有者が例に挙げた「州を束ねる」は、いまの画面にはもう無い。**「束ね」はコードの注釈の中にしか残っていない（`src/ui/discovery/axes.ts` ほか）。つまり、一語ずつ探して直すやり方では足りず、**いま画面に出ている同じたぐいの言い回しを、漏れなく並べて見る仕組み**が要る。これが目録を作る理由である。
2. **語を選ぶのは所有者、並べて候補を出すのが機械とモデル**、という役割分担を崩さない。モデルに「書き直させる」のではなく、「怪しい所に印を付けさせ、候補と理由を添えさせる」。
3. **いま並行して増分 8E の前半が文言を触っている。** 所有者が選んだ結果は「文そのもの」ではなく「どの表のどの見出し語（キー）か」に結びつけて記録する。そうすれば、直す直前に目録を作り直しても、選んだ結果をそのまま当て直せる。直す日だけは、ほかの作業で文言を触らない（短い凍結期間）。

## 2. 目録を機械的に作る方法

### 2.1 目録の 1 行に載せるもの

| 欄 | 中身 | 作り方 |
| --- | --- | --- |
| 識別子 | `ui/shell/strings.ts` の `APP_STRINGS.shortcutBusy` のように「ファイル＋キー」 | 構文の解析。**文そのものを識別子にしない**（文は直すと変わる） |
| いまの文 | 埋め込み部分は〔件数〕〔年〕〔名前〕のように日本語の札に置き換える | 関数の引数名から札を決める対応表（count→件数、year→年、name/label→名前 …）を 1 つ持つ |
| 見本の文 | 札に見本の値を入れた実際の文（南ケナ州／1200年／3 件） | 表の関数を見本の値で実際に呼ぶ。**所有者は札入りの文より、本物らしい文のほうが自然さを判断しやすい** |
| 種類 | ボタン／見出し／説明文／断り文／結果の知らせ／ツールチップ／読み上げ用（`aria-label`） | 置き場所（JSX の属性名、表の命名）からおおよそ自動で振り、外れは手で直す |
| 使われている場所 | そのキーを参照している部品と行 | 構文の解析で参照元を引く。**参照が 0 件の文言＝画面に出ない死んだ文言の疑い**も同時に見つかる（`docs/現状.md` B38 の再発防止。種類で表を引く所は 0 件に見えるので「要確認」止まり＝§5.2） |
| 出る場面 | 場面の名前と写真（§2.3） | 部品からの推定＋画面の巡回で確かめる |
| 同じ文の仲間 | 同じ文を持つ他のキー | 文の一致でまとめて、1 回の判断で全部に効かせる |

形式は 1 本の JSON と、それを見るための HTML 1 枚（§3.3）。目録を作る道具は、今回の調査で書いた `scan.cjs`（約 100 行）を育てれば足りる。構文の解析には、リポジトリに既にある TypeScript 5.9 の解析器をそのまま使う。

### 2.2 埋め込みのある文の扱い

- 表の中の埋め込み文は 158 件、表の外が 83 件。どれも「引数を受けて文を返す小さな関数」なので、**目録には関数の本体の文を札入りで載せ、見本の値で呼んだ結果も並べる。**
- **埋め込む値そのものが別の表の文**の場合がある（例: 「{操作名}はいま使えません」の操作名は `command-result.ts` の表から来る）。目録には「この札には〔別の表〕の文が入る」と書き、組み合わせて不自然にならないか（助詞のつながり）を点検の対象に入れる。
- 直すときは**文字列の置き換えではなく、関数の本体を書き直す**。数の言い方（「1 件」「3 件」）、助詞（「〔名前〕を」「〔名前〕に」）が崩れていないかを、見本の値を何通りか入れた単体の検査で確かめる。

### 2.3 「出る場面」と画面写真を結びつける

**主は静的な推定、確かめは実際に画面を巡回して行う**、の 2 段にする。

1. **静的な推定（主）**: 「このキーはどの部品から参照され、その部品はどの画面のどこにあるか」を構文の解析でたどる。短い文（「やめる」13 か所、「閉じる」10、「・」10）は文字の一致では場所を特定できないので、こちらが主になる。
2. **画面の巡回（確かめ）**: 探索用の検査群（`npm run e2e:explore` の側）に、文言の点検専用の巡回を 1 本足す。
   - 評価シナリオ V1〜V15 と、既存の `e2e/__bughunt__/scene-layout.ts` の場面づくりを流用して、**30〜40 の場面**を順に開く（初回起動、追加の道具を構えた所、所属変更の 3 択、削除の確認、保存の確認、設定、右クリック、重なりの解決、修復の確認、空の状態 3 種 など）。
   - 各場面で、写真を 1 枚撮り、**画面に見えている文字（`innerText`）と、`aria-label`・`title`・`placeholder` の値を JSON に書き出す。**
   - 書き出した文字を目録と突き合わせる。埋め込みのある文は、札の部分を「何でもよい」にした照合の型を作って当てる。
   - 突き合わせの結果、**(a) 目録にあるのにどの場面にも出てこなかった文**（場面を足すか、本当に使われていないか）と、**(b) 画面に出ているのに目録に無い文**（表の外の取りこぼし。利用者のデータ由来の地名などは除く）の 2 つの一覧が出る。(b) が 0 件になることが目録の網羅の証明になる。
3. **巡回で写せないものは手で 1 行ずつ足す**: OS のダイアログ（`shell/main/index.ts` の応答なしの確認）、ウィンドウのタイトル（`src/ui/index.html` の `<title>` と `buildWindowTitle`）、キャンバスに描く文字（`src/render/` の 2 件）、ホバーしないと出ないツールチップ（巡回の中でホバーして撮るか、属性の値だけで判断するか、場面ごとに決める）。

**既存の写真は使えない。** `screenshots/__visual__`（52 枚）と `screenshots/__bughunt__`（356 枚）はいずれも増分 7 より前の画面で、文言も配置も変わっている。巡回は新しく撮る。巡回の検査自体は、直したあとにもう一度走らせて「直した文がその場面に出ていること」の確認に使い回せる。

## 3. 所有者が少ない手数で選べる形

### 3.1 段取りは「用語を先に、文は後に」

全 1,100 件余りを所有者に読ませない。次の順で絞る。

1. **用語の第一表記を先に決める（15 行以内）。** 決まった語は機械的に置き換える。これだけで「同じものに 2 つの名前」の類は片づく。
2. **残りの文は、モデルが「怪しい」と印を付けたものだけを見せる。** 見込みは全体の 15〜25%、つまり **200〜300 件**。
3. **画面ごとに、写真の横に並べる。** 文を単独で読むより、どこに出るかが見えたほうが判断が速い。
4. **何も選ばなければ「いまのまま」**。押すのは変えたいものだけ。

### 3.2 用語の短い一覧の作り方

1 行に次を載せる。候補は **2〜3 個**（4 個以上は迷うだけ）。**いま最も多く使われている言い方を必ず候補に含める。**

| 欄 | 例（「上の側の地物」の行） |
| --- | --- |
| 何を指すか（ふつうの言葉で 1 文） | 州から見た国のように、いま選んでいる地物を囲む側 |
| いま画面に出ている言い方と数 | 上位領域 53 か所 ／ 親 12 か所 |
| 候補 | ①上位領域 ②親 ③（モデルの提案から 1 つ） |
| 候補ごとの例文（実際の画面の文に当てはめたもの） | ①「新しい上位領域を作る（連邦化・自治化）」 ②「新しい親を作る（連邦化・自治化）」 |
| おすすめと理由（1 行） | |

一覧に載せる行の見込み（§1.4 の数から）:
上の側／下の側の地物、形を持つ地物の呼び方（B54「末端地物」の行き先と、「選んだ地物」欄の見出しの右肩と、対象欄の種類の呼び名を同時に）、まとめる側の地物、取りやめのボタン（B57）、選ぶ／選択、消す／削除、見えなくする、操作を戻す、経緯線の網（グリッド／格子）、変化の記録の呼び方（§6 の D1）、所属変更、分け残し（直轄領）、種別と種類、読むだけ ⇄ 直せる（裁定済みなので確認だけ）。**15 行を超えたら 2 回に分ける。**

所有者への聞き方は、これまで効いた形（平易な説明＋選択肢で 1 項目ずつ。メモリ「報告は普通の日本語で」）を踏襲する。

### 3.3 文を選ぶための画面（HTML 1 枚）

- 左に場面の写真、右にその場面に出る文の一覧。モデルが印を付けた文だけ色を付け、他は畳んでおく。
- 1 行ごとに「いまのまま（既定）」「候補 A」「候補 B」「自分で書く」を選ぶ。候補には、どのモデルがいくつ同じ指摘をしたか（§4.4）と、短い理由を添える。
- 選んだ結果は「キー → 新しい文」の JSON で書き出す。**この JSON がそのまま一括の直しの入力になる**（§6 の手順 6）。
- 置き場所は scratchpad かリポジトリの外の作業用フォルダ。リポジトリには選んだ結果の JSON だけを入れる（何をなぜ変えたかの記録として）。
- 見せ方の選択肢として、claude.ai の非公開ページ（選んだ結果をページ側に保存できる）に載せる手もある。手元の HTML で足りるなら手元で。どちらにするかは所有者の好み（§6 の D6）。

### 3.4 「型」で決めて数を減らす

断り文の大半は「〜できません。〜してください。」の形をしている。1 件ずつ選ばせる代わりに、**型を 1 つ決めてもらう**（例: 設計書 §H.5 の「何が起きたか → なぜか → 次に何をするか」。結果の知らせは「過去形で言い切り、副次的な結果を丸括弧で」）。型が決まったら、モデルがその型に沿って候補を作り、所有者は見本を数件だけ見て通す。ボタンの文言、見出し、説明文も同様に型を先に決める（§4.2 の SmartHR の規則が叩き台になる）。

## 4. モデルが日本語の文言で陥りやすい癖と、避ける手順

### 4.1 このアプリの文言に実際に見える癖

| 癖 | 実例（いまの画面の文） | 直す向き |
| --- | --- | --- |
| 硬い漢語を重ねる | 「対象の面情報が見つからないため、所属変更できません」「存在期間が対象と両立しない」「循環参照になります」 | 和語・訓読みの動詞へ（「見つからない」は良い。「対象の」「存在期間」「両立しない」を開く） |
| 「対象」「指定」「情報」を便利に使う | 「対象」44、「指定」49、「面情報」14 | 何を指すか具体的な名詞にする（「この州」「選んだ面」） |
| 英語の直訳の名詞 | 「グリッド表示切替」「経度シフト」「左へシフト」 | 動作を言う（「格子を出す／消す」「左へずらす」） |
| 体言止めの見出しと、です・ます文の混在 | ボタン「グリッド表示切替」と説明文「〜選んでください。」が隣り合う | 種類ごとに型を決める（§3.4） |
| 「〜してください」の連続 | 145 文 | 次の一手をボタンにできる所はボタンへ（設計書 §H.5） |
| 内部の英語・記号がそのまま出る | 「ON / OFF」、過去には「元に戻せます: edit」 | 英字を出さない検査を広げる（§5） |
| 主語の欠落で誰の話か分からない | 「対象の種別では直接所属変更できません。下位領域を対象にしてください。」 | 主語か対象の名前を入れる |
| 言い換えを作りすぎて、同じものに別名が生える | 上位領域／親、やめる／キャンセル | 用語集で第一表記を固定し、検査で守る |

### 4.2 外部の指針（要点だけ）

1. **SmartHR デザインシステム「その他の UI テキスト」**（https://smarthr.design/products/contents/ui-text/app-writing/ ）
   - ボタンは動詞の終止形で「する」を付けない（「追加」「削除」「戻る」。「追加する」は非推奨）。目的語があれば「権限を追加」のように「を」を入れる。
   - 画面の題名・項目名は名詞（「権限の追加」）。説明文はです・ます調で動詞まで書く（「権限を追加できます」。体言止めは非推奨）。
   - 移動は、具体的な場所なら「に」（「一覧に戻る」）、相対的な位置なら「へ」（「前へ戻る」）。
   - リンクは行き先を具体的に（「詳細はこちら」は非推奨）。
   - 用字用語（漢字とかなの使い分け）は別ページ（https://smarthr.design/products/contents/idiomatic-usage/ ）にまとまっていて、**言葉を決めた根拠を公開する**方針を取っている。本件の「用語の一覧に理由を 1 行添える」はこれに倣う。
2. **文化審議会「公用文作成の考え方」（建議、令和 4 年 1 月 7 日）**（https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93731901_01.pdf 本体の pp.(6)〜(8)）
   - Ⅱ-2: 専門用語は「言い換える」「説明を付けて使う」「工夫してそのまま使う」のどれかを、語の性質と場面で選ぶ。→ 本件の用語一覧の 3 択（変える／残して初出に言い換えを添える／そのまま）と同じ考え方。
   - Ⅱ-3: カタカナ語は、定着しているものはそのまま、そうでないものは日常の漢語・和語に言い換えるか説明を付ける。
   - Ⅱ-8: 聞き取りにくい難しい漢語は言い換える。親しみやすさを高めるには、述語に訓読みの動詞を使う（例: 「作業が進捗する」→「はかどる」）。
   - Ⅲ-3: 一文を短く、論点は一つ。三つ以上並べるなら箇条書き。主語と述語の関係が分かるように。
3. **鹿野桂一郎（ラムダノート）「japanese-tech-writing」**（紹介記事 https://www.gamebusiness.jp/article/2026/06/22/27286.html 、本体は GitHub Gist）
   - モデルに「AI くさい文」を書かせないための禁止規則集。無意味な予告やまとめ、空虚な形容（「鍵となる」）、ごまかしの動詞（「深掘りする」）、「さらに」「また」の連打、意味のない強調（「非常に」）を禁じる。
   - **技術文書向けなので、画面の短い文言にはそのまま当てはまらない。** 使えるのは「モデルに渡す禁止事項の書き方の手本」としてで、説明文やガイドの文（初回ガイド 4 枚など、長めの文）の点検に効く。

### 4.3 避ける手順

1. **手本を渡す。** モデルに一般論の指針だけを渡すと、無難で硬い文に寄る。**このアプリの中で読みやすいと所有者が認めた文を 10〜20 件選び、手本として渡す**（候補: 設計書 §H.3 の初回ガイド、§H.5 の結果の知らせ、「そこは世界の外です…」、重なりの解決の案内）。手本の選定は所有者にお願いするか、取りまとめ役が選んで所有者が承認する（§6 の D4）。
2. **書き直させず、印を付けさせる。** 各モデルへの依頼は「この文のどこが不自然か（種類は §4.1 の表から選ぶ）」「候補を 1〜2 個」「理由を 1 行」。全文の書き直しを頼むと、問題の無い文まで変わって、所有者の確認が増える。
3. **モデルごとに独立に走らせる。** 他のモデルの結果を見せない。混ぜると最初のモデルの癖に引きずられる。
4. **用語の一覧と型を固定して渡す。** 第一表記が決まった語は変えないこと、を依頼文の最初に書く。
5. **声に出して読む規則を依頼文に入れる。** 「画面の横に立った人が、隣の人に口で説明するときの言い方に近いか」「一息で読めるか（目安 40 字）」を判定基準にする。
6. **最終判断は人。** 選ぶのは所有者で、モデルの多数決ではない。

### 4.4 複数モデルの組み方

- 4 モデル（Fable・Opus・GPT・Grok）に、**同じ依頼文と同じ材料**を渡す。材料は目録を**画面ごとに分けたもの**（全体で約 21,000 字。GPT は 1 回 40KB 以下に分け、1 回に 1 ファイルずつ読ませる＝メモリ「外部の審査役の呼び方」）。
- 外部のモデル（GPT・Grok）は読むだけの環境で動かす。今回は検査を走らせる必要が無いので、その制約は問題にならない。実行係は Sonnet（メモリ「モデル配分の均衡」）。
- 結果を突き合わせ、**何モデルが同じ文に印を付けたか**を並べ替えの鍵にする。4 モデル中 3 以上が指摘した文を上に、1 モデルだけの指摘は下に畳む。
- 候補が割れたら、割れたまま所有者に見せる（2〜3 個まで）。取りまとめ役（司令塔）が 1 つに絞らない。

## 5. 規則を検査で守る方法と、既存の検査への影響

### 5.1 規則

「利用者に見える文字列は、文言の表（画面側は `src/ui/**/strings.ts` 等、中核の処理側は `src/domain/**/messages.ts`、Electron の本体側は新しく作る `src/shell/**/strings.ts`）から引く」。**表は層ごとに置く**（中核の処理側は画面側を読み込めない決まりがあるため、1 本にはまとめられない）。

### 5.2 守り方（2 つを併用する）

**(a) ESLint の `no-restricted-syntax`（書いた瞬間に赤くなる）。** 今回、リポジトリの設定を触らずに scratchpad の設定（`eslint-probe.config.mjs`）で試し、**日本語の文字の範囲を使った条件で、文字列・テンプレートの各部分・JSX の本文を拾えることを確かめた。** 結果（`src/` の検査ファイル以外）:

| 拾った種類 | 表の外 |
| --- | ---: |
| 文字列 | 299 |
| テンプレート文字列の部分（埋め込みの前後で別々に数える） | 120 |
| JSX の本文 | 21 |
| `aria-label`・`title`・`placeholder`・`alt` の直書き（言語を問わず） | 17 |

（表の中では 1,006 件拾った＝表を対象から外す設定が要る。）
対象から外すもの: 表のファイル、検査ファイル、見本データ（`**/fixtures.ts`、`ui/e2e/**`）、診断ログ（`shell/io/diagnostic-log.ts`、`shell/main/close-guard.ts` のログ部分は「ログの表」に分けるか 1 行ずつ除外の注記）、正規表現の部品。

**(b) 単体の検査でソースを走査する（目録の網羅の保証）。** 前例がある ―― `ui/shell/command-result.test.ts` と `ui/a11y/modal-registration.test.tsx` は、どちらも「手書きの一覧では漏れる」ことを理由に、ソースを読んで機械的に確かめている。同じ書き方で次を見る。
- 表の外に日本語の直書きが無いこと（(a) の二重化。ESLint を飛ばしても落ちる）。
- **目録の JSON が、表の全キーを含んでいること**、そして**参照が 0 件のキーが無いこと**（死んだ文言）。ただし `MESSAGES[kind]` のように断りの種類で表を引く所は、キーの名前が直接は出てこないので 0 件に見える。**0 件のキーは「削除候補」ではなく「要確認」として扱い**、種類で引いている表は検査の側で例外として名指しする。
- 用語集で「出さない」と決めた語（例: 「末端地物」「面情報」、決まった後の旧称）が表の中に無いこと。**用語集を検査で守る**のはこれで初めて実現する。

### 5.3 既存の検査（約 5,800 件）への影響

数えた結果: 単体の検査 5,448 件（402 ファイル）、画面を動かす検査 323 件（81 ファイル）。

| | 日本語を直書きして照合している箇所 | 表の定数で照合している箇所 |
| --- | ---: | ---: |
| 単体の検査 | 637（104 ファイル） | 246 |
| 画面を動かす検査 | 418（53 ファイル） | 3 |

- **表の外の文を表へ移す作業そのものは、文が変わらないので既存の検査を壊さない。** 移す作業は所有者の判断を待たずに先にできる。
- **文を直すと、直書きの照合 約 1,055 か所が影響を受けうる。** 対処は、一括の直しに使うのと**同じ「旧い文 → 新しい文」の対応表**で検査側も機械的に置き換え、差分を目で確かめる。全部を定数参照に書き換える案もあるが、**「設計書で決めた文が一字一句その通りに出ること」を固定している検査は、直書きのほうが仕様として読みやすい**ので、一律には書き換えない。
- 画面を動かす検査も表を読み込める（`e2e/inc6-rail.spec.ts` などが既に `rail-strings` を読み込んでいる）。新しく書く検査は定数で照合することを勧める。
- 赤くなって困らない検査: 中核の処理側と画面側の重複を見る一致の検査（§1.3）は、両方を直せば緑に戻る。むしろ直し漏れを教えてくれる。
