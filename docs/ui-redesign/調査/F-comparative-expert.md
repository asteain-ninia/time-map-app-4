# F 類似ツールの定石との比較（専門家レビュー）

対象: gimoza（内部名 time-map-app-4）の UI 全面再設計。
技法: 競合比較（competitive analysis）。同種の道具が長年かけて収束させた「定石」を 15 個に整理し、gimoza が
**外れている点／従うべき点／独自でよい点**を、把握フェーズの調査報告 01〜12 と要件 ID を根拠にして判定する。

この文書は次工程が読む**生データ**である。断定は根拠（`ファイル:行` / 要件 ID / スクリーンショットのパス / 報告書の節）を添えた。
比較対象ツールの記述は WebSearch で確認した一次資料（§7 に出典）と、確認が取れなかった部分は筆者の一般知識による。
**どの記述が検索で裏を取ったもので、どれが知識由来かは各所に明記した。**
ソースコードは一切変更していない。ビルドも git 操作も行っていない。

---

## 0. 調べ方と限界

1. 把握フェーズの報告書 01〜12（`docs/ui-redesign/調査/*.md`、計 5,819 行）を全部読んだ。本文の gimoza 側の事実は、
   すべてこの 12 本のいずれかに実測・コード根拠つきで載っているものだけを引いている（引用元の節番号を併記した）。
2. 比較対象は指示された 8 群: QGIS/ArcGIS、Inkscape/Illustrator、Figma、Premiere/DaVinci、Aeon Timeline、
   歴史地図系（Chronas / Running Reality / GeaCron）、創作者向け（Azgaar / Wonderdraft / Inkarnate）。
3. **WebSearch は使えた**ので、記憶に頼りたくない事実（QGIS のスナップ／トポロジー編集、Aeon Timeline のビュー構成、
   Running Reality の時間モデル、Azgaar のレイヤーパネル、Chronas の年スライダー、Figma のレイヤーパネル、
   Premiere のマーカーとタイムラインズーム、Inkscape の単一キー）は検索で裏を取った（§7）。
4. **裏が取れなかったもの**: ArcGIS Pro の最新のリボン構成、DaVinci Resolve の細部、Wonderdraft / Inkarnate の
   現行 UI、Illustrator の現行ツールパレット、GeaCron の操作系。これらは筆者の一般知識で書き、**本文中に「（知識による）」と明記**した。
   定石の主張はいずれも複数ツールに共通する部分だけを使っているので、1 ツールの細部が違っても結論は動かない。

**限界**: 比較対象は誰も「架空世界の歴史地図を 1 人で編纂する」道具ではない。gimoza の中核（地物の親子階層 × 時間軸の錨）に
そのまま対応する製品は存在しない。したがって本文の「定石」は、**部分ごとに最も近い製品群から借りてきた寄せ集め**であり、
丸ごと真似できるお手本は無い。§3 で「独自でよい点」を明示的に切り出したのはそのためである。

### 定石 1 — モードを減らし、編集は常時可能にする（ツールを持ち替えても選択を失わない）

> 指示された論点 (a)「モードを減らす／モードレス化の定石」

**定石**: 作図系の道具は「今どのツールか」という 1 段だけを持ち、モードという上位の段は持たない。
ツールの切替は単一キーで、切り替えても選択オブジェクトは保持される。
「選択してから動詞を選ぶ」（名詞→動詞）の順序が壊れないことが、あらゆる編集系 UI の前提になっている。

**他ツールでの実例**

- Inkscape は選択ツール `S`/`F1`、ノード編集ツール `N`/`F2` を単一キーで往復でき、キャンバスにフォーカスがあれば
  いつでも効く（テキスト編集中だけ Esc で抜ける必要がある）[出典 8]。モードという概念は無い。
- Illustrator も `V`（選択）/`A`（ダイレクト選択）/`P`（ペン）の単一キー（知識による）。
- Figma は移動ツールが既定で、ダブルクリックで階層を降りる（知識による）。
- QGIS だけは例外的に「編集モードの開始／終了」という 1 段のトグルを持つが、**それは 1 個だけ**で、
  レイヤ単位の書き込みロックという明確な意味を持っている[出典 1]。gimoza のような 3 モードではない。

**gimoza の現在**

| 事実 | 根拠 |
| --- | --- |
| モード 3 個 × ツール 11 個の 2 段構造 | `src/ui/shell/tools.ts:33-53`、報告 02 §3.1 |
| 起動直後は表示専用。最初の操作が「表示専用を**解除**する」という否定形 | `src/ui/state/store.ts:1066-1067`、報告 01 §6-6 |
| 「表示専用」ボタンは押されている状態で押すと**編集モードへ着地**する（ラベルと結果が逆） | `src/ui/shell/useShell.ts:50-63`、報告 01 §6-6（実測） |
| ツール 11 個のうち「選択」は**何の効果も無い**（`TOOL_ID.EditSelect` を読む実装がツール定義以外に存在しない） | 報告 02 §3.3、報告 03 §1.1 |
| 「頂点編集」は右クリックメニューの品揃えが変わるだけ。頂点の掴み・移動・追加・削除は**ツール未選択でも同じように動く** | `src/ui/map/context-menu-adapter.ts:64-76`、報告 03 §1.1 |
| **ツールを押すと選択が消える**（既定の契約） | `src/ui/state/store.ts:1405-1414`、実測でハンドル 8→0（報告 03 §1.2） |
| モード切替・ツール選択にキーボード割当が **1 つも無い** | `src/ui/shell/menu.ts:70-153`、報告 02 §4.1 |
| ツールを選んでいる間は Ctrl+Z・Delete・Escape・右クリックが**全部止まる** | `src/ui/App.tsx:2780-2792`（11 項目の手書き OR）、報告 04 §3.5（実測） |
| 確定後のふるまいがツールごとに違う（分割だけツールが外れ、他 3 つは居座る） | 報告 04 §3.4（実測） |

スクリーンショット: `shots/01-shell-1600x1000-edit.png`（編集モードのツール 8 個）、`shots/01-shell-1600x1000-add.png`。

**判定: 大きく外れている。** モードが 1 段多く、その中のツールの 3 分の 1 が実効を持たず、しかもツールを押すと損をする
（選択が消える／全体ショートカットが止まる）。**押すと不利益しかないボタンが並んでいる**状態は、他のどの比較対象にも無い。

**再設計への含意**（意見）

- モードの段を廃し、「表示専用／編集可能」の 1 トグル（QGIS の編集セッションに相当）＋ツール 1 段に畳めるかを検討する。
  追加と編集を分ける必然性は、コード上は `src/ui/map/dispatch.ts:81-84` のボタン割り当てしか無い（報告 02 §3.4）。
- 「選択」「頂点編集」は統合するか削除する。編集モードでツール未選択のときが実質の既定編集状態になっている（報告 02 §3.3）。
- `setActiveTool` の既定を `preserveSelection` 側へ倒す。現状その経路は右クリック起動と競合解決後の再武装だけが使っている
  （`src/ui/App.tsx:2335-2352`, `2813-2831`）。
- `shortcutsSuspended` の 11 項目 OR（`App.tsx:2780-2792`）は「ツールを選んだだけで全体ショートカットが死ぬ」原因。
  「下書きがあるときだけ止める」に狭められないか検討する。

### 定石 2 — 作図中のスナップとトポロジー編集は、境界を扱う道具の必須装備

**定石**: 隣り合う面の境界を編集する道具は、(1) 作図中に既存の頂点／辺へ吸着し、(2) 吸着したことを画面で見せ、
(3) 共有された境界は片方を動かすともう片方も動く（トポロジー編集）、の 3 点を必ず持つ。
これが無いと「隣国と境界を共有する」が原理的に作れない。

**他ツールでの実例**

- QGIS: スナップツールバーで頂点／セグメントを対象に許容距離つきで吸着。`T` キーで**トレース**（既存の境界に沿って
  最短経路を辿る）。**トポロジー編集**を有効にすると共有境界の頂点を 1 回動かすだけで両側が更新される。
  **Avoid overlaps（新規ポリゴンの重なり回避）**も列で指定できる[出典 1]。
- CAD 系・Illustrator のスマートガイドも同型（知識による）。

**gimoza の現在**

| 事実 | 根拠 |
| --- | --- |
| **追加中に既存頂点への吸着が配線されていない**。`AddToolController` は `resolveProximity` / `isInsideTerminal` を任意ポートとして受けるが、合成ルートがどちらも渡していない | `src/ui/App.tsx:3259-3270`（供給元ゼロ、テストのみ）、`useAddTool.ts:216-231`、報告 03 §9.1 |
| その結果、**同じ画素をクリックしても頂点は共有されない**。実測で面 A の右辺と面 B の左辺を同一画素で描き、A の角をドラッグしたら B は動かず境界が裂けた | 実測 `obs-share.mjs`、`shots/03-61-Aの角をドラッグ後-Bは連動するか.png`、報告 03 §9.1 |
| **編集モードでドラッグして離すと共有化される**（既定 50px） | `src/ui/state/settings.ts:255-256`、実測 `obs-share2.mjs` |
| 現状で隣接国を正しく作る唯一の手順は「B を適当に描く → 編集モードへ → B の境界頂点を 1 個ずつ A の頂点へドラッグして離す」を頂点数ぶん繰り返すこと | 報告 03 §9.1、§10 の表 |
| FR-29（must、「末端地物追加時に他の末端地物の内部には頂点を設置できない」）も未配線のため効いていない。仮に配線しても拒否は `return current` の無反応で理由表示が無い | `useAddTool.ts:227-230`、報告 03 §9.1 |
| グリッドスナップの既定刻みは **10 度 ≒ 1,100km**。国境作業には使えない粒度 | `src/domain/basemap/grid.ts:33-38`、報告 03 §8 |
| 吸着したことを示すハイライトは**出ない** | 報告 03 §8 |
| トポロジー編集（共有頂点）はドメインには存在し、重なり解消後の溶接も裁定済み（HB3-10） | 報告 09 §3.3、報告 12 §4.3 |

**判定: 最も深刻な逸脱。** 比較対象のうち、面の境界を扱うすべての道具（QGIS が代表）が持っている中核機能が、
**ドメインには実装済みなのに合成ルートで未配線**という形で欠けている。報告 03 は「実運用に踏み切れない」の主要因である
可能性が高いと述べているが、比較の観点からもそれは妥当と評価する。

**再設計への含意**（意見）

- 定石に完全に従うべき箇所。`resolveProximity` / `isInsideTerminal` の配線は再設計の前提条件に置く。
- QGIS の「トレース」（既存境界に沿って引く）に相当するものが入れば、既存 775 地物の隙間を埋める作業が桁で速くなる。
  ただしドメインに該当関数は無いので新規実装になる。優先度は吸着の配線より下。
- グリッドスナップの既定値（10 度）は再設計とは独立に見直せる。

### 定石 3 — いま何を掴んでいるかを、文字で示す

**定石**: 選択中のオブジェクト名と件数は、常に文字で読める場所（ステータスバー／パネル見出し／属性表）に出す。
色や塗りだけで示すのは補助であって主ではない。

**他ツールでの実例**

- QGIS: ステータスバーと属性テーブルに選択件数が出る（知識による）。
- Figma: 右パネルの見出しが選択オブジェクトの名前になり、複数選択なら件数が出る（知識による）。
- Premiere: 選択クリップ名がプログラムモニタ／エフェクトコントロールに出る（知識による）。

**gimoza の現在**

| 事実 | 根拠 |
| --- | --- |
| 結合・所属変更ツールの**対象名と件数は `hidden` 属性つき**（テスト専用）で、画面には出ない | `src/ui/merge/MergeToolController.tsx:344-346`、`src/ui/reparent/ReparentToolController.tsx:352-357`、報告 04 §3.2 |
| 手掛かりは地図上の淡い塗りだけ。実データの海域のような細い地物では点にしか見えない | 報告 04 §3.2 |
| 頂点を何個選んでいるかを示す表示が**どこにも無い** | 報告 03 §5.2-3 |
| 矩形選択のラバーバンドが**描かれない**（描画層自体が存在しない）。ドラッグ中も確定後もプリミティブ数が変わらない | `src/render/` に該当なし、実測、`shots/03-24-編集-矩形選択ドラッグ中.png`、報告 03 §5.2-1 |
| ステータスバーに出るのは**カーソル座標 1 項目だけ**。選択件数・モード・ツール・縮尺は出ない | `src/ui/shell/StatusBar.tsx:15-24`、報告 01 §2.6 |
| 所属変更で同じ地物を 2 回クリックすると**黙って対象が外れる**。実験者本人が隠し要素を読むまで気付けなかった | `src/ui/reparent/useReparentTool.ts:231-236`、報告 04 §5-D |

**判定: 外れている。** 過去の実機報告でも同型の躓きが繰り返し出ている（HB3-6/15/16/18、報告 12 §F2）。

**再設計への含意**（意見）: ステータスバー（現在 28px・1 項目）を「モード／ツール／選択対象／件数／縮尺／時刻」を出す
帯として作り直すのが最小コスト。`hidden` を外すだけでも大半は改善する。

### 定石 4 — オブジェクト一覧は階層ツリーで、行の中に可視・ロックを置く

> 指示された論点 (b)「階層ツリー付きレイヤーパネル」

**定石**: 数百件の要素を扱う道具は、フラットな一覧を出さない。親子の入れ子で折りたためるツリーにし、
各行に「表示／非表示」「ロック」のトグルを置き、キャンバス上の選択と双方向に同期させる。

**他ツールでの実例**

- Figma: レイヤーパネルは親（フレーム・グループ）の下に子を入れ子にし、折りたたみ／展開できる。
  各行に**目玉アイコン（表示切替）**と**鍵アイコン（ロック）**があり、親をロックすると子も全部ロックされる[出典 5]。
  （なお **Figma のレイヤーパネル自体には検索／絞り込みが標準では無い**ことも検索で確認できた[出典 5]。
  つまり「一覧に絞り込み欄がある」gimoza の A1 裁定は Figma より進んでいる。）
- QGIS: レイヤーパネルはグループ化とチェックボックスによる表示切替を持つ（知識による）。
- Azgaar: レイヤーのプリセット（political / cultural / religions / biomes / provinces / heightmap …）を
  1 クリックで切り替える。各レイヤーの表示順・不透明度も操作できる[出典 4]。

**gimoza の現在**

| 事実 | 根拠 |
| --- | --- |
| 一覧は **775 行のフラットな名前の羅列**。インデントも折りたたみも無い | `src/ui/shell/SidebarContent.tsx:571-585`（`featuresAt(...).filter(...).map(...)` の平坦な写像）、報告 08 §5.1、現状.md **R9** / **FR-111** |
| 幅 220px 固定、行の高さ約 36px、内容高 **29,086px** | 実測、報告 01 §4.2 |
| 行に可視トグルもロックも**無い**。個別の非表示・強調は**右クリックからしか設定できず**、解除は表示制御パネルからしかできない | `src/ui/context-menu-launch.ts:113-124`、報告 07 §1・§5.2 |
| その表示制御パネルは一覧の**下に積まれており**、実データで `offsetTop` = **28,519px**（表示高 580px、約 49 画面ぶん下） | 実測、報告 07 §5.1、報告 01 §4.2 |
| 一覧（775 件）と検索（689 件）で**母集団が違う**。検索は「実際に描かれているもの」だけが対象なので、深度 0 では州が 0 件 | `src/ui/help-tools/HelpToolsController.tsx:276-289`、実測、報告 11 §4 |
| 集約の子 86 件は自分の履歴を持たないため、選んでもプロパティ欄に「歴史の錨」の欄が**出ない** | `src/ui/shell/SidebarContent.tsx:89`、`shots/11-real-data-10-child-aawen.png`、報告 11 §0 |
| 一覧から集約の子を選ぶと**カメラは飛ぶのに地図には何も描かれない**（深度 0 では州は描画対象外） | 実測、報告 11 §4 |

## 6. 確かめられなかったこと

1. **比較対象を実際に触っていない**。QGIS・Figma・Premiere・Aeon Timeline・Azgaar のいずれもこの PC には無く、
   記述は公式ドキュメント／ヘルプの検索結果（§7）と筆者の一般知識による。細部の操作感は未検証。
2. **ArcGIS Pro / DaVinci Resolve / Wonderdraft / Inkarnate / GeaCron / Illustrator の現行 UI は検索していない**。
   本文でこれらに言及した箇所は「（知識による）」と明記した。定石の主張はいずれも複数ツールに共通する部分だけを使っているので、
   1 ツールの細部が違っても結論は動かないが、これらを根拠に単独の主張をしてはいない。
3. **gimoza を自分では起動していない**。本文の gimoza 側の事実はすべて報告 01〜12 の実測・コード根拠を引いたもので、
   筆者による追加の実機観察は行っていない（担当が比較のため）。
4. **「錨をタイムラインに描く」が D32 に抵触するかは判断していない**。要件 §7.4 の文面（「重要な出来事を時間軸へ印として置き、
   そこへ飛ぶ機能」）は自分で置くしおりを指しているように読めるが、これは筆者の読みであってユーザーの意図ではない。
5. **定石 2（スナップ）の配線が本当に 2 本のポートを渡すだけで済むかは検証していない**。
   報告 03 §9.1 が「合成ルートがどちらも渡していない」ことまでは確認しているが、渡した後に
   `resolveSnap` が期待どおり動くか、FR-29 の拒否表示をどう出すかは未確認。
6. **重症度の付け方は筆者の判断**。「同種の道具なら必ず持っている度合い」は比較対象の選び方に依存する。
   所有者の実際の不満（未聴取、報告 09 §8・報告 12 §6）と突き合わせれば順序は変わりうる。
7. **競合他社の「架空世界の歴史地図エディタ」は見つけられなかった**。Running Reality が最も近い（時間データ専用の
   エディタを持つ[出典 7]）が、実在の歴史が対象で、階層（国 → 州 → 郡）の編纂機能があるかは確認できていない。
