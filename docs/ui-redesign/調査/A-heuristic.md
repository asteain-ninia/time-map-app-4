## 4. 再設計への申し送り（この評価から導かれるもの）

1. **「UI から届くか」を合否の基準にする。** 重症度 4 の 6 件のうち 5 件は「ドメインには実装があるのに画面から呼べない／届かない」型（A-02 A-03 A-05 A-06 と、A-01 の未配線）。新しい画面案は、要件 ID ごとに「どのボタンから何クリックで届くか」を書けなければ未完成とみなすのが妥当。
2. **状態表示を 1 か所に作る（N1 の 17 件がまとめて解ける）。** ウィンドウタイトル（プロジェクト名・ファイル名・未保存）とステータスバー（モード・ツール・選択件数・縮尺・最終保存時刻）。要件 §7.4 の非目標 2 番（世界名の常時表示）と 3 番（トースト）は、どちらも「地図の上への常時表示」「自動で消える通知」を禁じているだけなので、**この置き場所なら要件を書き換えずに解決できる**（09 報告 §2.1）。
3. **見た目の統一は安い。** 設計変数は `shell.css:17-30` に 11 個そろっている。A-33・A-34・A-61 は変数へ寄せるだけで消える。HB3-27（「デザインがイケてない」→「最後に装飾でOK」）は 2026-06-22 以来一度も着手されていない（12 報告 §4.4）ので、今回の計画に明示的に入れる。
4. **A-07（ツールチップがクリックを飲む）は 1 行で直る。** `.tooltip__bubble` に `pointer-events: none` を足すだけ。再設計を待たずに潰してよい種類の欠陥で、しかも開発ガイド §5.14「重なる UI は入力を受ける層も同時に設計する」の直接の違反例が現役で残っている、という意味で象徴的。
5. **「取り消せるか」で確認の要否を揃える（A-28）。** いまは地物の削除だけ確認があり、錨・リング・頂点の削除には無い。しかも A-12 のせいでツール中は取り消しも効かない。「取り消せるものは確認しない／取り消せないものは必ず確認する」という単純な規則に揃えるのが、覚えることを減らす。
6. **回帰テストの作り直しを見積もりに入れる。** E2E は 52 ファイル・130 テストで全緑（10 報告）。`data-testid` を変えると総取り替えになるが、「何を守るか」の一覧としては最良の資産なので移植する前提で読む。

## 6. 確かめられなかったこと

1. **実機（GPU あり・オフスクリーンでない）での見え方。** 今回はすべて `offscreen: true` のヘッドレス。ホバーの見え方・フォーカスリング・アニメーションは未検証（フォーカスの可視化は CSS 上 `.sidebar-list__filter-input:focus` 以外に定義が見当たらない、01 報告 §7）。
2. **修復ダイアログの実物。** 壊れた `.gimoza` を作る必要があり実施していない。A-50 はコード読解による所見（07 報告と同じ）。
3. **ベースマップ差し替えの実行結果。** ネイティブの画像選択ダイアログが開くためヘッドレスでは進められない。
4. **自動保存が 5 分で発火する様子。** タイマー待ちが要るため未確認。A-08 の「自動保存が無言」は結線（`FileOpsController.tsx:736`）と通知経路の不在からの所見。
5. **`vertexMarkerCap`（2000）を超えてハンドルが全部消える瞬間の実画面。** 実データで観測できた最大は 1736（03 報告）。
6. **タッチ・ペン入力。** `touch-action: none` の指定があるだけで未検証。
7. **A-07（ツールチップのクリック阻害）が実際の利用でどのくらい踏まれるか。** 合成イベントでは 100% 再現するが、生身のマウスは移動中に一度吹き出しから外れる可能性があるため、体感頻度は未測定。ただし吹き出しは `.tooltip` の子なので、ボタンから真上の吹き出しへ入っても `mouseleave` は発火しない（`src/ui/shell/Tooltip.tsx:27-34`）。構造上は「真上のボタンへ最短経路で動かすと必ず踏む」。
8. **スクリーンリーダーでの読み上げ。** `aria-pressed` / `role` の宣言はあるが、実際の読み上げは未検証。
