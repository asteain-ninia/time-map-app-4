# 11 — 実データの規模と、実運用のシナリオ

対象: `derle-import/derle-world-full-2026-08-16.gimoza`（正準・フル解像度）と `derle-import/derle-world-2026-08-16.gimoza`（間引き版）。
調査日: 2026-09-03。ソースは一切変更していない。ビルド済み `out/` をそのまま起動して観察した。

この文書は次の 4 つに答える。

1. 実データの規模（何がどれだけ入っているか）
2. 所有者が日常的にやるであろう作業を、デーレ界の固有名詞入りの具体シナリオにしたもの
3. ヘッドレス起動で実データを読み込む方法
4. 実データを読み込んだ画面のスクリーンショット

---

## 0. 結論の要約（先に読むところ）

- **実データは「世界の一枚絵」であって「歴史」がまだ 1 つも無い**。775 個の地物すべてが「0 年 → 継続中」の錨 1 個だけを持ち、歴史の錨は 1 地物あたり 1 個しかない。所有者がこれからやるのは**ほぼ全部が「歴史を足す作業」**であり、今の UI はその作業の入口が非常に細い。
- **集約地物（デーレ共和国・正統ノル王国・ラヴィエンド・ウィル同君王国）の子 86 個は、自分の歴史を 1 つも持っていない**。その結果、たとえば「アアウェン州」を選んでもプロパティ欄に**「歴史の錨」の欄そのものが出ない**（根拠: `src/ui/shell/SidebarContent.tsx:89` — 自分の履歴が無い地物は錨列が `null` になり、欄が描かれない。実測は §6 の `11-real-data-10-child-aawen.png`）。州の割譲・独立を記録するという中核作業が、いま画面から到達できない。
- **一覧（775 件）と検索（689 件）で母集団が違う**。一覧は全地物を出すが、検索は「実際に描かれているもの」だけを対象にする（`src/ui/help-tools/HelpToolsController.tsx:276-289`）。そのため階層深度 0 のままだと「アアウェン州」を検索しても 0 件になる（実測、§4）。
- **種別ラベル（島国・内陸国・州・領海など 10 種）は 775 件すべてに入っているのに、画面のどこにも出ないし編集もできない**（docs/現状.md R5）。にもかかわらず検索の属性値としては効いてしまい、「島国」で 341 件ヒットする（実測、§4）。見えないものが検索に引っかかる状態。
- 性能は問題になっていない。読み込みは実測 **2.2 秒**、選択の切り替えは **1〜2 ms**、1 フレームの描画入力生成は **2 ms**。つまり**今の使いづらさは速度の問題ではなく、情報の並べ方と作業導線の問題**である。

### 1.7 時間軸の現状 — **歴史はまだ 1 つも入っていない**

これが再設計にとっていちばん大きい事実。

- 履歴 689 本のすべてが**エントリ 1 個**（分布は `{"1": 689}`）。
- そのエントリはすべて `start = 0年 / end = null`（＝「0 年 → 継続中」）。
- 地物の属性も全 775 件が `startYear: 0, endYear: 9999` で同一。
- 実測: タイムラインで **3000 年へジャンプしても一覧は 775 件のまま、地図も一切変わらない**（`11-real-data-08-year3000.png`）。

要件の想定規模（要件定義書 §5.2）は **5,000 地物 × 平均 10 錨**。今の実データは **775 地物 × 1 錨**。つまりこれから、

- 地物数で **約 6.5 倍**、
- 錨の数で **約 10 倍**（775 → 7,750 前後）

まで育てる前提で UI を設計する必要がある。今でも一覧が 775 行の平坦なリストで扱いにくいのに（docs/現状.md R9 = FR-111 の階層表示未実装）、目標規模はその 6 倍以上ある。

### 1.8 データ固有の申し送り（`derle-import/README.md` より・調査不要と裁定済み）

再設計の際に「バグだ」と誤認しないための既知事項。

- **バアカが海域を持たないのは正しい**（ユーザー裁定 2026-08-09）。南極圏に近い国で、南限とコルニアとの境界だけが定まっている。
- **トルエホニエが「共有する海」なのは正しい**（ユーザー確認 2026-08-16）。トゥインクとの間に非武装地帯があり、海岸線で終わる国境線が実在する。
- **ラヴィエンド・ウィル同君王国は一国で正解**だが、1 段下でラヴィエンとウィルの 2 国に分かれる（同君連合）。
- 命名の衝突 1 件（「ジアーラ・ジアーラ内不明国」）、未割当ラベル 2 件（「（東ウィータ不明国）」「マカ」）。**アプリ内で改名・再割当できるはず**の残作業。
- 東西の地図端で分断された大陸は端で別地物のまま（アプリ内で合体できる）。

## 2. 実測した性能（今の使いづらさは速度のせいではない）

すべて正準データ（フル解像度）での実測。

### 2.1 読み込み

| 項目 | 実測 |
| --- | ---: |
| ヘッドレス起動 → 実データ投入 → 一覧に 775 件が出るまで | **2.2 秒** |
| 修復ダイアログ（FR-106） | 出ない（整合性 ok=true） |

要件 §5.1 の「データロード時間はある程度長くてよい」に対して十分速い。

### 2.2 表示解決と描画（`derle-import/tools/diagnose-perf-depth.ts` / `diagnose-selection.ts` の実出力）

| 項目 | 実測 |
| --- | ---: |
| 表示解決 深度0 初回 | 266 ms |
| 表示解決 深度0 2 回目（キャッシュ命中） | 0.05 ms |
| 表示解決 深度1 初回 | 21 ms |
| 別時刻へ移動して深度0 | 18 ms |
| 選択なしの描画入力組み立て | 1.4 ms |
| 末端地物を選択 | 1.0 ms |
| デーレ共和国（子 60 の集約）を選択 | 1.2 ms |
| 選択の付け外しの往復 | 1.9 ms |
| 1 フレームの描画入力生成（全体表示） | 1.9〜2.0 ms |

要件 §5.1 の「選択・編集操作の応答 100 ms 以内」を大きく下回っている。過去に報告のあった「デーレ共和国を選択すると待たされる」は解消済み。

**したがって UI 再設計の争点は速度ではない。** 情報の見つけやすさ・作業の到達しやすさが争点である。

### 2.3 ただし残っている性能上の制限

- `docs/現状.md` L2: 海岸線のように頂点が密な地物を大量選択したまま動かすと 1 フレーム 27 ms 程度かかる（描画予算 16.6 ms 超過）。実データは頂点 2,230 の地物を持つので、この経路には確実に触る。

## 3. デーレ界の所有者が日常的にやるであろう作業（具体シナリオ）

固有名詞は実データに実在するものだけを使った。各シナリオに「いま何が要るか」「今の UI でどこまで行けるか」を付けた。

### 3.1 いますぐ必要になる整備作業（歴史を書き始める前の地ならし）

| # | シナリオ | 要る操作 | 今の UI での到達度 |
| --- | --- | --- | --- |
| **S1** | 「デーレ共和国の ???州（10 件）」に本当の州名を入れる。同じく「デーレ共和国の領域01〜27」の断片に名前を付けるか、隣の州へ吸収する | 名前の変更 ×37、または結合（FR-50） | **名前変更は可能だが到達が重い**。深度 0 では州が描かれないので、まず階層深度を 1 に上げてからでないと地図で選べない（実測: 深度0 のクリック → agg-02、深度1 → area-341 ???州）。一覧には深度 0 でも出るので一覧からは選べるが、775 行のフラットな並びから 10 個の「???州」を拾うことになる |
| **S2** | 「ヴィオニア大陸付近の領域01」「アレクリオ大山脈付近の領域24/25」など **220 件の仮名領域**を、実在の国名に順次改名していく | 名前の変更 ×220 | 1 件ずつ「一覧で探す → 選ぶ → プロパティタブへ切り替える → 編集モードにする → 名前を直す → 保存」。**一括改名も、次の未命名へ送る導線も無い**。選択してもプロパティタブへ自動で切り替わらない（要件定義書 §7.4 で非目標と明記） |
| **S3** | 「（アクセル不明国A〜Z）」15 件のように、同じ地方にまとまっている不明国を調べて確定していく | 名前の変更＋種別ラベルの付与 | 名前は変更可。**種別ラベルの入力欄がそもそも無い**（R5 / FR-40）。データには「海岸線まで国境界」等が入っているのに画面から見えない |

## 5. ヘッドレス起動で実データを読み込む方法

### 5.1 結論: **「ダイアログを使わない裏口」は用意されていない。ただし D&D 経路を合成イベントで叩けば読み込める。**

調べた結果:

- **`E2E_TEST=1` はファイル読み込みには一切関与しない**。オフスクリーン描画（`src/shell/main/index.ts:192`）、単一インスタンスロックの回避（同 :73）、終了ガードの素通し（同 :587）だけ。
- **コマンドライン引数からの読み込みは意図的に非対応**。`src/shell/main/index.ts:75` に「§7.4 非目標により argv の .gimoza パス処理は行わない（focus のみ）」と明記されている。要件定義書 §7.4 の「OS ファイル関連付け起動読込」非目標と対応。
- **`e2e/` 配下に実データを読み込む spec は 1 本も無い**。`grep -rn "loadDropped" e2e/` のヒットは `e2e/launch.spec.ts:46,54` の 2 か所だけで、いずれも「preload に `loadDropped` という関数が生えているか」を型で確かめているだけ。**実ファイルを読み込む E2E は存在しない**。
- **`window.timeMapApi.loadDropped(path)` を直接呼ぶだけでは足りない**。それはメインプロセスから解析済み manifest を返すだけで、レンダラの状態には反映されない。反映は `dropLoadCommand`（`src/ui/file-ops/file-commands.ts:181`）が `reflectProject` まで通したときに起きる。
- **使える口は 1 つ**: `#app-shell` に貼られている React の `onDrop`（`src/ui/App.tsx:3222-3224`）。ハンドラは `src/ui/file-ops/FileOpsController.tsx:831-841` にあり、`e.dataTransfer.files[0].path` しか見ていない:

```
const file = e.dataTransfer.files[0];
const droppedPath = (file as (File & { path?: string }) | undefined)?.path;
if (droppedPath === undefined || droppedPath === '') return;
void runExclusive(() => dropLoadCommand(ports, droppedPath));
```

したがって、`dataTransfer` を差し替えた `drop` イベントを `#app-shell` へ流せば、**メニューの読み込みとまったく同じフロー**（教訓 5.6「同一フロー」）でファイルが読める。

### 5.2 手順

1. `e2e/helpers.ts` の `launchApp()` と同じ引数で `_electron.launch` する（`E2E_TEST=1`、`--user-data-dir=一時ディレクトリ`、`--disable-gpu`、`--no-sandbox`、`--disable-software-rasterizer`、`cwd` はプロジェクト直下、`ELECTRON_RUN_AS_NODE` は env から**削除**）。
2. `[data-testid="app-shell"]` が attach されるまで待つ。
3. 下の合成イベントを `page.evaluate` で流す（`p` は `.gimoza` の絶対パス）。
4. 読み込み完了は `[data-testid="unified-list-count"]` が `775件` になるのを待つのが確実（`diagnostics-feature-count` は診断ダイアログの中なので普段は DOM に無い）。実測 2.2 秒。

手順 3 で流すコード:

```js
const root = document.getElementById('app-shell');
const mk = (type) => {
  const ev = new Event(type, { bubbles: true, cancelable: true });
  Object.defineProperty(ev, 'dataTransfer', {
    value: { files: [{ path: p, name: 'x.gimoza' }], types: ['Files'] },
  });
  return ev;
};
root.dispatchEvent(mk('dragover'));
root.dispatchEvent(mk('drop'));
```

注意点:

- スクリプトを scratchpad に置くと `playwright` / `fflate` が解決できない。`import { _electron } from 'file:///E:/WORKSPACE/time-map-app-4/node_modules/playwright/index.mjs'` のように**絶対パスで import** する。
- `--user-data-dir` は必ず一時ディレクトリにする（他のエージェントと同時に Electron を起動するため。`e2e/helpers.ts` の注記どおり、放置すると利用者の本番 userData を汚し GPU キャッシュを奪い合う）。
- 実データは整合性 `ok=true` なので修復ダイアログ（FR-106）は出ない。壊れたファイルを流す場合は `[data-testid="repair-dialog"]` の面倒を見る必要がある。

### 5.3 代替案（合成イベントを使いたくない場合）

- **保存側から回す**: 新規プロジェクトで作業して `Ctrl+S` → ネイティブの保存ダイアログが出るので、こちらは裏口が無い。読み込みだけが D&D で回避できる非対称な状態。
- **ドメイン層で読む**: `derle-import/tools/diagnose-*.ts` と同じく `readTmap` → `parseManifest` → `manifestToProject` を `vite-node` で直接呼ぶ。画面は出ないが、データの中身と性能はこれで測れる（本調査の §1・§2 の数値はこの経路）。
- **本筋の改善案**: `E2E_TEST=1` のときだけ `--open-file=<path>` を受け付ける起動オプションを足せば、実データを載せた E2E が書けるようになる。今は「実データで動くこと」を守るテストが 1 本も無い。

## 7. 再設計に効く発見（優先度つき）

1. **集約の子に歴史が持てない（＝持っていない）ことが、いちばん大きな穴**。実データの 86 件（デーレ 60・正統ノル 14・ラヴィエンド・ウィル 12）が該当。「州が独立する」「州を割譲する」というこのアプリの中核作業が、その地物のプロパティ欄からは着手できない。再設計では「子を選んだときに何が起きるべきか（親の錨を編集するのか、子に錨を生やすのか）」を先に決める必要がある。
2. **一覧・検索・地図で「見えているもの」が三者三様**。一覧 775、検索と地図 689。ユーザーから見れば同じ「デーレ界の地物」なのに、探す場所によって出たり出なかったりする。深度スライダーがこの三者を別々に動かしている。最悪の形が「一覧からアアウェン州を選ぶ → カメラは飛ぶ → 地図は真っさら」で、**選んだのに見えない**という状態が普通に起きる（`11-real-data-10-child-aawen.png`）。選択したものが描画対象外なら深度を自動で上げる、といった手当が要る。
3. **一覧が 775 行のフラットな羅列で、目標規模は 5,000**。階層・種別・年代のどれでもグループ化できず、並べ替えも無い。仮名 600 件超を潰していく作業（S1〜S4）が、そのまま一覧の使い勝手の勝負になる。
4. **種別ラベルが「データにはあるが画面に無い」**。10 種・775 件すべてに入っていて、検索には効いてしまう。表示・編集できるようにするだけで、S3・S6・S19 が一気に楽になる。
5. **時間の表現が 2 か所にある**（属性の開始年/終了年 と 錨の存続期間）。実データは両方が別の値（属性 0〜9999／錨 0年→継続中）で入っているので、歴史を書き始めた瞬間に食い違う。
6. **歴史を俯瞰する画面が無い**。689 本の履歴に何年の錨があるのかを一望できないので、「1200 年に何が起きたか」を確かめられない。要件定義書 §7.4 でイベントマーカーは非目標とされ、錨一覧が代替とされているが、実データ規模ではその一覧が 689 行のフラットなリストになる。
7. **性能は足を引っ張っていない**。読み込み 2.2 秒、選択 1〜2 ms。速度のための妥協（描画を減らす、深度を上げないと見えない、等）を UI 側で続ける理由はもう無い。
8. **実データで動くことを守るテストが 1 本も無い**。`e2e/` に実ファイルを読む spec が存在しない。再設計するなら、実データを載せた E2E を用意できる読み込み口（`--open-file` 相当）を先に足すのが安い。

## 8. 確かめられなかったこと

- **集約の子に「自分の錨」を生やせるかどうか**。ドメイン側に手段があるのか、UI に導線が無いだけなのかを、コードの読み込みだけでは確定できなかった（所属変更ツールを実データで最後まで通す実験はしていない）。S7・S8・S12 の可否がここで決まる。
- **編集・保存を伴う実データでの往復**。保存はネイティブダイアログを通るのでヘッドレスから実行できず、「775 地物を編集して保存し直すのに何秒かかるか」は測っていない。
- **1 地物あたり 10 錨まで育てたときの挙動**。要件の目標規模（5,000 地物 × 10 錨）に近いデータを持っていないので、表示解決 266 ms がどう伸びるかは未測定。
- **`docs/現状.md` L2（密な地物の大量頂点移動で 27 ms）が実データで実際にどれだけ出るか**。ヴィオニア大陸付近の領域01（2,230 頂点）で再現実験はしていない。
- **地図を直接クリックしたときの選択の実測**。編集モードへの切り替え後にクリックした座標が海上（北緯15度・西経79.2度）だったため未選択に終わった。深度別の当たり判定は `diagnose-perf-depth.ts` の出力（深度0→agg-02、深度1→area-341 ???州）で代用している。
