# UI 全面再設計の資料（`docs/ui-redesign/`）

この配下は、2026-09 に始めた **gimoza の UI 全面再設計** の作業資料である。

開発ガイド §2.1 が定める文書は 5 つ（要件定義書 / 技術方針 / 開発ガイド / 現状 / 実装済み）で、
**この配下はそのどれでもない補助資料**である。位置づけは `specs/`（着手指示書）や
`reference/`（前世代の参照素材）と同じ「補助」だが、あちらが**凍結した過去の資料**なのに対し、
こちらは**進行中の作業資料**である点が違う。

## 恒久文書との関係（どちらが正か）

| 迷ったとき | 正 |
| --- | --- |
| 「何を満たすべきか」（仕様） | `docs/要件定義書.md` |
| 「どう実現するか」（技術選定・確定した設計判断） | `docs/技術方針.md` |
| 開発作法・再発防止の恒久知識 | `docs/開発ガイド.md` |
| 未解決課題・既知の不具合・残作業 | `docs/現状.md` |
| いつ何を実装したか | `docs/実装済み.md` |
| **この再設計で何をどう変えるつもりか** | この配下（`02-設計書.md` が中心） |

**この配下と恒久文書が食い違ったら、恒久文書が正である。** 再設計で確定した判断は、
実装と同じ変更単位で恒久文書側（技術方針・要件定義書）へ反映する。この配下は
「そこへ至った経緯と、まだ実装していない計画」を保持する。

再設計が完了したら、この配下は `specs/` と同じ枠組みで**凍結**する（このファイルに凍結宣言を置く）。

## 中身の区分

| 場所 | 役割 | 書かないもの |
| --- | --- | --- |
| `01-現状分析.md` | **いまの UI の何がどう困るのか**（実測つき）。欠陥は `N-◯◯` の番号で参照する | 直し方（設計書の役目） |
| `案/` | 5 つの**設計案**（P1〜P5）。方向性の異なる素案で、採用したのは 1 つではなく**要素の組み合わせ** | 現状の分析・実装の手順 |
| `調査/` | 分析の**素材**（画面ごとの読み取り、専門家別の評価、実データ試行、実測ログ）。番号は分析の観点ごと | 結論（分析・設計書の役目） |
| `審査/` | 設計案と実装に対する**外部の審査・反証**の全文。査読者ごとに 1 ファイル | 直したかどうか（進捗の役目） |
| `02-設計書.md` | **採用した設計**。画面の構成・寸法・語彙・守るべき制約（`K-◯`）・却下した案とその理由（§O） | 実装の手順・進捗 |
| `03-実装計画.md` | **増分の切り方**と、各増分の中身・受け入れ条件 | 設計の理由（設計書の役目） |
| `進捗/` | 増分ごとの**完了報告と申し送り**。実際にやったこと、設計書との食い違い、次への引き継ぎ | 再発防止の恒久知識（開発ガイド §5 へ） |

## 番号の読み方

- `N-◯◯` … 現状分析で挙げた**欠陥**（`01-現状分析.md`）。
- `K-◯` … 設計が**守り続けなければならない制約**（`02-設計書.md` §J.1）。
- `V◯` … 所有者が挙げた**実運用に踏み切れない理由**（同上）。
- `B-◯◯` … 審査での**指摘**（`02-設計書.md` §O が採否と理由を記録する）。
- `BH1-◯◯` … 増分 1 に対する**探索的バグ狩り**の観察（`進捗/増分1.md` §4）。
- `BH2-○○` … 増分 2 に対する探索的バグ狩りの観察（`進捗/増分2.md` §5）。

いずれもこの配下の中でだけ使う番号である。恒久文書側の課題番号（`docs/現状.md` の `R◯` / `B◯` /
`L◯` / `V◯` / `N◯`）とは**別の体系**なので、混ぜないこと。後の増分へ送る項目は、
この配下の番号のまま置いておかず、`docs/現状.md` に恒久文書側の番号で立て直す。
