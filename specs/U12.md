# U12 純粋コマンド基盤とアンドゥ/リドゥ二重スタック

## 目的

本ユニットは、ユーザーの各編集操作を「コマンド → 新ドメイン状態」を生成する純粋関数として表現し、その実行履歴をアンドゥスタックとリドゥスタックの二重スタックで純粋に管理する基盤を構築する。この基盤は、点・線・面の追加/編集/削除、錨の追加/変更/削除、分割・結合・所属変更といった複合操作、そして競合解決プロセスの結果全体に至るまで、本アプリのあらゆる状態変更が共通して載る「履歴付き状態遷移」の唯一の経路となる。

本ユニットが提供するのは「コマンドという契約・コマンドを適用して状態を進める実行器・履歴を二重スタックで保持する履歴マネージャ」という三点であり、個々の編集ロジック（具体的なコマンドの中身）は本ユニットでは実装しない。ここで定める契約と不変条件を、後続のユニットが実装する個別コマンドがすべて遵守することで、複合操作の不可分性（FR-94）、単一アンドゥ単位（FR-73）、二重スタックと上限管理（FR-74）が構造的に保証される。

## スコープ

### やること

1. **ドメイン状態への純粋関数によるコマンド適用の契約定義**
   - コマンドは「現在のドメイン状態」を入力に取り、「新しいドメイン状態」と「コマンド結果」を出力する純粋関数として定義する。同一入力に対し常に同一出力を返し、入力状態を破壊的に変更しない。
   - イミュータブル更新は Immer（`produce`）で行い、構造共有により大規模データ（目安 5,000 オブジェクト × 平均 10 錨）でも履歴を効率よく保持する。

2. **コマンド結果契約（残存/新規/削除 ID を返す）**
   - すべてのコマンドは、適用後に「残存した要素 ID」「新規生成された要素 ID」「削除された要素 ID」を含む結果オブジェクトを返す（教訓 5.11）。UI 層・選択管理層は、固定の全クリアではなくこの結果から選択状態を再解決できる。

3. **二重スタックによるアンドゥ/リドゥの純粋実装**
   - アンドゥスタックとリドゥスタックを持つ履歴マネージャを、副作用のない純粋関数（または不変な履歴値を入れ替える薄い保持構造）として実装する。
   - 履歴の深さ上限はデフォルト 100 操作で、設定で変更可能とする（FR-74）。上限到達時は最古の操作から破棄する。
   - 新しい編集操作を実行したとき、リドゥスタックを全破棄する（FR-74）。

4. **複合操作の原子性（単一アンドゥ単位）**
   - 複数の下位操作からなる複合操作（分割・結合・所属変更・競合解決の結果全体など）を、1 件のアンドゥ単位として原子的に積む基盤を提供する。1 回のアンドゥで複合操作前の状態へ、1 回のリドゥで複合操作後の状態へ、過不足なく復元できる（FR-73 / FR-94）。

5. **redo での初回生成 ID の復元**
   - ID を生成するコマンドは、undo に必要な情報（生成した ID を含む依存データ）を過不足なく保存し、redo 時に ID を採番し直さず初回生成 ID を復元する（教訓 5.20）。

6. **execute / undo / redo の対称通知規約**
   - 状態変更を伴うコマンドの execute / undo / redo は、同じイベント規約で、操作が触れた（touch した）全要素へ対称に通知する契約を定義する（教訓 5.23）。同一の状態変化を二重通知しない。

7. **アンドゥ/リドゥ可否の問い合わせ**
   - 現時点でアンドゥ可能か・リドゥ可能かを返す純粋な述語を提供し、UI 側がメニュー項目とショートカットの有効/無効を切り替えられるようにする（FR-74）。

### やらないこと

- 個別コマンドの具体的ロジック（点/線/面の追加・編集・削除、錨編集、分割・結合・所属変更、競合解決の差分適用）の実装。本ユニットは契約と基盤のみを提供し、個別コマンドは後続ユニットが本契約に従って実装する。
- ドメインモデルそのもの（地物・頂点・リング・錨・ツリーの型と不変条件）の定義。これは依存ユニット U03 が提供する前提とする。
- UI 層（React）・描画層（Canvas）・状態ブリッジ（Zustand subscribe）への接続実装。本ユニットは UI 非依存・描画非依存の `domain` 層に閉じる。通知規約は「契約」として定義し、実際の購読配線は別ユニットが行う。
- 永続化（履歴のファイル保存）。履歴はセッション内のメモリ上のもので、保存対象ではない。
- ドラッグ中の連続更新そのもの（毎フレームの一時状態管理）。ホットパスは確定時にのみ正式コマンドを発行する方針（後述「注意点」）であり、連続更新の実体は編集ツール側ユニットが扱う。

## 依存（dependsOn）

- **U03**: ドメイン状態の型・地物/頂点/リング/錨の表現・ドメイン不変条件を提供する基盤ユニット。本ユニットのコマンドは U03 が定義する「ドメイン状態」を入出力とし、U03 の型（点/線/末端/集約、領土リング/穴リングなどの判別共用体）に依存する。

U03 がまだ着手対象である場合でも、本ユニットの実装者は U03 が公開する「ドメイン状態のルート型」「要素 ID 型」を前提インタフェースとして仮定し、その境界に対してコマンド契約を組み立てること。U03 の具体的な内部表現に踏み込まず、ルート状態を不変に受け渡す純粋関数として閉じる。

## 実装方針（技術方針に沿う）

技術方針の 1.（採用スタック）・2.6（純粋コマンド ＋ Immer ＋ 二重スタック）・2.5（Zustand ＋ 純粋ドメインコア）・2.13（ディレクトリ層分離と依存方向の内向き固定）に従う。

### 配置と依存方向

- 本ユニットの全コードは `domain` 層（フレームワーク非依存・純粋）に配置する。Electron / React / Canvas / Zustand を一切 import しない。`domain` は Vitest 単体で実行できる状態を保つ。
- 依存方向は `domain` へ内向きに固定する。本ユニットは外側の層（render / ui / shell）へ依存してはならない。通知規約は `domain` 内で完結する抽象（後述）として定義し、外側の購読は外側から `domain` を購読する形にする。

### コマンドの契約

- コマンドは「ドメイン状態 → { 新ドメイン状態, コマンド結果 }」を返す純粋関数として表現する。状態の不変更新は Immer の `produce` を用い、入力状態を破壊しない（構造共有）。
- コマンド結果は少なくとも以下を含む契約とする（教訓 5.11）。
  - 残存した要素 ID の集合
  - 新規生成された要素 ID の集合
  - 削除された要素 ID の集合
  - execute / undo / redo の対称通知に用いる「touch した要素 ID の集合」（通知対象。教訓 5.23）
- ID を生成するコマンドは、生成した ID を結果および履歴エントリへ保存し、redo 時にこの保存値を復元して採番し直さない（教訓 5.20）。
- コマンドの判別は型定義・定数・ファクトリを経由し、表示文字列や思い込みで分岐しない（教訓 5.19）。

### 履歴（二重スタック）の実装

- アンドゥスタックとリドゥスタックを保持する履歴値（不変なデータ構造）を定義する。履歴操作（push / undo / redo / clearRedo / trim）は、現在の履歴値を入力に取り新しい履歴値を返す純粋関数として実装し、前後を直接テスト比較できるようにする。
- 履歴エントリは、その操作を「元に戻す」「やり直す」のに必要な情報を過不足なく持つ。実装方式は次のいずれか（または併用）を許容するが、いずれの場合も Immer の構造共有でメモリ効率を確保すること（技術方針 2.6、リスク R4）。
  - 操作前後の関連状態スナップショット（差し替え方式）
  - もしくは execute/undo/redo を再現できる逆操作情報
- 上限管理: 履歴の深さ上限はデフォルト 100、設定で変更可能。新規 push 時に上限超過分は最古から破棄する（FR-74）。
- リドゥ全破棄: 新しい編集操作を execute（push）したとき、リドゥスタックを全破棄する（FR-74）。
- アンドゥ/リドゥ可否: アンドゥスタックが空でなければアンドゥ可、リドゥスタックが空でなければリドゥ可、を返す純粋述語を提供する。

### 複合操作の原子性

- 複合操作は、内部の複数下位操作を 1 件の履歴エントリ（複合エントリ）にまとめて push する。アンドゥ/リドゥは複合エントリを単位として処理し、部分的なアンドゥ/リドゥを許可しない（FR-73 / FR-94）。
- 複合エントリの結果オブジェクトは、構成下位操作全体を通じての「残存/新規/削除/touch」を集約して返す（途中で削除され最終的に残らない ID は新規にも残存にも数えない、など集約規則を明示する）。

### 通知規約

- execute / undo / redo は、コマンド結果の「touch した要素 ID の集合」に対して、同じイベント規約で対称に通知する契約とする（教訓 5.23）。`domain` 内では通知を「結果に含まれる touch 集合」という値として表現し、実際の発火/購読は外側の層が結果を読んで行う（純粋性を保つため、`domain` 内で副作用的にイベントを撒かない）。
- execute 後に「直後の手動リフレッシュ」を呼びたくなる状況は通知漏れのサインとみなし、touch 集合の取りこぼしを疑うこと。

### ホットパスへの配慮

- ドラッグ中の連続更新など毎フレーム不変コピーを取ると応答 100ms（NFR 5.1）を脅かすホットパスは、本ユニットの履歴へ毎フレーム push しない。連続操作は一時バッファ（Immer のトランジェント等）で処理し、操作確定時にのみ正式なイミュータブルコマンドを 1 件発行して履歴へ積む（技術方針リスク R5）。本ユニットは「確定時に 1 件積む」入口を提供することでこの方針を支える。

### no-op ガード

- 値が変わっていなくても発火しうる確定（blur / Enter 等）を履歴へ載せる場合、確定値が現在状態（baseline）と一致するなら履歴エントリを積まない no-op ガードを設けられるようにする（教訓 5.24）。ガードの baseline は確定元と同一ソースから導出する。

### テスト方針（技術方針 2.14 / NFR 5.8）

- Vitest でコマンドの「入力状態 → コマンド → 期待状態」を直接比較する単体・契約テストを書く。
- fast-check のプロパティテストで、履歴操作の不変条件（後述「受け入れ基準」の機械検証可能な性質）を生成入力で網羅する。
- 通知（touch 集合）の回帰テストは、期待集合を厳密一致で検証する（包含判定にしない。教訓 5.23）。

## 受け入れ基準

以下はすべてテスト可能な形で満たすこと。

1. **コマンドの純粋性と前後比較**
   - 任意のコマンドについて、適用前のドメイン状態が破壊的に変更されないことをテストで確認できる（同一参照ではなく構造共有された新状態が返る）。
   - 同一入力状態に同一コマンドを適用すると、常に同一の新状態・同一のコマンド結果が得られる（決定性）。
   - 「入力状態 → コマンド → 期待状態」を Vitest で直接比較できる。

2. **二重スタックの上限・最古破棄・リドゥ全破棄（FR-74）**
   - 上限（デフォルト 100、設定変更可）を超えて push すると、アンドゥスタックの長さが上限を超えず、最古のエントリから破棄される。
   - 設定で上限値を変更でき、変更後の上限が適用される。
   - アンドゥ後に新しい編集操作を execute すると、リドゥスタックが全件破棄される。
   - アンドゥ不可（アンドゥスタック空）・リドゥ不可（リドゥスタック空）を返す述語が正しく、UI 無効化判定に使える。

3. **複合操作が単一アンドゥ単位として復元される（FR-73 / FR-94）**
   - 複数下位操作からなる複合操作を実行後、1 回のアンドゥで複合操作前の状態へ完全復元され、1 回のリドゥで複合操作後の状態へ完全復元される。
   - 複合操作のアンドゥ/リドゥが、構成下位操作のいずれかだけを部分的に適用する結果にならない（不可分）。

4. **コマンド結果が残存/新規/削除 ID を返す（教訓 5.11）**
   - 構造変更操作（生成・削除・置換を含む）のコマンド結果に、残存 ID 集合・新規 ID 集合・削除 ID 集合が含まれる。
   - 複合操作の結果は、構成下位操作を集約した残存/新規/削除を返し、途中生成かつ最終削除された ID が新規にも残存にも計上されない集約規則を満たす。
   - UI 側がこの結果から選択を再解決できる（固定全クリアに依存しない）ことを、選択再解決を模したテストで確認できる。

5. **redo で初回生成 ID を復元・対称通知（教訓 5.20 / 5.23）**
   - ID 生成を伴うコマンドを execute → undo → redo したとき、redo 後の要素 ID が初回 execute 時に生成した ID と一致し、採番し直されない。
   - execute / undo / redo が、コマンド結果の touch した全要素 ID の集合に対して対称に通知する（同じイベント規約・二重通知なし）。通知の回帰テストは期待集合の厳密一致で検証する。

## 関連要件（FR-id）

- **FR-73**（must）: すべての編集操作（錨の追加・変更・削除および競合解決の結果全体を含む）にアンドゥ・リドゥで対応し、単一のユーザーアクションをアンドゥ単位とする。複合操作も一連全体を単一アンドゥ単位として扱う。
- **FR-74**（should）: アンドゥスタックとリドゥスタックの二重スタックで管理し、深さ上限はデフォルト 100（設定変更可）、上限到達時は最古から破棄、新しい編集操作実行時はリドゥスタックを全破棄、アンドゥ/リドゥ不可時は対応メニュー項目とショートカットを無効化する。
- **FR-94**（must）: 分割・結合・所属変更などの複合操作は不可分の 1 操作として履歴記録・イベント通知・整合性検証を一括完了し、1 回のアンドゥで復元できる。

参照する教訓（開発ガイド §5）: 5.11（構造変更後の選択は結果から再解決）、5.20（元に戻す情報の過不足ない保存・redo で初回生成 ID 復元）、5.23（execute/undo/redo の対称通知）。あわせて 5.19（分岐識別子はファクトリ経由）、5.24（no-op ガード）も適用する。

## 注意点・既知の落とし穴（教訓を踏まえる）

作業開始前に、以下の教訓を引用し「適用:」を 1 文以上で宣言してから着手すること（開発ガイド §1.6 AI 作業開始ゲート）。

- **教訓 5.11（構造変更操作後の選択は結果から再解決する）**: 「結合・分割・移動・削除のように対象 ID や形状が変わる操作では、完了後の選択状態を固定の全クリアで決めない。コマンド結果が『残る要素 ID』『新規要素 ID』『削除された ID』を返し、UI はその結果から選択を再解決する。」
  適用例: コマンド結果型に残存/新規/削除 ID 集合を必須フィールドとして含め、これを返さないコマンドが型レベルで作れないようにする。複合操作はこれらを集約して返す。

- **教訓 5.20（元に戻す情報は依存データも含めて過不足なく保存する）**: 「ID 等を生成するコマンドは、redo で採番し直さず初回生成 ID を復元する。」
  適用例: ID 生成コマンドは生成 ID を履歴エントリへ保存し、redo はその保存値で復元する。redo が新規採番すると undo/redo を往復するたびに ID が変わり、参照（親子関係・共有頂点・選択）が壊れる。execute→undo→redo で ID 不変を回帰テストする。

- **教訓 5.23（コマンドの execute/undo/redo は対称に通知する）**: 「同じイベント規約で、touch した全要素へ対称に通知する。直後に手動リフレッシュを書きたくなったら、通知漏れのサインである。同一の状態変化を二重通知しない。検出: 期待イベント集合を厳密一致で検証する。」
  適用例: コマンド結果に touch 集合を持たせ、execute/undo/redo すべてが同一規約で通知する。通知テストは厳密一致（包含判定にしない）で重複・過剰・欠落を捕まえる。

- **教訓 5.24（確定ハンドラには no-op ガードを入れる）**: blur/Enter のように値不変でも発火する確定を履歴へ載せると「幽霊 undo エントリ」が積まれる。確定値が baseline と一致するなら履歴に積まない。baseline はフォーム同期と同一ソースから導出する。

- **教訓 5.19（分岐識別子は型定義・定数・ファクトリを経由する）**: コマンド種別を文字列リテラルの直書きで分岐せず、型・定数・ファクトリを経由する。新コマンド種別の追加・改名時は作成・実行・undo・redo の全経路で同じ値を使うテストを置く。

- **横断指針（開発ガイド §4「層をまたぐ契約の固定」）**: コマンド結果型・履歴値型は層をまたぐ契約であり、偶然の一致に頼らず共有型と両側テストで固定する（教訓 5.33 / 5.34 の精神）。

- **純粋性の死守（技術方針 2.6 / 5.4）**: 履歴・コマンドは `domain` に閉じ、副作用（イベント発火・ログ・I/O）を `domain` 内で起こさない。通知は「結果に含まれる touch 集合という値」として表現し、発火は外側の層に委ねる。これにより前後状態をテストで直接比較でき、Worker へのオフロードも純粋関数ゆえ容易になる（技術方針リスク R9）。

- **メモリ上限（技術方針リスク R4 / NFR 5.2）**: 上限 100 のアンドゥスタックを 5,000 オブジェクト規模で保持してもメモリ 2GB を超えないよう、Immer の構造共有を前提とし、履歴エントリで状態全体のディープコピーを保持しない（差分または構造共有された参照で持つ）。

- **ホットパスの分離（技術方針リスク R5 / NFR 5.1）**: ドラッグ等の連続更新を毎フレーム履歴へ積まない。確定時に 1 件だけ正式コマンドを発行する。これを破ると 100ms 応答が脅かされ、かつ「1 ドラッグ＝多数の undo エントリ」という単一アンドゥ単位違反（FR-73）を生む。

- **やり残しの記録（開発ガイド §1.8）**: 本ユニットで保留した判断（履歴エントリの実装方式選択など後続ユニットへ波及するもの）は現状.md に記録する。新たに根本原因を教訓化すべき事象があれば開発ガイド §5 へ追記してから完了とする（§1.5）。
