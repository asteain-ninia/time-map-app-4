# U15 型付きIPCとファイルI/Oアダプタ(.tmap ZIP・アトミック保存・世代バックアップ)

本書は実装ユニット U15 の実装指示書である。実装者（別エージェント）はこの指示書だけを読んで着手できることを目的とし、前提知識は本書内に閉じて記述する。要件・技術方針・開発作法の根拠は本文および末尾の「関連要件」「注意点・既知の落とし穴」に引用する。本書は time-map-app-4（以下「本アプリ」）のクリーンルーム文書であり、過去版・他プロダクト・外部の既存実装には一切依存しない。必要な制約はすべて本アプリ自身の要件・方針として直接記述する。

---

## 目的

本アプリのプロジェクトデータを、単一の `.tmap` ファイル（ZIP コンテナ）として安全に保存・読み込みする層を確立する。具体的には次の 4 点を満たす。

1. **`.tmap`（ZIP コンテナ）の読み書き**: マニフェスト JSON＋ベースマップ画像＋添付画像を 1 ファイルに同梱し、保存内容の論理的完全性（FR-103）を確保する。
2. **アトミック保存（破損防止）**: 書き込みは「一時ファイルへ書く → fsync → アトミックリネーム」で行い、書き込み途中のクラッシュでも既存ファイルを破損させない（NFR 5.3）。
3. **自動保存と世代バックアップ**: 設定可能な間隔（既定 5 分）の自動保存と、保存ファイルごとに最大 10 世代のタイムスタンプ付きバックアップ（超過は古いものから削除）を提供する（FR-108）。
4. **型付き IPC のみの公開**: Electron の preload では型付き IPC のみを公開し、レンダラがファイルシステムへ直接触れる経路を作らない。IPC チャネルの契約は呼び出し側・公開側・受信側の両側テストで固定する（開発ガイド §5.33）。

本ユニットは「シェル／preload 層」のファイル I/O アダプタである。地物・錨・ツリーといったドメインモデルそのものは実装しない。本ユニットが扱うのは「ドメインが直列化したデータ構造（バイト列・JSON・画像バイナリ）を、安全に永続化し、安全に読み戻して U14 の Zod 検証へ渡す」までの責務である。

## スコープ

### やること

- **`.tmap`（ZIP コンテナ）の書き込みアダプタ**
  - マニフェスト JSON（全頂点・点情報・線情報・面情報・各歴史の錨・各錨の最上位フラグ／親子関係／種別ラベル・アプリケーション設定などを直列化したもの）を ZIP 内の固定パスのエントリとして格納する。
  - ベースマップ画像（プリセット出界図またはユーザー指定地図のコピー）を ZIP 内アセットとして格納する。
  - 詳細文書に埋め込まれた添付画像群を ZIP 内アセットとして格納する。
  - マニフェスト先頭に保存形式のバージョン文字列を保持する（FR-104）。
  - ZIP 入出力には fflate を用いる。
- **`.tmap` の読み込みアダプタ**
  - ZIP コンテナを展開し、マニフェスト JSON・ベースマップ画像・添付画像を取り出す。
  - 取り出したマニフェスト（外部入力）を、ドメインへ渡す前に必ず U14 の Zod スキーマ検証に通す（後述「依存」「実装方針」）。本ユニットは検証を迂回してドメインへ生データを流す経路を作らない。
- **アトミック保存メカニズム（NFR 5.3）**
  - 書き込みは「同一ボリューム上の一時ファイルへ全内容を書く → ファイル内容を fsync で確実にディスクへ反映 → 既存ファイルへアトミックにリネーム置換」の固定手順で行う。
  - 一時ファイルは保存先と同一ディレクトリ（同一ファイルシステム）に作成し、リネームがアトミックに成立することを保証する。
  - 書き込み失敗時は一時ファイルを後始末（削除）し、既存ファイルを温存する。
- **自動保存（FR-108）**
  - 設定可能な間隔（既定 5 分）のタイマーで自動保存をトリガーする仕組みを提供する。間隔値は設定から取得し、本ユニット内にハードコードしない（既定値の 5 分のみ定数として持つ）。
  - 自動保存は通常保存と同じアトミック書き込み経路を通る。
- **世代バックアップ（FR-108）**
  - 保存（自動保存を含む）の際に、タイムスタンプをファイル名に含めたバックアップを作成する。
  - 保存ファイルごとに最大 10 世代を保持し、世代数が上限を超えたら古いものから削除する。
  - 世代上限値は設定から取得可能とし、既定 10 を定数として持つ。
- **ファイル操作 UI フロー連携の入口**
  - 「保存」「名前を付けて保存」「読み込み」「ドラッグ＆ドロップによる読み込み」の各操作が、本ユニットの型付き IPC を通じて I/O アダプタへ到達する経路を提供する（FR-105）。ファイル選択ダイアログの起動（保存先・読込元のパス決定）はメインプロセス側で行う。
- **preload の型付き IPC 公開（開発ガイド §5.33）**
  - レンダラへ公開する API は型付きの最小集合（保存・名前を付けて保存・読み込み・ドラッグ＆ドロップ読み込み・自動保存設定の受け渡し等）に限定する。
  - チャネル名・引数型・戻り値型を共有型で一元定義し、呼び出し側（レンダラ）・公開側（preload）・受信側（メイン）の三者が同一の契約を参照する。
  - 契約は両側テストで固定する（受信側ハンドラと、preload が公開する API 形状の双方をテストする）。

### やらないこと

- **データ整合性チェックの本体（FR-106）**: 不整合（存在しない頂点参照・ツリー位相不整合・末端/集約形状保持規則違反・末端排他違反・親領域と下位領域の和の不一致・時間プロパティ矛盾・錨間オーバーラップ）の検出と自動修復オプションの提示は、ドメイン側の整合性チェック責務であり本ユニットでは実装しない。本ユニットは「Zod のスキーマ／構造レベル検証（U14）を通す」までを担い、ドメイン論理整合の検証は呼び出し先へ委ねる。
- **Zod スキーマ本体の定義（U14）**: 保存データ・設定・外部入力のスキーマ定義とバージョン分岐（discriminated union）の宣言は U14 の責務。本ユニットは U14 が公開する検証関数を呼び出すだけで、スキーマを再定義しない（単一の真実源）。
- **ドメインモデルの直列化ロジックそのもの**: 「ドメイン状態 → マニフェスト用のプレーンデータ構造」への変換（serialize）と「プレーンデータ → ドメイン状態」への復元（deserialize）のドメイン側ロジックは、ドメイン層の責務である。本ユニットは「直列化済みのプレーンデータを受け取り ZIP へ書く／ZIP から読み出したプレーンデータを Zod 検証して返す」境界に閉じる。
- **互換マイグレーション**: 旧バージョン形式の読み込み互換・版間データマイグレーションは本アプリのスコープ外（要件 5.3「セーブデータの互換・マイグレーションについて」）。本ユニットはバージョン不一致を警告／拒否するのみとし、旧形式を読み替える機構は作らない。
- **未保存変更がある場合の警告ダイアログ（FR-107）**: 「保存／保存せず続行／キャンセル」の終了確認・読み込み前確認の UI フローは別ユニットの責務。本ユニットは I/O アダプタと IPC 契約を提供するに留まる。
- **設定値の管理・編集 UI（FR-109 / FR-110）**: 自動保存間隔・バックアップ世代数の編集 UI は別ユニット。本ユニットはこれらの値を「設定から受け取る」前提で動く。
- **ベースマップ画像の自動補正・適合検証（FR-04）**: ユーザー指定地図の出界図形式への補正やフォールバック判定は別ユニットの責務。本ユニットは渡された画像バイナリをそのまま ZIP に格納／取り出すのみ。
- **Markdown のレンダリング・無害化（FR-98 / FR-116）**: 詳細文書の描画・サニタイズは別ユニット。本ユニットは添付画像バイナリの格納／取り出しのみを担う。

## 依存（dependsOn）

- **U14（Zod スキーマ検証・保存データ／設定／外部入力の検証層）**
  - U14 は、保存データ（マニフェスト）・設定・外部入力のスキーマを Zod の単一宣言として定義し、そこから TS 型を導出する。保存形式のバージョンは discriminated union で表現し、バージョンの妥当性検証（FR-104）と構造レベルのサニタイズ（FR-116）を提供する。
  - 本ユニットの読み込みアダプタは、ZIP から取り出したマニフェスト JSON を**必ず** U14 の検証関数に通してから呼び出し側へ返す。検証に失敗した場合（スキーマ不一致・バージョン不一致）は、成功結果ではなく拒否理由を伴う結果を返す（後述「実装方針」の結果型）。
  - U14 のスキーマを本ユニットで再実装・再定義してはならない（単一の真実源）。本ユニットは U14 が公開する検証関数とそこから導出される型のみを参照する。
  - U14 の本実装が先行していない場合でも、本ユニットは「U14 の検証関数を経由する」境界点を明確に保ち、検証関数の入出力契約（入力＝ZIP から読んだプレーンデータ、出力＝検証済みドメイン入力データ または 拒否理由）に対して結合する。検証ロジックそのものを本ユニットへ取り込まない。

- **U01（リポジトリ基盤・ビルド・層分離・lint 依存方向強制）**
  - U01 は単一 npm パッケージ／electron-vite による main・preload・renderer の 3 ターゲット／strict 群 4 種を有効化した共有 tsconfig／`src/domain`・`src/render`・`src/ui`・`src/shell` のディレクトリ層と依存方向の lint 強制／レンダラのセキュリティ設定（`contextIsolation: true` / `nodeIntegration: false` / `sandbox: true`）／`domain` を Electron・React 抜きで Vitest 実行できる土台を提供する。
  - 本ユニットのファイル I/O アダプタ・自動保存・バックアップ・preload の型付き IPC は、すべて `src/shell` 層（Electron の main / preload）に配置する。`shell` は `domain` を import してよいが `ui` / `render` は import しない（U01 の依存方向規律）。
  - preload は U01 が確立したサンドボックス設定（`sandbox: true` / `contextIsolation: true`）下で動作する形（`contextBridge` 経由公開）に従う。

本ユニットは Electron の main / preload（`src/shell` 層）と Node.js の `fs` に依存する。ただし、後述のとおりファイル I/O・ZIP・アトミック保存・世代管理の中核ロジックは Electron 非依存の純粋／薄いアダプタ関数として切り出し、Vitest で単体テスト可能にする（開発ガイド §5.41）。

## 実装方針（技術方針に沿う）

技術方針.md の採用スタック（§1, §2.2, §2.10, §2.12, §2.13）に従う。

### 1. 配置と層境界（技術方針 §2.13 / U01）

- ファイル I/O アダプタ・自動保存・世代バックアップ・preload の型付き IPC は `src/shell` 層に置く。`shell` は `domain` を import してよいが `ui` / `render` を import しない。
- レンダラ（`ui`）はファイルシステムへ直接アクセスせず、preload が公開する型付き IPC のみを経由する（FR-02 完全オフライン・サンドボックス前提）。

### 2. `.tmap` ZIP コンテナ（技術方針 §2.12）

- 永続化形式は単一の `.tmap` ファイル（ZIP コンテナ）とする。1 ファイルに次を同梱して保存内容の論理的完全性（FR-103）を確保する。
  - **マニフェスト JSON**: 全地物・全錨・各錨の最上位フラグ／親子関係／種別ラベル・アプリケーション設定などを直列化したプレーンデータ。先頭に保存形式のバージョン文字列を持つ（FR-104）。
  - **ベースマップ画像**: プリセット出界図またはユーザー指定地図のコピー。
  - **添付画像群**: 詳細文書に埋め込まれた画像。
- ZIP 内のエントリパス（マニフェスト・画像アセットの配置）は固定規約として一箇所に定義し、書き込み側・読み込み側で同一規約を共有する（単一の真実源）。エントリパスを書き込みと読み込みで別々にハードコードしない。
- ZIP 入出力には fflate を用いる。

### 3. アトミック保存（技術方針 §2.12 / NFR 5.3）

- 書き込みは固定手順で行う。
  1. 保存先と**同一ディレクトリ（同一ファイルシステム）**に一時ファイルを作成し、ZIP バイト列を全量書き込む。
  2. 一時ファイルの内容を fsync でディスクへ確実に反映する。
  3. 一時ファイルを目的のファイルへ**アトミックにリネーム**して置換する。
- 一時ファイルを別ボリュームに作るとリネームがアトミックにならない（コピー＋削除に劣化する）ため、必ず保存先と同一ディレクトリに作る。
- いずれかの段階で失敗した場合は、一時ファイルを削除して後始末し、既存ファイルを温存する（破損させない）。失敗はテスト可能な戻り値（拒否理由を含む結果型）として返し、例外を握りつぶさない。

### 4. 自動保存と世代バックアップ（技術方針 §2.12 / FR-108）

- 自動保存は設定可能な間隔（既定 5 分）のタイマーでトリガーする。間隔値は設定から受け取り、既定値 5 分のみを定数として持つ。
- 世代バックアップは Node `fs` のファイル単位コピーで単純に実装する。
  - バックアップファイル名にはタイムスタンプを含める。
  - 保存ファイルごとに最大 10 世代を保持し、世代数が上限超過時は古いものから削除する。世代上限値は設定から受け取り、既定値 10 のみを定数として持つ。
  - 世代の「古い／新しい」の判定は、ファイル名のタイムスタンプ等、決定的で安定した基準を一箇所に定義して使う（システム時刻の取り違えに注意。後述 §5.15）。
- バックアップ作成もアトミック保存と同じ安全な書き込み経路を通すか、すでにアトミックに置換済みの正規ファイルからのコピーとして行い、書き込み途中の不完全なバックアップを残さない。

### 5. 読み込みと Zod 検証の必須化（技術方針 §2.10 / R8 / FR-104・FR-106・FR-116）

- 読み込みアダプタは ZIP を展開し、マニフェスト JSON を取り出した直後に**必ず** U14 の Zod 検証を通す。検証を迂回してドメインへ生データを渡す公開経路を作らない（R8: 境界での Zod 通過漏れを構造的に塞ぐ）。
- バージョン不一致（保存形式バージョンが本アプリの対応形式と一致しない）は、互換マイグレーションを行わず、警告／拒否の対象とする（要件 5.3）。拒否はテスト可能な戻り値として返す。
- 外部から読み込むデータ（ファイル・ドラッグ＆ドロップ）はすべて検証・サニタイズの対象とする（FR-116 / NFR 5.5）。

### 6. preload の型付き IPC 契約（技術方針 §1, §2.2 / 開発ガイド §5.33・§5.34）

- preload では型付き IPC のみを公開する。公開 API は最小集合に限定し、汎用的な `fs` アクセスやチャネル名文字列をレンダラへ露出しない。
- IPC のチャネル名・引数型・戻り値型は、レンダラ・preload・メインの三者が参照する**共有型**で一元定義する。文字列の偶然一致に依存しない。
- 両側テストで契約を固定する（開発ガイド §5.33）。
  - 受信側（メインプロセスのハンドラ）が、共有型どおりの引数を受け取り共有型どおりの戻り値を返すことをテストする。
  - 公開側（preload）が、共有型どおりの API 形状をレンダラへ公開することをテストする（`contextBridge` 経由の公開キー・関数シグネチャの固定）。
- チャネル名や API 名を変更する場合は、共有型・preload・メインハンドラ・テストを同一変更単位で更新し、旧名が残っていないかを検索する（開発ガイド §5.33）。

### 7. テスト容易性のためのアダプタ分離（技術方針 §2.14 / 開発ガイド §5.41）

- ZIP の組み立て／展開、アトミック書き込み手順、世代バックアップの選定・削除、エントリパス規約、結果型の生成は、Electron に直接依存しない純粋／薄いアダプタ関数として切り出す。これにより、IPC や Electron ランタイムを起動せずに Vitest 単体テストできる（開発ガイド §5.41「E2E で検証できなくなる範囲はアダプタ分離・純粋関数化で単体テスト対象にして補う」）。
- 永続化の読み（deserialize 入口）・書き（serialize 出口）・検証（Zod 通過）・往復テストは同じ変更単位で同期する（開発ガイド §5.31）。保存して読み戻す往復テスト（round-trip）を必ず置く。

### 8. 結果型（判別共用体）

- 保存・読み込みの各アダプタは「成功」と「拒否（理由）」を判別共用体で返し、不正状態を表現不能にする。拒否理由（書き込み失敗・ZIP 破損・スキーマ不一致・バージョン不一致など）はユーザー通知とテスト可能な戻り値の両方で扱える形にする。エラーは例外で暗黙に流さず、結果型で明示する。

## 受け入れ基準（テスト可能な形で列挙）

各基準は Vitest（アダプタ単体・往復テスト・IPC 両側テスト）等で検証可能な形とする。実装者は完了前に全項目を確認すること。

1. **`.tmap`（ZIP）にマニフェスト＋ベースマップ＋添付画像を保存／読込できる（FR-103 / FR-105）**
   - マニフェスト JSON・ベースマップ画像・複数の添付画像を含むデータを `.tmap`（ZIP コンテナ）として保存し、同じファイルを読み戻すと、マニフェスト・ベースマップ・全添付画像が欠落・破損なく取り出せることを往復テスト（round-trip）で確認する。
   - ZIP 内のエントリパス規約が書き込み側・読み込み側で同一であり、片側だけ変えると往復テストが落ちることを確認する（単一の真実源）。
   - 添付画像が複数ある場合に全件が保存・復元される（片落としがない）ことを確認する。

2. **書込が一時ファイル→fsync→アトミックリネームで破損防止（NFR 5.3）**
   - 書き込みが「保存先と同一ディレクトリの一時ファイルへ書く → fsync → アトミックリネーム」の順で行われることを確認する（一時ファイルを別ボリュームに作らない／リネームで置換する）。
   - 書き込みがリネーム前に失敗した場合、既存ファイルが温存され（上書き破損しない）、一時ファイルが後始末（削除）されることを確認する。
   - 書き込み失敗が例外の握りつぶしではなく、拒否理由を伴う結果型として返ることを確認する。

3. **5 分間隔自動保存と最大 10 世代バックアップ（古い順削除・タイムスタンプ名）（FR-108）**
   - 自動保存間隔が設定値から取得され、既定が 5 分であることを確認する（間隔をハードコードしていないこと）。
   - 自動保存が通常保存と同じアトミック書き込み経路を通ることを確認する。
   - バックアップファイル名にタイムスタンプが含まれることを確認する。
   - 保存を世代上限（既定 10）を超えて繰り返すと、最大 10 世代に保たれ、超過分が古いものから削除されることを確認する。世代上限値が設定から取得できることを確認する。
   - 古い／新しいの判定基準が一箇所に定義され、決定的であることを確認する（同一時刻内の複数保存でも判定が破綻しない）。

4. **preload の型付き IPC 契約が両側テストで固定される（開発ガイド §5.33）**
   - IPC のチャネル名・引数型・戻り値型が共有型で一元定義され、レンダラ・preload・メインが同一定義を参照していることを確認する。
   - 受信側（メインハンドラ）が共有型どおりの引数を受け取り共有型どおりの戻り値を返すことを単体テストで確認する。
   - 公開側（preload）が共有型どおりの API（保存・名前を付けて保存・読み込み・D&D 読み込み等）をレンダラへ公開していることを単体テストで確認する。
   - チャネル名を変更すると両側テストの少なくとも一方が落ちる（偶然一致に頼っていない）ことを確認する。

5. **読込データが必ず U14 の Zod 検証を通る（FR-104 / FR-106 / FR-116）**
   - 読み込みアダプタが、ZIP から取り出したマニフェストを U14 の Zod 検証へ通してから呼び出し側へ返すことを確認する。
   - 検証を迂回して生データをドメインへ返す公開経路が存在しないことを確認する。
   - スキーマ不一致・バージョン不一致のデータを読み込むと、成功結果ではなく拒否理由を伴う結果型を返すことを確認する（互換マイグレーションは行わない）。
   - 破損した ZIP・必須エントリ欠落のファイルを読み込んだとき、例外で落ちず拒否理由を返すことを確認する。

6. **保存／名前を付けて保存／読込／D&D の各操作が IPC を通って I/O へ到達する（FR-105）**
   - 保存・名前を付けて保存・読み込み・ドラッグ＆ドロップ読み込みの各操作が、型付き IPC を経由してファイル I/O アダプタに到達する経路を持つことを確認する。
   - レンダラがファイルシステムへ直接アクセスせず、preload の型付き IPC のみを経由することを確認する。

7. **アダプタが Electron 無しで単体テストできる（開発ガイド §5.41 / NFR 5.8）**
   - ZIP 組み立て・展開・アトミック書き込み・世代バックアップ選定・エントリパス規約・結果型生成が、Electron ランタイムを起動せずに Vitest 単体テストできることを確認する。

## 関連要件（FR-id）

- **FR-103（must）**: プロジェクトデータを保存・読み込みできる。保存内容はすべての頂点・点情報・線情報・面情報、各オブジェクトの時間依存プロパティ（歴史の錨）、各錨の最上位フラグ・親子関係・種別ラベル、アプリケーション設定、ベースマップを含む。
  - 本ユニットは `.tmap`（ZIP コンテナ）にマニフェスト JSON＋ベースマップ画像＋添付画像を同梱することで、保存内容の論理的完全性を担保する。
- **FR-105（should）**: 保存操作（ショートカット相当・名前を付けて保存）と読み込み操作（ショートカット相当・ドラッグ＆ドロップ）を提供する。
  - 本ユニットは保存・名前を付けて保存・読み込み・ドラッグ＆ドロップ読み込みの各操作を型付き IPC を通じて I/O アダプタへ到達させる。
- **FR-108（should）**: 設定可能な間隔（デフォルト 5 分）で自動保存・自動バックアップを作成し、世代管理（保存ファイルごとに最大 10 世代、超過分は古いものから削除、タイムスタンプをファイル名に含める）を行う。
  - 本ユニットは既定 5 分間隔の自動保存と最大 10 世代のタイムスタンプ付きバックアップ（古い順削除）を実装する。

補助的に支える要件・非機能要件:

- **FR-104（should）**: 保存形式にバージョン情報を保持し、読み込み時にバージョンの妥当性を検証して非互換ファイルは警告／拒否する。本ユニットはマニフェスト先頭にバージョン文字列を持ち、読み込み時に U14 の検証へ通す。
- **FR-106（must）**: 読み込み時のデータ整合性チェックと自動修復オプション。本ユニットは構造レベルの Zod 検証（U14）までを担い、ドメイン論理整合の検証・修復は呼び出し先へ委ねる（やらないこと参照）。
- **FR-116（should）／NFR 5.5**: 外部から読み込むデータ形式の検証とサニタイズ。本ユニットは読み込みデータを必ず U14 の Zod 検証に通す。
- **FR-02（must）**: 完全オフライン・スタンドアロン。本ユニットは Node `fs` によるローカル I/O のみを行い、ネットワークを前提としない。レンダラはサンドボックス下で型付き IPC のみを経由する。
- **NFR 5.3（保存の意図と安全性）**: アトミック保存（一時ファイル→fsync→アトミックリネーム）と自動保存・世代バックアップによる破損防止・回復性。
- **NFR 5.2（ディスク使用量管理）**: バックアップ世代管理（最大 10 世代）・一時ファイルの適切な削除。
- **NFR 5.8（テスト容易性）**: I/O 中核ロジックをアダプタ分離・純粋関数化し、Electron 無しで単体テスト・往復テスト・IPC 両側テストを可能にする。

## 注意点・既知の落とし穴（開発ガイドの教訓を踏まえる）

着手前に、以下の関連教訓を節番号・見出し・本文ごと引用し、今回の実装判断へどう適用するかを「適用:」として明示してから着手すること（開発ガイド §1.6 AI 作業開始ゲート）。

- **§5.33 層をまたぐ API 契約は両側テストで固定する**: 「層をまたぐ API 契約（呼び出し側・公開側・受信側のチャネル名/関数名）は、文字列の偶然一致に任せず、共有型・型付きラッパー・両側の単体テストで固定する。API 名変更時は、全層とテストを同じ変更単位で更新し、旧名が残っていないか検索する。」
  - 適用: preload の型付き IPC チャネル名・引数型・戻り値型を共有型で一元定義し、レンダラ・preload・メインが同一定義を参照する。受信側ハンドラと preload 公開形状の両側テストを置き、チャネル名変更時は共有型・両側・テストを同一変更単位で更新して旧名を検索する。受け入れ基準 4 で固定する。

- **§5.31 永続化の読み書き・検証・移行・往復テストを同期する**: 「永続化の読（deserialize）・書（serialize）・検証（validation）・移行（migration）・往復テストは、同じ変更単位で同期する。片側だけ変えると『保存はできるが次に開けない』壊れたファイル経路ができ、型チェックでも実行時テストでも検出されず、データ損失リスクになる。検出: フィールドを optional 化・撤去・固定値化する変更では、再保存往復テストを必ず追加する。」
  - 適用: ZIP のエントリパス規約・マニフェストのバージョン文字列・読み書きの対応を同一変更単位で同期し、保存して読み戻す往復テスト（受け入れ基準 1）を必ず置く。互換マイグレーションはスコープ外のため、移行は実装せずバージョン不一致は拒否する。

- **§5.41 検証不能になった範囲は別手段で補う**: 「E2E 等で一時的に検証できなくなった範囲（外部統合・ファイル I/O・終了確認等）は、未検証のまま放置しない。純粋関数化・アダプタ分離・モックで単体テスト対象にして補う。」
  - 適用: ZIP 組み立て・展開・アトミック書き込み手順・世代バックアップ選定・結果型生成を Electron 非依存のアダプタ関数として切り出し、Vitest 単体テスト可能にする（受け入れ基準 7）。Electron 起動を前提とする部分は最小に閉じる。

- **§5.15 タイムスタンプはコンテキスト上の時刻を参照する**: 「時間軸を持つデータのタイムスタンプは、必ずコンテキスト上の時刻（現在時刻）を参照し、システム時刻と混同しない。時刻源は一元管理するサービスから取得する。」
  - 適用（注意点として）: ここで扱うバックアップファイル名のタイムスタンプは**作中時間（歴史の錨の時刻）ではなく、実際の保存実行時刻（実時間）**である。両者を取り違えないこと。バックアップ名・世代の新旧判定に用いる実時間の時刻源は一元化し、同一時刻内の複数保存でも世代判定が破綻しない決定的な基準（§5.37 とも整合）を一箇所に定義する。

- **§5.37 ID 生成はタイムスタンプ単独に依存しない**: 「ID 生成はミリ秒精度タイムスタンプだけに依存すると、同一ミリ秒内で衝突する。ID 生成サービスを経由し、既存データとの重複検査を行う。」
  - 適用: バックアップファイル名をミリ秒タイムスタンプ単独で生成すると、同一ミリ秒内の連続保存で衝突し世代が上書き欠落する恐れがある。連番付与や既存名の重複検査など、衝突しない命名規約を一箇所に定義する。世代の新旧判定もこの命名規約と整合させる。

- **§5.22 確定まで共有データを破壊的に更新しない**: 「結果が確定するまで、共有キャッシュ/共有データを破壊的に更新しない。検証用の仮データで成功を確認してから反映し、失敗時は追加した要素をすべてロールバックする。永続化が失敗してもキャッシュが汚染されないようにする。」
  - 適用: 保存はアトミックリネームで確定するまで既存ファイルを破壊しない。書き込み途中失敗時は一時ファイルを後始末し既存ファイルを温存する（受け入れ基準 2）。世代削除は新バックアップの確定後に行い、削除が先行して回復不能にならないようにする。

- **§5.18 空配列・空オブジェクトは真値である**: 「空配列・空オブジェクトは真値である。論理和による短絡評価のデフォルト補完に頼らず、型や状態を明示的に判定する。」
  - 適用: 添付画像が 0 件のプロジェクト・バックアップが 0 世代の初回保存など、空の集合を正当値として扱う。空を「未設定」と短絡で取り違えない。読み込み結果が空（地物 0 件など）でもエラーと混同しない。

- **R8（境界での Zod 検証が運用規律に依存し、漏れると型安全の前提が崩れる）／開発ガイド §4「層をまたぐ契約の固定」**: 技術方針 R8「境界モジュールでの Zod 通過を lint ルールで強制し、未検証の外部入力がドメインへ流入する経路を構造的に塞ぐ。」
  - 適用: 読み込みアダプタは ZIP から取り出したデータを U14 の Zod 検証へ通してから返す唯一の経路とし、検証を迂回する公開関数を作らない（受け入れ基準 5）。本ユニットでスキーマを再定義しない（単一の真実源、U14 が唯一の定義元）。

- **その他の落とし穴**:
  - **同一ボリューム上の一時ファイル**: アトミックリネームはファイルシステムをまたぐと成立しない（コピー＋削除に劣化し原子性を失う）。一時ファイルは必ず保存先と同一ディレクトリに作る。
  - **fsync の対象**: ファイル内容の fsync に加え、ディレクトリエントリの永続化が必要な環境がある点に留意し、リネーム後に既存ファイルが確実に置換されていることを往復テストで担保する。
  - **エントリパス規約の二重定義禁止**: ZIP 内のマニフェスト・画像アセットのパスを書き込み側と読み込み側で別々にハードコードしない。規約を一箇所に定義して双方が参照する（単一の真実源）。
  - **設定値のハードコード禁止**: 自動保存間隔・世代上限は設定から取得する。既定値（5 分・10 世代）のみを定数として一箇所に置き、本ユニット内に間隔・世代数を散在させない。
  - **クリーンルーム原則（開発ガイド §3.1）**: 本ユニットの設計・実装の根拠は本書および要件定義書.md / 技術方針.md / 開発ガイド.md の v4 自身の記述のみとし、過去版・他プロダクト・「従来こうしていた」式の外部参照に頼らない。
