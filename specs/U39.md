# U39 ファイル操作UI(保存/読込/D&D・未保存警告・新規プロジェクト)とズーム制限

本書は実装ユニット U39 の実装指示書である。実装者（別エージェント）はこの指示書だけを読んで着手できることを目的とし、前提知識は本書内に閉じて記述する。要件・技術方針・開発作法の根拠は本文および末尾の「関連要件」「注意点・既知の落とし穴」に引用する。本書は time-map-app-4（以下「本アプリ」）のクリーンルーム文書であり、過去版・他プロダクト・外部の既存実装には一切依存しない。必要な制約はすべて本アプリ自身の要件・方針として直接記述する。

## 目的

本ユニットは、ファイル操作の「ユーザー向け UI フローと配線」、および「ズームレベル制限の設定値の保持・適用」を確立する。本アプリの永続化基盤（型付き IPC・I/O アダプタ）と整合性チェック層・設定ストア・UI シェルはすでに別ユニットが提供しており、本ユニットはそれらを束ねてユーザーが操作できる形にする「上位の配線層」である。具体的には次の 5 点を満たす。

1. **保存・名前を付けて保存・読み込み・ドラッグ＆ドロップ（D&D）読み込みの UI** を、U15 の型付き IPC／I/O アダプタへ接続して動かす（FR-105）。保存ショートカット相当・名前を付けて保存・読み込みショートカット相当・D&D の各入口を提供する。
2. **未保存変更がある状態での「新ファイル読み込み」「アプリ終了」「新規プロジェクト開始」** において、警告ダイアログ（保存／保存せず続行／キャンセル）を表示し、ユーザーの選択に従って分岐する（FR-107）。
3. **読み込み時のデータ整合性チェック（U14）で検出された不整合に対する自動修復オプションを、ユーザーが選択できる UI** を提供する（FR-106）。
4. **新規プロジェクトの初期化**を、表示中データだけでなく保存先パス・メタデータ・バックアップ対象・dirty 状態・終了確認ガードまで同じ保存文脈として同時に初期化する（教訓 5.36）。出界図（プリセットベースマップ）を背景とする初期状態にする。
5. **ズームレベル制限の設定値**を保持・適用する。既定は最小 1 倍〜最大 50 倍、ユーザー設定可能範囲は最小 0.1 倍〜最大 10000 倍とし、この制限が実際のズーム操作に効くようにする（FR-10）。

本ユニットは「UI フローと配線」「ズーム制限の設定値とクランプ範囲の供給」を担う。ファイル I/O の物理処理（ZIP・アトミック保存・世代バックアップ）、Zod スキーマ・整合性チェックの検出／修復ロジック本体、カメラのワールド↔スクリーン変換そのもの、UI シェルの骨格（メニュー枠・ショートカット基盤・ドラッグ可能パネルの器）は、いずれも依存ユニットの責務であり本ユニットでは再実装しない（単一の真実源）。

## スコープ

### やること

#### A. ファイル操作 UI（FR-105）

- **保存（ショートカット相当）**: 現在のプロジェクトを、現在の保存先パスへ保存する操作を提供する。保存先が未確定（新規プロジェクトで一度も保存していない）場合は「名前を付けて保存」フローへ委譲する。保存は U15 の型付き IPC（保存）を経由する。
- **名前を付けて保存**: 保存先パスをファイル選択ダイアログ（起動はメインプロセス側＝U15 の責務）で決定し、その新パスへ保存する。保存後は現在の保存先パスを新パスへ更新し、dirty 状態を解消する。
- **読み込み（ショートカット相当）**: 読込元パスをファイル選択ダイアログで決定し、U15 の型付き IPC（読み込み）を経由してプロジェクトを読み込む。読み込み結果は U14 の検証・整合性チェックを通って返る（後述 C）。
- **ドラッグ＆ドロップ読み込み**: アプリのメインマップ領域（または所定のドロップ領域）へファイルがドロップされたとき、そのファイルを読み込み対象として U15 の D&D 読み込み IPC へ渡す。D&D による読み込みも通常の読み込みと同じ後続フロー（未保存警告 → 検証 → 整合性チェック → 自動修復 UI → 反映）を通る（教訓 5.6: 同じ結果状態を生む別経路を漏らさない）。
- これらの操作の起動点（メニュー項目「ファイル」配下・キーボードショートカット・D&D）は、U20 が提供するメニュー枠・ショートカット基盤・入力レイヤへ「コマンド」として登録・接続する。本ユニットは各操作の実コマンド（ハンドラ）を実装し、U20 の枠へ嵌める。

#### B. 未保存変更がある場合の警告ダイアログ（FR-107）

- **dirty（未保存変更）状態の判定基準を一箇所に定義**し、それを参照する。dirty は「最後の保存（または新規初期化）以降にドメイン状態が変化したか」で判定する（後述 §実装方針）。
- 次の 3 つの契機で、dirty が真のときに限り警告ダイアログを表示する。
  1. **新ファイル読み込み**（読み込み・D&D 読み込みの開始時）。
  2. **アプリ終了**（ウィンドウクローズ／アプリ終了の要求時）。
  3. **新規プロジェクト開始**。
- 警告ダイアログは 3 択（**保存** ／ **保存せず続行** ／ **キャンセル**）とし、それぞれ次の分岐を行う。
  - **保存**: 保存（必要なら名前を付けて保存）を実行し、保存が成功した場合のみ元の操作（読み込み／終了／新規）を続行する。保存が失敗・キャンセルされた場合は元の操作を中止する（誤って未保存のまま破棄しない）。
  - **保存せず続行**: 保存せずに元の操作を続行する。
  - **キャンセル**: 元の操作を中止し、現在の状態を維持する。
- dirty が偽（未保存変更なし）の場合は、警告ダイアログを出さずに元の操作へ直接進む。
- これら 3 契機は「dirty かつ破壊的に状態を置き換える操作」という同一の結果状態でガードする。経路ごとに別々のゲートを書かず、共通のガード関数を全経路が通る（教訓 5.6）。

#### C. 読み込み時整合性チェックの自動修復オプション UI（FR-106）

- 読み込み時、U14 が返す検証結果・整合性チェックレポートを受け取り、以下を UI で扱う。
  - **バージョン非互換・スキーマ不一致（U14／U15 が拒否理由を返す）**: 互換性の警告を日本語で表示し、読み込みを中止する（互換マイグレーションはスコープ外）。
  - **ドメイン整合性の不整合（FR-106 の 7 種）が検出された場合**: 検出レポート（不整合種別・関連地物名／ID・該当作中時刻または時間範囲・競合種類）を一覧表示し、各不整合に対して U14 が提示する**自動修復オプション（複数案）をユーザーが選択できる UI** を提供する。
    - ユーザーが各不整合に修復オプションを選び、確定すると、選択結果を U14 の修復適用（純粋関数）へ渡し、修復後データを得てから読み込みを反映する。
    - 「修復せず読み込まない（中止）」を選べる経路も用意する。
  - **不整合 0 件（空レポート）**: 自動修復 UI を出さず、そのまま読み込みを反映する（過剰検出・誤った確認ダイアログを出さない。教訓 5.18: 空レポートは正当値）。
- 検出された不整合の **7 種すべて**を UI 上で提示・選択可能にする（「同様に」で省略しない。開発ガイド §1.2）。種別ごとに修復オプションの選択肢が異なりうるため、UI は U14 のレポート構造から動的に選択肢を組み立てる（修復オプションを種別横断で安易に共有しない。教訓 5.30 過剰共有の戒め）。
- 拒否理由・警告メッセージはユーザー通知（日本語）とテスト可能な戻り値の両方で扱える形にする（教訓 5.26、FR-115）。

#### D. 新規プロジェクト初期化（教訓 5.36 / FR-03）

- 新規プロジェクト開始時に、次を**同じ保存文脈として同時に初期化**する。表示中データだけを差し替えて他を取り残さない。
  - **表示中データ（ドメイン状態）**: 地物 0 件の空プロジェクト状態へ初期化する。
  - **ベースマップ**: プリセット地図（出界図）を背景に初期化する（FR-03: 新規作成時はプリセット地図を表示）。
  - **保存先パス**: 未確定（未保存）状態へ初期化する。以後の「保存」は名前を付けて保存フローへ委譲される。
  - **メタデータ**: プロジェクト名・説明等のプロジェクト固有メタデータを初期値へ。
  - **バックアップ対象**: 世代バックアップの対象（保存先）を新規プロジェクトの文脈へ初期化する（旧プロジェクトのバックアップ系列を引き継がない）。
  - **dirty 状態**: 初期化直後は「未保存変更なし（クリーン）」とする（新規初期化を保存基点とみなす）。
  - **終了確認ガード**: 未保存警告（B）のガードを新規プロジェクト文脈に対して有効化する。
- 新規プロジェクト開始は、未保存警告（B）の契機の 1 つである。dirty なら先に警告ダイアログを通す。

#### E. ズームレベル制限の設定値と適用（FR-10）

- **ズーム制限の設定値**（現在有効な最小ズーム倍率・最大ズーム倍率）を保持・編集できるようにする。
  - **既定値**: 最小 1 倍〜最大 50 倍。
  - **ユーザー設定可能範囲（設定 UI で入力できる値の許容境界）**: 最小 0.1 倍〜最大 10000 倍。ユーザーが入力した最小・最大はこの許容境界内に収まること、かつ最小 ≤ 最大であることを検証する。範囲外・逆転入力は無効として弾く（即時エラー表示）。
  - これらの既定値・許容境界は定数として一箇所に定義し、本ユニット内に散在させない（単一の真実源）。
- ズーム制限の設定値は、ズーム操作（カーソル中心ホイールズーム等）のクランプ範囲として **U17 のカメラへ供給**する。U17 は「渡されたクランプ範囲を適用する／範囲未供給時の暫定既定は FR-10 の 1 倍〜50 倍」という契約であるため、本ユニットは現在有効なクランプ範囲を U17 が参照できる経路（設定ストア経由）へ反映する。
- ズーム制限が **実際に効く**こと（クランプ範囲外へズームしようとしても下限・上限で止まる）を、設定変更が即時反映される形で担保する（FR-10 / FR-109 即時反映）。

### やらないこと

- **ファイル I/O の物理処理（U15）**: `.tmap`（ZIP コンテナ）の組み立て／展開、アトミック保存（一時ファイル→fsync→アトミックリネーム）、自動保存タイマー、世代バックアップの作成・削除、preload の型付き IPC チャネルの定義そのもの。本ユニットはこれらを U15 の型付き IPC 経由で**呼び出す**だけで、I/O 実装を再実装しない。ファイル選択ダイアログ（OS ネイティブ）の起動はメインプロセス側（U15）が行う。
- **Zod スキーマ定義・バージョン検証・整合性チェック検出／修復ロジック本体（U14）**: 7 種の不整合の検出関数・修復適用の純粋関数・バージョン判別の discriminated union は U14 の責務。本ユニットは U14 が返すレポート・修復オプションを **UI として提示し、ユーザー選択を U14 へ渡す**配線のみを行う。検出・修復ロジックを再実装しない。
- **カメラのワールド↔スクリーン変換・ホイールズーム計算そのもの（U17）**: ズームのクランプ「適用」は U17 がカメラ計算内で行う。本ユニットはクランプ範囲（最小・最大倍率）を供給するに留まり、変換・クランプの計算式を書かない。
- **UI シェルの骨格（U20）**: メニューバーの構造・メニュー項目枠・ショートカット基盤・ドラッグ可能パネル／モーダルの器・入力レイヤの層構造・表示専用一括無効化ヘルパーは U20 が提供する。本ユニットはこれらの「枠」へファイル系コマンド・ダイアログ本体を嵌める。モーダルの器（ドラッグ可能・前面化）も U20 のものを使う。
- **設定ストアの境界定義そのもの（U16）**: プロジェクト固有設定／アプリ全体設定の分類・即時反映通知経路・カメラ／ズーム状態の保持は U16 の責務。本ユニットはズーム制限の設定値を U16 のストアに載せて保持・反映するが、ストア境界の枠組み自体は再定義しない。
- **設定編集モーダルの汎用フレーム（FR-109/FR-110 の設定ダイアログ全体）**: 設定ダイアログの総合 UI が別ユニットにある場合、本ユニットはズーム制限の入力欄・検証をそこへ提供する形をとる。ズーム制限以外の設定項目（赤道長・グリッド・スナップ距離等）の編集 UI は扱わない。
- **アンドゥ／リドゥ・整合性維持プロセス（編集中のリアルタイム競合解決）**: 本ユニットの整合性チェック UI は「読み込み時の一度きりの検査・修復」であり、編集中のリアルタイム検証（FR-61〜63）とは別物。dirty 判定はドメイン状態の変化観測に基づき、編集コマンドの履歴管理そのものは扱わない。
- **ベースマップ画像の自動補正・適合検証・差し替え UI（FR-04）**: 新規プロジェクトでは出界図（プリセット）を背景に初期化するのみ。ユーザー指定地図への差し替え・補正・フォールバックは別ユニットの責務。

## 依存（dependsOn）

本ユニットは以下のユニットへ依存する。これらが公開する API・型・ストア・契約を前提として、その上に UI フローと配線を構築する。再実装はしない（単一の真実源）。

- **U15（型付き IPC とファイル I/O アダプタ）**
  - U15 は `.tmap`（ZIP コンテナ）の保存・読み込み、アトミック保存、自動保存、世代バックアップを実装し、保存・名前を付けて保存・読み込み・D&D 読み込みの各操作を型付き IPC を通じて I/O アダプタへ到達させる。ファイル選択ダイアログの起動（保存先・読込元のパス決定）はメインプロセス側で行う。
  - U15 は「未保存変更がある場合の警告ダイアログ（FR-107）の UI フローは別ユニットの責務」と明示しており、本ユニット（U39）がその UI フローを担う。
  - 本ユニットは U15 の公開する型付き IPC（保存・名前を付けて保存・読み込み・D&D 読み込み）を呼び出し、結果（成功／拒否理由を含む判別共用体）を受け取って UI へ反映する。IPC のチャネル名・引数型・戻り値型は U15 の共有型を参照し、文字列の偶然一致に頼らない（教訓 5.33）。

- **U14（永続化スキーマ・バージョン検証・整合性チェック・自動修復）**
  - U14 は読み込みデータの Zod スキーマ検証・バージョン妥当性検証と、ドメイン整合性チェック（FR-106 の 7 種の不整合）の検出、各不整合に対するユーザー選択可能な自動修復オプションの提示・適用（純粋関数）を提供する。
  - 本ユニットは U14 が返す「検証結果（成功／非互換の警告・拒否）」と「整合性チェックレポート＋修復オプション」を受け取り、自動修復オプション選択 UI として提示し、ユーザーの選択を U14 の修復適用へ渡す。検出・修復ロジックを本ユニットで再実装しない。

- **U20（アプリレイアウトシェルとモード/ツールバー骨格）**
  - U20 は標準メニュー（ファイル・編集・表示・ツール・ヘルプ）の枠・項目枠・有効/無効連動・ショートカット対応づけ、キーボードショートカット基盤（コマンド ID への対応づけ・ディスパッチ）、ドラッグ可能パネル／モーダルの器（複数同時表示・前面化）、中央マップ領域の入力レイヤと重なる UI の層構造、表示専用一括無効化ヘルパー、日本語文言定数モジュールを提供する。
  - 本ユニットは「ファイル」メニュー配下の項目（保存・名前を付けて保存・読み込み・新規プロジェクト等）と対応ショートカットへ実コマンドを登録し、未保存警告ダイアログ・自動修復オプション UI を U20 のモーダルの器に載せる。D&D の入口は U20 の入力レイヤの層構造（教訓 5.14）に従って配置する。

- **U38（本ユニットが土台とする UI 配線ユニット）**
  - U39 は U38 に依存する。U38 が提供する UI フロー基盤・コマンド配線・ダイアログ運用などの土台の上に、本ユニットのファイル操作 UI・未保存警告・新規プロジェクト初期化・ズーム制限を接続する。U38 が提供する仕組み（モーダル運用・コマンド登録の作法・状態通知経路など）と重複する実装を本ユニットで作らず、U38 の公開する枠組みへ嵌める。U38 が提供する API・契約に結合し、再実装しない（単一の真実源、教訓 5.30 過少共有の戒め）。

- **U17（MapRenderer インタフェースと Canvas カメラのワールド↔スクリーン VTransform）**
  - U17 はカメラのワールド↔スクリーン変換・カーソル中心ホイールズームを実装し、「ズーム範囲の上下限クランプの結線点を用意する。既定の制限値・ユーザー設定可能範囲はセッション設定が保持する想定で、本ユニット（U17）は渡されたクランプ範囲を適用する。範囲が未供給の場合の暫定既定は FR-10 の既定値=最小 1 倍〜最大 50 倍に従う」という契約を持つ。
  - 本ユニットは現在有効なズーム制限（最小・最大倍率）を、U17 がクランプに用いるクランプ範囲として供給する（設定ストア経由）。クランプの計算式は U17 が持つため本ユニットでは書かない。

補助的に前提とするユニット（直接の dependsOn ではないが文脈上の接続先）:

- **U16（UI/セッション状態ストア）**: ズーム制限の設定値はアプリ全体設定／プロジェクト固有設定の境界（教訓 5.36）に従って U16 のストアへ載せ、即時反映通知経路で U17 のカメラへ伝える。dirty 状態・現在の保存先パスなどセッション文脈の保持も U16 のストア境界に従う。

本ユニットのコードは UI 層（React）と、UI/セッション状態ストア（U16）への接続に属する。ファイル I/O・Zod 検証・カメラ計算といったドメイン／シェル／描画の中核ロジックは依存ユニットに委ね、本ユニットは「ユーザー操作 → 依存ユニット呼び出し → 結果の UI 反映」という配線とフロー制御に集中する。

## 実装方針（技術方針に沿う）

技術方針.md の採用スタック（§1, §2.3 React UI シェル, §2.5 Zustand＋純粋ドメインコア, §2.10 Zod, §2.12 永続化, §2.13 層分離, §2.14 テスト）に従う。

### 1. 配置と層境界（技術方針 §2.3 / §2.13 / U20 / U16）

- 本ユニットの UI（ファイルメニューのコマンド・未保存警告ダイアログ・自動修復オプション UI・ズーム制限の設定入力）は `ui` 層（React 関数コンポーネント）に置く。`ui` は `domain` を参照してよいが、依存方向は `domain` へ内向きに固定し、`shell`／`render` の具象実装へ直接依存しない（U15 の型付き IPC・U17 の `MapRenderer` インタフェース・U16 のストア経由でのみ接続する）。
- レンダラはファイルシステムへ直接アクセスせず、U15 の preload 型付き IPC のみを経由する（FR-02 完全オフライン・サンドボックス前提）。本ユニットで `fs` を直接触らない。
- 状態（現在の保存先パス・dirty・ズーム制限の設定値）は U16 のストアに保持し、UI はそれを購読・更新する。本ユニットでドメインの真実を複製して別の状態源を作らない（単一の真実源）。

### 2. 保存／読み込み／D&D の UI フロー（FR-105 / 技術方針 §2.12）

- 各ファイル操作は「コマンド」として実装し、U20 のメニュー枠・ショートカット基盤へ登録する。コマンドは U15 の型付き IPC を呼び出し、結果（判別共用体: 成功／拒否理由）を受けて UI を更新する。
- 「保存」は現在の保存先パスを参照し、未確定なら「名前を付けて保存」へ委譲する（保存先決定は U15 のファイル選択ダイアログ起動を経由）。保存成功時に dirty を解消し、現在の保存先パスを更新する。
- 読み込み・D&D 読み込みは、**同一の後続フロー**（未保存警告ガード → U15 読み込み → U14 検証・整合性チェック → 自動修復 UI → ドメイン反映）を通る単一の入口へ収束させる。D&D 専用に別フローを書かない（教訓 5.6: 同じ結果状態を生む別経路を網羅）。
- 操作の起点（メニュー・ショートカット・D&D）が複数あっても、最終的に同一のコマンド／ガードを通すことを両側で固定する（教訓 5.33: 層をまたぐ契約は型と両側テストで固定）。

### 3. 未保存警告ダイアログのガード（FR-107 / 技術方針 §2.5）

- **dirty 判定の単一基準**: dirty は「最後の保存（または新規初期化）以降にドメイン状態が変化したか」で判定する。判定基準を一箇所に定義し、保存成功時・新規初期化時に「クリーン」へリセットする。dirty の baseline（基準）は保存／初期化と同一ソースから導出し、フォーム同期と取り違えない（教訓 5.24 の baseline 一致の考え方を援用）。
- **共通ガード関数**: 「dirty かつ破壊的に現在状態を置き換える操作」を実行する前に通す共通ガード関数を 1 つ用意し、新ファイル読み込み・アプリ終了・新規プロジェクト開始の 3 経路すべてがこれを通る。経路ごとに個別のダイアログ表示判定を書かない（教訓 5.6）。
- ダイアログは 3 択（保存／保存せず続行／キャンセル）。**保存**を選んだ場合は保存（必要なら名前を付けて保存）を実行し、**保存成功時のみ**元の操作を続行する。保存失敗・保存ダイアログのキャンセル時は元の操作を中止し、未保存データを保護する。
- アプリ終了経路では、終了確認ガードがウィンドウクローズ要求（U20／シェル側のクローズイベント）に確実に介入できるよう接続する。終了の最終確定は、ガードの選択結果に従ってのみ行う。終了確認は E2E で検証しづらいため、ガードの分岐ロジックを純粋関数として切り出し単体テスト対象にする（教訓 5.41）。

### 4. 自動修復オプション UI（FR-106 / 技術方針 §2.10 / §2.3）

- 読み込みアダプタ（U15）→ Zod 検証・整合性チェック（U14）を通った結果を受け取る。バージョン非互換・スキーマ不一致は互換性の警告を表示し読み込みを中止する（互換マイグレーションはスコープ外）。
- 整合性チェックレポートが空でなければ、レポート構造から UI を**動的に**組み立てる。不整合ごとに「種別・関連地物名／ID・該当作中時刻または時間範囲・競合種類」を提示し、U14 が提示する修復オプション（複数案）から選択させる。種別ごとに選択肢が異なる前提で、選択肢を種別横断で共有しない（教訓 5.30 過剰共有の戒め）。7 種すべてを提示・選択可能にする（省略しない。§1.2）。
- ユーザーが各不整合の修復オプションを確定したら、選択を U14 の修復適用（純粋関数）へ渡し、修復後データを得る。U14 は修復適用後に全不変条件・スキーマを再検証してから返す契約であるため、本ユニットは「修復後データが妥当である」結果を受けてからドメインへ反映する（確定まで現在のドメイン状態を破壊しない。教訓 5.22）。
- 「修復せず中止」も選べる。レポートが空（不整合 0 件）のときは修復 UI を出さずそのまま反映する（教訓 5.18: 空は正当値、誤った確認を出さない）。
- 拒否理由・警告は日本語で表示し、必要に応じて「開発者へ報告してください」を付与する（FR-115）。通知文言とテスト可能な戻り値の両方で扱う（教訓 5.26）。

### 5. 新規プロジェクト初期化（教訓 5.36 / FR-03）

- 新規プロジェクト初期化を 1 つの操作として実装し、**表示中データ・ベースマップ（出界図）・保存先パス・メタデータ・バックアップ対象・dirty 状態・終了確認ガード**を同じ保存文脈として同時に初期化する。「表示だけ差し替えて保存先や dirty を取り残す」状態を作らない（教訓 5.36 を直接の根拠とする）。
- 初期化直後の dirty は「クリーン」とし、終了確認ガード（§3）を新規プロジェクト文脈に対して有効化する。
- 新規プロジェクト開始は未保存警告ガード（§3）の契機の 1 つ。dirty なら先に 3 択ダイアログを通す。
- 初期化の各項目を確実に同時設定するため、初期化ロジックは「初期化対象の全項目を 1 つの初期状態オブジェクトとして構築して反映する」形にし、項目を個別に散発設定しない（取り残し防止）。

### 6. ズームレベル制限（FR-10 / FR-109 即時反映 / U16 / U17）

- ズーム制限の設定値（現在有効な最小・最大倍率）を U16 のストアに保持する。既定値（1 倍〜50 倍）とユーザー設定可能範囲（0.1 倍〜10000 倍）を定数として一箇所に定義する。
- 設定 UI（ズーム制限の最小・最大入力欄）では、入力値がユーザー設定可能範囲（0.1〜10000 倍）内かつ最小 ≤ 最大であることを検証し、無効値は即時エラー表示して確定させない。
- 設定変更が確定したら、U16 の即時反映経路で U17 のカメラへクランプ範囲として伝える（FR-109 即時反映）。U17 は渡されたクランプ範囲を適用するため、本ユニットは「現在有効なクランプ範囲を供給する」ことに徹し、クランプ計算式を書かない。
- ズーム制限がアプリ全体設定とプロジェクト固有設定のどちらに属するかは U16 の境界定義（教訓 5.36）に従って一意に分類し、保存先・反映先を一貫させる。

### 7. 結果型・エラーの扱い（技術方針 §2.10 / §2.12）

- ファイル操作・読み込み・修復適用の結果は判別共用体（成功／拒否理由）で受け取り、例外を握りつぶさない。拒否理由はユーザー通知（日本語）とテスト可能な戻り値の両方で扱う（教訓 5.26）。

### 8. テスト容易性（技術方針 §2.14 / 開発ガイド §5.41）

- 未保存警告ガードの分岐（dirty 判定 × 3 択 × 保存成否）、新規プロジェクト初期化の同時初期化、ズーム制限の検証・クランプ範囲供給は、Electron／OS ダイアログを起動せずに単体テストできるよう、UI コンポーネントから分岐ロジック・初期化ロジック・検証ロジックを純粋関数／薄いハンドラとして切り出す（教訓 5.41）。
- U15／U14／U17 への接続は依存をモック可能な境界（型付き IPC・U14 の検証関数・U16 のストア経由）に閉じ、Vitest で「ユーザー操作 → 依存呼び出し → UI 反映」を入力→期待状態で検証する。E2E（Playwright for Electron）で D&D・終了確認の実フローを補う。

## 受け入れ基準（テスト可能な形で列挙）

各基準は Vitest（純粋分岐・ハンドラ単体）／Playwright for Electron（D&D・終了確認の実フロー）等で検証可能な形とする。実装者は完了前に全項目を確認すること。

1. **保存／名前を付けて保存／読込／D&D が U15 の I/O へ接続して動く（FR-105）**
   - 保存・名前を付けて保存・読み込み・D&D 読み込みの各操作が、U15 の型付き IPC を経由してファイル I/O へ到達することを確認する。
   - 「保存」で保存先が未確定なら「名前を付けて保存」フローへ委譲され、保存成功後に保存先パスが更新され dirty が解消されることを確認する。
   - D&D 読み込みが、通常読み込みと同一の後続フロー（未保存警告 → 検証 → 整合性チェック → 自動修復 UI → 反映）を通ることを確認する（D&D 専用の別経路がない）。
   - レンダラがファイルシステムへ直接アクセスせず、U15 の型付き IPC のみを経由することを確認する。

2. **未保存時の読込／終了／新規で警告ダイアログ（保存／保存せず続行／キャンセル）（FR-107）**
   - dirty が真のとき、新ファイル読み込み・アプリ終了・新規プロジェクト開始の 3 経路すべてで 3 択（保存／保存せず続行／キャンセル）の警告ダイアログが表示されることを確認する。
   - 3 経路が同一の共通ガード関数を通ることを確認する（経路ごとに別ゲートを書いていない。教訓 5.6）。
   - **保存**選択時、保存成功なら元の操作が続行し、保存失敗・保存キャンセル時は元の操作が中止され未保存データが保護されることを確認する。
   - **保存せず続行**選択時は保存せず元の操作が続行、**キャンセル**選択時は元の操作が中止され現在状態が維持されることを確認する。
   - dirty が偽のときは警告ダイアログが出ず、元の操作へ直接進むことを確認する。
   - dirty 判定の baseline が保存成功時・新規初期化時にクリーンへリセットされることを確認する。

3. **読込時整合性チェックの自動修復オプションを UI で選択できる（FR-106）**
   - U14 の整合性チェックレポートが空でないとき、検出された不整合（種別・関連地物名／ID・作中時刻または時間範囲・競合種類）が一覧表示され、各不整合に対する自動修復オプション（複数案）をユーザーが選択できることを確認する。
   - FR-106 の 7 種の不整合すべてについて、レポートに現れた場合に UI で提示・選択できることを確認する（省略がない）。
   - 種別ごとに修復オプションの選択肢が異なる場合、UI がレポート構造から動的に正しい選択肢を組み立てることを確認する（選択肢を種別横断で誤って共有しない）。
   - ユーザーの修復選択を U14 の修復適用へ渡し、修復後データ（U14 が再検証済み）を反映してから読み込みが完了することを確認する。確定までドメイン現状態を破壊しないことを確認する。
   - バージョン非互換・スキーマ不一致時は互換性の警告（日本語）を表示し読み込みを中止することを確認する（互換マイグレーションを行わない）。
   - 不整合 0 件（空レポート）のとき、自動修復 UI を出さずそのまま読み込みが反映されることを確認する（誤った確認ダイアログが出ない）。

4. **新規プロジェクトが出界図・dirty・終了確認ガードを同時初期化（教訓 5.36）**
   - 新規プロジェクト開始時に、表示中データ（地物 0 件）・ベースマップ（出界図プリセット）・保存先パス（未確定）・メタデータ・バックアップ対象・dirty 状態（クリーン）・終了確認ガード（有効化）が**同時に**初期化されることを確認する。
   - 初期化後に「保存」を実行すると保存先未確定のため「名前を付けて保存」へ委譲されることを確認する（保存先パスが新規文脈へ初期化されている）。
   - 初期化直後は dirty がクリーンで、その後の編集で dirty が真になり、終了・読み込み・再度の新規でガードが効くことを確認する。
   - 新規プロジェクト開始自体が dirty 時に未保存警告ガード（基準 2）を通ることを確認する。

5. **ズーム制限が既定 1〜50 倍・設定可能範囲 0.1〜10000 倍で効く（FR-10）**
   - 既定のズーム制限が最小 1 倍〜最大 50 倍であることを確認する。
   - ユーザー設定でズーム制限を変更でき、入力許容境界が最小 0.1 倍〜最大 10000 倍であること、範囲外・最小>最大の入力が無効として弾かれ即時エラー表示されることを確認する。
   - 設定変更が即時反映され、現在有効なクランプ範囲が U17 のカメラへ供給されること、クランプ範囲外へズームしようとしても下限・上限で止まることを確認する。
   - 既定値・許容境界が定数として一箇所に定義され、本ユニット内に散在していないことを確認する。

6. **依存への配線が単一の真実源で固定される**
   - U15 の型付き IPC／U14 の検証関数・修復適用／U17 のクランプ範囲供給／U20 のメニュー・ショートカット・モーダル器への接続が、いずれも本ユニットでの再実装ではなく依存ユニットの公開 API への呼び出しであることを確認する。
   - 層をまたぐ接続（コマンド ID・IPC 契約・ストアキー）が共有型で固定され、文字列の偶然一致に頼らないことを確認する（教訓 5.33）。

7. **OS／Electron 非依存の単体テスト可能性（開発ガイド §5.41 / NFR 5.8）**
   - 未保存警告ガードの分岐ロジック・新規プロジェクト初期化ロジック・ズーム制限の検証ロジックが、Electron／OS ダイアログを起動せずに Vitest 単体テストできることを確認する（純粋関数／薄いハンドラとして分離されている）。

## 関連要件（FR-id）

- **FR-10（should）**: ズームレベルを設定で一定範囲に制限できる。デフォルトは最小 1 倍〜最大 50 倍、ユーザー設定可能範囲は最小 0.1 倍〜最大 10000 倍とする。
  - 本ユニットはズーム制限の設定値（既定 1〜50 倍・許容境界 0.1〜10000 倍）を保持・検証し、現在有効なクランプ範囲を U17 のカメラへ供給して制限を効かせる。
- **FR-105（should）**: 保存操作（ショートカット相当・名前を付けて保存）と読み込み操作（ショートカット相当・ドラッグ＆ドロップ）を提供する。
  - 本ユニットは保存・名前を付けて保存・読み込み・D&D 読み込みの UI を U15 の型付き IPC／I/O へ接続する。
- **FR-106（must）**: 読み込み時のデータ整合性チェックで 7 種の不整合を検出し、ユーザーが選択可能な自動修復オプションを提供する。
  - 本ユニットは U14 が検出したレポート・修復オプションを UI として提示し、ユーザー選択を U14 の修復適用へ渡す。検出・修復ロジック本体は U14。
- **FR-107（should）**: 未保存変更がある状態で新ファイル読み込み・アプリ終了・新プロジェクト開始を行う際に警告ダイアログ（保存／保存せず続行／キャンセル）を表示する。
  - 本ユニットは dirty 判定と共通ガードにより、3 経路すべてで 3 択ダイアログを表示し、選択に従って分岐する。

補助的に支える要件・非機能要件:

- **FR-03（must）**: 新規作成時はプリセット地図（出界図）を表示する。本ユニットの新規プロジェクト初期化は出界図を背景に初期化する。
- **FR-104（should）**: 保存形式のバージョン検証・非互換ファイルの警告。本ユニットは U14／U15 が返す非互換結果を互換性の警告として表示し読み込みを中止する。
- **FR-109（should）**: プロジェクト固有設定の変更を関連表示へ即時反映。本ユニットはズーム制限の変更を即時反映し U17 へ供給する。
- **FR-112（should）／FR-118（should）**: ショートカット・ドラッグ＆ドロップ・よく使う操作へのクイックアクセス。本ユニットは保存・読み込みのショートカット相当と D&D 入口を提供する。
- **FR-115（must）／NFR 5.6 / 5.7**: UI・エラーメッセージは日本語のみ。必要に応じ「開発者へ報告してください」を付与。警告・拒否理由を日本語で表示する。
- **FR-116（should）／NFR 5.5**: 外部から読み込むデータの検証・サニタイズ。本ユニットは読み込みデータが必ず U14 の検証を通った結果のみを反映する。
- **FR-02（must）**: 完全オフライン・サンドボックス。本ユニットは `fs` を直接触らず U15 の型付き IPC のみを経由する。
- **NFR 5.8（テスト容易性）**: ガード分岐・初期化・ズーム制限検証を純粋関数／薄いハンドラへ分離し単体テスト可能にする。

## 注意点・既知の落とし穴（開発ガイドの教訓を踏まえる）

着手前に、以下の関連教訓を節番号・見出し・本文ごと引用し、今回の実装判断へどう適用するかを「適用:」として明示してから着手すること（開発ガイド §1.6 AI 作業開始ゲート）。

- **§5.36 プロジェクト設定とアプリ全体設定の境界を先に定義する**: 「プロジェクト固有設定とアプリ全体設定の境界を先に定義し、保存先と反映先を一貫させる。新規プロジェクト開始時は、表示中データだけでなく、保存先パス・メタデータ・バックアップ対象・dirty 状態・終了確認ガードも、同じ保存文脈として同時に初期化する。」
  - 適用: 新規プロジェクト初期化を 1 つの初期状態オブジェクトとして構築し、表示中データ・出界図・保存先パス・メタデータ・バックアップ対象・dirty・終了確認ガードを同時に初期化する（受け入れ基準 4）。ズーム制限の設定がプロジェクト固有／アプリ全体のどちらかは U16 の境界定義に従って一意に分類し、保存先・反映先を一貫させる。

- **§5.6 状態変化の検出は結果状態で判定する**: 「『ある状態変化が起きたら追加処理を走らせる』検出は、特定の入力経路（呼び出しフラグ・引数の有無）でゲートせず、変異後の結果状態で判定する。同じ状態変化を複数経路が引き起こす場合、特定経路に絞ったゲートは別経路で必ず漏れる。検出: 起動条件に『この経路でだけ起きる』と書いたら、同じ結果状態を生む他経路を列挙して網羅を確認し、回帰テストを経路ごとに置く。」
  - 適用: 未保存警告は「dirty かつ破壊的に状態を置き換える操作」という結果状態で共通ガードを起動し、新ファイル読み込み・アプリ終了・新規プロジェクトの 3 経路すべて（および読み込みのメニュー／ショートカット／D&D の各入口）が同じガードを通す。経路ごとに回帰テストを置く（受け入れ基準 2）。

- **§5.18 空配列・空オブジェクトは真値である**: 「空配列・空オブジェクトは真値である。論理和による短絡評価のデフォルト補完に頼らず、型や状態を明示的に判定する。」
  - 適用: 整合性チェックレポートが空（不整合 0 件）でも正当な読み込み結果として扱い、自動修復 UI を出さずそのまま反映する。地物 0 件の新規プロジェクトも正当値として扱い「未初期化」と取り違えない（受け入れ基準 3・4）。

- **§5.22 確定まで共有データを破壊的に更新しない**: 「結果が確定するまで、共有キャッシュ/共有データを破壊的に更新しない。検証用の仮データで成功を確認してから反映し、失敗時は追加した要素をすべてロールバックする。」
  - 適用: 読み込み・修復は、U14 の検証・修復適用が成功（再検証済み）した結果を得てから現在のドメイン状態へ反映する。検証・修復・保存が失敗・中止された場合は現在状態を維持し、未保存データを破壊しない（受け入れ基準 2・3）。

- **§5.26 編集制約はコマンド確定前にも同じサービスで検証する／拒否理由は通知と戻り値の両方**: 「編集制約（…禁止条件）は、UI の候補表示だけでなく、コマンド/ユースケースの確定前にも同じサービスで検証する。…拒否理由は、ユーザー通知とテスト可能な戻り値の両方で扱う。」
  - 適用: ズーム制限入力の検証（範囲・最小≤最大）と、読み込みのバージョン非互換・整合性拒否は、UI 表示だけでなく確定前にも検証し、拒否理由を日本語通知とテスト可能な戻り値の両方で扱う（受け入れ基準 3・5）。

- **§5.33 層をまたぐ API 契約は両側テストで固定する**: 「層をまたぐ API 契約（呼び出し側・公開側・受信側のチャネル名/関数名）は、文字列の偶然一致に任せず、共有型・型付きラッパー・両側の単体テストで固定する。」
  - 適用: U15 の型付き IPC・U20 のコマンド ID／ショートカット対応づけ・U16 のストアキー・U17 のクランプ範囲供給は、共有型で固定し本ユニットでチャネル名・キーをハードコードしない。接続変更時は全層とテストを同一変更単位で更新する（受け入れ基準 6）。

- **§5.41 検証不能になった範囲は別手段で補う**: 「E2E 等で一時的に検証できなくなった範囲（外部統合・ファイル I/O・終了確認等）は、未検証のまま放置しない。純粋関数化・アダプタ分離・モックで単体テスト対象にして補う。」
  - 適用: 終了確認ガード・D&D・OS ファイルダイアログは E2E で検証しづらいため、ガード分岐ロジック・新規初期化ロジック・ズーム制限検証を純粋関数／薄いハンドラへ分離し Vitest で単体テストする。実フローは Playwright for Electron で補う（受け入れ基準 7）。

- **§5.24 確定ハンドラには no-op ガードを入れる（dirty 判定の baseline 一致）**: 「…確定値が現在状態（baseline）と一致するなら実行しない no-op ガードを入れる。…ガードの baseline は、フォーム同期と同一ソースから導出する。」
  - 適用（注意点として）: dirty 判定の baseline（最後の保存／新規初期化時点のクリーン基準）は保存・初期化と同一ソースから導出し、フォームの一時値と取り違えない。値が変わっていない保存・設定確定で誤って dirty を立てない／消さない。

- **§5.30 過少共有と過剰共有の両方を戒める**: 「同じ判定・同じ baseline・同じ既定値処理は、同じ実装を共有する（過少共有の戒め）。一方で、見た目が同じピッカー UI でも除外規則が操作種別ごとに異なるなら…安易に共有しない（過剰共有の戒め）。」
  - 適用: 読み込みの後続フロー・dirty 判定・ズーム制限の既定値処理は単一実装を共有する（過少共有を戒める）。一方で自動修復オプションは不整合種別ごとに選択肢が異なるため、UI の選択肢生成を種別横断で安易に共有しない（過剰共有を戒める）。検出・修復ロジック本体は U14、I/O は U15、カメラ計算は U17 を再実装せず共有する。

- **その他の落とし穴**:
  - **保存失敗時の保護**: 未保存警告で「保存」を選んだ際、保存が失敗・キャンセルされたら元の破壊的操作（読み込み／終了／新規）を**中止**する。保存成否を確認せず続行して未保存データを失わない。
  - **同一フローへの収束**: 読み込みの入口（メニュー・ショートカット・D&D）が複数あっても、未保存警告 → 検証 → 整合性チェック → 自動修復 → 反映の単一フローへ収束させる。入口ごとに別フローを書かない（教訓 5.6）。
  - **クランプは供給に徹する**: ズームのクランプ計算式は U17 が持つ。本ユニットはクランプ範囲（最小・最大倍率）を供給するのみで、クランプ判定を二重実装しない（単一の真実源）。
  - **設定値のハードコード禁止**: ズーム制限の既定値（1〜50 倍）・許容境界（0.1〜10000 倍）は定数として一箇所に定義し、本ユニット内に散在させない。
  - **`fs` 直接アクセス禁止**: レンダラ（`ui`）はファイルシステムへ直接触れず、U15 の型付き IPC のみを経由する（FR-02 サンドボックス前提）。
  - **クリーンルーム原則（開発ガイド §3.1）**: 本ユニットの設計・実装・コメント・テスト名で過去版・他プロダクト・「従来こうしていた」式の外部参照に頼らない。制約はすべて v4 自身の要件（FR-10 / 105 / 106 / 107）・技術方針・開発ガイドの記述として直接記述する。
