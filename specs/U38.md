## 目的

本アプリには、地図表示・編集挙動・描画性能・配色などに作用する多数の設定値が存在する。これらは「プロジェクトごとに固有の設定」と「アプリ全体（どのプロジェクトを開いても共通）の設定」の二系統に明確に分かれる。本ユニットは、その二系統の設定をモーダルダイアログで編集できる UI と、編集結果を関連表示・編集挙動へ即時反映する経路を提供する。

本ユニットの中核責務は次の四点である。

1. **プロジェクト固有設定のモーダル編集（FR-109）**: プロジェクト名・説明、赤道長、扁平率、タイムライン最小/最大年、グリッド間隔/色/不透明度、ベースマップ指定、面情報ラベル画面占有率閾値、新規面の自動配色既定値、既定パレットテーマ、カスタムパレットを、モーダルダイアログで編集できるようにする。赤道長・グリッド設定の変更は関連表示（測地計算結果・グリッド描画）に即時反映する。
2. **アプリ全体設定のモーダル編集（FR-110）**: 共有頂点スナップ距離（既定 50px）、描画更新頻度（1〜60FPS・既定 60）、全頂点マーカー表示上限を編集でき、保存後は即時反映する。
3. **二系統の境界の一貫（教訓 5.36）**: どの設定がプロジェクト固有でどれがアプリ全体かを型・定数で一意に定義し、保存先（プロジェクト固有＝プロジェクトデータの一部・dirty 化対象、アプリ全体＝アプリレベルの永続化対象）と反映先（購読する描画/編集挙動）を一貫させる。
4. **設定値の単一の真実源（教訓 5.19）**: 設定キー・既定値・分類を型/定数/ファクトリ経由で定義し、編集・表示・保存・反映の全経路が同一の値を使うことを保証する。

本ユニットは「設定を編集する UI（React モーダル）と、編集を確定して状態層へ反映する調停層」である。設定の状態保持・分類・購読者への即時反映通知という基盤（Zustand ストアと設定境界の型定義）は依存ユニット U16 が提供し、本ユニットはその基盤の上に編集ダイアログと確定フローを載せる。設定の物理永続化（プロジェクトデータへの書き込み・アプリ設定ファイルの読み書き）は別ユニット（永続化基盤）に委ねる。

## スコープ

### やること

#### プロジェクト固有設定の編集（FR-109）

モーダルダイアログで以下のプロジェクト固有設定をすべて編集できる。各項目は U16 が定義する「プロジェクト固有設定」型のフィールドに 1 対 1 対応させ、本ユニットでは新たに別の保持場所を作らない。

- **プロジェクト名・説明**: 文字列入力。
- **赤道長（km）**: 正距円筒図法における赤道長（FR-05）。数値入力。変更は測地計算（距離・長さ・面積）と、それらを表示する箇所に即時反映する。
- **扁平率**: 数値入力。
- **タイムライン最小/最大年**: タイムラインがカバーする時間範囲の下限・最大（FR-66、プロジェクト既定 0 年〜10000 年）。最小 < 最大の妥当性を検証する。
- **グリッド間隔/色/不透明度**: 緯線・経線グリッドの間隔（5/10/15/30 度から選択、FR-13）、色、不透明度（FR-13 / FR-109）。変更はグリッド描画に即時反映する。
- **ベースマップ指定**: ベースマップとして用いる地図の指定（プリセット出界図／ユーザー指定地図）への入口。本ユニットは「ベースマップ指定の起動点（ファイル選択・差し替え要求）」をダイアログ内に提供するに留め、差し替え・自動補正・フォールバック・プロジェクト内コピー登録の処理は U18（ベースマップ描画と差し替え）へ委譲する。
- **面情報ラベル画面占有率閾値**: 面情報のリングごとのラベル表示可否を判定する画面占有率の閾値（FR-86）。数値入力。
- **新規面の自動配色既定値**: 新規面情報を作成したときの自動配色許可フラグの既定値（FR-100）。真偽値。
- **既定パレットテーマ**: 新規面で使う配色パレット（テーマ名）の既定（FR-100）。選択。
- **カスタムパレット**: ユーザー定義の配色パレットの管理（追加・編集・削除）。

赤道長・グリッド設定の変更が「再起動を要さず」関連表示に即時反映されること（FR-109）を満たす。

#### アプリ全体設定の編集（FR-110）

モーダルダイアログで以下のアプリ全体設定をすべて編集できる。各項目は U16 が定義する「アプリ全体設定」型のフィールドに 1 対 1 対応させる。

- **共有頂点スナップ距離（px）**: 既定 50px（FR-31 / FR-110）。数値入力。変更は共有頂点化候補の近接判定（編集挙動）に即時反映する。
- **描画更新頻度（FPS）**: 1〜60FPS の範囲、既定 60（FR-110）。範囲外を弾く妥当性検証を行う。変更は描画ループの更新頻度に即時反映する。
- **全頂点マーカー表示上限**: アクティブ地物選択時に全頂点を半透明マーカーで表示する（FR-79）際の表示数上限。数値入力。変更は描画挙動に即時反映する。

保存後（確定後）に再起動を要さず即時反映されること（FR-110）を満たす。

#### 二系統のダイアログ構成と確定フロー

- プロジェクト固有設定とアプリ全体設定を、どちらに属するかが利用者にも明確に分かる形で提示する（別ダイアログまたは同一ダイアログ内の明確に区別されたセクション/タブ）。どの設定がどちらに属するかは U16 の型/定数による分類に従い、本ユニットの UI でその分類を可視化する。
- 編集中はダイアログ内のドラフト値（編集途中の値）として保持し、**確定（保存/適用）するまで共有の設定状態（Zustand ストアの確定値）を破壊的に更新しない**（教訓 5.22）。
- 確定操作で、ドラフト値を妥当性検証したうえで U16 の設定更新アクションへ渡す。プロジェクト固有設定の確定は保存文脈（プロジェクトデータの一部として dirty 化・保存対象）として、アプリ全体設定の確定はアプリレベルの永続化対象として、それぞれ一貫した経路で反映する（教訓 5.36）。物理 I/O は委譲する。
- キャンセル操作・ダイアログを閉じる操作で、ドラフト値を破棄し確定値へ影響を残さない（教訓 5.2 / 5.22）。
- 値が変更されていない項目を確定した場合に「何も変わっていないのに dirty 化や履歴/通知が走る」幽霊エントリを作らない no-op ガードを設ける（教訓 5.24）。
- 妥当性検証で拒否した項目（最小≥最大年、FPS 範囲外、赤道長や扁平率が非正など）の拒否理由を、日本語のユーザー通知（FR-115）とテスト可能な戻り値の両方で扱う（教訓 5.26）。拒否理由のメッセージは、発生元と無関係なクリックで即時消去しない（教訓 5.12）。

#### 新規プロジェクト開始時の設定初期化への連動（教訓 5.36）

- 新規プロジェクト開始時、表示中データだけでなく、保存先パス・メタデータ・バックアップ対象・dirty 状態・終了確認ガードも同じ保存文脈として同時に初期化される必要がある（教訓 5.36、FR-103 / FR-107）。本ユニットは「プロジェクト固有設定の既定値ファクトリ」を提供し、新規プロジェクト開始処理（U39／プロジェクトライフサイクル側）がそれを用いてプロジェクト固有設定を既定へ初期化できるようにする。
- 本ユニットの責務は、新規開始時に使うプロジェクト固有設定の既定値（赤道長・扁平率・タイムライン範囲 0〜10000 年・グリッド既定 10 度などの初期セット）を単一のファクトリで供給し、設定境界（どれがプロジェクト固有か）を保存文脈初期化と整合させることである。保存先パス・dirty 状態・終了確認ガードそのものの初期化は U39 が行い、本ユニットはそれと矛盾しない設定初期化の入口を提供する。

#### 上記すべてに対するテスト

- 純粋に検証可能な部分（妥当性検証・既定値ファクトリ・分類・ドラフト→確定の差分判定・no-op ガード）は Vitest で単体テストする。
- ダイアログ操作（開く→編集→確定／キャンセル、即時反映、拒否表示）は React コンポーネントテストおよび E2E（Playwright for Electron）で検証する。

### やらないこと

- **設定の状態保持・分類・購読者への即時反映通知という基盤の実装**: プロジェクト固有設定とアプリ全体設定の型・分類（どのキーがどちらに属するか）・Zustand ストアでの保持・変更時の購読者通知経路は U16 が提供する。本ユニットはそれを複製せず、編集 UI と確定フローから U16 の設定型・更新アクション・通知経路を利用する（単一の真実源。開発ガイド §4、教訓 5.19）。
- **設定の物理永続化・スキーマ検証・ファイル I/O**: プロジェクト固有設定の `.tmap` への書き込み、アプリ全体設定のアプリレベル永続化、Zod スキーマ検証、アトミック保存、世代バックアップは永続化基盤ユニット（U14 / U15）の責務。本ユニットは確定値を渡すまでで、保存先の物理 I/O・スキーマ検証は委ねる。
- **ベースマップ差し替え・自動補正・フォールバック・プロジェクト内コピー登録**: U18 の責務。本ユニットはダイアログ内に差し替え要求の起動点を置くのみ。
- **赤道長を用いた測地計算そのもの（距離・長さ・面積）**: 測地計算ユニットの責務。本ユニットは赤道長を設定値として編集し U16 経由で反映するのみで、計算ロジックは持たない。
- **グリッド描画・経度シフトそのもの**: U18 の責務。本ユニットはグリッド設定値を編集し反映するのみ。
- **共有頂点スナップ判定・描画ループ・全頂点マーカー描画そのもの**: それぞれ編集ツール／共有頂点（U24 がスナップ判定本体・U11 が共有化）・描画ユニット（U19）の責務。本ユニットはスナップ距離・FPS・マーカー表示上限を設定値として編集し反映するのみ。
- **自動配色アルゴリズム・パレット適用ロジック**: 配色ユニットの責務。本ユニットは新規面の自動配色既定値・既定パレットテーマ・カスタムパレットを設定値として管理し反映するのみ。
- **保存先パス・dirty 状態・終了確認ガードそのものの初期化と管理**: U39／プロジェクトライフサイクル側の責務。本ユニットはプロジェクト固有設定の既定値ファクトリを供給し、保存文脈初期化と矛盾しない入口を提供するに留める。
- **新規オブジェクト型の追加や設定項目の将来拡張機構**: 本ユニットは FR-109 / FR-110 が列挙する設定項目のみを対象とする。

## 依存（dependsOn）

本ユニットは以下のユニットに依存する。これらが提供する型・状態・経路・処理を前提として実装する。実装着手時に各ユニットが公開する正確なシグネチャを確認し、本ユニットの UI・確定フロー・既定値ファクトリをそれに整合させること。依存ユニットが未完了の場合は、各ユニットが公開する境界（下記）を前提インタフェースとして仮定し、その境界に対して組み立てる。

- **U16（UI/セッション状態ストアとドメインブリッジ）**: プロジェクト固有設定とアプリ全体設定の境界（型・分類）の定義、Zustand ストアでの設定保持、設定更新アクション、設定変更時の購読者（描画・編集挙動）への即時反映通知経路を提供する。本ユニットはこの設定型・分類・更新アクション・通知経路を利用し、設定の保持や分類を再実装しない。U16 が公開する「プロジェクト固有設定型」「アプリ全体設定型」「設定キーの分類（定数）」「設定更新アクション」を前提インタフェースとして参照する。
- **U18（ベースマップ描画と差し替え・グリッド・経度シフト）**: ベースマップ指定の差し替え（自動補正・フォールバック・プロジェクト内コピー登録）とグリッド描画を提供する。本ユニットのダイアログ内ベースマップ指定はこの差し替え入口へ要求を渡し、グリッド設定の即時反映先は U18 のグリッド描画である。
- **U39（ファイル操作UI／プロジェクトライフサイクル）**: プロジェクトデータの保存・読み込み（その実体は永続化ユニット U14 / U15 が担う）、保存先パス・dirty 状態・終了確認ガード・自動バックアップの管理、新規プロジェクト開始処理を提供する。本ユニットはプロジェクト固有設定の確定を U39 が扱う保存文脈（dirty 化・保存対象）と整合させ、新規開始時の設定初期化の入口（既定値ファクトリ）を U39 へ供給する。
- **U24（編集ツール）と U11（共有頂点システム）**: 共有頂点化の近接判定はスクリーン座標のスナップ距離に依存する（FR-31、既定 50px）。スクリーン座標近接スナップ判定の本体は編集セッション（U24）が所有し、決定済みペアの共有化は U11 が担う。本ユニットが編集するアプリ全体設定「共有頂点スナップ距離」の反映先がこの近接判定であることを前提とし、設定値が U24 のスナップ判定／U11 の共有化と同一値（単一の真実源）を使うことを保証する。
- **U19（地物描画）**: 描画更新頻度（FPS）と全頂点マーカー表示上限の反映先は描画ループ・全頂点マーカー描画である。本ユニットが編集するこれらアプリ全体設定が、再起動を要さず描画挙動へ即時反映されることを前提とする。

依存ユニットが公開する設定型・分類・通知経路・差し替え入口・既定値の利用契約を再実装せず、本ユニットからは呼び出して利用する（単一の真実源。開発ガイド §4「単一の真実源」、教訓 5.30 過少共有の戒め）。

## 実装方針（技術方針に沿う）

技術方針が定める採用スタックと層分離に厳密に従う。

### 配置と層分離

- **設定モーダルダイアログ**（プロジェクト固有設定・アプリ全体設定の編集 UI）は `ui` 層（React 18 関数コンポーネント）に配置する。多数の設定項目を宣言的・状態駆動で構築する（技術方針 2.3 / 2.5）。
- **設定値の妥当性検証・既定値ファクトリ・ドラフト→確定の差分判定（no-op 判定）・分類の参照**は、React・Canvas・Electron に依存しない純粋ロジックとして `domain`（またはそれに準じる純粋ロジック）へ切り出し、Vitest で単独実行できるようにする（NFR 5.8）。
- **設定の確定値・分類・通知経路**は U16 の Zustand 設定ストアに置き、本ユニットの UI は確定時にそのアクションを呼ぶのみとする。設定の確定値を本ユニットの React state に二重に持たない（編集中のドラフト値はダイアログのローカル状態に持ち、確定で U16 ストアへ渡す）。
- 依存方向は内向きに固定する。`ui` / `domain` は U16 の公開境界・依存ユニットを参照してよいが、`domain` は `ui` / `render` / `shell` を参照しない（技術方針 2.13）。

### 設定キー・既定値・分類の単一定義（教訓 5.19）

- 設定キー・既定値・分類（プロジェクト固有／アプリ全体）は、表示文字列や思い込みで判定せず、型定義・定数・ファクトリ経由で一意に定義する（教訓 5.19）。可能な限り U16 が公開する設定型・分類定数を参照し、本ユニットで別定義を作らない。本ユニットで既定値ファクトリを提供する場合も、U16 の設定型に厳密に整合させる。
- 既定値（共有頂点スナップ距離 50px、描画更新頻度 60FPS、タイムライン 0〜10000 年、グリッド 10 度など）は単一のファクトリ/定数で定義し、ダイアログの初期表示・新規プロジェクト初期化・テストの期待値がすべて同一の値を参照する（単一の真実源）。

### ドラフト編集と確定フロー（教訓 5.22 / 5.2 / 5.24）

- ダイアログを開いたら、現在の確定値（U16 ストア）からドラフト値を初期化する。編集中はドラフト値のみを更新し、確定値は更新しない（教訓 5.22）。
- 確定（保存/適用）操作で、ドラフト値を妥当性検証し、合格した値だけを U16 の設定更新アクションへ渡す。プロジェクト固有設定とアプリ全体設定で別々の更新経路を通し、保存文脈（プロジェクト＝ dirty 化・保存対象、アプリ全体＝アプリレベル永続化対象）を一貫させる（教訓 5.36）。
- 確定時、ドラフト値が現在の確定値（baseline）と一致する項目は更新・dirty 化・通知を起こさない no-op ガードを入れる。baseline はダイアログ初期化と同一ソース（U16 の確定値）から導出する（教訓 5.24）。
- キャンセル・閉じる・別タブ切替・モーダル外クリックなどダイアログを離れる全経路でドラフト値を破棄し、確定値へ残らないようにする（教訓 5.2）。

### 即時反映（教訓 5.35、FR-109 / FR-110）

- 設定確定で U16 の設定更新アクションを呼ぶと、U16 は依存する全購読者へ変更を通知する。本ユニットはその通知経路に確実に乗せ、一部の購読者だけ古い設定値を持つドリフトを作らない（教訓 5.35）。
  - 赤道長 → 測地計算結果の表示、グリッド間隔/色/不透明度 → グリッド描画（U18）。
  - 共有頂点スナップ距離 → 近接判定（U24 のスナップ判定本体 / U11 の共有化）、描画更新頻度・全頂点マーカー表示上限 → 描画ループ・マーカー描画（U19）。
- 即時反映は「再起動を要さない」ことが要件である（FR-109 / FR-110）。確定後ただちに該当表示・挙動が更新されることをテストで確認する。

### 妥当性検証と拒否理由（教訓 5.26 / 5.12、FR-115）

- 妥当性検証は UI のフォーム表示だけでなく、確定処理の入口でも同じ検証関数で行う（UI を通らない確定経路があっても不正値が入らないようにする。教訓 5.26）。検証は純粋関数として切り出す。
  - タイムライン最小 < 最大、赤道長 > 0、扁平率の範囲、FPS が 1〜60、不透明度の範囲、スナップ距離・マーカー上限・面ラベル閾値が許容範囲、など。
- 拒否理由は日本語で通知し（FR-115）、必要に応じて「開発者へ報告してください」を付与する。拒否理由のメッセージは、発生元と無関係なクリック・マウス操作で即時消去せず、同種操作の再試行・明示的な閉じる・成功した確定で置換する（教訓 5.12）。拒否理由はテスト可能な戻り値としても扱う（教訓 5.26）。

### テスト方針（技術方針 2.14 / NFR 5.8、開発ガイド 1.9）

- Vitest で、妥当性検証・既定値ファクトリ・分類参照・ドラフト→確定差分（no-op）判定の「入力 → 期待結果」を直接比較する。境界値（最小=最大年、FPS=0/1/60/61、赤道長=0/負、不透明度境界）を網羅する。
- 各設定項目について、確定が U16 の正しい分類（プロジェクト固有／アプリ全体）の更新アクションを呼び、保存文脈が一貫することをテストする（教訓 5.36 / 5.19）。
- 即時反映を、確定後に購読者（描画・編集挙動を模したテスト購読者）が新値を観測できることで確認する（教訓 5.35、FR-109 / FR-110）。
- ドラフト破棄を「開く→編集→キャンセル→再度開く」で確定値が変わっていないこと、no-op ガードを「変更なしで確定→ dirty 化/通知が起きないこと」で確認する（教訓 5.22 / 5.24 / 5.2）。
- ファイル選択や物理 I/O など E2E で検証しにくい範囲は、純粋関数化・アダプタ分離・モックで単体テスト対象にして補う（教訓 5.41）。
- 実装フローは開発ガイド 1.9 の順序（機能宣言+仕様引用 → 教訓引用・適用宣言 → 実装 → テスト全パス → ビルド確認 → 状態文書更新 → コミット）に従う。

## 受け入れ基準（テスト可能な形で列挙）

以下はすべてテスト可能な形で満たすこと。テストは実装と同時に作成する（開発ガイド 1.9）。

1. **プロジェクト固有設定をモーダルで編集でき赤道長/グリッド変更が即時反映（FR-109）**
   - モーダルダイアログで、プロジェクト名・説明、赤道長、扁平率、タイムライン最小/最大年、グリッド間隔/色/不透明度、ベースマップ指定、面情報ラベル画面占有率閾値、新規面の自動配色既定値、既定パレットテーマ、カスタムパレットを編集できることを確認できる（列挙したすべての項目を網羅する。省略しない）。
   - 赤道長を変更して確定すると、再起動を要さず測地計算結果の表示へ即時反映されることを確認できる。
   - グリッド間隔/色/不透明度を変更して確定すると、再起動を要さずグリッド描画へ即時反映されることを確認できる。
   - ベースマップ指定はダイアログ内の起動点から U18 の差し替え入口へ要求が渡ることを確認できる（差し替え処理自体は U18 が行う）。

2. **アプリ全体設定(スナップ距離/FPS/マーカー上限)を編集でき保存後即時反映（FR-110）**
   - モーダルダイアログで、共有頂点スナップ距離（既定 50px）、描画更新頻度（1〜60FPS・既定 60）、全頂点マーカー表示上限を編集できることを確認できる。
   - スナップ距離変更が共有頂点化の近接判定（編集挙動）へ、FPS 変更が描画ループへ、マーカー上限変更が全頂点マーカー描画へ、保存後ただちに（再起動を要さず）即時反映されることを確認できる。
   - FPS が 1〜60 の範囲外の値は妥当性検証で拒否され、日本語の拒否理由が通知されることを確認できる。

3. **プロジェクト設定とアプリ全体設定の保存先/反映先が一貫（教訓 5.36）**
   - 各設定キーが、UI 上でプロジェクト固有かアプリ全体かが明確に区別されて提示されることを確認できる。
   - プロジェクト固有設定の確定はプロジェクトデータの保存文脈（dirty 化・保存対象）として、アプリ全体設定の確定はアプリレベルの永続化対象として、それぞれ一貫した経路（U16 の対応する更新アクション）を通ることをテストで確認できる。取り違え（プロジェクト設定をアプリ全体として保存する等）が起きないことを確認できる。

4. **設定値が型/定数経由で全経路同一値を使う（教訓 5.19）**
   - 設定キー・既定値・分類が型定義・定数・ファクトリ経由で定義され、編集（ダイアログ初期表示）・表示・保存（確定）・反映（購読者）・新規プロジェクト初期化のすべてが同一の値を参照することをテストで確認できる。
   - 既定値（スナップ距離 50px、描画更新頻度 60FPS、タイムライン 0〜10000 年、グリッド 10 度など）が単一のファクトリ/定数から供給され、ダイアログ初期表示・新規初期化・テスト期待値で同一であることを確認できる。

5. **新規プロジェクト開始時に保存先パス/dirty/終了確認ガードも同時初期化（教訓 5.36）**
   - 本ユニットがプロジェクト固有設定の既定値ファクトリを供給し、新規プロジェクト開始処理（U39）がそれを用いてプロジェクト固有設定を既定へ初期化できることを確認できる。
   - 新規開始時に、プロジェクト固有設定の初期化が、保存先パス・dirty 状態・終了確認ガードの初期化（U39 が担う）と同じ保存文脈として矛盾なく行われることを、本ユニットの既定値供給と U39 側初期化の接続テストで確認できる。

6. **ドラフト編集・確定・キャンセルの一貫（教訓 5.22 / 5.2 / 5.24）**
   - 編集中のドラフト値は確定するまで共有設定状態（確定値）を変更しないことを確認できる。
   - キャンセル・閉じる等でダイアログを離れるとドラフト値が破棄され、確定値へ残らないことを「開く→編集→キャンセル→再度開く」で確認できる。
   - 値を変更せずに確定しても dirty 化・通知（幽霊エントリ）が起きない no-op ガードが働くことを確認できる。

7. **妥当性検証と拒否理由（教訓 5.26 / 5.12、FR-115）**
   - 不正値（最小≥最大年、赤道長≤0、FPS 範囲外、不透明度範囲外 等）が UI と確定処理の入口の両方で同じ検証関数により拒否されることを確認できる。
   - 拒否理由が日本語で通知され、テスト可能な戻り値としても扱えることを確認できる。拒否理由が発生元と無関係な操作で即時消去されないことを確認できる。

8. **純粋ロジックの単独実行（NFR 5.8）**
   - 妥当性検証・既定値ファクトリ・分類参照・ドラフト→確定差分判定が副作用のない純粋関数として `domain` で Vitest 単独実行でき、境界ケースを網羅したテストが通る。

## 注意点・既知の落とし穴（開発ガイドの教訓を踏まえる）

### 適用宣言（AI 作業開始ゲート, 開発ガイド 1.6）

着手前に以下の教訓を節番号・見出し・本文ごと直接引用し、本ユニットへの適用を「適用:」として 1 文以上で宣言してから実装すること。引用と適用宣言を省略して着手してはならない。

- **教訓 5.36「プロジェクト設定とアプリ全体設定の境界を先に定義する」**（引用: 「プロジェクト固有設定とアプリ全体設定の境界を先に定義し、保存先と反映先を一貫させる。新規プロジェクト開始時は、表示中データだけでなく、保存先パス・メタデータ・バックアップ対象・dirty 状態・終了確認ガードも、同じ保存文脈として同時に初期化する。」）。**適用**: FR-109 / FR-110 の各設定キーを U16 の型/定数による分類に従ってプロジェクト固有/アプリ全体に一意に割り当て、確定経路（保存文脈）と反映先を一貫させる。新規開始時のプロジェクト固有設定既定値ファクトリを供給し、保存先パス・dirty・終了確認ガードを初期化する U39 と同じ保存文脈で矛盾なく初期化する（受け入れ基準 3 / 5）。

- **教訓 5.19「分岐識別子は型定義・定数・ファクトリを経由する」**（引用: 「種別・モード名・設定キーのような分岐識別子は、表示文字列や思い込みで判定せず、型定義・定数・ファクトリを経由する。大文字小文字差でも分岐が変わる。検出: 新識別子を追加・改名したら、作成・表示・編集・保存・検索の全経路で同じ値を使うテストを置く。」）。**適用**: 設定キー・既定値・分類は型/定数/ファクトリ経由で定義し、ダイアログ初期表示・編集・確定保存・反映・新規初期化の全経路で同一値を使う。新識別子（新設定キー）の追加時は全経路で同値を使うテストを置く（受け入れ基準 4）。

その他、本ユニットで特に該当する教訓と落とし穴:

- **教訓 5.22「確定まで共有データを破壊的に更新しない」**: 編集中はドラフト値で保持し、確定するまで共有の確定設定（Zustand ストア）を破壊的に更新しない。確定が妥当性検証に失敗したら確定値を汚染しない（受け入れ基準 6 / 7）。
- **教訓 5.2「一時的 UI 状態は全経路で破棄する」**: ダイアログのドラフト値は、確定・キャンセル・閉じる・タブ切替・モーダル外クリックの全経路で破棄する。残ると次回開いたとき意図しない値が引き継がれる（受け入れ基準 6）。
- **教訓 5.24「確定ハンドラには no-op ガードを入れる」**: 値が変わっていない設定を確定しても dirty 化・履歴・通知を起こさない no-op ガードを入れる。baseline はダイアログ初期化と同一ソース（U16 の確定値）から導出する（受け入れ基準 6）。
- **教訓 5.26「編集制約はコマンド確定前にも同じサービスで検証する」**: 妥当性検証は UI のフォーム表示だけでなく確定処理の入口でも同じ検証関数で行う。UI を通らない確定経路があっても不正値が入らないようにし、拒否理由は通知とテスト可能な戻り値の両方で扱う（受け入れ基準 7）。
- **教訓 5.12「判断用メッセージを無関係な操作で消さない」**: 妥当性検証の拒否理由は、発生元と無関係なクリックやマウス操作で即時消去しない。消す契機は同種操作の再試行・明示的な閉じる・成功した確定に限る（受け入れ基準 7）。
- **教訓 5.35「共有リソース更新は全依存先へ通知する」**: 設定（共有リソース）の確定時、依存する全購読者（描画・編集挙動）へ U16 の通知経路を通じて即時反映し、一部購読者だけ古い設定値を持つドリフトを作らない（受け入れ基準 1 / 2）。
- **横断指針（開発ガイド §4「単一の真実源」、教訓 5.30 過少共有の戒め）**: 設定の保持・分類・通知は U16、グリッド描画は U18、近接判定は U24 のスナップ判定本体／U11 の共有化、描画は U19、配色は配色ユニット（U33）の単一実装を共有し、本ユニットで再実装しない。設定キー・既定値も一箇所で定義し全経路で共有する。
- **横断指針（開発ガイド §4「層をまたぐ契約の固定」、教訓 5.33 / 5.34）**: 本ユニットが U16 へ渡す設定型・分類・更新アクションの名前/型/構造は層をまたぐ契約であり、偶然の一致に頼らず共有型・両側テストで固定する。U39 へ供給する既定値ファクトリの型も同様に固定する。
- **教訓 5.41「検証不能になった範囲は別手段で補う」**: ファイル選択（ベースマップ指定）・物理 I/O など E2E で検証しにくい範囲は、妥当性検証・既定値ファクトリ・確定値生成を純粋関数化／アダプタ分離してモックで単体テストする（受け入れ基準 8）。
- **クリーンルーム（開発ガイド 3.1）**: 本ユニットの実装・コメント・テスト名で過去版や外部の既存実装に言及しない。制約はすべて v4 自身の要件（FR-109 / FR-110 ほか）・技術方針として直接記述する。
