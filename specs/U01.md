# U01 リポジトリ基盤・ビルド・層分離・lint依存方向強制

本書は実装ユニット U01 の実装指示書である。実装者（別エージェント）はこの指示書だけを読んで着手できる。前提知識は本書の中に閉じて記述する。要件・技術方針・開発作法の根拠は本書末尾の「関連要件」「注意点・既知の落とし穴」に引用する。

---

## 目的

time-map-app-4 のリポジトリ基盤を確立する。具体的には以下の 5 点を満たす最小スケルトンを構築する。

1. 単一 npm パッケージで Electron デスクトップアプリが空ウィンドウとして起動する。
2. TypeScript の strict 群 4 種をすべて有効化した tsconfig を全層で共有する。
3. ディレクトリ層 `domain` / `render` / `ui` / `shell` を作成し、依存方向を `domain` へ内向きに固定する import lint ルールを導入し、違反を機械検証可能にする。
4. `domain` のテストを Electron / React 抜きで Vitest 実行できる。
5. レンダラのセキュリティ設定（`contextIsolation: true` / `nodeIntegration: false` / `sandbox: true`）を有効にする。

本ユニットはアプリの「土台」だけを作る。地図描画・ドメインロジック・UI 機能は一切実装しない。後続の全ユニットが本ユニットの上に積み上がるため、層境界・型厳密性・依存方向の機械検証という規律を最初の 1 ユニットで確実に固める。

## スコープ

### やること

- npm 単一パッケージの初期化（`package.json`、ロックファイル、`.gitignore` への成果物追記）。
- electron-vite による main / preload / renderer の 3 ターゲット構成。
- Vite + React 18 + TypeScript の導入と最小起動。
- strict 群 4 種（`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`）を有効にした共有 tsconfig の整備。
- ディレクトリ層 `src/domain` / `src/render` / `src/ui` / `src/shell` の作成（各層に最小の実体ファイルを 1 つ以上置く）。
- ESLint による import 依存方向の内向き固定ルール導入と、違反検出の確認。
- Vitest 設定（`domain` 配下を Electron / React なしで実行）。
- 空のエントリで起動するだけのウィンドウ表示（白紙の `index.html` 1 枚をレンダラに表示する程度で十分）。
- 各受け入れ基準を満たすことを確認できる npm スクリプト（`dev` / `build` / `lint` / `test` / `typecheck`）。

### やらないこと

- 地図描画（Canvas 2D、`MapRenderer` インタフェース）は実装しない。`render` 層には空のプレースホルダのみ置く。
- ドメインモデル（地物・錨・ツリー・頂点）は実装しない。`domain` 層には依存方向と Vitest を確認するための最小の純粋関数とそのテスト 1 件のみ置く。
- React の業務 UI（ツールバー・サイドバー・タイムライン等）は実装しない。`ui` 層は空ウィンドウを描く最小コンポーネントのみ。
- preload の型付き IPC API の本実装はしない（型付き IPC の枠組み確立は後続ユニット）。本ユニットでは preload エントリが存在し、`contextIsolation` 下で安全に動くことのみ確認する。
- 永続化・Zod・状態管理（Zustand）・テスト補助ライブラリ（fast-check）・Playwright・性能計測ハーネスは導入しない（後続ユニット）。
- electron-builder 等の配布パッケージング設定は本ユニットの対象外。

## 実装方針

技術方針.md の採用スタックに従う。以下は本ユニットで確定させる事項のみを抜粋・具体化したものである。

### 1. パッケージ構成（技術方針 §2.13）

- **モノレポを採用しない。** pnpm/npm のワークスペースは使わず、単一 npm パッケージ内のディレクトリ構造で層分離する。ワークスペース参照解決・tsconfig 共有・ビルド順序という偶発的複雑性を持ち込まない。
- 層分離は「ディレクトリ構造 + 依存方向の lint 強制」で実現する。

### 2. ビルド（技術方針 §1, §2.13）

- ビルドは Vite + electron-vite。electron-vite で main / preload / renderer の 3 ターゲットを 1 つの設定ファイル（`electron.vite.config.ts` 等）に明示的に構成する。設定は一読で理解できる薄さを保つ。
- renderer は Vite + React 18（関数コンポーネント）。

### 3. ディレクトリ層と依存方向（技術方針 §2.13, §5.1）

`src/` 配下に 4 層を置く。各層の役割と依存可否は次のとおり。

| 層 | ディレクトリ | 役割 | import してよい層 |
| --- | --- | --- | --- |
| domain | `src/domain` | フレームワーク非依存・純粋ロジック。Electron / React / Canvas に一切依存しない。 | （外部 npm の純粋ライブラリのみ。他の内部層は import 不可） |
| render | `src/render` | 描画層（将来 Canvas 2D / `MapRenderer`）。 | `domain` |
| ui | `src/ui` | React の UI シェル。 | `domain`, `render` |
| shell | `src/shell` | Electron の main / preload。 | `domain`（ui/render は import しない） |

依存方向は **`domain` へ内向きに固定** する。すなわち `domain` はいかなる内部層も import してはならない。これを ESLint の import 制限ルール（例: `eslint-plugin-import` の `no-restricted-paths`、または `eslint-plugin-boundaries` 等）で機械的に強制し、`npm run lint` で検出可能にする。

> 本ユニットで最低限機械検証すべき不変条件は「`domain` から `render` / `ui` / `shell` を import すると lint エラーになる」ことである（受け入れ基準 3）。他の越境（例: `shell` が `ui` を import 等）も同じ枠組みで禁止できるよう設定するが、必須の合否判定は domain 内向き固定である。

main / preload は Electron に依存するため `src/shell` に置く。renderer のエントリ（React マウント）は `src/ui`、描画プレースホルダは `src/render` に置く。

### 4. TypeScript strict 群（技術方針 §1, §2.1）

- 全層で共有する単一の `tsconfig` 基盤（例: `tsconfig.base.json`）に、次の 4 種を **すべて** 有効化する。
  - `strict: true`
  - `noUncheckedIndexedAccess: true`
  - `exactOptionalPropertyTypes: true`
  - `noImplicitOverride: true`
- 各ターゲット（main / preload / renderer）や Vitest 用に個別 tsconfig を派生させる場合も、これらの strict オプションは基盤から継承し、層ごとに緩めない。
- `npm run typecheck`（`tsc --noEmit` 相当）で全層をまとめて型検査できるようにする。

### 5. Electron レンダラのセキュリティ（技術方針 §1, §2.2）

- `BrowserWindow` の `webPreferences` に以下を設定する。
  - `contextIsolation: true`
  - `nodeIntegration: false`
  - `sandbox: true`
- レンダラはネットワークを前提としない（FR-02 完全オフライン）。本ユニットでは外部 URL を読み込まず、ビルド済みローカル HTML を表示する。
- preload は `contextIsolation: true` / `sandbox: true` 下で動作する形（`contextBridge` 経由の公開を前提とする枠組み）で配置する。本ユニットでは公開 API の中身は空でよいが、preload エントリが存在し、サンドボックス下でロードエラーを起こさないことを確認する。

### 6. テスト（技術方針 §2.14）

- Vitest を導入し、`domain` 配下のテストを Electron / React なしで実行できるようにする。
  - テスト環境は Node 環境（`environment: 'node'`）とし、jsdom / Electron ランタイムを要求しない。
  - `domain` に最小の純粋関数（例: 自明な恒等関数や加算）とそのテスト 1 件を置き、`npm run test` で緑になることを確認する。
- 本ユニットでは fast-check は導入しない（後続でドメイン不変条件のプロパティテストを追加する際に導入）。

### 7. 直接依存の宣言（開発ガイド §5.40）

- テスト・型チェック・ビルド・lint・スクリプトが直接 import / 実行する依存は、推移依存に頼らず `package.json` の直接依存として宣言する。
- 設定ファイル（`electron.vite.config.ts`、`vitest.config.ts`、ESLint 設定、各 tsconfig）のモジュール形式（拡張子・ESM/CJS 種別）は実行環境に揃える。形式を変更する場合は型チェック・起動確認まで同じ変更単位に含める。

## 受け入れ基準

各基準はコマンドまたは観察可能な挙動で検証できる形で記す。実装者は完了前に全項目を実機で確認すること。

1. **空ウィンドウ起動（FR-02）**
   - クリーンな状態から `npm install` を実行し、続けて起動コマンド（例: `npm run dev`、必要なら `npm run build` 後の起動）を実行すると、Electron アプリが空ウィンドウで起動する。エラーダイアログ・クラッシュ・白画面以外の異常が出ないこと。

2. **strict 群 4 種の全層共有**
   - 共有 tsconfig 基盤に `strict` / `noUncheckedIndexedAccess` / `exactOptionalPropertyTypes` / `noImplicitOverride` の 4 種がすべて有効である。
   - main / preload / renderer / Vitest の各 tsconfig がこの基盤を継承し、4 種を緩めていない。
   - `npm run typecheck` がこの設定下で成功する。

3. **依存方向の内向き固定が機械検証される**
   - `src/domain` 内のファイルから `src/render` / `src/ui` / `src/shell` のいずれかを import するコードを一時的に追加すると、`npm run lint` が **エラー** で失敗する。
   - その import を取り除くと `npm run lint` が成功する。
   - （確認手順を完了報告に残し、検証用の一時 import は最終成果物に残さないこと。）

4. **Vitest が domain を Electron/React 無しで実行できる**
   - `npm run test` が `domain` 配下のテスト（最低 1 件）を実行し緑になる。
   - テスト実行に Electron ランタイム・jsdom・React のレンダリングを要求しない（テスト環境は Node）。

5. **レンダラのセキュリティ設定**
   - `BrowserWindow` 生成箇所で `contextIsolation: true` / `nodeIntegration: false` / `sandbox: true` が設定されている。
   - これらの設定下でウィンドウが正常に表示される（基準 1 と同時に満たされること）。

## 注意点・既知の落とし穴

開発ガイドの教訓を本ユニットの判断へ適用する（適用宣言）。

- **§5.40 直接利用する依存は直接依存として宣言する**
  - 適用: 本ユニットは設定ファイルが多数（electron-vite / Vitest / ESLint / tsconfig 群）であり、それらが import する依存（型定義・プラグイン・テストランナー等）はすべて `package.json` の直接依存に明記する。推移依存任せにすると、後続ユニットでの依存更新時に沈黙して壊れる。設定ファイルのモジュール形式は実行環境（Electron main = Node、renderer = ブラウザ）に揃え、形式変更時は型チェックと起動確認を同一変更に含める。

- **§5.33 層をまたぐ API 契約は両側テストで固定する**
  - 適用: 本ユニットでは preload と renderer の型付き IPC は本実装しないが、層境界（`shell` の preload と `ui` の renderer）が後続で増えることを見越し、境界の越境 import を ESLint で禁止しておく。文字列の偶然一致や暗黙の越境に頼らない構造を最初から敷く。

- **依存方向 lint の「設定したつもり」リスク**
  - lint ルールを書いただけでは機械検証になっていない可能性がある。受け入れ基準 3 のとおり、`domain` から越境 import する一時コードを実際に追加して `npm run lint` が落ちることを確認し、確認後に一時コードを除去する。「ルールが存在する」ではなく「違反が実際に検出される」までを確認する。

- **strict オプションを層ごとに緩めない**
  - 派生 tsconfig（renderer 用・main 用・テスト用）で 4 種の strict を上書き解除しないこと。とくに `exactOptionalPropertyTypes` と `noUncheckedIndexedAccess` は外部ライブラリ型と衝突して赤くなりやすく、安易に層単位で無効化したくなるが、本ユニットの基盤確立ではこれを許さない。衝突は型注釈・ガードで個別に解消する。

- **sandbox: true と preload の制約**
  - `sandbox: true` 下では preload で利用できる Node API が制限される。本ユニットでは preload は最小（`contextBridge` の枠組みのみ、または空）で十分だが、サンドボックス下でロードエラーにならないことを起動時に確認する。Node のフル機能を preload で前提にしない。

- **空ウィンドウは外部 URL を読み込まない**
  - FR-02（完全オフライン）の規律として、renderer は外部 URL ではなくローカルのビルド成果物（または dev サーバのローカル HTML）を読み込む。本ユニットの「空ウィンドウ」は白紙のローカル HTML 1 枚で足り、ネットワーク到達を前提にしない。

- **クリーンルーム原則（開発ガイド §3.1）**
  - 本プロダクトの文書・コードは過去版・他プロダクト・外部の既存作業文脈に依存しない。設定や構成の根拠は本書および技術方針.md / 要件定義書.md の v4 自身の記述のみとし、「従来こうしていた」式の外部参照に頼らない。
