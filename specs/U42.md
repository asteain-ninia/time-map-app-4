## 目的

本アプリの**全体方針（FR-01 / FR-02）が、個別ユニットの統合によって実際に充足されていること**を、再現可能な自動検証として確証することが本ユニットの目的である。U42 は新しいドメイン機能を追加するユニットではなく、**検証ハーネスとエンドツーエンド（E2E）テスト群を整備する「検証ユニット」**である。具体的には以下の三本柱を提供する。

1. **全体方針の統合充足確認（FR-01 / FR-02）**: 「歴史を時間軸に沿って網羅的に視覚化・追跡できる」（FR-01）「通信不要・オフライン完結のスタンドアロンデスクトップとして動作する」（FR-02）が、追加・編集・分割・結合・所属変更・競合解決・保存読込という主要フローを通したときに統合で成立していることを、E2E で機械的に確認する。
2. **自作性能計測ハーネス（NFR 5.1 / 5.2）**: FPS・操作応答時間・メモリ使用量を記録できる計測ハーネスを整備し、データ規模 5,000 オブジェクト × 平均 10 錨の合成データで、60FPS・応答 100ms・メモリ 2GB 以内という目標を**計測可能な指標として記録**する。本ユニットの責務は「計測値を取得・記録・しきい値と比較できる仕組みを作ること」であり、性能未達が判明した場合の描画層強化（WebGL 退避路）そのものは本ユニットの対象外である。
3. **E2E と検証不能範囲の単体補完（教訓 5.2 / 5.11 / 5.41）**: Playwright for Electron による E2E で主要フローの回帰を固定し、特に「一時状態の破棄」（選択 → キャンセル → 再作成）と「構造変更後の選択維持」（分割・結合・所属変更・削除の後に選択が結果から再解決される）を回帰 E2E として置く。E2E で安定して検証できない範囲（ファイル I/O・終了確認・外部地図入力など外部統合の境界）は、純粋関数化・アダプタ分離・モックで単体テスト対象に落として補完する。

本ユニットは、本アプリのテスト基盤（技術方針 1. の「テスト」行＝Vitest／fast-check／Playwright for Electron／自作性能計測ハーネス）の最終的な統合運用層を構成する。

## スコープ

### やること

1. **全体方針の統合充足確認（FR-01 / FR-02）**
   - **FR-01（時間軸での網羅的視覚化・追跡）の統合確認**: 起動 → 地物を時間軸上に複数錨で定義 → タイムライン時刻を移動 → メインマップ表示が当該時刻の有効な錨に基づき即時更新される（FR-71 / FR-72）、という一連を E2E で確認する。少なくとも「ある時刻には存在し別の時刻には非存在になる地物」「時刻移動で形状・所属が変化する地物」を含め、時間軸に沿った状態の再現が網羅的に成立することを検証する。
   - **FR-02（オフライン完結のスタンドアロン）の統合確認**: E2E 実行中、レンダラがネットワークへ発信しないこと（ネットワーク要求が発生しない、または遮断下でも全フローが完走すること）を検証する。保存・読込・自動バックアップがすべてローカルファイル操作で完結し、外部サービス接続を前提としないことを確認する。
   - FR-01 / FR-02 の充足確認は、個別 FR の網羅再検証ではなく、**主要フローを貫通させたときに全体方針が崩れていないことの統合的確認**として位置づける（個別 FR は各実装ユニットが担保済みである前提）。

2. **自作性能計測ハーネスの整備（NFR 5.1 / 5.2、技術方針 2.14 / R1 / R4 / R5 / R9）**
   - **計測する指標**:
     - **FPS**: ズーム／パン操作中のフレーム描画レートを記録し、60FPS 以上を維持できるかを判定（NFR 5.1）。
     - **操作応答時間**: 選択・編集操作（地物選択、頂点ドラッグ確定、属性編集確定など）の入力から結果反映までの所要時間を記録し、100ms 以内かを判定（NFR 5.1）。
     - **メモリ使用量**: レンダラプロセスのヒープ／全体メモリを記録し、最大 2GB 以内かを判定（NFR 5.2 / R4）。
   - **計測条件のデータ規模**: 5,000 オブジェクト規模・各オブジェクト平均 10 錨の**合成データ生成器**を本ユニットで用意し、その規模で上記 3 指標を計測する（NFR 5.2、技術方針 5.8 末尾）。合成データは末端地物・集約地物・点・線・穴・飛び地・複数錨をバランスよく含み、現実的な負荷を再現する。
   - **記録と判定**: 計測結果（指標・条件・値・目標しきい値・合否）を構造化された機械可読レコードとして出力し、しきい値超過を検出できるようにする。値は「計測可能な指標として記録」できれば足り（NFR 5.8 / 技術方針 5.4）、CI 等で回帰計測に再利用できる形にする。しきい値（60FPS / 100ms / 2GB / 5,000×10）は単一の定数モジュールに集約し、計測コードと判定コードで二重定義しない（開発ガイド §4 単一の真実源）。
   - **計測 API の純粋／副作用分離**: 「計測値を集計・判定する純粋関数（サンプル列 → FPS / パーセンタイル応答 / 合否）」と、「実環境から計測値を採取する副作用層（タイマー・performance API・プロセスメモリ取得）」を**アダプタ分離**し、集計・判定ロジックを Vitest で単体テストできるようにする（教訓 5.41）。

3. **Playwright for Electron による主要フロー E2E**
   - 次の主要フローが一連の操作として通ることを E2E で固定する（各フローはアプリ実体を起動して操作し、期待される地図状態・選択状態・パネル表示を検証する）:
     - **追加**: 点・線・面の追加（クリックで形状作成 → プロパティ入力 → 保存で現在時刻を開始時刻とする錨として記録 → 整合性維持プロセスが起動）（FR-76）。
     - **編集**: 頂点移動・追加・削除、属性編集の確定（FR-87〜FR-89）。
     - **分割**: ナイフツールで末端地物を 2 分割し、継承先選択ダイアログで一方へプロパティを継承（FR-90 / FR-93）。
     - **結合**: 複数の面情報を 1 つの結果地物へ統合し、上位領域・プロパティ決定ダイアログを経る（FR-50〜FR-52）。
     - **所属変更**: 単一フローで親子関係を張り替える（割譲／独立等の代表ケース）（FR-46〜FR-48）。
     - **競合解決**: 編集確定で末端地物同士の空間競合が検出され、競合解決モーダルで方針を指定して一括確定し、単一アンドゥ単位になる（FR-61〜FR-63 / FR-94）。
     - **保存・読込**: プロジェクトを `.tmap` として保存 → 新規／別状態へ遷移 → 読み込み → 保存内容（全地物・全錨・親子関係・最上位フラグ・種別ラベル・設定・ベースマップ）が論理的に完全に復元される（FR-103〜FR-106、NFR 5.3）。

4. **回帰 E2E（教訓 5.2 一時状態破棄 / 教訓 5.11 構造変更後の選択維持）**
   - **一時状態の破棄（教訓 5.2、FR-78）**: 「選択 → キャンセル → 再作成」と「選択 → 確定 → 再作成」の連続操作で、描画プレビュー・選択中の値・ドラフト設定がキャンセル／確定／ツール切替／モード切替の全経路で破棄され、次回操作へ意図しない値が引き継がれないことを E2E で確認する（教訓 5.2 の「検出」記述に直結）。
   - **構造変更後の選択維持（教訓 5.11、FR-94）**: 分割・結合・移動・削除のように対象 ID や形状が変わる操作の後、選択状態が固定の全クリアではなく**コマンド結果（残る要素 ID／新規要素 ID／削除された ID）から再解決**され、次に調整すべき対象が残る場合に選択が維持されることを回帰 E2E で確認する（教訓 5.11 の「検出」記述に直結）。

5. **E2E で検証不能な範囲の単体補完（教訓 5.41）**
   - E2E で安定的・決定論的に検証しづらい範囲を未検証のまま放置せず、純粋関数化・アダプタ分離・モックで単体テスト対象にして補う。対象例:
     - **ファイル I/O**（`.tmap` の保存・読込・アトミック置換・世代バックアップ）: シリアライズ／デシリアライズの純粋部分を単体・往復テストし、`fs` 副作用はアダプタ越しにモックして検証する（FR-103〜FR-108、教訓 5.31）。
     - **終了確認ガード**（未保存変更がある状態での終了・新規・読込時の警告）: 「警告を出すか／どの選択肢を返すか」を決める純粋判定関数として分離し単体テストする（FR-107）。
     - **外部地図入力**（出界図形式への適合判定・自動補正・フォールバック）: 検証・補正の純粋判定を単体テストし、ファイル読込の副作用はモックする（FR-04、NFR 5.5）。
     - **ネットワーク遮断・オフライン性**（FR-02）: 「外部発信が一切ないこと」を、副作用境界（IPC・ネットワーク呼び出し点）の有無として静的・単体レベルでも確認できる形に落とす。
   - 補完した単体テストは、対応する E2E と**同一の期待を別レンズで二重に固定する**位置づけで記述する（E2E が落ちたとき原因切り分けに使える）。

6. **テスト基盤の運用整備**
   - 上記テスト群（E2E・性能ハーネス・補完単体）を実行可能なエントリポイント（スクリプト／テストランナー設定）として整え、開発ガイド §1.9 のフロー（実装 → テスト全パス → ビルド確認）に乗せられるようにする。
   - 機械算出値（テスト件数等）はナラティブへ手書きせず自動更新に委ねる（開発ガイド §2.6）。本ユニットの成果記述は「追加したテスト群の名称・カバレッジ対象」という質的記述で表す。

### やらないこと

- **新規ドメイン機能・新規 UI の実装**。本ユニットは検証ハーネスと E2E の整備であり、追加・編集・分割・結合・所属変更・競合解決・保存読込・描画・タイムラインといった機能本体は各実装ユニット（依存参照）が提供する。本ユニットはそれらを**統合して検証する**のみで、機能ロジックを再実装しない。
- **個別 FR の網羅的な単体再検証**。各 FR の単体・契約・プロパティテストは当該機能ユニットが担保済みである前提とし、本ユニットは「統合で全体方針が崩れていないこと」と「E2E で検証不能な境界の補完」に絞る。
- **性能未達時の描画層強化（WebGL 実装への差し替え）そのもの**（技術方針 R1）。本ユニットは計測して未達を**検出可能にする**までを担い、`MapRenderer` の WebGL 実装や最適化の実装は対象外。計測結果が未達を示した場合は、未解決課題として記録し当該描画ユニットへ差し戻す（開発ガイド §1.8）。
- **整合性維持プロセス・競合検出・ブーリアン演算・空間インデックス等のアルゴリズム本体**（依存ユニットの責務）。本ユニットは E2E でそれらの統合挙動を観測するのみ。
- **保存形式の互換マイグレーション**（要件第 7.3 節で将来実装）。保存読込 E2E はバージョン情報の保持・妥当性検証・非互換ファイルの警告／拒否（FR-104）までを対象とし、旧形式の読み込み互換は検証対象に含めない。
- **配布パッケージング・署名運用**（技術方針 R10）。E2E はビルド成果物または開発ビルドのアプリ起動を対象とするが、インストーラ署名・配布運用自体は対象外。

## 依存(dependsOn)

本ユニットは以下のユニットに依存する。依存ユニットの公開インタフェース（関数名・引数・戻り値型、IPC チャネル名、UI 要素の識別子）は、偶然の一致に頼らず共有型・両側テストで固定する（教訓 5.33）。依存ユニットがまだ未実装の場合は、本仕様に記す検証観点に沿ったテストの骨格（スケルトン・スキップ可能ケース）と、計測ハーネス・合成データ生成器・補完単体テストの土台を先に実装し、依存実装が揃い次第 E2E を有効化する。

- **U19 — 地物描画（点／線／面・穴透過・飛び地独立・派生集約形状・ラベル・LOD）**: FR-01 の「時間軸に沿った視覚化」と FPS 計測の主対象。性能ハーネスのズーム／パン FPS 計測、時刻移動による即時再描画（FR-71）の E2E はこの描画層を対象に行う。
- **U23 — 追加ツール（点／線／面・仮表示・取消／キャンセル・親選択・確定で整合性）**: 「追加」E2E と、一時状態破棄の回帰 E2E（選択／作成中プレビューのキャンセル破棄、FR-78・教訓 5.2）の主対象。
- **U24 — 編集ツール（頂点／エッジハンドル・移動・点／線／面編集・エッジ滑り・確定で整合性）**: 「編集」E2E と応答時間計測（頂点ドラッグ確定・属性編集確定）の主対象。
- **U26 — ナイフツール（分割）と継承先選択ダイアログ**: 「分割」E2E と、構造変更後の選択維持の回帰 E2E（分割後に選択が結果から再解決、教訓 5.11）の主対象。
- **U28 — 所属変更フロー（割譲／連邦化／独立／帰属／直轄化／自治化／解体・単一フロー）**: 「所属変更」E2E の対象。所属変更確定が単一アンドゥ単位になること（FR-94）も検証する。
- **U30 — 合体（結合）フロー（末端のみ／集約のみ／混在・結合ダイアログ）**（合体フロー＝FR-50〜FR-52）: 「結合」E2E と、結合後の選択維持の回帰 E2E（教訓 5.11）の対象。依存未実装時は、本仕様の検証観点に沿った E2E スケルトンを先に用意する。
- **U35 — 整合性維持プロセス／競合解決ダイアログ・単一アンドゥ単位の確定**（固定順序の整合性維持＝FR-61〜FR-63、複合操作の不可分性＝FR-94 / FR-73 / FR-74）: 「競合解決」E2E（編集確定 → 競合検出 → 方針指定 → 一括確定 → 単一アンドゥ）の対象。アンドゥ・リドゥで複合操作全体が 1 単位で復元されることを検証する。
- **U39 — プロジェクトデータの保存・読込・整合性チェック・自動バックアップ（`.tmap` ／アトミック保存／世代管理）**（FR-103〜FR-108、NFR 5.3）: 「保存・読込」E2E と、ファイル I/O 補完単体テスト（往復・終了確認ガード・外部地図入力）の対象。シリアライズ／デシリアライズの純粋部分と `fs` 副作用アダプタの分界点に依存する。

> dependsOn に挙がっていない要件・実装には依存しない。各依存ユニットが供給する公開 API・IPC・UI 識別子に対して E2E と計測ハーネスを接続するのみで、機能ロジックを本ユニットで再実装しない。依存ユニットの安定したセレクタ（要素識別子・テスト用属性）が無い場合は、当該ユニットへセレクタ付与を依頼する未解決課題を記録する（教訓 5.33 層境界契約の固定）。

## 実装方針(技術方針に沿う)

技術方針（`docs\技術方針.md`）に従う。

### テスト基盤の構成（技術方針 1. テスト行 / 2.14）

- **E2E**: Playwright for Electron を用い、ビルド済み（または electron-vite の開発ビルド）アプリを起動して操作・検証する。E2E はメイン／preload／レンダラの 3 ターゲットが統合された実アプリを対象にし、UI シェル・ダイアログ・タイムライン・地図描画を貫通して確認する。
- **性能計測ハーネス**: 自作する。FPS・応答時間・メモリのサンプル採取は副作用層（performance API・`requestAnimationFrame`／フレームタイミング・プロセスメモリ取得）に閉じ込め、集計・判定（FPS 換算・応答パーセンタイル・しきい値比較・合否）は `domain` 同様にフレームワーク非依存の純粋関数として切り出し Vitest で単体テストする（技術方針 2.14、教訓 5.41）。
- **補完単体テスト**: Vitest で、E2E で検証不能な境界（ファイル I/O・終了確認・外部地図入力・オフライン性）の純粋判定をテストする。必要に応じ fast-check で境界網羅する（NFR 5.8）。

### 層分離と依存方向（技術方針 2.13 / 5.1）

- 計測ハーネスの純粋部分・補完単体テスト対象の純粋判定は、Electron／React／Canvas に依存しない純粋関数として配置し、依存方向を内向き（`domain` 方向）に保つ。副作用採取アダプタは `render`／`shell` 寄りに置き、純粋部分と分界する。
- 直接 import・実行する依存（Playwright、性能計測に使うランタイム API、合成データ生成器が依存する `domain` 型）は推移依存に頼らず直接依存として宣言する（教訓 5.40）。テスト設定ファイルのモジュール形式は実行環境に揃える（教訓 5.40）。

### 合成データ生成器（NFR 5.2、技術方針 5.8）

- 5,000 オブジェクト × 平均 10 錨の合成プロジェクトを決定論的に生成する関数を実装する。生成は実体クラス／正規ファクトリを経由し、リテラルオブジェクトで型だけ満たす作り方をしない（教訓 5.39。未参照プロパティ欠落が別経路で沈黙失敗するため）。
- 生成データは末端地物の排他性・リング階層の交互性・錨列の昇順非重複といった**全不変条件を満たす合法な状態**であること（不正な合成データで性能を測ると意味がない）。生成直後に当該不変条件検証（依存ユニットの検証サービス）を通して合法性を保証する。
- 合成規模・分布（点／線／面比率、集約／末端比率、穴飛び地の混入率、錨数分布）はパラメータ化し、しきい値定数モジュールと同じ場所で管理する。

### 計測の決定論性と再現性（技術方針 R5 / R9、開発ガイド §4）

- 応答時間計測は、ドラッグ中の連続更新ではなく**操作確定**の応答を測る（技術方針 R5：ドラッグ中はトランジェント、確定時に正式コマンド）。FPS はズーム／パンの連続操作区間で測る。計測区間と確定点を明示し、計測対象の意味（何の応答か）を一箇所に定義する（開発ガイド §4）。
- 計測値は環境差で変動するため、しきい値判定は固定値比較だけでなく、サンプルの代表値（例: フレーム時間のパーセンタイル、応答時間の上位パーセンタイル）で評価する。代表値算出は純粋関数として単体テストで固定する。

### E2E の安定化（技術方針 5.3 / 開発ガイド §5.41）

- E2E は実時間・実描画に依存し fragile になりやすい。要素特定は安定したセレクタ（テスト用識別子）で行い、座標やタイミングのハードコードに頼らない。
- 安定検証が難しい範囲は E2E で無理に固定せず、補完単体テストへ役割分担する（教訓 5.41）。E2E は「主要フローが通る」ことと「回帰観点（一時状態破棄・選択維持）」に集中させる。

### 日本語 UI とエラー（FR-115 / FR-117）

- E2E がエラーメッセージを検証する場合、日本語メッセージで照合する。例外捕捉とユーザーフレンドリーな日本語表示（必要に応じ「開発者へ報告してください」）が成立していることも確認対象に含めてよい。

### 成果物・公開インタフェース（型レベルの契約）

実装者は以下の概念を型／モジュールとして定義すること（名称は実装で確定してよいが、契約の意味は固定）。

- **性能しきい値定数モジュール**: `{ 目標FPS: 60, 応答上限ms: 100, メモリ上限: 2GB相当, 規模: { オブジェクト数: 5000, 平均錨数: 10 } }` 等を単一宣言として持つ。計測・判定・合成データ生成が同一定数を参照する（単一の真実源）。
- **計測サンプル → 指標の純粋集計関数**: `(フレーム時間サンプル列) → FPS 代表値`、`(応答時間サンプル列) → 応答代表値`、`(メモリサンプル列) → ピーク／代表メモリ`、`(指標, しきい値) → 合否レコード`。すべて副作用なし。
- **計測採取アダプタ**: 実環境からサンプルを採取する副作用層インタフェース（純粋集計関数へ供給する）。テストでモック差し替え可能にする。
- **合成データ生成器**: `(規模パラメータ, シード) → 合法な合成プロジェクト状態`。決定論的・不変条件充足。
- **計測結果レコード**: 指標・条件・規模・値・しきい値・合否を持つ機械可読構造。回帰計測の出力。
- **E2E フロー定義**: 主要フロー（追加／編集／分割／結合／所属変更／競合解決／保存読込）と回帰観点（一時状態破棄／選択維持）の E2E シナリオ。
- **補完単体テスト対象の純粋判定**: 終了確認ガード判定、`.tmap` 往復シリアライズ、外部地図適合判定、オフライン性（外部発信なし）の検査点。

## 受け入れ基準(テスト可能な形で列挙)

各基準は、E2E（Playwright for Electron）または Vitest 単体／fast-check／自作計測ハーネスで「実行 → 観測 → 期待との照合」を機械的に検証できる形で満たすこと。

1. **FR-01 / FR-02 の全体方針が統合で充足されている（FR-01 / FR-02）**
   - FR-01: 複数錨を持つ地物（存在／非存在の切替を含む、形状・所属が時刻で変化するものを含む）を用意し、タイムライン時刻を移動するとメインマップ表示が当該時刻の有効な錨に基づき即時更新される（FR-71 / FR-72）ことを E2E で確認する。時間軸に沿った状態の再現が主要フロー貫通後も成立する。
   - FR-02: E2E 実行中にレンダラが外部ネットワークへ発信しないこと、保存・読込・自動バックアップがローカル完結すること、外部サービス接続なしで全フローが完走することを確認する（オフライン性の補完単体テストと二重に固定）。

2. **性能計測ハーネスが FPS／応答／メモリを記録し 5,000×10 錨で目標を計測（NFR 5.1 / 5.2）**
   - 5,000 オブジェクト × 平均 10 錨の合成プロジェクトを生成でき、生成データが全不変条件（末端排他・リング交互・錨列昇順非重複）を満たす（教訓 5.39）。
   - ハーネスがズーム／パンの FPS、選択・編集確定の応答時間、レンダラのメモリ使用量を採取・記録し、60FPS／100ms／2GB のしきい値と比較した合否レコードを出力する。
   - 集計・判定（FPS 換算・応答代表値・メモリピーク・合否）の純粋関数が、既知のサンプル列に対し期待どおりの代表値・合否を返すことを Vitest で単体検証する（採取アダプタをモック）。しきい値は単一定数モジュールから参照され二重定義されない。
   - 計測が未達を示した場合に、未達指標・条件・値を含むレコードとして検出でき、回帰計測に再利用できる（記録できることが受け入れ要件であり、未達時の描画層強化は本ユニット対象外）。

3. **Playwright の E2E で主要フローが通る**
   - 追加（点／線／面、保存で錨記録 → 整合性維持起動／FR-76）、編集（頂点移動・追加・削除・属性編集確定／FR-87〜89）、分割（ナイフ → 継承先選択／FR-90 / 93）、結合（複数 → 1 結果地物・ダイアログ経由／FR-50〜52）、所属変更（単一フロー／FR-46〜48）、競合解決（編集確定 → 競合検出 → 方針指定 → 一括確定／FR-61〜63）、保存・読込（`.tmap` 保存 → 読込で論理的完全復元／FR-103〜106）の各フローが E2E で通る。
   - 競合解決を含む複合操作が単一アンドゥ単位で復元される（FR-94 / FR-73）ことを、アンドゥ 1 回で操作前状態へ戻ることで確認する。
   - 保存・読込 E2E で、全地物・全錨・親子関係・最上位フラグ・種別ラベル・設定・ベースマップが復元される（保存内容の論理的完全性／FR-103）。バージョン情報の保持と妥当性検証（FR-104）が機能する。

4. **一時状態破棄と構造変更後の選択維持の回帰 E2E がある（教訓 5.2 / 5.11）**
   - 一時状態破棄（教訓 5.2 / FR-78）: 「選択 → キャンセル → 再作成」と「選択 → 確定 → 再作成」の連続操作で、前回のプレビュー・ドラフト値が次回操作へ引き継がれないことを E2E で確認する。ツール切替・モード切替経路でも一時状態が破棄されることを含める。
   - 構造変更後の選択維持（教訓 5.11 / FR-94）: 分割・結合・移動・削除の後、選択が固定全クリアではなくコマンド結果（残る／新規／削除 ID）から再解決され、次に調整すべき対象が残る場合に選択が維持されることを E2E で確認する。

5. **E2E で検証不能な範囲が純粋関数化／モックで単体補完されている（教訓 5.41）**
   - ファイル I/O（`.tmap` 往復シリアライズ／デシリアライズ、世代バックアップの世代管理判定）の純粋部分が単体・往復テストで検証され、`fs` 副作用がアダプタ越しにモックされている（教訓 5.31 読み書き・検証・移行・往復の同期）。
   - 終了確認ガード（未保存変更時の警告要否・選択肢）の純粋判定が単体テストされている（FR-107）。
   - 外部地図入力の出界図適合判定・自動補正・フォールバック判定の純粋部分が単体テストされている（FR-04）。
   - オフライン性（外部発信が一切ない）の検査点が単体／静的に確認されている（FR-02）。
   - 各補完単体テストが、対応する E2E と同一の期待を別レンズで二重固定する位置づけで存在する（E2E 失敗時の原因切り分けに使える）。

6. **回帰・非機能・運用**
   - 性能ハーネスの純粋集計関数・合成データ生成器・補完単体の純粋判定は副作用がなく、同一入力（同一シード）に同一結果を返す（決定論性）。
   - テスト群（E2E・性能ハーネス・補完単体）が実行エントリポイントから起動でき、開発ガイド §1.9 のフロー（テスト全パス → ビルド確認）に乗る。テスト件数はナラティブへ手書きせず自動集計に委ねる（開発ガイド §2.6）。
   - しきい値・規模・分布パラメータが単一定数モジュールに集約され、計測・判定・合成生成で同一値を参照する（単一の真実源／開発ガイド §4）。
   - 依存ユニット未実装時は、E2E はスキップ可能なスケルトンとして存在し、計測ハーネス・合成データ生成器・補完単体は依存実装に先行して単体で成立する。依存の安定セレクタ／API が無い箇所は未解決課題として記録される（開発ガイド §1.8）。

## 注意点・既知の落とし穴(開発ガイドの教訓を踏まえる)

着手前に開発ガイド §1.6 の作業開始ゲートに従い、下記の該当教訓を節番号・見出し・本文ごと引用し、今回の実装判断へどう適用するかを「適用:」として明示してから実装すること。

- **§5.41 検証不能になった範囲は別手段で補う** — 適用: E2E で安定検証できないファイル I/O・終了確認・外部地図入力・オフライン性を、純粋関数化／アダプタ分離／モックで単体テスト対象に落とし、未検証のまま放置しない。各補完単体は対応 E2E と二重に期待を固定する。受け入れ基準 5。
- **§5.2 一時的 UI 状態は全経路で破棄する** — 適用: 「選択 → キャンセル → 再作成」「選択 → 確定 → 再作成」、およびツール／モード切替経路での一時状態破棄を E2E の回帰として置く。教訓本文の「検出」記述をそのまま受け入れ基準 4 に反映する。
- **§5.11 構造変更操作後の選択は結果から再解決する** — 適用: 分割・結合・移動・削除の後、選択がコマンド結果（残る／新規／削除 ID）から再解決され維持されることを E2E で固定する。固定全クリアになっていたら回帰として検出する。受け入れ基準 4。
- **§5.6 状態変化の検出は結果状態で判定する** — 適用: 性能ハーネスの「目標未達」「不変条件違反」の判定は、特定経路フラグではなく計測結果・結果状態で判定する。複数フローが同じ未達を起こしうるため経路ゲートにしない。
- **§5.23 execute/undo/redo は対称に通知する** — 適用: 競合解決を含む複合操作のアンドゥ E2E で、1 回のアンドゥで全 touch 対象が操作前へ戻ることを厳密一致で確認する（包含判定ではなく操作前状態との一致）。
- **§5.20 元に戻す情報は依存データも含めて過不足なく保存する** — 適用: 保存読込・アンドゥ E2E で、新規生成 ID が redo・再読込で再採番されず初回 ID が保たれることを確認する。
- **§5.26 編集制約はコマンド確定前にも同じサービスで検証する** — 適用: 競合解決・保存読込 E2E は UI 経路だけでなく、確定前検証が効いていること（整合性チェック・バージョン検証が機能すること）を観測する。
- **§5.31 永続化の読み書き・検証・移行・往復テストを同期する** — 適用: `.tmap` の保存・読込・検証・往復テストを同一観点で固定する。フィールドの optional 化・撤去変更があれば再保存往復テストを必須にする。保存読込 E2E と往復補完単体を併置する。受け入れ基準 3・5。
- **§5.33 層をまたぐ API 契約は両側テストで固定する** — 適用: E2E のセレクタ・IPC チャネル名・依存ユニットの公開 API を偶然一致に任せず、共有型・テスト用識別子で固定する。依存に安定セレクタが無ければ付与依頼を未解決課題に記録する。
- **§5.39 テスト fixture は実体クラスをインスタンス化する** — 適用: 5,000×10 錨の合成データ生成器は実体クラス／正規ファクトリを経由し、リテラルで型だけ満たさない。未参照プロパティ欠落が別経路で沈黙失敗するのを防ぐ。受け入れ基準 2。
- **§5.40 直接利用する依存は直接依存として宣言する** — 適用: Playwright・性能計測ランタイム API・合成データが使う `domain` 型を直接依存として宣言し、推移依存に頼らない。テスト設定ファイルのモジュール形式を実行環境に揃える。
- **§2.6 機械算出値は手書きしない** — 適用: テスト件数等は自動集計に委ね、ナラティブへ手書きしない。本ユニットの成果は追加テスト群の名称・カバレッジ対象という質的記述で表す。
- **§1.8 やり残しの記録** — 適用: 性能未達・依存未実装による E2E スキップ・付与依頼などのやり残しは未解決課題文書（現状.md）へ追記する。口頭・記憶・コミットメッセージだけに残さない。
- **§1.9 テストは実装と同時に書く** — 適用: 本ユニットはテスト整備そのものだが、計測ハーネスの純粋部分・合成データ生成器・補完単体も同時に単体テストで自己検証する（ハーネス自体のテスト）。
- **単一の真実源**（開発ガイド §4）— 注意: しきい値（60FPS / 100ms / 2GB / 5,000×10）・規模・分布パラメータは単一定数モジュールに集約し、計測・判定・合成生成で重複定義しない。
- **性能の段階戦略**（技術方針 9 / R1 / R5 / R9）— 注意: 本ユニットは未達を**計測で可視化する**までを担い、未達時の描画層強化（WebGL 退避路）・Worker オフロードの実装本体は当該ユニットへ差し戻す。計測は段階戦略の判断材料を提供する位置づけである。
- **クリーンルーム原則**（開発ガイド §3.1）— 注意: 本書および実装・テストに、過去版・他プロダクト・「従来」「前回」等の外部参照を持ち込まない。制約・しきい値はすべて本アプリ要件として直接記述する。
