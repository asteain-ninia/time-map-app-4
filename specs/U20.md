# U20 アプリレイアウトシェルとモード/ツールバー骨格

本書は実装ユニット U20 の実装指示書である。実装者（別エージェント）はこの指示書だけを読んで着手できる。前提知識は本書の中に閉じて記述する。要件・技術方針・開発作法の根拠は本書末尾の「関連要件」「注意点・既知の落とし穴」に引用する。

---

## 目的

time-map-app-4 の React UI シェル（アプリケーション全体の骨格レイアウト）を構築する。具体的には次を満たす。

1. 標準的な業務 UI レイアウト（左ツールバー・中央メインマップ領域・右サイドバー・下部の時間スライダー領域とステータスバー・上部の標準メニュー）を配置する（FR-111）。
2. 追加モードと編集モードを排他トグルで切り替え、有効なモードに応じて関連ツール群をツールバーに表示する（FR-75）。
3. ウィンドウサイズに追従してレイアウトを調整し、最小ウィンドウサイズを 800×600 ピクセルとする（FR-114）。
4. ドラッグ可能なパネル／ウィンドウ・ツールチップ・キーボードショートカットの共通基盤を整備する（FR-112）。
5. 表示専用（閲覧）経路における編集 UI・編集メニュー項目・編集ショートカットを、単一の共通判定で一括無効化するヘルパーを提供する（開発ガイド 教訓 5.13）。

本ユニットは UI の「骨格」と「枠組み」を作る。各パネルの中身（プロパティパネルの実フォーム、タイムラインの時間計算、地図描画そのもの、各ツールの実動作）は実装しない。それらは後続ユニットが本シェルの中に差し込む。本ユニットの責務は、後続のパネル・ツール・ダイアログが嵌まる「場所」と「枠組み」、モード状態機械、共通操作性基盤（ドラッグ・ツールチップ・ショートカット・表示専用無効化）を確立することにある。

## スコープ

### やること

- アプリ全体のルートレイアウトコンポーネント（シェル）を構築する。領域構成は以下とする（FR-111）。
  - **上部**: 標準メニューバー（ファイル・編集・表示・ツール・ヘルプの 5 メニュー）。各メニューは項目を持つが、本ユニットでは項目の「枠」と表示専用無効化の連動のみを担い、各項目の実処理は後続ユニットへ委譲する（後述）。
  - **左**: ツールバー。モード切替（追加／編集の排他トグル）と、有効モードに対応するツール選択ボタン群を表示する。
  - **中央**: メインマップ領域（地図描画のためのマウント先となる領域。本ユニットでは描画は行わず、後続の描画層を載せるための領域とコンテナのみを用意する）。
  - **右**: サイドバー。イベント一覧・階層/ツリー管理パネル（地物一覧）・プロパティパネルの 3 区画（タブまたは縦積みの区画）を配置する。本ユニットでは各区画の「入れ物」と切替のみを担い、中身は後続ユニットへ委譲する。
  - **下部**: 時間スライダー領域とステータスバー。本ユニットでは両領域の「入れ物」と配置を担い、タイムライン本体・ステータス表示の実装は後続へ委譲する。
- 追加モードと編集モードの排他トグル状態機械を実装する（FR-75）。
  - 一方を有効にすると他方が自動的に無効になる（同時に両方が有効・両方とも無効が「編集系モード未選択」の意味で許容されるかを後述の方針で確定する）。
  - 有効なモードに応じて、ツールバーに当該モードの関連ツール群を表示する。追加モードでは点／線／面の追加ツール枠、編集モードでは選択／頂点編集／地物移動／ナイフ（分割）／所属変更／結合などのツール枠を表示する（各ツールの「ボタンと選択状態」のみを本ユニットで提供し、ツールの実動作は後続ユニットが担う）。
  - モード切替時に、前モードに紐づく一時的 UI 状態（選択中ツール・進行中ドラフト等のシェル側状態）を破棄する（教訓 5.2）。
- ウィンドウサイズ追従とレスポンシブ調整（FR-114）。
  - 最小ウィンドウサイズを 800×600 ピクセルとして強制する（ウィンドウ側の最小サイズ設定と、レイアウト CSS の最小寸法の両面で担保する）。
  - ウィンドウリサイズに追従して各領域の寸法を再配分し、中央メインマップ領域が可変・周辺パネルが追従するレイアウトとする。
  - メインマップ領域の寸法変化を後続の描画層が購読できるよう、領域サイズ（ピクセル）を通知する経路を用意する。
- 操作性の共通基盤（FR-112）。
  - **ドラッグ可能なウィンドウ／パネル**: モーダル形式の詳細パネルや浮遊パネルをドラッグで移動できる共通機構（ドラッグ可能コンテナ）。複数同時表示・前面化（z 順）を扱える枠組みとする。本ユニットは「ドラッグ可能なパネルの器」を提供し、その中身（詳細文書・各種ダイアログ本体）は後続ユニットが入れる。
  - **ツールチップ**: ツールバーボタン・メニュー項目等に操作ガイドのツールチップを表示する共通機構（日本語文言。FR-115）。
  - **キーボードショートカット基盤**: ショートカットの登録・解決・ディスパッチを一元管理する仕組み。各ショートカットは「コマンド ID」へ対応づけ、後続ユニットが実コマンドを登録する。本ユニットでは枠組みと、表示専用時の一括無効化連動、ショートカットとメニュー項目の有効/無効の単一判定共有を担う。
- 表示専用経路の一括無効化ヘルパー（教訓 5.13）。
  - 編集 UI（ツールバーの編集系ボタン・コンテキストメニューの編集項目等）、編集メニュー項目、編集ショートカットを、同一の権限判定（編集可能か否かの単一の状態）で一括無効化する共通ヘルパー（または状態機械）を提供する。
  - 部品ごとに個別の無効化判定を書かず、各部品はこの共通判定を参照して有効/無効を決める。
- 中央マップ領域上で発生するポインタイベント（パン・ズーム・地物操作の入口）を後続の描画層・操作層へ受け渡すための入力レイヤの配置と、重なる UI（オーバーレイ・モーダル・ドラッグ可能パネル）が入力を奪う層構造の設計（教訓 5.14）。本ユニットは入力経路の「層構造」を正しく設計し、実際の地図操作ロジックは後続が載せる。
- UI 文言（メニュー名・ツール名・ツールチップ等）を日本語で定数モジュールへ集約する（FR-115、技術方針 5.5 の i18n 抽象なし方針）。

### やらないこと

- 地図描画そのもの（Canvas 2D、`MapRenderer` 実装、ワールド↔スクリーン変換、地物・グリッド・ラベルの描画）。本ユニットは中央領域に描画層をマウントする「場所」と寸法通知のみを用意する（描画は後続ユニットの責務）。
- 各ツールの実動作（点／線／面の追加、頂点編集、地物移動、ナイフ分割、所属変更、結合、測量など）。本ユニットはツールボタンと選択状態のみを提供し、ツールの操作ロジックは後続ユニットへ委譲する。
- プロパティパネルの実フォーム・歴史の錨一覧・スタイルセクション・削除ボタンの実処理（FR-83〜FR-102）。本ユニットは右サイドバーの「区画と切替」のみを用意する。
- タイムライン本体（時間スライダーの値計算・時間入力欄・再生制御・目盛り・イベントマーカー）と時間計算ロジック（FR-64〜FR-70）。本ユニットは下部に「入れ物」を置くのみ。
- 標準メニュー各項目の実処理（ファイル保存／読込・アンドゥ／リドゥ・設定ダイアログ起動・ヘルプ表示など）。本ユニットはメニューの「構造・項目枠・有効/無効連動・ショートカット対応づけ」のみを担い、各コマンドの実装は後続ユニットが登録する。
- 地物の表示制御・検索機能（FR-113）の実装。右サイドバーの階層/ツリー管理パネル（地物一覧）区画は「入れ物」のみ用意する。
- コンテキストメニューの動的内容生成（オブジェクト種別・ツール種別に応じた項目組み立て。FR-96）。本ユニットはコンテキストメニュー表示の共通機構（表示・位置決め・閉じる契機）と、表示専用時の編集項目一括無効化までを担い、項目の動的構成と各操作の実処理は後続ユニットへ委譲する。
- 自動配色・幾何演算・整合性維持プロセス・競合解決ダイアログ本体などのドメイン処理。
- 状態管理ストアそのものの新規定義（UI/セッション状態ストアは依存ユニットが提供する。本ユニットはそれを購読・更新して使う）。

## 依存（dependsOn）

本ユニットは以下のユニットに依存する。これらが提供する基盤の上に UI シェルを積み上げる。依存先が公開する仕組みを再実装せず、購読・利用する（単一の真実源。開発ガイド §4「単一の真実源」、教訓 5.30 過少共有の戒め）。

- **U16**: 本ユニットが提供する UI シェルが土台とする基盤ユニット。UI シェルの起動・マウント、および UI/セッション状態（モード・選択・現在時刻・ズーム等）の薄いストア（技術方針 §2.5 の Zustand 層に相当する状態管理）と、React からその状態を購読・更新する経路を前提とする。本ユニットのモード状態・選択中ツール・表示専用フラグ等のシェル側 UI 状態は、この状態管理基盤の上に置く（ドメインの真実とは分離された UI/セッション状態として扱う）。
- **U17**: 本ユニットのシェルが連携する基盤ユニット。標準メニュー項目・ショートカット・ファイル操作系が呼び出す型付き IPC／コマンド経路、ないしアプリ起動・ウィンドウ管理（最小サイズ設定を含むウィンドウ生成）に関わる枠組みを前提とする。本ユニットはメニュー項目・ショートカットを「コマンド ID」へ対応づける枠組みを提供し、各コマンドの実体登録はこの基盤および後続ユニットを通じて行われる。

> 注: 依存先 U16 / U17 が公開する正確な API 名・型は、それらのユニットの成果物に従う。本ユニットは「状態管理基盤（UI/セッション状態の購読・更新）」「アプリ起動・ウィンドウ管理・コマンド/IPC 経路」という能力に依存するものとし、層をまたぐ契約（チャネル名・関数名・状態キー）は偶然の一致に頼らず共有型・両側テストで固定する（教訓 5.33 / 5.34）。依存先 API が未確定の段階では、本ユニット内に明示的な境界インタフェース（adapter）を定義し、そこへ依存先を接続する形にして、未確定部分を局所化する。

依存ユニット（U16 / U17）の成果物が前提とする土台（リポジトリ基盤・層分離・React 18・TypeScript strict・Electron セキュリティ設定）は U01 で確立済みである。

## 実装方針（技術方針に沿う）

技術方針 の採用スタックと層分離に厳密に従う。

### 配置と層分離

- 本ユニットのコードは `ui` 層（React）に属する。`ui` 層は `domain`（純粋ドメインコア）を参照してよいが、`render` / `shell` への依存方向は技術方針の依存方向ルール（内向き固定）に従う。`domain` から `ui` を参照しない。
- React は UI シェル・パネル・ダイアログ・メニュー・ツールバー・タイムライン UI の枠組みに限定して用いる。**中央メインマップの高頻度描画は React の再レンダリングサイクルから完全に切り離す**（技術方針 §2.3）。地図描画状態を React state に持たせない。本ユニットは中央領域に描画層をマウントする境界（コンテナ要素・寸法通知）だけを React で用意し、描画は命令的な描画層（後続）に委ねる。
- UI/セッション状態（モード・選択中ツール・表示専用フラグ・ズーム・現在時刻など）は、依存ユニットが提供する薄い状態ストア（技術方針 §2.5）に置き、React は購読のみで描画経路に乗らない規律を守る（技術方針 §2.3）。本ユニットでドメインの真実（地物・錨・ツリー）を持たない。

### レイアウト（FR-111 / FR-114）

- ルートレイアウトは「上部メニュー／左ツールバー／中央マップ／右サイドバー／下部（時間スライダー＋ステータスバー）」の固定領域構成とする。中央マップ領域を可変、周辺を追従とする（CSS Grid / Flexbox いずれでも可。レイアウトの寸法ロジックを一箇所に集約し、ドリフトを生まないこと）。
- 最小ウィンドウサイズ 800×600 を二重に担保する。
  - ウィンドウ生成側（依存ユニット U17 のウィンドウ管理経路）で `minWidth=800` / `minHeight=600` を設定する。本ユニットからこの設定を要求・確認する。
  - レイアウト CSS 側でも全体の最小寸法・各領域の最小寸法を指定し、800×600 でも全領域が崩れず表示されることを保証する。
- メインマップ領域のサイズ（ピクセル）変化を観測し、後続の描画層が購読できる形で通知する経路を用意する（リサイズ監視）。リサイズイベントは高頻度になりうるため、必要に応じてスロットリングする（NFR 5.1）。

### モード状態機械（FR-75）

- 追加モードと編集モードは排他トグルとして単一の状態（例: 現在の編集系モードを表す判別値）で表現する。状態は判別共用体／列挙の定数を経由して扱い、表示文字列や思い込みで分岐しない（教訓 5.19）。
- 一方を有効化すると他方を無効化する遷移を状態機械として一箇所に実装する。両方有効になる中間状態を表現不能にする（不正状態を作らない）。
- 表示専用（閲覧）状態は、追加/編集モードとは別軸の「編集可能か否か」の権限判定として表現する。表示専用時は追加・編集いずれのモードも選べず、編集系ツールは一括無効化される（教訓 5.13）。表示モードの切替は編集・追加モードと干渉しない（FR-42 の方針と整合）。
- 有効モードに応じたツール群表示は、モード→表示ツール集合の対応を単一の定義から導出する。モード切替時は前モードの選択中ツール等の一時 UI 状態を破棄する（教訓 5.2）。

### 操作性基盤（FR-112）

- **ドラッグ可能パネル/ウィンドウ**: 押下→移動→解放のドラッグシーケンスを全パス（クリックのみでドラッグ未発生の場合を含む）で正しく開始・更新・終了する共通フック/コンポーネントを実装する（教訓 5.8）。押下で設定した状態は解放で必ず解除する。複数同時表示・前面化（z 順）に対応する。
- **重なる UI の入力層**: ドラッグ可能パネル・モーダル・オーバーレイ・コンテキストメニューと、中央マップの入力レイヤの「描画順」だけでなく「入力を受ける層」も同時に設計する。透明な背景層が背面の操作ハンドル／地図操作を覆って入力を奪わないこと（教訓 5.14）。期待操作が前面/背面で正しく通ることをテストで確認できる構造にする。
- **ツールチップ**: ツールバーボタン・メニュー項目に日本語の操作ガイドを表示する共通機構（FR-115）。
- **ショートカット基盤**: ショートカット → コマンド ID → コマンド実体の三段を分離する。本ユニットは「ショートカットの登録・解決・ディスパッチ」と「メニュー項目／ツール／ショートカットの有効・無効を単一判定で共有」する枠組みを担う。各コマンドの実体登録は後続ユニットが行う。ショートカットとメニュー項目の有効/無効は同一の権限判定から導出し、見た目だけ無効でショートカットが残る不整合を作らない（教訓 5.13）。アンドゥ/リドゥ不可時のメニュー項目・ショートカット無効化（FR-74）は、この有効/無効判定の枠組みに乗せられるようにする（実際の可否判定値は後続ユニットが供給）。

### 標準メニュー（FR-111）

- メニュー構造（ファイル・編集・表示・ツール・ヘルプ）と各メニューの項目枠を定義する。各項目は「コマンド ID」「ショートカット（任意）」「有効/無効を決める権限判定」を属性として持つ。
- メニュー項目の有効/無効は、対応するショートカットの有効/無効と単一判定を共有する（教訓 5.13、教訓 §4「単一の真実源」）。
- 各メニュー項目の実コマンドは後続ユニット（保存・読込・アンドゥ・設定・ヘルプ等）が登録する。本ユニットは未登録項目を「無効（または非活性）」として安全に扱う。

### 表示専用一括無効化ヘルパー（教訓 5.13）

- 「編集可能か否か」を表す単一の状態（権限判定）を定義し、編集系の全 UI（ツールバー編集系ボタン・編集メニュー項目・編集ショートカット・コンテキストメニュー編集項目）がこの単一判定を参照して有効/無効を決める共通ヘルパー（または状態機械）を提供する。
- 部品ごとに個別の無効化判定を書かない。新たな編集系部品を追加する際も、この共通判定に接続することを規約とする。
- 表示専用時は、見た目の非表示/非活性だけでなく、ショートカット・右クリック（コンテキストメニュー）からの編集経路も同時に塞ぐ（教訓 5.13 の検出観点）。

### 文言とエラー処理

- UI 文言は日本語のみ。文言は定数モジュールへ集約する（FR-115、技術方針 5.5）。i18n の抽象レイヤは設けない（将来の FR-7.2 ローカライズに備え、文言を集約するに留める）。
- UI 層で捕捉する例外はユーザーフレンドリーな日本語メッセージで表示し、必要に応じて「開発者へ報告してください」を付与する（FR-115 / FR-117）。

### テスト

- React コンポーネント／フックのテスト（レイアウト配置・モード排他・表示専用無効化・ドラッグ・ショートカット解決）を実装と同時に書く（開発ガイド 1.9）。
- レイアウト寸法・モード状態機械・表示専用権限判定・ショートカット解決など、UI から切り出せるロジックは純粋関数／純粋フックとして分離し、副作用なくテストできるようにする（教訓 5.41、NFR 5.8）。
- 重なる UI の入力層は、前面/背面の期待操作が通ることを確認するテストを置く（教訓 5.14 の検出）。
- 「選択→キャンセル→再作成」「選択→確定→再作成」相当（モード/ツール切替に伴う一時状態の破棄）を確認する（教訓 5.2 の検出）。

## 受け入れ基準（テスト可能な形で列挙）

1. **レイアウト配置（FR-111）**: アプリを起動すると、上部に標準メニュー（ファイル・編集・表示・ツール・ヘルプ）、左にツールバー（モード切替＋ツール選択）、中央にメインマップ領域、右にサイドバー（イベント一覧・階層/ツリー管理パネル（地物一覧）・プロパティパネルの 3 区画）、下部に時間スライダー領域とステータスバーが、それぞれ所定の位置に配置されることを確認できる（各領域の存在と配置をコンポーネントテストで検証）。
2. **モード排他トグル（FR-75）**: 追加モードを有効にすると編集モードが無効になり、編集モードを有効にすると追加モードが無効になる（同時に両方が有効にならない）ことをテストで確認できる。両方が有効な状態は表現不能（または到達不能）であることを状態機械のテストで確認できる。
3. **モード別ツール群表示（FR-75）**: 追加モードでは点／線／面の追加ツール枠が、編集モードでは編集系ツール枠（選択・頂点編集・地物移動・ナイフ・所属変更・結合 等）がツールバーに表示され、モード切替に追従して表示ツール集合が切り替わることを確認できる。モード切替時に前モードの選択中ツール等の一時 UI 状態が破棄されることを確認できる（教訓 5.2）。
4. **最小ウィンドウサイズとサイズ追従（FR-114）**: ウィンドウの最小サイズが 800×600 ピクセルに設定され、800×600 でも全領域が崩れず表示されることを確認できる。ウィンドウをリサイズすると中央マップ領域を中心にレイアウトが追従して再配分され、メインマップ領域のサイズ変化が購読可能な経路で通知されることを確認できる。
5. **ドラッグ可能パネル/ウィンドウ（FR-112）**: パネル/ウィンドウをドラッグして移動でき、押下→移動→解放のシーケンスで状態が正しく開始・更新・終了すること（クリックのみでドラッグ未発生の場合も状態が解除されること）を確認できる（教訓 5.8）。複数パネルの同時表示と前面化（z 順）が機能することを確認できる。
6. **ツールチップ（FR-112）**: ツールバーボタン・メニュー項目に日本語の操作ガイドツールチップが表示されることを確認できる。
7. **ショートカット基盤（FR-112）**: ショートカットがコマンド ID へ解決・ディスパッチされる枠組みがあり、未登録コマンドのショートカットは無効として安全に扱われることを確認できる。メニュー項目とショートカットの有効/無効が単一判定を共有していることを確認できる。
8. **重なる UI の入力層（教訓 5.14）**: モーダル/ドラッグ可能パネル/オーバーレイが前面にあるときと無いときで、前面 UI の操作と背面（中央マップ入力レイヤ）の操作がそれぞれ期待どおりに通る（または適切にブロックされる）ことをテストで確認できる。
9. **表示専用一括無効化（教訓 5.13）**: 表示専用（編集不可）状態にすると、編集系ツールボタン・編集メニュー項目・編集ショートカット・コンテキストメニューの編集項目が、すべて単一の共通判定によって一括で無効化されることを確認できる。とくに、見た目の非表示だけでなくショートカットおよび右クリック経由の編集操作も無効になることをテストで確認できる。逆に編集可能状態へ戻すと一括で再有効化されることを確認できる。
10. **層分離と React 切り離し（技術方針 §2.3）**: 本ユニットのコードは `ui` 層に属し、依存方向ルールに違反しない（lint で確認できる）。中央メインマップ領域は React の再レンダリングサイクルに地図描画状態を載せず、描画層をマウントする境界（コンテナ＋寸法通知）のみを提供していることを確認できる。
11. **日本語 UI（FR-115）**: メニュー名・ツール名・ツールチップ等の UI 文言が日本語で、定数モジュールに集約されていることを確認できる。

## 関連要件（FR-id）

- **FR-75** (must): 追加モードと編集モードを排他的なモードとして提供し、ツールバーのトグルで切り替える。一方を有効にすると他方が自動的に無効になる。各モードで関連ツール群がツールバーに表示される。
- **FR-111** (should): UI レイアウトは左側ツールバー（モード切替・ツール選択）、中央メインマップ、右側サイドバー（イベント一覧・階層/ツリー管理パネル（地物一覧）・プロパティパネル）、下部に時間スライダー・ステータスバーで構成する。標準的なメニュー構造（ファイル・編集・表示・ツール・ヘルプ）を備える。
- **FR-112** (should): 操作性として、ドラッグ可能なウィンドウとパネル、ツールチップによる操作ガイド、キーボードショートカット、コンテキストメニューでの操作提供をサポートする。
- **FR-114** (could): ウィンドウサイズに応じてレイアウトを調整し、最小ウィンドウサイズを 800×600 ピクセルとする。

補助的に関与する要件（本ユニットでは「枠組み・連動の準備」のみを担い、実処理は後続ユニット）:

- **FR-74** (should): アンドゥ/リドゥ不可時に対応するメニュー項目とショートカットを無効化する（本ユニットの有効/無効判定の枠組みに乗せる。可否値は後続が供給）。
- **FR-42** (should): 表示モードの切替は編集・追加モードと干渉しない（モード軸と権限/表示軸の分離方針と整合）。
- **FR-96** (should): コンテキストメニュー（本ユニットは表示・位置決め・閉じる契機・表示専用時の編集項目無効化までを担い、項目の動的構成と実処理は後続）。
- **FR-115** (must): UI 表示言語は日本語のみ。エラーメッセージも日本語で表示し、必要に応じて「開発者へ報告してください」を付与する。
- **FR-117** (should): 例外の捕捉とユーザーフレンドリーな日本語エラーメッセージ表示。
- **FR-118** (should): 学習容易性（直感的な UI 配置、ツールチップ）と操作効率（ショートカット、クイックアクセス）。

関連する非機能要件: NFR 5.1（リサイズ等の高頻度イベントのスロットリング、React 描画経路と地図描画の分離による 60FPS 防衛）、NFR 5.7（日本語のみ UI）、NFR 5.8（UI から切り出したロジックの純粋テスト容易性）。

## 注意点・既知の落とし穴（開発ガイドの教訓を踏まえる）

### 適用宣言（AI 作業開始ゲート, 開発ガイド 1.6）

着手前に以下の教訓を引用し、本ユニットへの適用を宣言してから実装すること。引用と適用宣言を省略して着手してはならない。

- **教訓 5.13「表示専用モードでは編集経路を一括無効化する」**（引用: 「表示専用モードでは、編集 UI・編集メニュー項目・編集ショートカットを同じ権限判定で一括無効化する。部品ごとに個別判定を書くと、見た目だけ非表示でショートカットや右クリック操作が残る。モード境界は共通ヘルパーまたは状態機械で表現する。」）。**適用**: 本ユニットでは「編集可能か否か」を単一状態として定義し、ツールバー編集系ボタン・編集メニュー項目・編集ショートカット・コンテキストメニュー編集項目がすべてこの単一判定を参照して有効/無効を決める共通ヘルパー（または状態機械）を実装し、部品ごとの個別判定を禁止する。受け入れ基準 9 でショートカット・右クリック経由も無効化されることを検証する。

その他、本ユニットで特に該当する教訓と落とし穴:

- **教訓 5.2「一時的 UI 状態は全経路で破棄する」**: 選択中ツール・進行中ドラフト等のシェル側一時状態は、モード切替・ツール切替・キャンセル・確定のすべての経路で明示的に破棄する。残ると次操作へ暗黙に引き継がれる。受け入れ基準 3 で確認する。
- **教訓 5.8「押下→移動→解放シーケンスを全パスで保証する」**: ドラッグ可能パネルは、ドラッグ（移動あり）とクリック（移動なし）の両パスで状態を正しく開始・更新・終了する。押下で設定した状態は解放で必ず解除する。移動が発生しなかった場合の考慮漏れに注意。
- **教訓 5.14「重なる UI は入力を受ける層も同時に設計する」**: ドラッグ可能パネル・モーダル・オーバーレイ・コンテキストメニューと中央マップ入力レイヤの「描画順」だけでなく「入力を受ける層」も設計する。透明な背景層が背面の地図操作・操作ハンドルを覆って入力を奪わないこと。受け入れ基準 8 で前面/背面の期待操作を検証する。
- **教訓 5.19「分岐識別子は型定義・定数・ファクトリを経由する」**: モード名・ツール種別・メニューコマンド ID・ショートカットキーは表示文字列や思い込みで判定せず、型定義・定数を経由する。新識別子の追加・改名時は作成・表示・編集・無効化の全経路で同じ値を使うテストを置く。
- **教訓 5.33 / 5.34（層をまたぐ契約・コンポーネント間契約を型で明示）**: 依存ユニット（U16 状態管理基盤 / U17 起動・コマンド/IPC 経路）との契約（状態キー・チャネル名・コマンド ID・関数名）は文字列の偶然一致に頼らず共有型・型付きラッパー・両側テストで固定する。依存先 API が未確定なら本ユニット内に境界インタフェース（adapter）を切って未確定部分を局所化する。
- **教訓 5.30「過少共有と過剰共有の両方を戒める」 / §4「単一の真実源」**: メニュー項目とショートカットの有効/無効、表示専用一括無効化など「同じ判定」は同じ実装を共有する（過少共有の戒め）。一方、見た目が同じツールボタンでもモードごとに対象・制約が異なる場合は安易に動作を共有しない（過剰共有の戒め）。
- **技術方針 §2.3（React 再レンダリングと地図描画の分離）**: 中央マップの高頻度描画状態を React state に持たせると 60FPS が破綻する（NFR 5.1）。本ユニットは中央領域に描画層をマウントする境界（コンテナ＋寸法通知）のみを React で用意し、地図描画状態を React に載せない規律を設計初期から徹底する。
- **NFR 5.1（高頻度イベントのスロットリング）**: ウィンドウリサイズ・ポインタ移動など高頻度イベントは必要に応じてスロットリングし、レイアウト再計算や通知の過剰発火を避ける。
- **教訓 5.41「検証不能になった範囲は別手段で補う」**: ウィンドウ最小サイズ設定・IPC 連携など E2E 寄りで検証しづらい範囲は、純粋関数化・アダプタ分離・モックで単体テスト対象にして補い、未検証のまま放置しない。
- **クリーンルーム（開発ガイド 3.1）**: 本ユニットの実装・コメント・テスト名で過去版や外部の既存実装に言及しない。制約はすべて v4 自身の要件（FR-75 / 111 / 112 / 114 ほか）・技術方針として直接記述する。
- **依存先未確定への備え**: U16 / U17 の API が確定していない場合でも、本ユニットは境界インタフェース（adapter）越しに依存することで着手可能。adapter の契約は型で明示し、依存先確定後に接続する（教訓 5.33）。状態の真実は依存ユニットの状態管理基盤に置き、本ユニットでドメインの真実を二重に持たない。
